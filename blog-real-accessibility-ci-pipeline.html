Accessibility CI/CD Case Study

Building a Real Accessibility CI Pipeline: Every Step, Every File

RN
6 min read
2026

The Shift-Left Accessibility series explains what Pa11y is and why it belongs in CI. This is the other half: the exact steps, the exact files, and where each one has to go to make a real pipeline run — for a project that already has axe-core running in Playwright or Cypress, and wants Pa11y as a second, genuinely different engine, not a repeat of the first one.

The goal was one workflow that proves itself both ways: a job that passes cleanly against a page that's actually fine, and a job that fails loudly against pages with deliberate violations — pa11y-success-demo and pa11y-fail-demo, run against a small set of target pages.

Step 1: decide where the files live

your-project/
├── .github/workflows/
│    └── accessibility.yml ← must live exactly here
└── your-project-path/
    ├── [the pages you want the gate to check, untouched]
    └── a11y-ci/ ← everything CI-specific lives here instead
        ├── package.json
        ├── package-lock.json ← generated by npm, must be committed
        └── pa11y-ci.json

Why: only one file's location is non-negotiable — GitHub Actions only ever scans .github/workflows/ at the repo root, nowhere else.

Everything else is kept in its own subfolder rather than the repo root or your target folder directly, so tooling doesn't get mixed in with the content or code the project actually ships. The workflow reaches into that subfolder with a single working-directory line instead of living there itself.

Step 2: package.json

Inside the new, empty a11y-ci/ folder: npm init -y first, then npm install --save-dev pa11y-ci — as a dev dependency, not global.

Why npm init -y first: --save-dev needs an existing package.json to record the dependency into. Skip this, and npm install --save-dev in an empty folder still installs the package — but with nowhere to save the entry. No error, just a package.json that never gets created, and a confusing failure later when there's nothing for npm ci to read.

Why a dev dependency, not global: a global install means your machine, a teammate's machine, and the CI runner could each silently be running a different version. A dev dependency gets pinned in package-lock.json instead, so npm ci installs the exact same version everywhere — provided that lockfile actually gets committed (Step 4 covers why that matters).

{
  "name": "a11y-ci",
  "private": true,
  "version": "1.0.0",
  "scripts": {
    "a11y": "pa11y-ci --config pa11y-ci.json"
  },
  "devDependencies": {
    "pa11y-ci": "^4.1.1"
  }
}

The scripts entry is optional — npm init -y won't add it for you — but it means anyone on the project can run npm run a11y instead of remembering the full npx pa11y-ci --config ... command.

Step 3: the Pa11y config

For your own project: one pa11y-ci.json, listing every page or URL you want the gate to check. It sets "standard": "WCAG2AA" and "ignore": ["notice", "warning"] — and deliberately leaves out "runners": ["axe"]. That one config passes or fails on its own, based on whatever's actually on those pages — you don't stage anything.

{
  "urls": [
    "../your-page.html"
  ],
  "defaults": {
    "standard": "WCAG2AA",
    "ignore": ["notice", "warning"],
    "chromeLaunchConfig": {
      "args": ["--no-sandbox"]
    }
  }
}

Why chromeLaunchConfig: { "args": ["--no-sandbox"] }: Pa11y loads each page in a real headless Chrome, and GitHub's Linux runners refuse to start Chrome's sandbox inside their containers without this flag. Leave it out, and the exact same config that works fine on your own machine fails in CI with a Chrome launch error that has nothing to do with accessibility — this is what makes it behave identically in both places.

Why the runner is left on its default (HTML_CodeSniffer), not switched to axe: axe-core is already running in your Playwright or Cypress suite. Adding runners: ["axe"] here would just run the identical engine a second time — duplicate detection, not broader coverage. Staying on Pa11y's actual default gives you a genuinely different rule set alongside axe-core instead.

(If Pa11y were your only automated check, with nothing else running axe-core anywhere, that's the one case where adding runners: ["axe"] here would make sense instead.)

Why ignore notices and warnings: only error is a definite violation. Gating the build on lower-confidence findings trains people to distrust the gate the first time it fails on something debatable.

Point it at the local, checked-out files, not the live deployed site — a relative path like ../your-page.html is enough (one level up from a11y-ci/ lands you back in your target folder); Pa11y converts it to a file:// URL itself.

Why local files, not live URLs: a live URL only tells CI about what's already deployed. Scanning the files GitHub just checked out means the gate is checking the change actually sitting in the pull request, before it ships — not confirming, a week later, that something already went out broken.

Why this post uses two configs instead of one: pa11y-ci.success.json and pa11y-ci.fail.json point at a clean page and a deliberately broken one — purely so this demo can prove, side by side, that the gate is capable of both passing and failing.

That split is a teaching device, not a pattern to copy. On your own project, one config covering your real pages is the whole setup.

This site's own demo now runs both halves for real: axe-core runs separately via Playwright, in its own passing and failing jobs, while these two Pa11y configs sit on the default HTML_CodeSniffer runner described above — two genuinely different engines checking the same pages, not one duplicated.

Step 4: the GitHub Actions workflow

One .yml file, one job, is the normal shape: check out the code, set up Node, npm ci, run Pa11y against your config, upload the result as an artifact even if the job fails.

  • package-lock.json must be committed: npm ci reads it to install the exact pinned versions. Skip it — say, by hand-writing package.json instead of running npm install — and this step fails before Pa11y ever runs, with an error that says nothing about accessibility.
  • node-version: 24, not 20: Node 20 reached end of life in April 2026. 24 is the current Active LTS.
  • actions/checkout@v7, setup-node@v7, upload-artifact@v7: the versions still commonly shown in older examples (@v4) target the retired Node 20 runtime and log a deprecation warning even though they still run.
  • if: always() on the upload step: by default, GitHub Actions skips every step after one that fails. Since the whole point of the artifact is to show you what failed, it needs to run in exactly that case — the default behaviour would skip it precisely when it's needed.
  • A paths filter scoped to your target folder: without it, editing an unrelated file anywhere else in the repo would still trigger the job — CI minutes spent on a check that had nothing to verify.
name: Accessibility Check

on:
  push:
    branches: [main]
    paths:
      - 'your-project-path/**'
  pull_request:
    branches: [main]
    paths:
      - 'your-project-path/**'

jobs:
  pa11y-check:
    runs-on: ubuntu-latest
    defaults:
      run:
        working-directory: your-project-path/a11y-ci
    steps:
      - name: Check out the code
        uses: actions/checkout@v7

      - name: Set up Node.js
        uses: actions/setup-node@v7
        with:
          node-version: 24

      - name: Install dependencies
        run: npm ci

      - name: Run Pa11y
        run: npx pa11y-ci --config pa11y-ci.json --json > pa11y-results.json

      - name: Upload results
        if: always()
        uses: actions/upload-artifact@v7
        with:
          name: pa11y-results
          path: your-project-path/a11y-ci/pa11y-results.json

This post's own workflow has two jobs, pa11y-success-demo and pa11y-fail-demo, one per demo config — again purely so both outcomes show up side by side in the Actions tab.

Two jobs matter here for a structural reason: a GitHub Actions job's status is a single pass/fail. If both demo checks were steps in the same job, one failing step would mark the whole job red — even the half that's supposed to pass. On a real project with one config, one job is all you need.

Step 5: verify locally, before it ever touches CI

Run npx pa11y-ci --config pa11y-ci.json (or npm run a11y, from Step 2's script) from a terminal, before writing a single line of workflow YAML.

Why: a misconfigured flag or a wrong path is far cheaper to catch in fifteen seconds locally than after pushing, waiting for a runner, and reading through an Actions log to find the same mistake.

Step 6: when it runs, and where to see it

When: on every push and pull request to main that touches a file under your target folder. Nothing runs before that push happens, and nothing runs for changes outside that path.

Where: repo → Actions tab → the latest run → scroll to the job graph under the workflow name.

pa11y-success-demo

0 errors · exit code 0

pa11y-fail-demo

real violations found · exit code 2

The overall run may still show "Failure" at the top — that's GitHub rolling every job into one status, and one of these two jobs is supposed to fail. The two jobs underneath are the actual signal.

Bottom Line

A working accessibility CI gate isn't a bigger idea than the series already covers — it's four small files, placed deliberately, each with a reason for sitting exactly where it does.
