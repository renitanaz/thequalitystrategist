Performance and caching testing

A CMS site's performance rarely degrades because the server got slower. It degrades one full-resolution image upload and one hastily-added marketing script at a time, each individually reasonable, each shipped with no performance review at all.

By RN ~10 min read Demo: Grove & Bean

Key takeaways
  • Core Web Vitals: LCP under 2.5s (loading), INP under 200ms (responsiveness), CLS under 0.1 (visual stability). All three need a "good" score to pass.
  • An image uploaded without dimensions causes layout shift (CLS) the moment it loads, entirely a content-side mistake, not a code bug.
  • A third-party script added without a performance review can single-handedly blow the loading budget of every page it's placed on.
  • Publishing an edit doesn't always mean it's live everywhere instantly. Caching layers between the CMS and the visitor can serve stale content for a stale-while-revalidate window or until manually purged.
  • A good Lighthouse score says nothing about concurrent capacity. Load testing (traffic spikes, launches) is a separate, real checklist item worth knowing about even without going deep on its tooling here.

The three numbers that define "fast enough"

Google's Core Web Vitals give performance three concrete, measurable thresholds instead of a vague "feels slow." All three need a "good" score, at the 75th percentile of real visitors, for a page to pass.

MetricMeasuresGood threshold
LCP (Largest Contentful Paint)How long the biggest visible element takes to renderUnder 2.5 seconds
INP (Interaction to Next Paint)How responsive the page feels to a click, tap, or keypressUnder 200 milliseconds
CLS (Cumulative Layout Shift)How much visible content jumps around as the page loadsUnder 0.1

The most common CMS-specific CLS bug

An image tag with no width or height reserves zero space in the layout before it loads. The moment it finishes downloading, everything below it jumps to make room, a layout shift the visitor directly feels and Google directly measures.

Why this is a content-layer bug, not a code bug

The template's CSS and markup didn't change. An editor uploaded an image, through the normal, sanctioned publishing flow, and that alone was enough to regress a Core Web Vital. Fixing it means the content model or upload process needs to set dimensions automatically, not a one-time code fix that a future upload can undo.

Cache invalidation: publish doesn't always mean live

Many CMS setups sit behind a CDN or a page cache for speed. That's good for performance and bad for a specific, easy-to-miss bug: an editor publishes an edit, and the cache keeps serving the old version until it expires or is explicitly purged.

"I published it and it's not showing" is often a caching bug, not a publishing bug. Before assuming the CMS itself failed, check whether a cache layer between the CMS and the visitor is still serving a stale copy. This is a real, recurring support ticket on any CMS with page caching enabled.

Third-party scripts: added without anyone testing performance

A chat widget, an analytics pixel, an embedded video player, a marketing automation snippet: these usually get added by whoever needs the feature, not by whoever thinks about page-load budget.

Common additionPerformance risk
Chat widget scriptIf loaded synchronously in <head> without async/defer, blocks the page from rendering until it resolves
Marketing/analytics pixelsEach one adds its own network request and JS execution, compounding on pages with several stacked
Embedded video or social widgetsOften loads a full iframe and its own script bundle even before anyone interacts with it

Load testing: a different question than Core Web Vitals

Everything above is about how fast one page loads for one visitor. Load testing asks a different question: does the site stay fast when many visitors arrive at once, a campaign launch, a press mention, a traffic spike a CMS's caching layer wasn't tuned for.

Why this deserves a mention, not a deep dive

A good Lighthouse score says nothing about concurrent capacity, and a site that scores well for one visitor can still fall over under real traffic. This is a legitimate item on any CMS project checklist, but the tooling (k6, JMeter, and similar) is a different discipline from the free, page-level tools this series otherwise uses. The risk is worth knowing about even without going deep on the tooling here.

GTmetrix is worth knowing for one thing Lighthouse can't do: testing from real server locations in different countries. For a site with visitors outside its hosting region, that catches a category of slowness Lighthouse's local run never will, and it connects directly to Post 13's localization concerns.

Try it: audit the demo site's performance

Try it

Open the Grove & Bean homepage, open Chrome DevTools → Lighthouse, and run a Performance audit.

Look specifically at the Cumulative Layout Shift score and the diagnostics list. Find the specific element Lighthouse blames for the shift, and confirm it's the hero image.

Then check the Network tab for the chat-widget script loaded in <head>, and note whether it has async or defer set.

Check your findings against demo-site/seeded-issues.md, PERF-1 and PERF-2.

Your deliverable

A short note: the CLS score Lighthouse reported, the specific element it blamed, and one concrete fix (a width/height attribute, a CSS aspect-ratio reservation) that would resolve it without changing the image itself.

Time: ~20 minutes.
