Content and editorial workflow testing

Post 1 established that content ships with no code review, no deploy pipeline, no automatic QA gate. This post is about the four things a CMS uses instead to keep that unreviewed process from being reckless: a content model that constrains what an editor can enter, a workflow that gates who can publish what, roles that draw the boundary, and version history that undoes a mistake after the fact.

Key takeaways
  • Four mechanisms replace code review for content: the content model (what fields exist), the publishing workflow (who can move content between states), roles (who can do what), and version history (undoing a mistake).
  • A gap in the content model, like a missing alt-text field, ships silently on every piece of content created after it.
  • A permission chart describes what's supposed to happen, not what a specific plugin actually does. Log in as the role and test it directly.
  • A "rollback" can restore the body text while leaving a changed featured image or SEO field in place. Test multi-field changes, not just one.

Content modeling: the shape editors are allowed to fill in

A content model is the schema behind every page: which fields exist for a given content type, whether each one is required, what type of data it accepts, and what an editor sees in the editing screen. It's decided once, during Plan, by whoever sets up the CMS, and every piece of content of that type is stuck inside the shape it defines from then on.

Why content modeling is a QA concern, not just a setup task

A missing or wrongly-typed field in the content model ships silently in every piece of content created after it. Nothing in the editing screen tells an editor a field is missing, only that it isn't there to fill in.

The "Featured image" field above has no alt text field at all. Accessibility testing later in this series (Post 7) will keep finding that same missing-alt-text issue on every post, because the real defect lives here, in the model, not in any individual editor's choices.

Publishing workflow: the states content moves through

Most CMS platforms give content a status beyond just "saved," typically Draft, Pending Review, Published, and often Scheduled. The workflow is which roles can move content between which statuses, and it's the actual QA gate a CMS has, if it's configured at all.

ContributorWrites a draft, submits for review. Can't publish directly.
→
EditorReviews the pending draft, approves, publishes.
StatusVisible whereWhat to test
DraftOnly to the author and roles with edit access, never on the live siteA draft URL should not be publicly reachable or indexed. Try loading it logged out.
Pending reviewSame as draft, plus visible in a reviewer's queueA Contributor account should not be able to skip this and publish directly, verify the publish control is actually absent, not just hidden by the UI.
ScheduledNot yet live, holds a future publish timeThe exact moment it goes live, and whether that time is evaluated in the server's timezone or the editor's, a common source of a post going live an hour early or late.
PublishedLive, publicly reachableWhether unpublishing (back to Draft) actually removes it from cache, search index, and any API consumers, not just the CMS's own front end.

"Hidden from the menu" is not the same as "not publicly reachable." A common CMS misconfiguration is a draft or unpublished page that isn't linked from anywhere, but is still reachable if someone has or guesses the direct URL. Test the URL directly, logged out, don't just check whether a link to it exists.

Roles and permissions: who can do what

WordPress ships with five default roles, and the same shape, a small number of tiers with increasing publish and admin rights, appears across most CMS platforms under different names.

ContributorNo, submits for review onlyNoNo
SubscriberNoNoNo
Why permission boundaries need to be tested, not just read off a chart

A role matrix like the one above describes what's supposed to happen. What actually happens depends on every plugin installed, since a plugin can add its own capabilities, or forget to check the current user's role before showing an admin control.

The only way to know a Contributor account truly can't publish, edit someone else's post, or reach an admin screen is to log in as that role and try, not to trust the chart.

Versioning and rollback

Every reasonable CMS keeps a revision history: a snapshot saved at intervals or on every save, that can restore a previous version of a piece of content. The QA question isn't whether the feature exists, it's whether restoring actually restores everything an editor would expect.

Why "restore" is easy to get partially wrong

Rich content usually has more attached to it than the body text: a featured image, SEO fields, category assignments, custom fields a plugin added. A rollback that only restores the body text while leaving a since-changed featured image or SEO field in place isn't really a rollback, it's a half-restore that looks correct until someone checks the parts that didn't revert.

That gap only shows up when you deliberately change more than one field, then roll back and check all of them, not just the one you expect to have changed.

Try the whole workflow yourself

Try it

Launch a fresh instance at wordpress.org/playground.

Under Users → Add New, create a second account with the Contributor role. Log in as that user and confirm there's genuinely no publish button, only "Submit for Review."

Back in the admin account, edit the sample post three times, changing the title, then the featured image, then a category, saving each time. Open Revisions from the post editor, restore the earliest version, and check all three fields, not just the one that changed first, to see whether the rollback was actually complete.

Your deliverable

A short table: the roles that exist in a real CMS you have access to (or the WordPress Playground defaults if not), and one specific action each role should not be able to do. Actually verify each row by logging in as that role, don't just write down what the docs claim.

Time: ~20 to 30 minutes.
