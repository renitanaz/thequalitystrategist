Headless CMS considerations

Post 4 covered API testing that applies to any CMS with an API, headless or not. This post is about the three things that are genuinely different once there's no built-in rendering layer at all: no default preview, content that has to work across channels nobody designed a single layout for, and a contract between CMS and front end that can break without either side's code changing.

Key takeaways
  • A headless CMS has no built-in rendering layer, so there's no default preview. What an editor saves and what a reader eventually sees are validated by two completely separate systems.
  • The same content often has to work across channels with very different constraints: a full webpage, a compact mobile screen, a voice assistant with no visuals at all.
  • The CMS and its front end are usually deployed independently. A content model change can break the front end's build without a single line of front-end code changing.
  • Contract testing, checking that what the CMS promises still matches what the front end expects, catches this class of bug before a release does.

No template means no default preview

A classic CMS ships a preview button because it owns the template: it can render a draft the same way it renders the live page, before anything is published. A headless CMS has no template to render with. Content is just structured data until some separate front end decides what to do with it.

Why this is a real QA gap, not just an inconvenience

Without a working preview, an editor's only way to check a draft is to trust the raw content form, or to publish it and check the live front end, which defeats the point of a draft.

If a preview integration exists, it's testable like anything else: does it show the same content model an editor filled in, does it update when the draft changes, and does it actually match what the production front end renders, or a simplified stand-in that quietly diverges over time.

The same content, rendered nowhere the same way twice

Headless architecture exists specifically so one piece of content can feed multiple channels: a website, a mobile app, a kiosk, a voice assistant. Each of those channels has different constraints the content itself has to survive.

ChannelConstraint content has to survive
WebsiteFull formatting, images, embedded HTML generally safe
Mobile appSmaller screen, often a stricter subset of rich-text formatting the app's renderer actually supports
Voice assistant / smart displayNo visuals at all. Content authored assuming an image or a table conveys meaning breaks completely
Third-party feed (RSS, partner API)Consumer has no relationship with your CMS's specific formatting choices, only the raw structured fields

Rich text is the most common multi-channel trap. A rich-text field that lets an editor embed a raw HTML table or an inline image renders fine on the website. The same field, read by a mobile app or a voice assistant, either strips it silently or crashes trying to parse markup it was never built to handle.

The contract between CMS and front end

In a headless setup, the CMS and its front end are usually separate codebases, deployed independently, often by different teams. The content model is the contract between them: the front end is built assuming certain fields exist, with certain types, and nothing enforces that assumption stays true.

Why this breaks without anyone touching the front end's code

A content editor renaming a field, or a CMS admin changing a field from single-value to a list, is a content-model change, not a code change. It ships the moment it's saved, the same zero-review path from Post 1, except now the "content layer" includes the shape of the data itself, not just its values.

The front end, built against the old shape, doesn't get rebuilt just because the model changed. It keeps running against a contract that no longer matches, and the failure shows up as a broken page with no corresponding code change to point at.

Try it: break the contract on purpose

Try it

Using the Strapi instance from Post 4, fetch http://localhost:1337/api/articles and note the exact shape of one entry's response.

In the admin panel, rename the "title" field to "headline" on the Article content type. Fetch the same endpoint again without changing anything else.

Compare the two responses. Anything that read the old field name, a front end, a script, another integration, now silently gets nothing back for that field instead of an error, which is exactly the kind of contract break that ships invisibly in a real system.

Your deliverable

A short note: for a headless (or API-driven) setup you know of or can imagine, name one content-model change, a rename, a type change, a field removal, that would break its front end, and whether that break would be obvious immediately or only show up later.

Time: ~20 minutes, using the Strapi instance from Post 4.
