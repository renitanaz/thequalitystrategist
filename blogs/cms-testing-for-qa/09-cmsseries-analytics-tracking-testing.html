Analytics and tracking validation

An analytics snippet can be syntactically perfect, present on every page, loading with no console errors, and still collect zero real data. It's one of the only categories of bug on this entire site where everything looks completely fine and is completely broken at the same time.

By RN ~9 min read Demo: Grove & Bean

Key takeaways
  • A present, syntactically valid tracking snippet is not proof it's collecting data. A wrong or placeholder ID produces zero errors and zero visible symptoms.
  • Verify with GA4 DebugView or a network-request inspection, checking the actual measurement ID in outgoing requests, not just that a request fired.
  • An event that's supposed to fire on a specific action, like a form submission, needs its own explicit check. Page-load tracking working proves nothing about it.
  • Analytics scripts that load unconditionally, with no consent gate, are both a tracking-accuracy problem and a legal-compliance problem (Post 14).

Looks right and is right are two different checks

Open view-source on almost any page and a tracking snippet either exists or it doesn't. That's a five-second check. Whether it's sending data to the correct property, under the correct ID, is a completely different question that view-source can't answer.

Why this specific bug survives so long in real CMS sites

A placeholder measurement ID left in a template, or copied from a staging environment and never swapped for production, breaks nothing visible. The site works, forms submit, pages load. The only symptom is a marketing dashboard quietly showing far less traffic than the site actually gets, and that discrepancy is usually blamed on the marketing channels, not the tracking code, until someone checks the code directly.

Verifying it actually works

MethodWhat it confirms
View-source / DevTools ElementsThe snippet exists and is syntactically present. Nothing about whether it works.
GA4 DebugViewEvents arriving in real time at the actual property, with full parameter detail, confirming the ID is correct and connected
Network tab, filtered to the collect requestThe exact measurement ID being sent in the live request payload, catching a wrong or placeholder ID directly
Google Tag AssistantA guided, official check of which tags fire on a given page and whether they're configured correctly

Event tracking needs its own check, separate from page-load tracking

Confirming that a page-view event fires proves the base snippet works. It proves nothing about whether a specific action, like a form submission or a button click, has its own tracking wired up.

Grove & Bean's contact form has no submit-event tracking at all. Even with a corrected measurement ID, a marketing team relying on "form submissions" as a conversion metric would see zero, forever, because nothing on that form ever fires an event. This has to be tested as its own case, not assumed from page-view tracking working.

Try it: catch both bugs on the demo site

Try it

Open the Grove & Bean homepage, open DevTools → Network, and filter for collect. Reload the page and look at the request that fires.

Find the tid parameter in that request's payload. It reads G-XXXXXXX, exactly the literal placeholder, never replaced with a real property ID.

Then go to the contact page, fill in the form, and submit it. Watch the Network tab again: no new tracking request fires at all on submit.

Check your findings against demo-site/seeded-issues.md, ANALYTICS-1 and ANALYTICS-2.

Your deliverable

A short note: the exact value you found in the tid parameter, and one sentence on what a marketing team would see in their dashboard as a result of this specific bug (not "broken analytics," the actual visible symptom).

Time: ~15 minutes.
