Cross-browser, responsive and visual testing

A hand-built page gets tested against the content it actually contains. A CMS template gets tested once, then has to survive every piece of content anyone will ever put in it, at every screen size, forever. Responsive testing on a CMS is really about that second part: content variability, not just viewport variability.

By RN ~9 min read Demo: Grove & Bean

Key takeaways
  • A CMS template has to survive every future piece of content at every screen size, not just the sample content it was tested with once.
  • A layout tested only at desktop width can hide an overflow bug that only appears once the viewport narrows past a breakpoint nobody checked.
  • Visual regression testing (screenshot diffing) is most valuable for a CMS specifically because a theme or CSS update can silently change how every existing page renders.
  • Cross-browser testing on a CMS mostly means checking rendering engines, not full manual passes: Chromium, WebKit (Safari), and Firefox cover the vast majority of real differences.
  • Back a "current version and −1" policy with real usage-share data rather than a rule of thumb, and know that a DevTools full-page screenshot is a fast, no-install way to capture evidence.

Content variability is the real test, not just screen size

A responsive layout built and checked with one editor's sample content can still break the moment a different editor publishes something longer, shorter, or differently shaped, at the exact same screen size that tested fine before. The viewport didn't change. The content did.

Why this connects back to Post 3

Post 3 covered content edge cases breaking a template's layout at a single, fixed viewport. This post adds the second dimension: the same edge cases, tested across the range of screen sizes real visitors actually use, not just the one the developer had open while building it.

See it break: Grove & Bean's overflow bug

The Grove & Bean homepage has a three-card feature row built with display:flex and no wrapping rule. It looks perfectly fine at desktop width, which is exactly the problem: nobody who only checks desktop width would ever find it.

Testing only at desktop width is testing only one point on a range. A responsive bug like this one exists at a specific range of viewport widths and is completely invisible outside it. "It looked fine" always needs a "fine, at what width."

Which breakpoints actually matter

BreakpointRoughly represents
~375pxA typical mobile phone in portrait
~768pxA tablet, or a phone in landscape
~1280pxA typical laptop or desktop window

These aren't the only widths that matter, they're the three that catch the large majority of real layout breaks with the least effort. Chrome DevTools' device toolbar (Ctrl/Cmd+Shift+M) lets you test all three without needing physical devices.

Visual regression: catching what a functional test won't

A functional test confirms a page still works, links click, forms submit. It says nothing about whether the page still looks right. A theme update, a shared CSS file change, or a plugin update can silently shift spacing, colors, or alignment across every page that shares that styling, with every functional test still passing.

Why this matters more on a CMS than a hand-built site

A CMS's shared templates and themes mean a single CSS change has the same reuse-multiplies-impact effect from Post 3, except for visual regressions instead of functional bugs. Screenshot-diffing tools exist specifically to catch this class of change automatically, by comparing a new screenshot against a known-good baseline and flagging pixel differences a human would otherwise have to notice by eye.

Cross-browser: fewer targets than it used to be

Most real cross-browser differences today come down to rendering engine, not individual browser brand. Chrome, Edge, and most other browsers share Chromium's engine; Safari uses WebKit; Firefox uses Gecko. Testing one representative browser per engine catches the large majority of real differences, without needing to manually check every browser name.

Back a version policy with real data, not a rule of thumb. A common shorthand is "test the current version and one back," but which browsers and OS versions actually deserve that effort depends on real traffic, not habit. gs.statcounter.com publishes real global usage share by browser and version, letting a "current and −1" policy be a defensible decision instead of an assumption.

Capturing evidence: full-page screenshots without a tool

A quick, no-install way to capture an entire page, not just the visible viewport, for a bug report or a before/after comparison, without reaching for a dedicated screenshot-diffing tool first.

PlatformHow
Chrome DevTools (any OS)Open DevTools (F12), open the Command Menu (Ctrl/Cmd+Shift+P), type "screenshot," choose "Capture full size screenshot"
AndroidTake a normal screenshot, then use the "Capture more" or scrolling-capture option most recent versions offer automatically
iOS SafariTake a screenshot, tap the preview, choose Full Page (saves as a PDF)

For a functional flow, a screen recording still captures more than a screenshot can. For a static page check, a full-page screenshot is faster to produce and faster for someone else to review than a video.

A related but distinct discipline worth knowing exists: comparing a rendered page directly against its Figma design file, pixel by pixel, using tools like Testsigma's Figma integration or browser extensions built for that comparison. That's implementation-fidelity QA, verifying the build matches the design, rather than the content-driven risk this series focuses on, but it's worth knowing the tooling category exists if a project needs it.

Try it: reproduce the overflow bug

Try it

Open the Grove & Bean homepage in Chrome, then open DevTools (F12) and toggle the device toolbar (Ctrl/Cmd+Shift+M). Set the width to 1280px first, confirm the three feature cards look fine.

Then set the width to 375px. Watch the feature-card row: it doesn't wrap, and a horizontal scrollbar appears at the bottom of the page.

Check your finding against demo-site/seeded-issues.md, VISUAL-1.

Your deliverable

A short note: the exact viewport width where the overflow first appears (test a few widths between 375px and 1280px to narrow it down), and the specific CSS property that would fix it without redesigning the section.

Time: ~15 minutes.
