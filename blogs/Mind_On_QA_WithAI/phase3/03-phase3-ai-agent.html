Test Cases, Generated in One Pass

Two agents, UI and API, draft test cases straight from the requirements doc. The speed is real. So is the need to check what came back.

By RN ~4 min read Series: AI-Augmented QA
Manual, No AI Manual + AI Automated, Playwright AI QA Agent

Phase 3 in a real project happens before anything is built. So these agents do not call a live API and they do not open the running site. They reason from one file only: peakandpack-requirements.md. That is all that exists yet, and it is enough to draft a full set of test cases.

Two agents, same idea

A project might have a UI only, an API only, or both. So this phase ships two separate agents, and you run whichever ones match what you are testing.

UI Test Case Generator
Reads the requirements and writes user-facing test cases: screens, forms, buttons, flows. Output speaks in clicks and visible results.
API Test Case Generator
Reads the same requirements and writes endpoint test cases: methods, status codes, response shapes, validation rules.

The system prompt is where the real design work happens. The code is a few lines. Both agents are the same short script wrapped around one carefully written instruction. What makes them produce good test cases is the prompt. That is why the full prompt text is printed below, exactly as used.

Pick a form

Each agent ships in three forms. They all do the same job and produce the same kind of output. They're listed easiest-first: start with prompt-only if you just want the result, and move down only if you want something reusable.

UI Test Case Generator: what it does

UI agent

You give it the requirements doc. It returns UI test cases in the same TC-ID / Title / Steps / Expected / Priority format used everywhere else in this phase, written in terms a person clicking through the site would recognise. It does not open the site. It reasons entirely from what the requirements say the screens should do.

The system prompt (this is the actual artifact)

You are a UI test case generator for a web application.

You will be given a requirements document. That document is the
ONLY source of truth. You cannot see the running app, call any API,
or take screenshots. Nothing is built yet. Work from the document.

For every user-facing feature described in the requirements, write
test cases of three kinds:
  - Happy path: valid input, the expected success result.
  - Negative: invalid input, the expected failure (a clear error,
    not a silent success).
  - Edge: boundary values, empty fields, very long input, special
    characters, unusual but legal states.

Output a Markdown table with these exact columns:
  TC-ID | Title | Steps | Expected | Priority

Rules:
  - Steps are written as user actions: "Click X", "Type Y in field Z".
  - Expected is what the user should SEE, not internal status codes.
  - Priority is one of: Critical, High, Medium, Low. Base it on how
    much damage the failure would cause, using any risk hints in the
    requirements.
  - If the requirements state a specific rule (for example a discount
    code is 10% off), write the Expected to match that rule exactly,
    so a wrong implementation will fail the test.
  - If the requirements are silent or unclear on something, add a row
    and put "ASSUMPTION:" at the start of the Expected cell, so a human
    reviewer can confirm it. Do not guess silently.

Aim for thorough coverage of every feature, not volume for its own
sake. Return only the table, no preamble.

Below are the three forms of this agent. They are alternatives, not steps. Use one.

1Prompt only, no key, no code

The fastest way to see what the agent does. No API key, no terminal, no file to run. You just need any Claude chat window.

  1. Open ui-testcase-agent-prompt.md and copy everything in it.
  2. Open a new chat with Claude and paste it as your first message.
  3. Open peakandpack-requirements.md, copy all of its text, and paste that in as your second message (or attach the file).
  4. Claude replies with the test case table. Copy it into your deliverable file.

The trade-off: nothing is saved or reusable, you copy-paste by hand each time. If you'll run this repeatedly, use one of the two forms below.

2Browser form, a reusable tool, no install

A small web page you keep and reuse. It runs entirely on your own machine, there is no server and nothing to install.

How to open it. The file is plain HTML, so your browser can open it directly from your computer, no internet host needed.

  1. Download ui-testcase-agent.html to somewhere easy to find, like your Desktop.
  2. Double-click it. It opens as a normal page in your default browser. If double-clicking does something unexpected, right-click the file, choose Open with, and pick your browser. The address bar will read something like file:///Users/you/Desktop/ui-testcase-agent.html, the file:// part just means it is running from your own disk.

How to use it.

  1. Get an Anthropic API key: go to console.anthropic.com, sign in, open the API Keys section, click Create Key, and copy the key it shows you (it starts with sk-ant-).
  2. Paste that key into the box on the page.
  3. Open peakandpack-requirements.md, select all the text, copy it, and paste it into the big text area.
  4. Click Generate UI test cases. The table appears below in a minute or so.

How it works under the hood. When you click the button, a few lines of JavaScript in the page take the requirements text you pasted, attach the system prompt, and make a single web request straight to Anthropic's API with your key. Claude's reply comes back and is written into the results area. Nothing is uploaded to any other server, the page talks only to Anthropic, and your key never leaves your browser tab. Close the tab and the key is gone; there is no storage and no account.

Why the key box mentions "dangerous". The browser sends your key directly to Anthropic using a header named anthropic-dangerous-direct-browser-access. The scary name is a warning against shipping your own key inside a public website that strangers use. Here the key is yours, on your own machine, used only by you, so it is fine. Nobody else sees it.

3Node.js form, in a terminal

Run it as a script from a terminal. This form saves the output to a file automatically, handy if you run it often. The only thing it needs installed is Node.js, the program that runs JavaScript files outside a browser. It does not need Claude Code or any other tool; the script talks to Anthropic's API on its own. Here is every step, nothing assumed.

  1. Check Node.js is installed.
    • Open a terminal: on Mac press Cmd+Space, type "Terminal", Enter. On Windows press Start, type "PowerShell", Enter.
    • Type node --version and press Enter.
    • If you see a number like v20.x.x (anything 18 or higher) you are set. Skip to step 2.
    • If it says "command not found" or similar, Node is not installed. Go to nodejs.org, click LTS, run the installer, then close and reopen the terminal and try again.
  2. Get an API key the same way as in the browser form: console.anthropic.com → API Keys → Create Key → copy the sk-ant- value.
  3. Download two files into the same folder: ui-testcase-agent.js and peakandpack-requirements.md. Put both in, say, a new folder on your Desktop called qa-agent.
  4. Point the terminal at that folder. Type cd (with a space after it), then drag the qa-agent folder onto the terminal window (this pastes its path), then press Enter.
  5. Give the script your key. This keeps the key out of the file.
    On Mac: type export ANTHROPIC_API_KEY=sk-ant-your-key-here and press Enter.
    On Windows (PowerShell): type $env:ANTHROPIC_API_KEY="sk-ant-your-key-here" and press Enter.
  6. Run it. Type node ui-testcase-agent.js and press Enter. The script reads the requirements file next to it, calls Claude, and writes the result to test-cases-ui-agent.md in the same folder.

If it fails:

  • "command not found: node": Node.js is not installed. Redo step 1.
  • Authentication error: the key in step 5 was wrong or had a typo. Redo step 5.
  • "Cannot find module": the terminal is not in the right folder. Redo step 4.
  • "ENOENT ... requirements": the .md file is not sitting next to the script. Redo step 3.

API Test Case Generator: what it does

API agent

Same idea, different output. It reads the same requirements doc and writes API-level test cases: which endpoint, which method, which inputs, the expected status code and response shape. Useful when the thing under test is a service rather than a screen.

The system prompt

You are an API test case generator for a web application.

You will be given a requirements document. That document is the
ONLY source of truth. You cannot call any endpoint or inspect a
live server. Nothing is built yet. Work from the document.

For every endpoint or data operation described in the requirements,
write test cases of three kinds:
  - Happy path: valid request, expected 2xx response and body.
  - Negative: invalid or missing input, expected 4xx response
    (never a 500, and never a silent 200).
  - Edge: boundary values, empty payloads, wrong types, oversized
    input, missing required fields.

Output a Markdown table with these exact columns:
  TC-ID | Title | Steps | Expected | Priority

Rules:
  - Steps name the request: method, path, and the key inputs. For
    example "POST /api/checkout with empty cart".
  - Expected names the status code AND what the body should contain
    or omit. For example "400, error message, no order created".
  - Priority is one of: Critical, High, Medium, Low, based on damage
    if the endpoint misbehaves.
  - If the requirements state a specific rule, write Expected to match
    it exactly so a wrong implementation fails the test.
  - If something is unspecified, add the row and begin the Expected
    cell with "ASSUMPTION:" for a human to confirm. Never guess silently.

Cover every endpoint thoroughly. Return only the table, no preamble.

The three forms work exactly like the UI agent's, so the steps are not repeated in full. The only differences:

  • Browser: download api-testcase-agent.html instead, and click Generate API test cases. Everything else (key, paste requirements) is identical to the UI browser steps above.
  • Node.js: download api-testcase-agent.js, follow the same six terminal steps, and run node api-testcase-agent.js. It writes test-cases-api-agent.md.
  • Prompt only: use api-testcase-agent-prompt.md as your first message, then paste the requirements.

The harness matters here. Both agents send the requirements once and get one answer back. There is no loop, no retry, no second opinion. That is fine for a first draft, but it means the quality of the output is capped by the quality of the prompt and the requirements doc. A vague requirement produces a vague test case. The agent is only as good as what you give it.

How to tell if the agent actually read the requirements

AI output looks confident whether or not it understood the specific app. Here is how to check before you trust it.

Trustworthy sign
A row whose Expected matches a rule that is only in the requirements doc. For example: "Apply SAVE10, total reduced by exactly 10%." The agent could only know "10%" by reading the doc.
Warning sign
Only generic rows that would fit any shop ("empty cart returns an error"), and no ASSUMPTION: rows at all. That usually means it pattern-matched a template instead of reading your specific rules.

What good output looks like

TC-IDTitleStepsExpectedPriority
TC-A01Checkout applies discount correctlyPOST /api/checkout with SAVE10 on a $100 cart200, total charged is $90.00 (10% off, per requirements)Critical
TC-A02Search with missing queryGET /api/search with no ?q parameter400, validation error, no crashHigh
TC-A03Checkout with empty cartPOST /api/checkout, no items400, no order createdHigh

TC-A01 is the one to look for. Its Expected says "$90.00", a number that only exists because the requirements say SAVE10 is 10%. If the running app later charges $0.00 (the planted BUG-009), this written test catches it. A generic template would never have known the right number to expect.

What changes when the app already exists

Everything above assumes the realistic Phase 2 and 3 situation: nothing is built yet, so the agent reasons from the requirements doc alone. But you won't always start that early. Sometimes you join a project where the site is already live, or you're asked to write tests for an app that shipped long ago. The premise flips, and an architect's approach flips with it.

The doc is no longer the only source of truth, but it's still the first one. A live app tells you what the system does. The requirements tell you what it's supposed to do. The gap between those two is where the most valuable bugs live, so an architect uses the live system to confirm and extend the requirements reasoning, never to replace it.

Concretely, what an architect does differently when the app is live:

  1. Start from the same risk ranking, not from the UI. It's tempting to open the site and start clicking. Resist it. Rank risk from the requirements first (as above), so your exploration is aimed at what matters instead of wherever the mouse wanders.
  2. Explore to verify, then to surprise. First confirm each requirement actually behaves as written (does SAVE10 really take 10%?). Then probe the spaces the requirements never mention: what the live app reveals that no document did, like an undocumented endpoint, a hidden admin route, or an error page that leaks a stack trace.
  3. Treat observed behaviour as evidence, not as the spec. If the live app does something the requirements don't mention, that's a question ("is this intended?"), not a confirmed feature to lock a test around. An app's current behaviour can itself be the bug.
  4. Let the agent read both. The same agents work, you just give them more to reason about: the requirements doc plus a captured API response, a page's HTML, or a list of real endpoints. The discipline stays identical, confirm app-specific rules made it into the Expected column, flag assumptions, delete the generic.

The throughline: a live system is a richer input, not a shortcut. The architect's job is the same in both worlds, decide where risk lives and aim testing there. Having the running app just gives you one more source to cross-check against, and one more place to find the gap between built and intended.

Your deliverable

Whichever agents apply to your project, reviewed by you before they count as final:

  • UI testing: test-cases-ui-agent.md
  • API testing: test-cases-api-agent.md

The review pass is the same as every other AI approach in this series: confirm the ASSUMPTION: rows, delete anything generic that does not apply, and make sure the app-specific rules from the requirements actually made it into the Expected column.

Time: ~10 minutes to generate. Review time on top of that, which is the real work, and the whole reason a human stays in the loop.
