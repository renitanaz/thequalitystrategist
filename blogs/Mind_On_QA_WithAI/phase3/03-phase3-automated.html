Test Cases That Run Themselves

Same test cases, now as code. Self-healing locators mean they survive the next UI redesign.

By RN ~5 min read Series: AI-Augmented QA
Manual, No AI Manual + AI Automated, Playwright AI QA Agent

Convert manual test cases into executable Playwright specs, organized by feature, with self-healing locators so they survive UI changes.

Never used Playwright? Read Playwright Basics first. It's a one-page foundation: what Playwright is, how to install it, and how to write and run your first test, everything this page builds on.

What you actually do

  • Convert manual test cases into Playwright scripts
  • Use Page Object Model (POM) so tests don't break when UI changes
  • Add self-healing locators: role-based + data-testid, with retry on failure
  • Organize by feature: tests/products.spec.ts, tests/auth.spec.ts, etc.

What "self-healing" means and why it matters

A test has to find an element on the page before it can click or check it. How it finds that element decides how fragile the test is. If a test locates the checkout button by its CSS class, .btn-checkout-submit, then the day a developer renames that class during a restyle, the test can no longer find the button and fails, even though checkout still works perfectly. That's a false alarm: the test broke, not the app. A suite full of these wastes your time chasing failures that aren't real bugs.

A self-healing locator avoids this by finding elements the way a user does: by the visible text or role ("the button that says Place order"), or by a stable data-testid that the team agrees not to change. A redesign can move that button, recolor it, or rewrite its surrounding HTML, and the test still finds it, because "the button labelled Place order" is still true. The test heals through the change instead of breaking on it.

They're called self-healing because the test keeps passing through cosmetic changes on its own, with no edit from you. It only fails when something that actually matters changes, the button's text, its test id, or the behaviour behind it. That's exactly when you want a failure. Nothing literally repairs itself; the name describes locators chosen so that surface churn doesn't count as breakage.

Self-healing locators, side by side

// Fragile: breaks the moment the class name changes
page.locator('.btn-checkout-submit')

// Self-healing: survives most UI redesigns
page.getByRole('button', { name: 'Place order' })
page.getByTestId('checkout-submit-btn')

TC-101 as actual code

test('TC-101: checkout with valid discount @critical', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('button', { name: 'Add to cart' }).first().click();
  await page.getByRole('link', { name: 'Cart' }).click();
  await page.getByRole('button', { name: 'Proceed to checkout' }).click();
  await page.getByPlaceholder('e.g. SAVE10').fill('SAVE10');
  await page.getByRole('button', { name: 'Place order' }).click();

  // This SHOULD show a 10% discount. It currently shows 100% off (BUG-009).
  const total = await page.getByText(/Total charged/).textContent();
  expect(total).not.toContain('$0.00');
});

This test is supposed to fail right now. That's not a mistake, it's a bug-detection test (more on this pattern in Phase 7). When BUG-009 gets fixed, this test turns green automatically.

Two that pass

Most of your suite should be green against correct behaviour. Here are two that pass today, so the deliverable isn't only made of failing cases.

test('TC-105: checkout happy path @critical', async ({ page }) => {
  await page.goto('/');
  await page.getByRole('button', { name: 'Add to cart' }).first().click();
  await page.getByRole('link', { name: 'Cart' }).click();
  await page.getByRole('button', { name: 'Proceed to checkout' }).click();
  await page.getByRole('button', { name: 'Place order' }).click();

  // A normal order with no discount code goes through and is confirmed.
  await expect(page.getByText(/order confirmed/i)).toBeVisible();
});
test('TC-102: checkout with empty cart @high', async ({ page }) => {
  await page.goto('/cart');
  await page.getByRole('button', { name: 'Proceed to checkout' }).click();

  // No items: the app correctly refuses to create an order.
  await expect(page.getByText(/cart is empty/i)).toBeVisible();
  await expect(page.getByText(/order confirmed/i)).toHaveCount(0);
});

A healthy suite is mostly green. Passing tests are not wasted: they're the safety net that tells you a future change didn't break something that used to work. The failing ones (TC-101, TC-104) are the exception, written ahead of a known fix, not the norm.

Your deliverable

A tests/ folder with one spec file per feature area, each covering the happy/negative/edge cases identified in your manual or AI-assisted test case docs. See a worked example: checkout.spec.ts.

Time: ~4 to 6 hours. The longest single time investment in this phase, but the only approach that leaves you with tests that run themselves on every future change.
