Phase 7 of 8 · Bug Detection

Bug Detection, By Hand

7 of 11 seeded bugs found, seven structured reports. Steps, expected, actual, severity, evidence.

By RN ~5 min read Series: AI-Augmented QA
Manual, No AI Manual + AI Automated, Playwright AI QA Agent

7 of the 11 seeded bugs, documented by hand. No AI, no automation — just the live site, the API, and a structured bug report format. The goal is thorough, actionable documentation that a developer can pick up and act on without follow-up questions.

What a good bug report contains. Five fields, no more: Steps to reproduce (exact, numbered, reproducible by anyone), Expected (what the requirements or common sense say should happen), Actual (what actually happened, specific), Severity (Critical/High/Medium/Low based on user and business impact), and Evidence (screenshot, API response, or test output). A bug report missing any of these will bounce back from a developer.

Seven bug reports (of 11 seeded bugs)

BUG-008 — No stock check before checkout

Steps1. Find a product with stock = 0. 2. Add it to cart via POST /api/cart. 3. Submit checkout via POST /api/orders/checkout.
Expected400, order rejected, clear message: "item out of stock".
Actual201, order created. The out-of-stock item is sold.
SeverityHigh — an order is created for stock that does not exist. Fulfillment fails downstream.
EvidenceTC-104 in checkout.spec.ts (designed to fail). POST /api/orders/checkout returns 201 with item quantity = 0 in stock.

BUG-009 — SAVE10 applies 100% off instead of 10%

Steps1. Add any in-stock item to cart. 2. POST /api/orders/checkout with body {"discount_code":"SAVE10"}.
Expected201, total is 90% of the cart value. A $100 cart becomes $90.00.
Actual201, total is $0.00. The full price is discounted.
SeverityCritical — the store gives products away for free. Every checkout using SAVE10 results in $0 revenue.
EvidenceTC-101 in checkout.spec.ts. API response: {"total":0.00,"discountApplied":true}.

BUG-002 — Product card renders blank title

Steps1. Open peakandpack-ui.onrender.com. 2. Find the product card whose name field is empty in the database.
ExpectedA fallback label (for example "Unnamed product" or the product SKU) so the card never appears broken.
ActualThe card renders with an empty gap where the product name should be.
SeverityMedium — visible to customers. Looks broken. Does not prevent purchase but erodes trust.
EvidenceScreenshot: product-empty-name.png. Visual baseline diff in Phase 4.

BUG-001 — Negative price displays as "-$89.00"

Steps1. Open the product listing page. 2. Find the product card with a negative price in the database.
ExpectedA valid price or a hidden/flagged product. A negative price should never reach the customer-facing UI.
ActualThe price renders as "-$89.00" in red. The store appears to be paying customers to take the product.
SeverityHigh — visible to all customers on the listing page. Undermines trust in pricing across the store.
EvidenceScreenshot: product-negative-price.png. Visual baseline diff in Phase 4.

BUG-003 — Price set at $9,999.99, no upper bound validation

Steps1. Open the product listing. 2. Find "Insulated Water Bottle," priced at $9,999.99.
ExpectedProduct prices are validated against a sane upper bound before they reach the catalog.
ActualThe price renders correctly, this is not a display defect. The data value itself is the problem: nothing stopped an absurd price from being seeded. Checked at 375px viewport width in case it also clipped visually, it does not, renders fully on one line.
SeverityLow — low likelihood of customer impact on its own, but the same missing validation is the general case behind BUG-004 (no price validation on the products endpoint).
EvidenceScreenshot: product-price-overflow.png (kept as evidence that it does not overflow, not that it does).

BUG-010 — Orders endpoint returns all users' orders

Steps1. Log in as User A. 2. GET /api/orders with User A's token. 3. Inspect the response body.
ExpectedOnly User A's orders appear. Orders belonging to other users are never returned.
ActualOrders from all users appear in the response. User A can see User B's order history.
SeverityCritical — a data privacy violation. A customer can see another customer's purchase history. In a regulated context this would be a reportable incident.
EvidenceGET /api/orders response contains orders with multiple distinct userId values. Orders isolation test in Phase 5 and Phase 6 both designed to fail on this.

BUG-011 — Search returns 500 on missing query parameter

Steps1. GET https://peakandpackshopdemo.onrender.com/api/search (no ?q= parameter).
Expected400, clear validation error: "q parameter is required".
Actual500, unhandled exception. Response body exposes an internal stack trace with file paths and line numbers.
SeverityHigh — two issues in one: the wrong status code (server fault vs client fault), and a stack trace leaking internal implementation details to any caller.
Evidencecurl -i https://peakandpackshopdemo.onrender.com/api/search returns HTTP/1.1 500. Body contains a Node.js stack trace. Phase 5 search contract test designed to fail on this.
