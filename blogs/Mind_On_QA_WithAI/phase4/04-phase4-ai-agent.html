Phase 4 of 8 · Visual Regression

Visual Regression, by an Agent That Reads Screenshots

Hand it a screenshot, get a visual bug report. It reviews the image; you confirm each finding on the live UI.

By RN ~4 min read Series: AI-Augmented QA
Manual, No AI Manual + AI Automated, Playwright AI QA Agent

Phase 4 is about how the UI actually looks. So this agent does the visual job: you hand it a screenshot of a PeakAndPack page, and it reviews the image for visual and UI problems, then writes them up as a short bug report. It reasons only from the picture you give it; it does not click, hover, or browse the live site, the same limit a tester has when handed a still screenshot to review.

What it does

  1. You give it a screenshot of a PeakAndPack page (and, optionally, the requirements for that page).
  2. Claude reviews the image for visual problems: broken data display, layout breaks, overflow, responsive issues, low contrast, missing focus states.
  3. It returns a short bug report: one finding per issue, each with a title, location, the visible symptom, and a severity.

How it works

The mechanism is the same as the earlier agents, with one addition: the screenshot is sent to Claude as an image. The browser and Node forms read the image file, encode it, and attach it to the API request ahead of the text instruction; Claude's vision then reads the picture the way it would read pasted text. The system prompt is still where the real work happens, it tells Claude to report only what is visible and never to invent behaviour it cannot observe in a still image.

The system prompt is the design work, the code just carries an image. What stops this agent from hallucinating problems is the prompt's instruction to report only what is actually in the picture, and to mark anything uncertain "to confirm" rather than asserting it. A still screenshot can't show you whether the cart total updates on click, so the agent is told to say so rather than guess.

How to build it: three forms

Like the earlier phases, the agent ships in three forms, listed easiest-first. Same prompt, same kind of report; they differ only in how you hand over the screenshot.

1Prompt only, no key, no code

The fastest path. Open visual-review-agent-prompt.md, copy the prompt into a Claude chat, and attach your screenshot to the same message. If you have the requirements for that page, paste them too. Claude replies with the report.

2Browser form, a reusable tool

A small web page that runs on your own machine.

  1. Download visual-review-agent.html and double-click it to open in your browser (it runs from file:// on your disk, no host needed).
  2. Paste your Anthropic API key (console.anthropic.com → API Keys → Create Key).
  3. Choose a screenshot file. Capture one from peakandpack-ui.onrender.com; for mobile checks, narrow the window before you screenshot.
  4. Optionally paste the page's requirements, then click Review screenshot.

Under the hood: when you pick a file, the page reads it, converts it to base64, and sends it as an image block straight to Anthropic with your key, nothing is uploaded anywhere else and the key never leaves the tab.

3Node.js form, in a terminal

A script that reads an image file and writes the report to disk. It needs Node.js installed, nothing else; it is not Claude Code, the script calls the API itself.

  1. Check Node.js. In a terminal, run node --version. If it errors, install the LTS build from nodejs.org and reopen the terminal.
  2. Get an API key from console.anthropic.com.
  3. Put three things in one folder: visual-review-agent.js, your screenshot, and (optionally) a requirements .md.
  4. Set your key in that terminal: export ANTHROPIC_API_KEY=sk-ant-your-key (Mac) or set ANTHROPIC_API_KEY=sk-ant-your-key (Windows).
  5. Run it: node visual-review-agent.js screenshot.png, or add the requirements file as a second argument: node visual-review-agent.js screenshot.png requirements.md. It prints the report and saves visual-review-output.md.

How to tell if the agent actually looked at the image

A visual report can sound confident whether or not it read your specific screenshot. Here is how to check.

Trustworthy
It names something that is genuinely in your image, the actual product name on the card, the exact "-$89.00" text, a specific element that is clipped. It could only know that by reading the picture.
Warning sign
Generic advice that fits any web page (“ensure good contrast,” “test on mobile”) with nothing tied to what is actually on screen. If it never points at a concrete element in your screenshot, it may not have used the image at all.

The Figma approach: comparing against the design, not just the screenshot

A screenshot review tells you whether the page looks broken. It cannot tell you whether the page matches what the designer intended, because the agent has never seen the design. That is what a Figma review adds: instead of judging a screenshot on its own, you compare the built UI against the design file it was supposed to match, and flag the drift.

PeakAndPack has no Figma file, so this series does not ship a Figma agent. But the approach is worth knowing, because in a real product it is where a lot of visual QA value lives. Here is how it is done in practice:

  1. Get the design out of Figma. Either export the relevant frames as PNGs, or pull them programmatically through Figma's API (each frame has a node id you can request an image for). Newer setups use Figma's own MCP server so an agent can read frames directly.
  2. Capture the same view from the built UI. A screenshot of the live page at the same viewport width as the design frame.
  3. Give the agent both images. The same image-in, report-out mechanism as this agent, except now it receives two pictures: "here is the design, here is the build, list the differences that matter."
  4. Ask for drift, not pixels. The useful output is not "these pixels differ" (a diff tool does that), it is judgement: spacing that is off, a font weight that does not match, a colour that drifted, a component that was simplified in the build. That judgement is exactly what a vision model adds over a pixel-diff.

Why it stays an "approach" here, not a tool. A Figma agent is only as honest as the design files behind it. Building one for a project that has no designs would mean inventing an artifact that does not exist. When you do have a design system, this is the natural next step beyond screenshot review, same agent shape, two images instead of one.

Your deliverable

One file: visual-review-output.md, the agent's report after you confirm each finding on the live UI. The review pass is the same as every AI approach in this series: keep what is real, drop anything generic, and confirm anything the agent marked "to confirm" before it counts as a bug.

Time: ~10 minutes to generate per screenshot. Confirming each finding on the live UI is the real work, and the reason a human stays in the loop.
