Git for QA: The Basics

Every automated phase in this series, and in Playwright: Zero to Architect, assumes your test code lives in a Git repository. This is the whole foundation in one page: what Git is, how to turn a folder of tests into a tracked project, how to commit and branch, and how to push it to GitHub. Already comfortable with Git? Skip straight back to the phase you came from.

By RN ~6 min read Shared across series

What Git is

  • Tracks every change made to your test files over time, no more tests-final-v2-ACTUAL.ts
  • Commit = a saved snapshot with a note on what changed
  • Branch = a copy of the history you can experiment on without touching the working version
  • GitHub = a copy of that history online, survives a dead laptop, lets others see and review it

Think of it like a local godown and a destination warehouse:

  • Your machine = the godown. You manufacture goods (write code) and store finished batches on the shelf = commit. Local only, nothing has shipped yet.
  • GitHub = the destination warehouse you export to. git push = the shipment leaving your godown.
  • Before every shipment, check the destination's current stock, not what it had last time you looked. That check is git pull.
  • Skip the check and your shipment may conflict with stock someone else already delivered, Git refuses it and tells you to check the warehouse's books first.

Glossary

  • Repository (repo): a folder Git is tracking
  • Commit: a saved snapshot with a message
  • Branch: a separate line of work off the main history
  • Remote: the copy of the repo hosted elsewhere (GitHub, here)
  • Push / pull: send commits to the remote / bring remote commits down to you
  • Clone: download a full copy of an existing remote repo
  • Pull request (PR): a request to merge one branch into another, usually reviewed first
  • .gitignore: a file listing what Git should never track

Step 1: check Git is installed

git --version
  • See a version number? You're set.
  • Error? Install Git from git-scm.com, then reopen the terminal.

Step 2: tell Git who you are

Set once, globally, used by every repo on your machine:

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

Step 3: turn your test project into a repo

cd peakandpack-tests
git init
  • git init just switches tracking on, nothing is saved yet, like putting up empty shelving in the godown
  • Joining a repo that already exists on GitHub? Use clone instead, that's opening a godown pre-stocked with a copy of the warehouse's contents:
git clone https://github.com/your-org/your-repo.git

Step 4: tell it what to ignore

Create .gitignore in the project root, before your first commit:

node_modules/
test-results/
playwright-report/
.env
  • node_modules, huge and rebuildable from package.json
  • Report folders, regenerated every run
  • .env, where API keys live

Already committed a secret by mistake? Adding it to .gitignore stops future commits but doesn't erase it from history. Rotate the key immediately, then clean the history.

Step 5: your first commit

git status
git add .
git commit -m "Initial Playwright test setup"
  • git add . stages everything not ignored, packing a batch onto a pallet
  • git commit saves that snapshot locally, labelled and on the shelf
  • Nothing has left your machine yet, that's the next step

Step 6: push it to GitHub

Create an empty repo at github.com/new (no README, yours already has content), then:

git remote add origin https://github.com/your-username/your-repo.git
git branch -M main
git push -u origin main
  • -u links local main to the remote one, so future pushes are just git push
  • This is the actual shipment: commits leave your godown and land in the shared warehouse

Step 7: branch per change

git checkout -b add-checkout-tests
# ...write and run your tests...
git add .
git commit -m "Add checkout flow test coverage"
git push -u origin add-checkout-tests
  • Working on main directly is fine solo; branching per change scales to a team
  • A branch is a separate production line, prototype without touching the shelf everyone ships from
  • Open a pull request on GitHub comparing your branch to main
  • CI (Phase 12 in Playwright: Zero to Architect) runs your suite here before anything merges
CommandWhat it does
git statusWhat's changed, staged, or untracked right now.
git diffThe exact line-by-line changes, not yet staged.
git log --onelineCommit history, one line per commit.
git checkout -b nameCreate and switch to a new branch.
git checkout mainSwitch back to the main branch.
git pullBring down the latest commits from the remote.

Common beginner snags

  • "fatal: not a git repository": you're not inside a folder Git has initialised, check with git status
  • Push rejected as "behind": the warehouse has stock your godown doesn't, someone shipped since you last checked, run git pull first
  • Merge conflict: not a failure, just two branches changing the same lines, resolve by hand then git add + git commit
  • Committed to the wrong branch: git status before you start, every time

You're ready

  • Init or clone
  • Ignore what shouldn't be tracked
  • Commit in small snapshots with clear messages
  • Branch per change
  • Push, then open a pull request

Every phase in this series and in Playwright: Zero to Architect that mentions committing test code or opening a PR is a variation on exactly this loop.
