Async and Await

Every Playwright step waits for something: a page to load, a button to appear, a server to answer. This is how JavaScript waits, and why one missing word causes so many flaky tests.

Series: JavaScript for Testers Demo: PeakAndPack By: RN

Draft. Structured from study notes; every example still needs running during review.

Goal

  • Explain why JavaScript doesn't wait on its own
  • Read a promise's states: pending, fulfilled, rejected
  • Use await and async, and handle a wait that fails
  • Tell which Playwright lines need await, and spot a missing one

1. Why testers need this

A browser is slow compared with your code. Clicking, loading a page, waiting for a server's answer: each takes milliseconds to seconds. Every Playwright test is full of await for this reason, and a missing await is one of the most common causes of a test that fails at random, or passes without checking anything. The examples on this page use small stand-in functions that take time on purpose, so you can watch the waiting happen without a browser.

The examples use await at the top level of a file, which needs "type": "module" in your practice folder's package.json (Part 4, section 9). Inside a Playwright test, you never need to think about it.

2. JavaScript doesn't wait on its own

When something takes time, JavaScript starts it, then carries straight on with the next line. It doesn't stop and wait unless you tell it to:

console.log('1. Click "Place order"');

// Pretend the server takes half a second to confirm
setTimeout(() => console.log('3. Server confirms the order'), 500);

console.log('2. Check for "Order placed!"');
Explain this code, line by line
  • setTimeout(work, 500) means "do this work in 500 milliseconds". It's a stand-in for anything slow.
  • JavaScript schedules it and moves on immediately, so the output is 1, 2, then 3: the check runs before the server has confirmed anything.
  • That's the bug a missing await causes in a test: the check runs against a page that isn't ready yet.

3. Promises: an answer that arrives later

A function that takes time gives back a promise: an object standing in for an answer that isn't ready yet, like a receipt you swap for your order later. Playwright's click, goto and textContent all return promises.

// A stand-in for a slow operation: answers with a price after half a second
function fetchPrice(name) {
  return new Promise((resolve) => {
    setTimeout(() => resolve(24.99), 500);
  });
}

const pricePromise = fetchPrice('Headlamp');
console.log(pricePromise); // Promise { <pending> }: no answer yet
Explain this code, line by line
  • new Promise((resolve) => { ... }) creates a promise. Calling resolve(24.99) later delivers the answer. You'll rarely write this yourself; Playwright's methods return promises for you.
  • Printing the promise straight away shows Promise { <pending> }: the answer hasn't arrived. If you ever see this in a test's output, an await is missing.

4. await and async

await means "stop here until this promise settles, then give me its answer". async marks a function that's allowed to use await:

// await: wait for the answer, then carry on
const price = await fetchPrice('Headlamp');
console.log(price); // 24.99, after half a second

// async: a function that waits inside
async function isPriceValid(name) {
  const price = await fetchPrice(name);
  return price >= 0;
}

console.log(isPriceValid('Headlamp'));       // Promise { <pending> }
console.log(await isPriceValid('Headlamp')); // true
Explain this code, line by line
  • await fetchPrice(...) pauses this code until the promise is fulfilled, then hands over the value, 24.99. Nothing below it runs until then.
  • async function is required for await inside a function. Use await in an ordinary function and the file won't run: SyntaxError: await is only valid in async functions and the top level bodies of modules.
  • An async function always returns a promise, even though its code says return price >= 0. That's why calling it without await prints Promise { <pending> }, and why Part 5's page object method had the return type Promise<boolean>: "true or false, later".
  • Every Playwright test is async ({ page }) => { ... } for exactly this reason: so its steps can await.

5. When the wait fails

A promise can also reject: the work failed, or took too long. With await, a rejection becomes an error at that line. Here's a stand-in for Playwright waiting for a heading that never appears:

// Resolves if the heading shows up, rejects with a timeout if it doesn't
function waitForHeading(found) {
  return new Promise((resolve, reject) => {
    setTimeout(() => {
      if (found) {
        resolve('Order placed!');
      } else {
        reject(new Error('Timeout 5000ms exceeded waiting for heading'));
      }
    }, 300);
  });
}

try {
  const heading = await waitForHeading(false);
  console.log(heading);
} catch (error) {
  console.log('Test failed:', error.message);
}
// Test failed: Timeout 5000ms exceeded waiting for heading
Explain this code, line by line
  • reject(new Error(...)) settles the promise as failed, with an error describing why.
  • await on a rejected promise throws that error at that line, so the lines after it don't run.
  • try { ... } catch (error) { ... } catches it: if anything in the try block throws, the catch block runs instead, with the error in error. error.message is its text.
  • This is exactly what happens when a Playwright check times out: the step's promise rejects, the error is thrown, and the test fails on that line with the message you see in the report.

Don't wrap test steps in try/catch to "keep going". In a test, the failure is the result: catching it hides a real problem and lets the test pass. Use try/catch in helper code that genuinely knows how to recover, and let test steps fail loudly. A rejection nobody catches at all also stops a plain Node.js script, with the error printed.

6. Which Playwright lines need await

The rule: if it returns a promise, await it. In VS Code, hover over a method: if its type mentions Promise, it needs await.

LineAwait?Why
await page.goto('/')YesLoading a page takes time.
await card.click(), await field.fill('x')YesActions wait for the element, then act.
await expect(locator).toBeVisible()YesLocator checks keep retrying, up to 5 seconds.
await locator.textContent(), await locator.all()YesReading from the page takes time.
const card = page.getByTestId('product-card')NoA locator is a description, not a search (Part 2 of the Playwright series); nothing happens yet.
expect(total).toBe(59.98)NoA plain value check: the value is already here.

What a missing await looks like: a printed Promise { <pending> }; a check that passes even though the page is wrong, because the test finished before the check ran; or a confusing error after the test has ended, about a page or browser that has already closed. Playwright recommends a lint rule, @typescript-eslint/no-floating-promises, that underlines any promise you forgot to await.

Starting a wait before the action. You've met this pattern in the Playwright series' Phases 3 and 8:

const cartUpdated = page.waitForResponse(r => r.url().includes('/api/cart'));
await addButton.click();
await cartUpdated;

The first line has no await on purpose: it starts listening and keeps the promise. The click happens next, and only then does the test await the promise. If the first line had await, the test would sit waiting for a response that can't come until the click it hasn't made yet.

7. One after another, or all at once

Part 4 warned that forEach doesn't wait. Here's why, with a stand-in that takes 100 milliseconds per item:

// Waits ms milliseconds, says it's done, then resolves
const delay = (ms, label) => new Promise((resolve) => {
  setTimeout(() => {
    console.log('done', label);
    resolve(label);
  }, ms);
});

// forEach starts every item, and moves on without waiting
['A', 'B', 'C'].forEach(async (item) => {
  await delay(100, item);
});
console.log('after forEach'); // prints FIRST, before A, B and C are done

// for...of waits for each round before the next
for (const item of ['A', 'B', 'C']) {
  await delay(100, item);
}
console.log('after for...of'); // prints LAST, after A, B and C
Explain this code, line by line
  • forEach calls the async function for each item, but ignores the promises they return. So "after forEach" prints immediately, and A, B and C finish later. In a test, that means checks still running after the test thinks it's done.
  • for...of with await inside waits for each round to finish before starting the next, so "after for...of" prints after all three. This is the loop to use in tests.

Sometimes you want several things to happen at once. Promise.all starts them together and waits for all of them:

// One after another: about 600 ms
await delay(300, 'first');
await delay(300, 'second');

// Together: about 300 ms
const results = await Promise.all([delay(300, 'x'), delay(300, 'y')]);
console.log(results); // [ 'x', 'y' ]
Explain this code, line by line
  • Promise.all([...]) takes a list of promises, runs them at the same time, and gives back a list of their answers, in the same order. If any of them rejects, the whole thing rejects.
  • Two 300 ms waits take about 600 ms in turn, but about 300 ms together.
  • Test steps normally run one after another, because each depends on the last. Promise.all is for independent work, like the Playwright series' Phase 6 bonus, where two customers check out at the same moment.

Common mistakes.

  • A missing await. Hover over the method: if it returns a promise, it needs one.
  • await on a locator. Harmless, but pointless: building a locator doesn't wait for anything.
  • await inside a function that isn't async. The file won't run.
  • forEach with await inside. It doesn't wait. Use for...of.
  • Catching errors in a test to keep it going. It hides the failure the test exists to find.
