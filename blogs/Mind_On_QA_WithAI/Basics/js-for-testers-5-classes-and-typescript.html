Classes and TypeScript

Classes are the shape of every page object; TypeScript is the safety net that catches mistakes before a test runs. Both, explained for testers.

Series: JavaScript for Testers Demo: PeakAndPack By: RN

Draft. Structured from study notes; every example still needs running during review.

Goal

  • Build objects from a class, with a constructor, this and methods
  • Share a class between files
  • Read and write TypeScript types: on variables, functions and your own type
  • Read the TypeScript in Playwright code: page: Page, Promise<boolean>, private page

1. Why testers need this

The Playwright series' Phase 9 organises tests into page objects: one class per page of the app, holding that page's locators and actions, so tests read like journeys. Every page object is a class. And every Playwright test is TypeScript, so its code is full of types like page: Page. This part explains both, so that code reads as plain sense rather than syntax.

2. Classes: a blueprint for objects

Part 2's objects were written out one at a time. A class is a blueprint that builds as many objects as you need, each with the same shape and the same abilities:

class Cart {
  // Runs once, when a new cart is built
  constructor(owner) {
    this.owner = owner;
    this.items = [];
  }

  // A method: something every cart can do
  add(name, price) {
    this.items.push({ name, price });
  }

  total() {
    let sum = 0;
    for (const item of this.items) {
      sum += item.price;
    }
    return sum;
  }
}

const anasCart = new Cart('Ana');
anasCart.add('Headlamp', 24.99);
anasCart.add('Camping Stove', 45.99);

const bensCart = new Cart('Ben');
bensCart.add('4-Season Tent', 320);

console.log(anasCart.owner, anasCart.items.length, anasCart.total().toFixed(2)); // Ana 2 70.98
console.log(bensCart.owner, bensCart.items.length, bensCart.total());            // Ben 1 320
Explain this code, line by line
  • class Cart { ... } creates the blueprint. By convention, class names start with a capital letter.
  • constructor(owner) runs once, automatically, each time a new cart is built. It sets up the cart's starting values.
  • this means "the object being built or used right now". this.owner = owner stores the owner on this cart; this.items = [] gives it its own empty list.
  • add(name, price) { ... } and total() { ... } are methods: functions that belong to the class. Unlike Part 4's functions, they're written without the word function.
  • this.items.push({ name, price }) adds an item to the end of this cart's list. push is the array method for adding; { name, price } is short for { name: name, price: price }.
  • new Cart('Ana') builds an object from the blueprint, running the constructor with 'Ana'. That object is called an instance.
  • anasCart.add(...) calls a method on one instance. Ana's items and Ben's items stay separate: each cart has its own this.

Two errors you'll meet. Forget new, as in Cart('Ana'), and you get TypeError: Class constructor Cart cannot be invoked without 'new'. Forget this. inside a method, writing items.push(...), and you get ReferenceError: items is not defined: without this., the method looks for an ordinary variable called items, and there isn't one.

3. Sharing a class between files

Classes are exported and imported like Part 4's functions. Each file that imports the class builds its own instances with new:

// helpers/cart.js
export class Cart {
  constructor(owner) {
    this.owner = owner;
    this.items = [];
  }

  /**
   * Adds one product to this cart.
   * @param {string} name  The product's name
   * @param {number} price The product's price
   */
  add(name, price) {
    this.items.push({ name, price });
  }
}
// shopping.js
import { Cart } from './helpers/cart.js';

const cart = new Cart('Ana');
cart.add('Headlamp', 24.99);
console.log(cart.items); // [ { name: 'Headlamp', price: 24.99 } ]
Explain this code, line by line
  • export class Cart makes the class available to other files, the same way export worked for functions.
  • /** ... */ is a documentation comment. VS Code shows it when you hover over add anywhere in your code, so whoever uses the class sees what it does and what to pass in. @param lines describe each parameter.
  • You can also export a ready-built instance, export const cart = new Cart('Ana');, so other files share that one object. For page objects, export the class instead: each test builds its own, with its own browser tab.

4. From class to page object

Here's the shape of a page object from the Playwright series' Phase 9, without the TypeScript yet. Read it with what you now know:

export class CartPage {
  constructor(page) {
    this.page = page; // the browser tab this page object works in
  }

  async goto() {
    await this.page.goto('/cart');
  }

  async proceedToCheckout() {
    await this.page.getByRole('button', { name: /proceed to checkout/i }).click();
  }
}

// In a test:
// const cart = new CartPage(page);
// await cart.goto();
// await cart.proceedToCheckout();
Explain this code, line by line
  • The constructor receives the test's browser tab and keeps it as this.page, so every method can use it.
  • Each method is one user action on that page. The test calls cart.proceedToCheckout() instead of repeating the locator, so if the button's wording changes, only this class needs fixing.
  • async and await are there because browser actions take time; Part 6 explains them.

5. TypeScript: JavaScript with types

TypeScript is JavaScript plus types: labels saying what kind of value something holds. All JavaScript is valid TypeScript; the types are the extra layer. The point is to catch mistakes in VS Code, while you type, instead of when a test fails. TypeScript files end in .ts.

// TypeScript works out the type from the first value...
let productName = 'Headlamp'; // hover over it: let productName: string

// ...or you can state it yourself, after a colon
let price: number = 24.99;

productName = 100;   // red underline: Type 'number' is not assignable to type 'string'.
price = '24.99';     // red underline: Type 'string' is not assignable to type 'number'.
Explain this code, line by line
  • Type inference: let productName = 'Headlamp' has no type written, but TypeScript infers string from the value. Hover over a variable in VS Code to see it.
  • Type annotation: let price: number states the type, after a colon.
  • In plain JavaScript, putting a number into productName is allowed, and the mistake surfaces later, somewhere confusing. TypeScript underlines it in red immediately.

The real power is describing the shape of your data, and the inputs and outputs of functions:

// Your own type: what every product must look like
type Product = {
  name: string;
  price: number;
  inStock: boolean;
  rating?: number; // the ? means optional
};

const headlamp: Product = { name: 'Headlamp', price: 24.99, inStock: true };

// Typed parameters, and a typed return value
function formatPrice(price: number): string {
  return `$${price.toFixed(2)}`;
}

const tent: Product = { name: '4-Season Tent', price: 320 };
// red underline: Property 'inStock' is missing in type ... but required in type 'Product'.

const stove: Product = { name: 'Camping Stove', price: 45.99, inStock: true, colour: 'red' };
// red underline: Object literal may only specify known properties, and 'colour' does not exist in type 'Product'.

formatPrice('24.99');
// red underline: Argument of type 'string' is not assignable to parameter of type 'number'.
Explain this code, line by line
  • type Product = { ... } creates your own type: every Product must have a text name, a number price and a true/false inStock.
  • rating?: number: the ? makes it optional. A product may have a rating or not, but if it has one, it must be a number.
  • function formatPrice(price: number): string: the parameter must be a number, and the function promises to return text. The part after the closing bracket is the return type.
  • The three underlined lines are the mistakes TypeScript catches for you: a missing property, an unknown property (often a typo), and the wrong type of argument. Each message names the problem precisely.

Type errors don't stop a test from running. TypeScript checks your code in VS Code, but Playwright doesn't type-check when it runs tests (Phase 0 noted this). A file full of red underlines still runs, and fails later, in a more confusing way. Treat red underlines as failures: fix them before you run. To check a whole project at once, run npx tsc --noEmit, which lists every type error without changing any files.

6. The TypeScript you'll see in Playwright code

Here's the same page object, in TypeScript, the way Phase 9 writes it:

import { Page } from '@playwright/test';

export class CartPage {
  constructor(private page: Page) {}

  async goto(): Promise<void> {
    await this.page.goto('/cart');
  }

  async isEmpty(): Promise<boolean> {
    return this.page.getByText('Your cart is empty.').isVisible();
  }
}
Explain this code, line by line
  • import { Page } from '@playwright/test' brings in Playwright's type for a browser tab. Types are imported like functions.
  • page: Page means "page must be a Playwright browser tab". Pass anything else and it's underlined.
  • constructor(private page: Page) {} is a shorthand. Writing private in front of a parameter means "store it as this.page": it replaces the this.page = page; line from section 4. private also means only the class itself can use it, so tests can't reach in and click things directly.
  • Promise<boolean> is the return type of an async method: "an answer that arrives later, and will be true or false". Promise<void> means "finishes later, with no answer". Part 6 covers promises.

Running TypeScript while practising. Node.js 20 can't run .ts files directly. Use npx tsx file.ts, which runs them without a separate build step, and npx tsc --noEmit to check types. Inside your Playwright project, you don't need either: Playwright runs .ts test files itself.

Common mistakes.

  • Forgetting new. "Class constructor ... cannot be invoked without 'new'".
  • Forgetting this. inside a method. "... is not defined".
  • Sharing one exported instance between tests. For page objects, export the class; each test builds its own.
  • Ignoring red underlines because the test still runs. Type errors are bugs found early; fix them first.
Exercise

Build a cart class, then type it

Do steps 1 to 6 in exercise-classes.js (run with node), and steps 7 to 10 in exercise-types.ts (run with npx tsx, check with npx tsc --noEmit):

  1. Write a Cart class whose constructor stores an owner and an empty items list.
  2. Add a method add(name, price) that pushes an item, and a method total() that returns the sum of the prices.
  3. Build two carts, Ana's with two items and Ben's with one, and print each owner, item count and total. Do they share items?
  4. Add a /** ... */ comment above add, then hover over a call to add in VS Code. What appears?
  5. Break it on purpose, one at a time: build a cart without new; inside add, write items.push without this.. Read each error.
  6. Move Cart into helpers/cart.js, export it, and import it into your exercise file.
  7. In exercise-types.ts, write a type Product with name, price and an optional rating.
  8. Rewrite Cart with types: owner: string, items: Product[], add(product: Product): void, total(): number. Build a cart, add two products (one with a rating), and print the total.
  9. Add three mistakes: a product whose price is '320', a product with no price, and cart.add('Tent'). Read each red underline, then run npx tsc --noEmit and compare.
  10. With the mistakes still in, run the file with npx tsx. Does it run? What does that tell you about red underlines?

type Product = {
  name: string;
  price: number;
  rating?: number;
};

class Cart {
  owner: string;
  items: Product[];

  constructor(owner: string) {
    this.owner = owner;
    this.items = [];
  }

  /** Adds one product to this cart */
  add(product: Product): void {
    this.items.push(product);
  }

  total(): number {
    let sum = 0;
    for (const item of this.items) {
      sum += item.price;
    }
    return sum;
  }
}

const cart = new Cart('Ana');
cart.add({ name: 'Headlamp', price: 24.99 });
cart.add({ name: 'Camping Stove', price: 45.99, rating: 4.5 });

What to notice.

  • Step 3: the two carts don't share items. Each new builds a separate object, with its own this.items.
  • Step 4: hovering shows your comment, "Adds one product to this cart". Other people using your class see it too.
  • items: Product[] reads "a list of Products": the square brackets after a type mean "a list of that type".
  • Step 10: with all three mistakes uncommented, npx tsx still runs the file and prints the totals. The underlines are the only warning you get before running, so treat them as failures.
