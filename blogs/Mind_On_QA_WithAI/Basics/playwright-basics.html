Playwright Basics for Beginners

The automated approaches in Phase 3 and Phase 4 use Playwright. This is the whole foundation in one page: what it is, how to install it, how to write and run your first test, and how to read the result. Already use Playwright? Skip straight back to the phase you came from.

By RN ~6 min read Series: AI-Augmented QA

What Playwright is, in one paragraph

Playwright is a free tool that drives a real browser for you: it opens pages, clicks buttons, fills forms, and checks what appears, all from code you write. Instead of clicking through the site by hand every time you want to test it, you describe the checks once and Playwright runs them in seconds, the same way every time. It can also call an API directly without a browser, which is how the Phase 5 API tests work.

Plain-English glossary. Test: one named check, written as a block of code. Spec file: a file ending in .spec.ts that holds one or more tests. Assertion: the line that says what should be true, for example "this text should be visible"; if it isn't, the test fails. Locator: how a test finds an element on the page (by its visible text, its role, or a test id). Baseline: a saved reference screenshot that later runs get compared against (used in Phase 4). Headless: running the browser invisibly in the background, the default; add --headed to watch it happen.

Step 1: check Node.js is installed

Playwright runs on Node.js, the same runtime the agent scripts use. Open a terminal (Mac: search "Terminal"; Windows: search "PowerShell") and type:

node --version

If you see a number like v20.x.x (anything 18 or higher), you're set. If it errors, install the LTS build from nodejs.org, then close and reopen the terminal.

Step 2: install Playwright

Make a folder for your tests, go into it, and let Playwright set itself up:

mkdir peakandpack-tests
cd peakandpack-tests
npm init playwright@latest

It asks a couple of questions. Accept the defaults: TypeScript yes, tests folder tests. This downloads Playwright and the browsers it drives (that download is a few hundred MB the first time, so give it a minute).

Step 3: point it at the site

Open the playwright.config.ts file it created and set the base URL, so every test can use short paths like / or /api/products instead of the full address:

use: {
  baseURL: 'https://peakandpack-ui.onrender.com/',
},

With that set, page.goto('/') opens the PeakAndPack home page. (For the API tests in Phase 5, the base URL is the API host instead.)

Step 4: write your first test

Create a file called tests/first.spec.ts and put this in it. Every test follows the same shape: go somewhere, then assert something is true.

import { test, expect } from '@playwright/test';

test('home page shows the product list', async ({ page }) => {
  await page.goto('/');
  // Assertion: a heading with this text should be visible.
  await expect(page.getByRole('heading', { name: /products/i })).toBeVisible();
});

Reading it in plain English: open the home page, then check that a heading containing the word "products" is visible. If it is, the test passes; if not, it fails and tells you why.

Why locators use text and roles, not CSS classes. Notice getByRole('heading', { name: /products/i }) instead of something like .product-header. Finding elements by what the user sees (a heading that says "products") means the test keeps working when a developer restyles the page and changes class names. This is the "self-healing" idea the automated phases talk about, and it starts right here in how you write the locator.

Step 5: run it

Back in the terminal, run:

npx playwright test

Playwright runs every test in the tests/ folder and prints a pass/fail summary. To watch it happen in a visible browser instead of silently, add --headed. To run just one file, name it: npx playwright test tests/first.spec.ts.

Step 6: read the result

A passing run prints green. A failing run prints red and, crucially, tells you what it expected versus what it found. Playwright also writes an HTML report you can open in a browser:

npx playwright show-report

The report shows each test, its status, and for failures a trace, screenshots, and the exact line that failed. That report is what you attach or screenshot when filing a bug.

Common beginner snags. "command not found: npx" means Node.js isn't installed (Step 1). A test that fails instantly on a fresh page usually means it checked before the page finished loading, add a wait for a known element. A first-ever visual test that "fails" with no baseline is normal: the first run captures the baseline, later runs compare against it (Phase 4 covers this). And if a test can't find an element, check the locator matches the visible text or role, not a CSS class.

You're ready

That's the whole loop: install Playwright, point it at the site, write a test (go somewhere, assert something), run it, read the report. Every automated test in this series is a variation on that shape, whether it's clicking through checkout in Phase 3, diffing screenshots in Phase 4, or calling endpoints in Phase 5.
