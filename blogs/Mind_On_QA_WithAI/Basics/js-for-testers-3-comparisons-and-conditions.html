JavaScript for Testers · Part 3 Comparisons Equality Logical Operators Conditions

Comparisons and Conditions

Every check a test makes comes down to comparing two values. Here's how JavaScript compares, and the traps that make a correct-looking check give the wrong answer.

Series: JavaScript for Testers Demo: PeakAndPack By: RN

Draft. Structured from study notes; every example still needs running during review.

Goal

  • Compare numbers with >, <, >= and <=
  • Check equality with === and !==, and know why to avoid ==
  • Convert text read from a page into a number before comparing it
  • Know why two identical-looking objects aren't "equal"
  • Combine checks with &&, || and !
  • Choose what code runs with if, else if and else

1. Why testers need this

A test is a list of checks, and every check is a comparison: is the price at least zero, is the cart count what we expect, is the heading the one we want. Playwright's checks, like expect(price).toBeGreaterThanOrEqual(0), are these same comparisons with better error messages. Knowing how JavaScript compares tells you why a check passed or failed, and catches the cases where it gives the wrong answer quietly.

2. Comparing numbers

Comparison operators ask a question about two values, and the answer is always a boolean: true or false.

const price = -89; // PeakAndPack's Sleeping Bag, a known bug

console.log(price > 0);  // false: is it more than 0?
console.log(price < 0);  // true:  is it less than 0?
console.log(price >= 0); // false: is it 0 or more?
console.log(5 >= 5);     // true:  5 is not more than 5, but it is equal
console.log(4 <= 5);     // true:  4 is less than 5

// The answer can be stored, like any value
const isValidPrice = price >= 0;
console.log(isValidPrice, typeof isValidPrice); // false boolean
Explain this code, line by line
  • Each operator compares the value on its left with the value on its right:
    • > more than, < less than;
    • >= more than or equal to, <= less than or equal to.
  • The difference between > and >= only shows when the two sides are equal: 5 > 5 is false, 5 >= 5 is true. Choosing the wrong one is a classic boundary bug, the kind Boundary Value Analysis in the Playwright series' Phase 1 is designed to catch.
  • price >= 0 is the business rule "a price can't be negative" written as code. On the Sleeping Bag, it's false: the check catches the bug.
  • The result is an ordinary boolean, so you can store it in a variable and use it later.

3. Equality: ===, not ==

To check whether two values are the same, use three equals signs. To check they're different, use !==:

console.log('Headlamp' === 'Headlamp'); // true
console.log('Headlamp' === 'headlamp'); // false: capitals matter
console.log('Headlamp' !== 'Tent');     // true: they're different

// Same-looking values of different types
console.log(89 === '89');  // false: a number is not text
console.log(89 == '89');   // true:  == converts one side first
Explain this code, line by line
  • === is strict equality: true only if the value and the type are the same.
  • !== is its opposite: true when they differ, in value or type.
  • == is loose equality: it quietly converts one side to the other's type before comparing. That's why 89 == '89' is true.
  • Remember from Part 1: a single = doesn't compare at all, it stores a value. Writing = where you meant === is a common slip.
  • Text comparisons are exact: 'Headlamp' and 'headlamp' are different.

Why to avoid ==: its conversions produce surprises. 0 == '' is true, 1 == true is true, and null == undefined is true. A test using == can pass when the values really are different. Use === and !== every time; Playwright's toBe check works the same strict way.

4. Converting text before comparing

Anything a test reads from a page is text, prices included (Part 1). Compared strictly with a number, it's never equal. Convert it with Number() first:

const priceFromPage = '89.00';

console.log(priceFromPage === 89);         // false: text vs number
console.log(Number(priceFromPage) === 89); // true:  both numbers now

// The $ sign has to go first
console.log(Number('$34.99')); // NaN: "Not a Number"
console.log(Number('34.99'));  // 34.99

// And an empty string quietly becomes 0
console.log(Number(''));       // 0
Explain this code, line by line
  • Number(text) turns text that looks like a number into a real number.
  • If the text isn't purely a number, the result is NaN, short for "Not a Number". '$34.99' fails because of the $. Prices on PeakAndPack's pages include it, so it has to be removed before converting. The Playwright series shows how in Phase 3.
  • Number('') gives 0, not an error. If a test reads an empty price and converts it, a check like "price is 0 or more" passes on a blank value. Check the text isn't empty first.

5. Comparing objects and arrays

Objects and arrays are compared by identity, not by what's inside them:

const expected = { id: 1, name: 'Headlamp' };
const actual = { id: 1, name: 'Headlamp' };
const sameOne = expected;

console.log(expected === actual);  // false: two separate objects
console.log(expected === sameOne); // true:  the very same object
console.log([1, 2] === [1, 2]);    // false: two separate arrays
Explain this code, line by line
  • === on objects asks "is this the very same object?", not "do they hold the same things?". expected and actual hold identical values, but they're two separate objects, so the answer is false.
  • sameOne = expected doesn't copy anything; both names point to one object, so the answer is true.
  • That's why Playwright has two checks: toBe works like ===, and toEqual compares what's inside. Comparing an API response with the object you expected needs toEqual.

6. Combining checks: &&, || and !

Business rules usually have more than one condition: you can buy an item if it's in stock and the quantity is available and the price is valid. Logical operators join comparisons into one answer:

const inStock = true;
const stock = 5;
const quantity = 3;
const price = 34.99;

// AND: every part must be true
const canBuy = inStock && quantity <= stock && price >= 0;
console.log(canBuy); // true

// OR: at least one part must be true
const isMember = false;
const hasCode = true;
console.log(isMember || hasCode); // true: gets the discount either way

// NOT: flips true and false
const isLoggedIn = false;
console.log(!isLoggedIn); // true: "not logged in" is true
Explain this code, line by line
  • && (AND) is true only if every part is true. One false part makes the whole thing false. canBuy is true because all three checks pass.
  • || (OR) is true if any part is true. It's false only when every part is false. The two vertical bars are on the backslash key on most keyboards.
  • ! (NOT) flips a boolean: !true is false. Read !isLoggedIn as "not logged in". !== from section 3 is the same idea built into one operator: !(6 === 10) and 6 !== 10 both give true.
  • When you mix && and ||, JavaScript does the && parts first, like multiplication before addition. Add brackets to make your meaning clear: (isMember || hasCode) && inStock.

Beyond true and false. &&, || and ! also work on values that aren't booleans. JavaScript treats six values as "false-like" (called falsy): false, 0, '' (empty text), null, undefined and NaN. Everything else counts as true. Two patterns use this, and you'll meet both in test configs:

// !! turns any value into a plain true or false
console.log(!!'Headlamp'); // true:  non-empty text
console.log(!!'');         // false: empty text is falsy
console.log(!!'0');        // true:  the TEXT "0" isn't empty
console.log(!!process.env.CI); // false on your laptop, true on a CI server

// || picks the first value that isn't falsy: a default
const baseUrl = process.env.BASE_URL || 'https://peakandpack-ui.onrender.com';
console.log(baseUrl); // the fallback address, unless BASE_URL is set
Explain this code, line by line
  • !! is two NOTs: the first flips the value into a boolean, the second flips it back. The result is "is this value true-like?" as a plain true or false. Phase 0's config uses it: forbidOnly: !!process.env.CI means "true if the CI variable is set".
  • '0' is text with one character in it, so it's not empty and counts as true. Only the number 0 is falsy.
  • a || b gives back a if it's true-like, otherwise b. With process.env.BASE_URL || '...', a test can be pointed at a different site by setting BASE_URL, and falls back to the live store when it isn't set.
  • The trap: || can't tell "missing" from a real 0 or ''. const quantity = 0 || 1; gives 1, quietly replacing a real quantity of zero. For numbers that can legitimately be 0, compare explicitly instead.

7. Conditions: choosing what runs

So far every line has run, top to bottom. A condition makes code choose: run this block if something is true, otherwise run that one. Here's PeakAndPack's stock label as code:

const stock = 3;

if (stock === 0) {
  console.log('Out of stock');
} else if (stock < 5) {
  console.log(`Only ${stock} left`);
} else {
  console.log('In stock');
}
// Only 3 left
Explain this code, line by line
  • if (condition) { ... }: the condition in the round brackets is checked; if it's true, the code in the curly braces runs.
  • else if (condition) { ... } is checked only if everything above it was false. You can have as many as you need.
  • else { ... } runs when nothing above was true. It's optional, and has no condition.
  • Only one block runs: the first whose condition is true. The rest are skipped, even if their conditions are also true.
  • The condition can be any comparison or combination from the sections above: stock >= 1 && stock < 5, isMember || hasCode, !isLoggedIn.
  • Change stock to 0, then 5, and rerun to see each block run.

The boundaries live in the conditions. This code has two: 0, where "Out of stock" begins, and 5, where "In stock" begins. Testing it properly means checking the values on each side, 0, 1, 4 and 5, the Boundary Value Analysis from the Playwright series' Phase 1.

Order matters. Swap the first two conditions, checking stock < 5 before stock === 0, and a stock of 0 shows "Only 0 left": 0 is less than 5, so that block wins and the "Out of stock" check never runs. Put the most specific condition first.

A one-line if/else. When you just need to choose between two values, ? : does it in one line. You've seen it in Phase 0's config:

const isCI = false;

// question ? value-if-true : value-if-false
const retries = isCI ? 2 : 0;
console.log(retries); // 0

// A condition can use a falsy value directly (section 6)
const discountCode = null;
if (discountCode) {
  console.log(`Apply ${discountCode}`);
} else {
  console.log('No code'); // runs: null is falsy
}
Explain this code, line by line
  • isCI ? 2 : 0 reads "is it CI? then 2, otherwise 0". It's called the ternary operator, and it gives back a value, so you can store it, which a full if can't do directly.
  • if (discountCode) works without a comparison: the condition is falsy for null, '', 0 and the rest, and true-like otherwise. Remember the trap from section 6: a real 0 counts as falsy too.

In tests, be careful with if. A test that checks something only if a condition holds can pass without checking anything: the condition was false, so the check never ran, and the test still shows green. A test should check the same things every run. Conditions belong in setup and helpers, such as closing a cookie banner if one appears, not around the checks themselves.

Common mistakes.

  • Using ==. It converts types behind your back. Use ===.
  • Comparing page text with a number. Convert with Number() first, after removing symbols like $.
  • Choosing > when the rule says "or equal". "At least 0" is >= 0; "more than 0" is > 0. The boundary value is where they differ.
  • Mixing && and || without brackets. The && parts run first, which may not be what you meant. Brackets make it explicit.
  • Using || for a default when 0 is a valid value. 0 || 1 is 1.
  • Putting a broad condition before a specific one. The first true condition wins, so stock < 5 before stock === 0 means the zero case never runs.
  • Wrapping a test's checks in if. If the condition is false, the test passes without checking anything.
  • Comparing objects with ===. Two objects with the same contents are still different objects. Compare contents, or use Playwright's toEqual.
Exercise

Check a product like a test would

Create exercise-comparisons.js, write code for each step, and run it with node exercise-comparisons.js. For every step, predict the answer before you run it.

  1. Store the Sleeping Bag's price, -89. Check, and print: is it more than 0? less than 0? 0 or more?
  2. Store the answer to "is the price valid (0 or more)?" in a variable, and print it with its type.
  3. Stock is 5 and the customer wants 5. Using >= and then >, check whether there's enough stock. Which operator matches the rule "you can buy if stock covers the quantity"?
  4. Check the quantity is no more than the maximum per order, 10, with <=.
  5. Check whether 'Headlamp' equals 'headlamp', and whether 'Headlamp' is different from 'Tent'.
  6. A price read from the page is '89.00'. Compare it with 89 using ===, then using ==. Why do they disagree?
  7. Convert it with Number(), and compare again with ===.
  8. Try converting '$89.00' and ''. What do you get, and what could go wrong in a test?
  9. Print 0 == '' and null == undefined, then the same with ===.
  10. Create two objects with the same id and name, and a third name pointing at the first. Which pairs are ===?
  11. Write the rule "a customer can buy if the item is in stock AND the quantity is no more than the stock AND the price is 0 or more" as one variable, canBuy, for the Sleeping Bag (in stock, stock 5, quantity 5, price -89). Which part makes it false?
  12. Write "gets free delivery if they're a member OR the order is over 100": check it for a non-member with an order of 120, then for a non-member with an order of 50.
  13. Store isLoggedIn = false, and print "not logged in" with !. Then show that !(price === 89) and price !== 89 give the same answer.
  14. Print !! of: 'Headlamp', '', '0', 0, null. Which surprise you?
  15. Set a base URL with process.env.BASE_URL || 'https://peakandpack-ui.onrender.com' and print it. Then print 0 || 1: why is that a problem for a quantity?
  16. Write the stock label with if, else if and else: 0 is "Out of stock", under 5 is "Only N left", otherwise "In stock". Run it with stock 0, 1, 4 and 5. Why those four values?
  17. Swap the first two conditions and run it with stock 0. What goes wrong, and why?
  18. Using ? :, set retries to 2 on CI and 0 otherwise, with isCI = false.
  19. With discountCode = null, use if (discountCode) to print either "Apply ..." or "No code". Then set it to 'SAVE10' and rerun.
Show solution: try it yourself first 
// 1. Comparing numbers: the answer is always true or false
const price = -89;
console.log(price > 0, price < 0, price >= 0);

// 2. The answer is a value you can store
const isValidPrice = price >= 0;
console.log(isValidPrice, typeof isValidPrice);

// 3. The boundary: stock exactly equal to the quantity
const stock = 5;
const quantity = 5;
console.log(stock >= quantity, stock > quantity);

// 4. At most the maximum per order
const maxPerOrder = 10;
console.log(quantity <= maxPerOrder);

// 5. Strict equality on text: exact, capitals included
console.log('Headlamp' === 'headlamp', 'Headlamp' !== 'Tent');

// 6. Text vs number: strict and loose disagree
const priceFromPage = '89.00';
console.log(priceFromPage === 89, priceFromPage == 89);

// 7. Convert first, then compare strictly
console.log(Number(priceFromPage) === 89);

// 8. Conversions that go wrong
console.log(Number('$89.00'), Number(''));

// 9. Loose equality's surprises
console.log(0 == '', null == undefined, 0 === '', null === undefined);

// 10. Objects compare by identity
const expected = { id: 1, name: 'Headlamp' };
const actual = { id: 1, name: 'Headlamp' };
const sameOne = expected;
console.log(expected === actual, expected === sameOne);

// 11. AND: every part must be true
const inStock = true;
const canBuy = inStock && quantity <= stock && price >= 0;
console.log(canBuy);

// 12. OR: any part can make it true
const isMember = false;
console.log(isMember || 120 > 100, isMember || 50 > 100);

// 13. NOT
const isLoggedIn = false;
console.log(!isLoggedIn, !(price === 89), price !== 89);

// 14. Falsy and true-like values
console.log(!!'Headlamp', !!'', !!'0', !!0, !!null);

// 15. || as a default, and its trap
const baseUrl = process.env.BASE_URL || 'https://peakandpack-ui.onrender.com';
console.log(baseUrl, 0 || 1);

// 16. if / else if / else: rerun with stockLeft set to 0, 1, 4 and 5
const stockLeft = 4;
if (stockLeft === 0) {
  console.log('Out of stock');
} else if (stockLeft < 5) {
  console.log(`Only ${stockLeft} left`);
} else {
  console.log('In stock');
}

// 17. The same checks in the wrong order (with stockLeft set to 0):
// if (stockLeft < 5) { ... } else if (stockLeft === 0) { ... }  -> "Only 0 left"

// 18. One-line if/else
const isCI = false;
const retries = isCI ? 2 : 0;
console.log(retries);

// 19. A falsy value as the condition: rerun with discountCode set to 'SAVE10'
const discountCode = null;
if (discountCode) {
  console.log(`Apply ${discountCode}`);
} else {
  console.log('No code');
}

What to notice.

  • Step 3 is a boundary. With stock and quantity both 5, >= says yes and > says no. The rule "stock covers the quantity" means >=; using > would wrongly block buying the last 5. This is why tests check the boundary value itself.
  • Step 6: === says no because the types differ; == converts the text and says yes. A test using == can't tell text from a number.
  • Step 8: the $ makes NaN, and empty text becomes 0. Both are quiet: no error, just a wrong value for the next check to trip over.
  • Step 10: identical contents, but separate objects. Only the name pointing at the same object is ===.
  • Step 11: stock and quantity pass, but price >= 0 fails, so && makes the whole rule false. One failing part is enough: that's how a test catches the negative price.
  • Step 13: !(price === 89) and price !== 89 are two ways to say the same thing. !== is easier to read.
  • Step 14: '0' is true-like because it's non-empty text; the number 0 is falsy.
  • Step 15: 0 || 1 gives 1. If 0 is a real answer, like a quantity of zero, || replaces it without warning.
  • Step 16: with stock 0, 1, 4 and 5 you see "Out of stock", "Only 1 left", "Only 4 left" and "In stock". Those four sit on each side of the two boundaries, 0 and 5, where a wrong < or <= would show.
  • Step 17: 0 is less than 5, so the "Only N left" block runs first and "Out of stock" is never reached. The first true condition wins.
  • Step 19: null is falsy, so "No code" runs; 'SAVE10' is true-like, so "Apply SAVE10" runs.
