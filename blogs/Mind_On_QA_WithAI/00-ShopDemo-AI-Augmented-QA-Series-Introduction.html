AI-Augmented QA Series: Testing One App, Four Ways

A hands-on series testing a real e-commerce app end to end, manually, with AI assistance, with Playwright automation, and with an AI QA agent, so the comparison is never theoretical.

By RN 8 phases Series: AI-Augmented QA

I have spent years designing how quality gets built into a system, not just where it gets checked at the end. The question I kept running into this year was a narrower one: when AI shows up as a fourth option alongside manual testing and automation, how does a QA architect actually decide what to use, when, and why.

There is plenty written about AI and QA in the abstract. What I wanted was something narrower: the same app, the same bugs, tested the same four ways, with the differences actually written down.

So I built PeakAndPack, a small e-commerce API and UI with 11 intentional bugs, and ran every phase of testing against it four times: once by hand, once with Claude assisting but not driving, once as a Playwright suite, and once through an AI QA agent with real browser control.

This series is the record of that work. Every post reflects something actually run.

The framework: one project, three shapes

Most QA advice assumes a project shape without saying so: UI-heavy, API-only, or both. The real question this series answers is: given a project that is one of those three shapes, how do you run each of the four approaches?

PeakAndPack is the “both” column throughout this series, since it ships a real UI and a real API. Every phase post says explicitly which column applies, so the framework transfers to whatever shape your own project happens to be.

Human-in-the-loop, by design. Every Manual + AI and AI QA Agent post in this series involves a human reviewing, correcting, or approving the output before it counts as done. That review step is the actual value being demonstrated, not the AI output on its own.

Harness and loop: what “AI QA agent” actually means

The AI QA Agent column in this series isn’t a single prompt that returns a bug list. It runs as a loop: plan, act, verify, and only then report. That loop is only as trustworthy as the harness around it, the tool access, the stop conditions, and the checks that catch the agent fooling itself.

This matters because the failure mode is real, not theoretical. Anthropic’s own engineering team has documented it directly: out of the box, an AI QA agent will identify a legitimate issue, then talk itself into deciding it isn’t a big deal, and approve the work anyway. Left unchecked, it also tends to test the obvious path and skip the edge cases where the real bugs hide.

Two terms worth knowing going into this series:

Agentic loop
The plan, act, verify cycle an agent runs on its own, deciding what to test and whether a result is a real failure, without a human in the loop for every step
Harness
The scaffolding around that loop: which tools it can touch, when it stops, and how its judgment gets checked against a human’s

The Phase 7 bug-finding consistency check later in this series (running the agent repeatedly against the same unchanged API) is a small, practical test of exactly this: not whether the agent can find a bug once, but whether the harness around it makes that finding reliable.

How the series is structured

Phase 0 (app setup) and Phase 1 (requirements) are single posts, since there is no 4-way split when there is only one way to do the work. From Phase 2 onward, every phase publishes as a landing post plus one post per approach, so each post stays short and finishable, and the comparison still lives in one place for anyone going deeper.

Phase 0 · App setup Confirm PeakAndPack’s API and UI are live before testing anything. Phase 1 · Requirements document What PeakAndPack is supposed to do, before anyone tests anything. Phase 2 · Test strategy The thinking behind the tests, including risk-based prioritisation of the 11 bugs. Phase 3 · Test case creation Happy path, negative, and edge case test cases across every feature area. Phase 4 · Visual UI regression Catching layout and rendering bugs on the real UI, not just inferred from data. Phase 5 · API contract testing Status codes, schemas, and error handling, verified against the spec. Phase 6 · Functional E2E flows Five full user journeys, walked through via the API and via the UI. Phase 7 · Bug detection Finding all 11 bugs systematically, including a consistency check across agent runs. Phase 8 · Reporting Consolidating everything found into a report built for a real audience.

The app under test

PeakAndPack is a full-stack sample: a Node.js and SQLite API (products, cart, checkout, auth, orders) plus a small React UI. It ships with 11 bugs seeded on purpose, so every testing approach has the same real targets to find.
