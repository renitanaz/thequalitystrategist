API Contract: Does It Behave Like It Promises To?

Status codes, response shapes, and errors that actually tell the truth about what went wrong.

By RN ~4 min read Series: AI-Augmented QA

Visual regression checks how the app looks. API contract testing checks whether it actually behaves the way it claims to, correct status codes, correct response shapes, correct errors when something's wrong.

11endpoints to verify
4scenarios per endpoint: happy, wrong input, no auth, not found
1contract every client depends on

Never tested an API before? Read API Testing for Beginners first. It's a one-page foundation: what a request is, how to send one with curl or Postman, how tokens work, and how to read a response. The four approaches below assume that groundwork.

The 4 scenarios, every endpoint

ScenarioWhat you're checking
Happy pathCorrect input gives a correct, expected response
Wrong inputMissing fields or wrong types give a correct error, not a crash
Unauthorized accessNo token gives 401, not a silent pass-through
Not foundA bad ID gives 404, not a 200 with empty data or a 500

BUG-014 lives here. GET /api/search without a ?q parameter should return 400, a clear client error. It currently returns 500, a server crash. The difference matters: 400 tells the client "you sent something wrong," 500 tells them "something broke on our end." Same missing parameter, very different signal to whoever's calling the API.
