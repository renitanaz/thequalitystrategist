Phase 5 of 8 · API Contract

API Contract, Endpoint by Endpoint

Postman, a browser, and a results table that doesn't lie about what came back.

By RN ~5 min read Series: AI-Augmented QA
Manual, No AI Manual + AI Automated, Playwright AI QA Agent

No tooling beyond Postman or a browser. Hit every endpoint, four scenarios each, and write down what actually came back versus what should have.

New to APIs? Start with API Testing for Beginners first. It covers what a request is, how to send one with curl or Postman, how to get a token, and how to read a response, everything this page assumes you already know.

What you actually do

For every endpoint, test happy path, wrong input, unauthorized access, and not-found, then record: endpoint, input, expected status, actual status, pass/fail.

Endpoints to test

All paths below are relative to the API base URL: https://peakandpackshopdemo.onrender.com. So GET /api/products means GET https://peakandpackshopdemo.onrender.com/api/products.

Base URL: https://peakandpackshopdemo.onrender.com

GET  /health                     → 200
GET  /api/products               → 200, array of products
GET  /api/products/:id           → 200 (valid id), 404 (invalid id)
GET  /api/search?q=tent          → 200
GET  /api/search                 → should be 400 (currently crashes, 500)
POST /api/auth/login             → 200 (valid), 401 (wrong password)
POST /api/auth/register          → 201 (new), 409 (duplicate email)
POST /api/cart (with token)      → 200
POST /api/cart (no token)        → 401
POST /api/orders/checkout        → 201, check total with SAVE10 code
GET  /api/orders                 → should return only your orders

Two of these are pre-flagged for a reason. The search endpoint and the orders endpoint are both expected to fail this check, BUG-014 and BUG-013 respectively. Writing the expected behavior down before testing means the failure is a confirmed contract violation, not a surprise discovered after the fact.

One endpoint, worked start to finish

Before you run all eleven, here is one complete trace you can copy the shape of. We'll test GET /api/search with no query parameter, which is expected to fail (BUG-014).

Step 1, know the expected behavior first. The requirements say a search with a missing query is bad input, so it should return 400 (a client error). Write that down before you call it, so the result is a verdict, not a guess.

Step 2, send the request. In a terminal:

curl -i https://peakandpackshopdemo.onrender.com/api/search

Step 3, read what comes back. The first line is the status; the rest is the body:

HTTP/1.1 500 Internal Server Error
Content-Type: text/html

<pre>TypeError: Cannot read properties of undefined (reading 'toLowerCase')
    at /app/routes/search.js:12 ...</pre>

Step 4, compare and record. Expected 400, got 500. That's a fail, and a confirmed contract violation. The row in your results file:

EndpointScenarioExpectedActualPass
GET /api/searchmissing q param400500FAIL (BUG-014)

Two things this one example teaches. First, a 500 is never the right answer to bad input; a missing parameter is the client's mistake, so it must be a 4xx. Second, notice the body leaks an internal stack trace with a file path and line number, which should never reach a user. You found a second, smaller issue just by reading the body instead of stopping at the status. Now repeat this same four-step trace for the other ten endpoints.

Your deliverable

One file: api-contract-manual.md, a results table covering all 11 endpoints across all 4 scenarios where applicable.

Time: ~2 to 3 hours. The slowest manual phase so far, but also the one that produces the cleanest evidence, a results table anyone can scan in thirty seconds.
