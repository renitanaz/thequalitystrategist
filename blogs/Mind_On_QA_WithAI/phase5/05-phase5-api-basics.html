API Testing for Beginners

Before you test PeakAndPack's API, this is the whole foundation in one page: what a request is, how to send one, and how to read what comes back. If you already work with APIs, skip straight to the four approaches.

By RN ~6 min read Series: AI-Augmented QA

What an API request actually is

An API is just a set of URLs a program can call to get data or make something happen. When you test one, you send a request and check the reply. Every request is made of four parts:

  • Method, the verb: GET reads data, POST creates or submits something. (There are others, but these two cover most of PeakAndPack.)
  • URL, the address: the base URL plus a path, for example https://peakandpackshopdemo.onrender.com/api/products.
  • Headers, extra info sent with the request. The one you'll use most is the auth token, which proves who you are on protected calls.
  • Body, the data you send with a POST, written as JSON (for example the email and password when logging in). GET requests have no body.

Plain-English glossary. Endpoint: one callable URL, like /api/products. Status code: the 3-digit number the server replies with, 2xx means OK, 4xx means you did something wrong (bad input, not logged in), 5xx means the server itself broke. Body: the actual content of the reply, usually JSON. Token: a string you get after logging in and then attach to later requests to prove it's you. Contract: what the endpoint promises to do, the right status and the right shape of data, which is exactly what you're testing.

How to send a request: two ways

You need a tool to send requests. The two most common are curl (a command in your terminal) and Postman (a free app with buttons and boxes). Same request, two styles. Pick whichever feels less scary.

With curl (terminal)

curl is built into Mac and most Windows setups already. Open a terminal and type this to read the product list:

curl https://peakandpackshopdemo.onrender.com/api/products

Press enter. The product data prints straight into the terminal. To also see the status code, add -i, which prints the response headers (including the status line) above the body:

curl -i https://peakandpackshopdemo.onrender.com/api/products

For a POST with a JSON body, like logging in, you spell out the method, a content-type header, and the body:

curl -i -X POST https://peakandpackshopdemo.onrender.com/api/auth/login \
  -H "Content-Type: application/json" \
  -d '{"email":"test@example.com","password":"your-password"}'

With Postman (app)

If a terminal feels intimidating, Postman does the same thing with a form. Download it from postman.com/downloads, then:

  1. Click New, then HTTP Request.
  2. Set the method dropdown to GET and paste the URL https://peakandpackshopdemo.onrender.com/api/products.
  3. Click Send. The response body appears in the bottom panel, and the status code (like 200 OK) shows on the right.
  4. For a POST, set the method to POST, open the Body tab, choose raw and JSON, and type your JSON in the box before sending.

Getting and using a token

Some endpoints (your cart, your orders) only work if the server knows who you are. You prove it with a token. The flow is always: log in once, copy the token from the response, then attach it to the protected requests.

  1. Log in with the POST /api/auth/login call above. The response body contains a token, a long string, usually in a field called token.
  2. Copy that token string.
  3. Attach it to a protected call as an Authorization header. In curl: 
    curl -i https://peakandpackshopdemo.onrender.com/api/orders \
  -H "Authorization: Bearer PASTE-YOUR-TOKEN-HERE"
    In Postman, open the Authorization tab, choose type Bearer Token, and paste the token.

Why this matters for testing. A protected endpoint should reject a request with no token (status 401). So you test it both ways: with a valid token (expect success) and without one (expect 401). If a no-token request succeeds, that's a security bug, exactly the kind of thing this phase looks for.

How to read the response

Every reply has two things you check: the status code and the body.

  • Status code first. Did you get the number you expected? 200 for a successful read, 201 for something created, 400/401/404 for the various client errors, 500 when the server itself fell over.
  • Then the body. This is the trap that separates a beginner from an expert: a 200 status does not mean the data is correct. The reply can have the right status and still contain wrong or leaked data. Always read the body, not just the number.

The single most important habit. Never sign off an endpoint on its status code alone. PeakAndPack's orders endpoint returns a perfectly healthy 200 while leaking other users' orders in the body (BUG-010). A tester who only checks the status passes it; a tester who reads the body catches it. Read. The. Body.

You're ready

That's the whole foundation: request (method, URL, headers, body), send it (curl or Postman), read the reply (status, then body), and use a token for protected calls. With just that, you can work through every approach in this phase.
