Test Strategy, Drafted by Two Agents

One agent plans your web and functional testing, the other plans your API testing. Both reason from the requirements doc, and you still have to check their work.

By RN ~4 min read Series: AI-Augmented QA
Test Strategy: Manual, No AI Test Strategy: Manual + AI Test Strategy: Automated, Playwright Test Strategy: AI QA Agent

At Phase 2, all you have is the requirements doc, nothing else exists yet. The agent works the same way: it reasons from peakandpack-requirements.md alone, no live API calls, no screenshots, the same starting point you'd have on day one of a real project.

One agent, both kinds of testing

The strategist's question is the same whether you're testing screens or endpoints: what's risky here, before anything is built? This agent answers it for both at once. It ranks web and functional risk (the user-facing flows) and API risk (the contracts and logic behind them) in a single pass. If your project only has one of those, ignore the section that doesn't apply.

What it does

  1. You give it your Anthropic API key (stays local, never sent anywhere but Anthropic)
  2. You give it the text of peakandpack-requirements.md
  3. Claude reads it and ranks both web/functional risk and API risk, the way a strategist would before any screen or endpoint exists

The actual system prompt, in full, this is what's doing the thinking. All three forms below send this exact text to Claude, they just differ in how you get it there:

You are a QA test strategist working on PeakAndPack, a trekking and
travel gear e-commerce app. Nothing has been built yet. You only have
the requirements document the user gives you. There is no live UI and
no live API to inspect.

Your job: reason about test risk the way a strategist would BEFORE
anything is built. Cover two kinds of testing:

Web and functional testing: which planned user-facing flows (e.g.
product browsing, cart, checkout, auth, order history) carry the most
risk if the UI or its behaviour is built wrong, in terms of user impact
and business impact.

API testing: which planned API areas (e.g. products, cart, checkout,
auth, orders, search) carry the most risk if the contract or logic for
them is built wrong, in terms of data integrity, business impact, and
security.

Do not invent screenshots, visual descriptions, endpoint names,
response shapes, or specific bugs you could not know about from a
requirements doc alone. If a project clearly has no UI or no API, say
so and skip that section. If you don't have enough information about a
given area, say so plainly rather than guessing.

Structure your output as:
1. Web and functional risk: a ranked list of UI risk areas (most risky
   first), each with a one-line reason
2. API risk: a ranked list of API risk areas (most risky first), each
   with a one-line reason
3. For the single highest-risk area across both lists, a short paragraph
   on what could go wrong if it is built carelessly
4. One thing you cannot assess yet because nothing is built, named
   explicitly

Keep the whole response under 500 words. Plain prose, no markdown
headers, no bullet symbols, just short paragraphs and simple numbered
lists where structure is needed.

2

Node.js script

Same system prompt as the browser version, just run from a terminal instead of clicked in a browser tab. If you've never used a terminal before, here's every step, nothing skipped.

Step 1: Check if Node.js is installed. Open a terminal (on Mac: search for "Terminal" in Spotlight; on Windows: search for "Command Prompt" or "PowerShell"). Type this and press enter:

node --version

If you see something like v20.11.0, you have it, skip to Step 2. If you see an error like "command not found," install Node.js from nodejs.org first (download the version marked "LTS"), then come back and try the command again.

Step 2: Get an Anthropic API key. Go to console.anthropic.com, sign up or log in, and create an API key. Copy it somewhere safe, you'll need it in Step 4.

Step 3: Download the script and the requirements doc. Download qa-strategy-agent.js and peakandpack-requirements.md, and put both files in the same folder, for example a new folder on your desktop called strategy-agent.

Step 4: Open a terminal in that folder. On Mac, right-click the folder and look for "New Terminal at Folder" (or open Terminal and type cd followed by dragging the folder into the window, then press enter). On Windows, open the folder in File Explorer, click the address bar, type cmd, and press enter.

Step 5: Set your API key. In that terminal, paste this, replacing the placeholder with the real key from Step 2, then press enter:

export ANTHROPIC_API_KEY=sk-ant-your-real-key-here

On Windows, use this instead:

set ANTHROPIC_API_KEY=sk-ant-your-real-key-here

This only lasts for the current terminal session, you'll need to do this again if you close and reopen the terminal.

Step 6: Run the script. Type this and press enter:

node qa-strategy-agent.js peakandpack-requirements.md

What happens next: the script reads the requirements file, sends it to Claude, and after a few seconds prints the risk strategy directly in your terminal. It also saves a copy to a new file called qa-strategy-output.md in the same folder, which you can open in any text editor.

If you see an error: "Missing ANTHROPIC_API_KEY" means Step 5 didn't take, try it again in the same terminal window before running the script. "File not found" means the script and the requirements doc aren't in the same folder, or you typed the filename slightly wrong. "command not found: node" means Step 1's install didn't finish, or you need to close and reopen your terminal after installing.

3

Prompt only, no code

No file to open at all. Open qa-strategy-agent-prompt.md, copy the system prompt, paste your own copy of the requirements doc where the prompt says to, and paste the whole thing into any Claude chat window. Same reasoning, same output shape, zero setup. The trade-off: no saved output file, and you're copy-pasting by hand every time instead of reusing a tool.

This is the actual lesson. Same skeleton, same input, same constraints, but the system prompt decides what the agent looks for and how it frames risk. Change the prompt, you change the agent. That's most of what building one of these "agents" actually is, the code that calls Claude is a few lines; the system prompt is where the real design work happens.

How to tell if the agent actually read the requirements

The agent's strategy can sound confident either way. The real test is whether it points to something specific in PeakAndPack's requirements doc, or could apply to any e-commerce app.

Trustworthy
References a rule that's only in the requirements, like the SAVE10 code being 10% off, not 100%. It could only know that by reading the doc, which is proof it did.
Warning sign
A risk list that could describe any e-commerce app: “checkout failures hurt revenue,” “auth bugs are a security risk,” “slow pages frustrate users.” True of every store on the internet, and proves nothing about whether the agent read PeakAndPack's actual requirements. If it never names a specific rule, value, or flow from the doc, it probably didn't read it closely.

Your deliverable

One file: test-strategy-agent.md, the agent's output after your review pass. Same structural elements as the other three approaches, scope, priorities, entry/exit criteria, generated from the requirements doc, the same starting point a human strategist would have at this stage.

Time: ~10 minutes, including the time to paste your key and the doc in. The fastest of the four, by a wide margin, but the value of that speed depends entirely on whether you actually read and correct what comes out.
