Drafts an Agent Writes, and the Review That Makes Them Tests

An agent can draft a Playwright test from a story in minutes. A draft only counts after a person has run it, read it and tried to make it fail.

Series: Agentic SDLC, Part 1 Demo: PeakAndPack 30 min read By: RN

Draft. Written before the steps have been run end to end, so it is marked and kept out of the site index.

Checked: test-gen-agent.ts compiled against the Agent SDK type definitions. The folder guard logic run on sample paths, including .. traversal and a look-alike folder name. The story's button labels and payment gate against the Phase 8 measurements of the real checkout.

Not checked: Any agent run, the Playwright MCP session, what the agent actually generates, the Gherkin output shape (shown as a format only), and every Rovo and Zephyr step. The curation metrics table is blank because it needs your runs.

Goal

Build an agent that drafts a Playwright test from a user story, by looking at the real app first. Then do the part that matters more: curate the draft against the standard the Playwright series set, and measure what the agent really saved. A draft is not a test until a person has run it, read it and tried to make it fail.

By the end of this phase you can:

  • give an agent a story and a live app, and confine its writing to one folder
  • put the team's test rules into the prompt so the first draft starts closer to the standard
  • review a generated test with the six rules and the mutation check from Playwright Phase 13
  • record how much of a draft survived, and how long curation took
  • draft Gherkin test cases from a story, its epic and a linked ticket

1. Why generated tests need a gate

A generated test can run green and still protect nothing. Playwright Phase 13 shows how: a test that never logs in, sleeps for two seconds and asserts "at least one button exists" passes whether or not the feature works. A model asked to make a test pass will often pick an assertion that is always true. So this phase has two halves, and the second matters more:

  1. Generate. The agent writes a draft into a holding folder, generated-tests/. It cannot write anywhere else.
  2. Curate. A person runs the draft, reviews it against the six rules, tries to make it fail, and only then moves it to curated-tests/, where it counts.

The folder move is the gate. It is deliberate friction. Nothing the agent writes joins the suite until a person has put it there.

2. A story to generate from

Create a folder stories/ in the agents folder and save this as stories/checkout-pay-first.md. Its three criteria describe how PeakAndPack's checkout really behaves: the button label and the payment gate are taken from the running app, not invented.

# Story: Pay before confirming

As a shopper, I want to pay in the payment form before I can confirm my order,
so that I never place an order I have not paid for.

## Acceptance criteria
1. On the checkout page the confirm button is disabled and reads "Complete payment above to continue".
2. After a successful payment in the payment form, the button is enabled and reads "Confirm Order".
3. Confirming the order shows an "Order placed" heading.

Why a story with exact wording: the agent can only check what the story says. Vague criteria such as "checkout works" produce vague tests. A criterion with a visible label produces a test that can fail.

3. The generator

import { readFileSync } from 'node:fs';
import { resolve, sep } from 'node:path';
import { query, type CanUseTool } from '@anthropic-ai/claude-agent-sdk';

const storyPath = process.argv[2];
if (!storyPath) throw new Error('Usage: npx tsx test-gen-agent.ts stories/checkout-pay-first.md');
const story = readFileSync(storyPath, 'utf-8');

const appUrl = process.env.APP_URL ?? 'http://localhost:3000';
const apiUrl = process.env.API_URL ?? 'http://localhost:3001';
const outputDir = resolve('generated-tests');

// The only place this agent may write. Everything else is refused, with no question asked.
const writeOnlyToGeneratedTests: CanUseTool = async (toolName, input) => {
  const path = typeof input.file_path === 'string' ? resolve(input.file_path) : '';
  if ((toolName === 'Write' || toolName === 'Edit') && path.startsWith(outputDir + sep)) {
    return { behavior: 'allow', updatedInput: input };
  }
  return { behavior: 'deny', message: `Writing is only allowed inside ${outputDir}.` };
};

const prompt = `You write Playwright tests (TypeScript) for the PeakAndPack shop. The store is at ${appUrl} and its API is at ${apiUrl}
(POST /api/auth/register creates a customer and returns a token and a user).

The user story:
${story}

First, open the app in the browser tool and look at the real pages this story touches.
Then write ONE spec file into generated-tests/ that checks the story's acceptance criteria.

The test must follow these rules:
1. No CSS class or structural selectors (getByRole, getByLabel, getByText, or getByTestId only when nothing else names it).
2. No waitForTimeout. Wait on an assertion or on waitForResponse.
3. Every assertion checks something a user can see.
4. Every test creates its own customer through the API. Never the shared demo account.
5. After any action that sends a request, wait for the response before leaving the page.
6. Every test must be able to fail. After each test, add a comment: "Fails if: <the change to the app that turns it red>".

Only use locators for things you actually saw on the page. If the story needs something the page does not have,
say so in a comment at the top of the file instead of inventing it.`;

const run = query({
  prompt,
  options: {
    mcpServers: {
      playwright: { command: 'npx', args: ['@playwright/mcp@latest', '--headless', '--isolated'] },
    },
    allowedTools: ['Read', 'Glob', 'Grep', 'mcp__playwright'],   // 'mcp__playwright' = every tool from that server
    canUseTool: writeOnlyToGeneratedTests,
    maxTurns: 40,
    maxBudgetUsd: 2,
  },
});

for await (const message of run) {
  if (message.type === 'result') {
    console.log(`${message.subtype}: ${message.num_turns} turns, about $${message.total_cost_usd.toFixed(3)}`);
    if (message.subtype === 'success') console.log(message.result);
  }
}
Explain this code, line by line
  • The script takes the story file as its argument and reads it. APP_URL and API_URL default to a local copy of the store. Why local: the agent will click through checkout, and a local copy is yours to change.
  • outputDir is the one folder the agent may write into, as a full path.
  • writeOnlyToGeneratedTests is the safety design. The SDK calls it for any tool not on the pre-approved list. It allows Write and Edit only when the target path is inside generated-tests/, and refuses everything else without asking. Checking the path with a trailing separator matters: it stops a folder called generated-tests-evil from passing, and resolving the path first stops generated-tests/../tests/cart.spec.ts from slipping out.
  • The prompt gives the story, then the instruction to look at the real pages first. Why: an agent that has not seen PeakAndPack invents what a shop "should" have, such as a cart badge or a test id that does not exist. Looking first replaces guessing.
  • The six rules are written into the prompt, the same ones as Playwright Phase 13. Each test must also end with "Fails if: ...", which forces the agent to say what would turn it red. That comment is the starting point for your own check later.
  • The last paragraph gives the agent a way out: if the story needs something the page lacks, write a comment instead of inventing it. Without an exit, a model fills the gap.
  • mcpServers starts the Playwright MCP server for this run, headless and --isolated (a fresh browser profile kept in memory, so no saved logins leak in). 'mcp__playwright' in allowedTools allows every tool from that server. Reading is allowed freely, and writing goes through the folder rule.
  • maxTurns: 40 and maxBudgetUsd: 2 are larger than earlier phases. Exploring pages and writing a test takes more steps, but there is still a ceiling.

Start your local PeakAndPack (backend and frontend), then from the agents folder:

npx tsx test-gen-agent.ts stories/checkout-pay-first.md

A draft should appear in generated-tests/. If it does not, read the agent's final message: it should explain what blocked it.

4. Curate the draft

Work through these in order. Each catches something the one before cannot.

  1. Run it. From the project root: npx playwright test agents/generated-tests/checkout-pay-first.spec.ts (use the file name the agent chose). A failure here is useful: it usually means the agent used something that does not exist on the page.
  2. Read it against the six rules. No CSS classes, no waitForTimeout, every assertion visible to a user, its own data, a response awaited after each request, and a stated way to fail. You can hand it to the reviewer prompt from Playwright Phase 13 as a second pair of eyes. You still decide.
  3. Check each "Fails if" line is true. This is the mutation check. For each claim, make that change to your local app and run the test. If the story says the button is disabled until payment, make the app enable it early and check the test goes red. A test that stays green under its own "Fails if" is the finding.
  4. Move it. Only then copy it to curated-tests/ and, from there, into your real tests/ folder as part of a normal pull request.

On committing it: curated tests join the suite through the same route as any other test. Create a branch, commit, push and open a pull request for a person to review. An agent can draft the pull request description, but the review and the merge belong to your team.

git switch -c tests/checkout-pay-first
git add tests/shop/checkout-pay-first.spec.ts
git commit -m "Add pay-before-confirm test, generated and curated"
git push -u origin tests/checkout-pay-first
Explain this code, line by line
  • git switch -c creates a new branch and moves onto it, so the new test sits apart from main until reviewed.
  • git add names the one file, not .. Why: an agent folder can hold drafts and reports you do not want to commit by accident.
  • The commit message says the test was generated and curated. A reviewer deserves to know a draft came from an agent.
  • git push -u origin uploads the branch and remembers it, so the next push is just git push.

5. Measure what it saved

"The agent wrote a test in two minutes" is not the number that matters. The number that matters is the time from story to a test you trust, compared with writing it yourself. Keep a record for every draft:

StoryTests draftedKept as writtenEditedDiscardedCuration minutesProblems found in the draft
checkout-pay-first

Fill the last column with the specific problem and the rule or check that caught it, for example "invented a test id, caught on the first run" or "asserted before the page loaded, caught by asking when the assertion could first be true". A pattern in that column is the most useful output of the whole exercise: it tells you what to add to the prompt next. After a few stories, compare your minutes against how long you take to write one yourself.

6. The same idea, as test cases in plain language

Not every team writes Playwright code first. Many write test cases in Gherkin: plain sentences in a fixed shape, Given (the starting point), When (the action), Then (what you should see). A product owner can read them.

Atlassian's Rovo can host an agent that drafts these inside Jira when a story's status changes, using the story plus the other stories in its epic and its linked tickets. If your site has that, build it with Atlassian's current documentation: the menus and agent settings change, so this page does not reproduce them.

The same pattern works without Rovo, using Claude on files. Save three small files in stories/:

stories/checkout-pay-first.md       (the story above)

stories/epic-checkout.md
# Epic: Checkout
- Pay before confirming (checkout-pay-first)
- Apply a discount code at checkout (SAVE10 takes 10% off)

stories/linked-payment-iframe.md
# Linked ticket: Payment form
The payment form is a separate page embedded in checkout (an iframe titled "Payment form").
Fields: Card number, Expiry, CVV, Cardholder name, and a "Pay now" button.

Then ask Claude, in a session started in the agents folder:

Read stories/checkout-pay-first.md, stories/epic-checkout.md and stories/linked-payment-iframe.md.
Write Gherkin test cases for the first story only. Cover each acceptance criterion.
Use the epic and the linked ticket for context and for edge cases a tester would add.
After the scenarios, list every assumption you made that the three files do not state.
Do not invent behaviour. If something is unclear, put it in the assumptions list.
Explain this code, line by line
  • Three files, not one, because context is what makes a drafted test case better: the epic shows what else is nearby, and the linked ticket shows a technical fact (the iframe) the story never mentions.
  • "For the first story only" keeps the output reviewable. Asking for everything at once produces a wall of text nobody reads closely.
  • The assumptions list is the most valuable part. Every assumption is a question for a person: is the discount stacked with anything? Does a failed payment keep the button disabled? Gaps found here cost minutes. The same gaps found after building cost days.
  • "Do not invent behaviour" and the exit through the assumptions list serve the same purpose as the exit in the generator prompt.

The output shape to expect, shown as a format only (your output will differ):

Feature: Pay before confirming

  Scenario: The confirm button is disabled before payment
    Given a signed-in shopper with one item in the cart
    When they open the checkout page
    Then the confirm button is disabled
    And it reads "Complete payment above to continue"

To get these into Zephyr Scale, a team usually imports them or creates them through Zephyr's API. That needs a Zephyr instance, so it is not covered here. As in Phase 2, the person curates first, and only curated cases are pushed.

7. Common mistakes

  • Moving a draft straight into tests/. The holding folder is the point.
  • Judging the draft by "it ran". Passing says nothing about whether it can fail.
  • Letting the agent test on the shared live demo. It will add things to carts and create customers.
  • A story with no visible detail. The test can only be as specific as the criteria.
  • Skipping the measurement. Without minutes recorded, "it saves time" is a feeling.

8. Deliverables

  • agents/test-gen-agent.ts: the generator, run on at least two stories
  • generated-tests/: the raw drafts, kept so you can compare them with the curated versions
  • curated-tests/: the tests that passed your review
  • curation-metrics.md: the table from section 5, filled in
Assignment

Generate for two stories, and keep a record of what the agent got wrong

Write a second story for a different PeakAndPack feature, with visible detail in each criterion (a button label, a message, a count). Run the generator on both stories. Curate each draft with the four steps above. Fill in the metrics table, including the specific problems found, and add one line to the generator's prompt in response to the most common one. Run it again on the first story and note whether that problem went away.

Show solution: try it yourself first

The findings are yours, because they depend on what the agent produced. A few outcomes to expect, and what to do with each:

  • An invented locator. The first run fails with "element not found". The fix is the real locator from the page. The prompt change is "only use locators for things you saw", which is already in the generator, so if it still happens, strengthen it by asking the agent to quote the page snapshot line each locator came from.
  • A shared account. The draft logs in as the demo user. Rule 4 catches it on review. The prompt already states the rule, so name the helper to call: "create the customer with POST /api/auth/register".
  • A "Fails if" line that is false. The mutation check catches it. This is the one to take most seriously, because the comment reads as reassurance.

Did the prompt change work? One run proves little, because the agent's output varies between runs. Run the same story three times and count how often the problem appears. "It went away once" is not evidence. "It appeared in three of three runs before and none of three after" is.

Bonus challenge

Give it a story with a bug in it. Take a criterion the app does not meet, for example "SAVE10 takes 10% off the total". Generate a test without telling the agent anything about the app's behaviour. Does the draft assert what the story says (and so fail, correctly), or what the app actually does (and so pass)? What does the answer tell you about generating tests from the behaviour of a system you are testing?
