Giving an Agent Tools, With a Person at the Gate

An agent acts only through tools. Connect them one by one, allow reading freely, and make every write wait for a yes.

Goal

Give an agent tools in other systems, with a limit on each, and use them to build a small agent that turns a failed Playwright test into a drafted bug report, filed only after you say yes. This is the phase where an agent first touches something outside your machine, so the controls from Phase 0 start to matter.

By the end of this phase you can:

  • explain what MCP is and why an agent uses it instead of a free-for-all shell
  • connect Claude Code to the Playwright, GitHub and Atlassian MCP servers
  • read a Playwright JSON report and hand its failures to an agent
  • let an agent read freely but write only with a person's approval
  • compare an agent that calls Jira from outside with one that lives inside Jira
  • lay out a test repository so an agent can find its way around

1. What MCP is, in plain words

An agent can only act through tools. A tool is a named action with defined inputs, such as "search issues in this repository" or "open this web page". Someone has to provide those tools. MCP (Model Context Protocol) is a standard way to do that: a program called an MCP server exposes a list of tools, and any MCP-aware agent, Claude Code included, can connect and use them.

Think of it as a standard socket. Before sockets were standard, every device needed its own plug. With MCP, the GitHub team builds one GitHub server, and every agent that speaks MCP can use it.

Why not just let the agent run shell commands and call APIs itself? It could, but you would lose the things that make an agent safe to use at work:

  • Permission per tool. You can allow "search issues" and hold back "create issue". With a raw shell, you allow a command or you do not.
  • Defined inputs and outputs. The agent cannot invent a malformed request, and you can read exactly what it asked for.
  • One place to audit. Every action is a named tool call.

The CCAR-F for QA series covers tool design and MCP from the exam angle: Domain 2.

2. Connect three servers

You add a server to Claude Code with claude mcp add. Do these three in your peakandpack-tests folder.

Playwright MCP: a browser the agent can drive

claude mcp add playwright -- npx @playwright/mcp@latest
Explain this code, line by line
  • claude mcp add playwright registers a server and gives it the name playwright. The name appears in every tool it provides, for example mcp__playwright__..., and you use it in permission rules.
  • Everything after -- is the command that starts the server: npx @playwright/mcp@latest downloads and runs Microsoft's Playwright MCP server. The -- separates Claude Code's own options from the server's command.
  • The server opens a real browser when the agent asks it to. By default you can watch it. Later phases add --headless for pipelines, where there is no screen.

Try it. Start your PeakAndPack store locally, run claude, and ask: "Open http://localhost:3000 in the browser and list the names of the first four products." Type /mcp to see the connected servers and their tools. Why a local copy rather than the live demo: the agent may click things, and a local copy is yours to change.

GitHub MCP: issues and pull requests

First, a token. In your GitHub settings, create a fine-grained personal access token that can reach one throwaway repository, peakandpack-bugs (create it empty), with only the Issues permission set to read and write. Why so narrow: an agent acts with whatever the token allows. If the token can reach one practice repository, the worst outcome is a mess in one practice repository.

claude mcp add --transport http github https://api.githubcopilot.com/mcp/ --header "Authorization: Bearer YOUR_TOKEN"
Explain this code, line by line
  • --transport http says this server is reached over the web, not started as a local program. GitHub hosts it.
  • The URL is GitHub's own MCP server address.
  • --header "Authorization: Bearer YOUR_TOKEN" sends your token with every request, which is how GitHub knows what the agent may do. Replace YOUR_TOKEN with the real one. By default this is saved in your own local Claude Code settings, not in the repository.

Run /mcp again and open the GitHub server's tool list. Read the tool names there rather than trusting any list in a blog post, including this one: servers change. This phase's code uses issue_read, list_issues and search_issues as the read tools and issue_write for creating issues. Check they match what you see.

The --scope option (local, user or project) decides who gets the server. local, the default, is just you in this folder. project writes a .mcp.json file that is meant to be committed so the whole team shares the setup. Never put a token in a file you commit.

Atlassian MCP: Jira and Confluence

claude mcp add --transport http atlassian https://mcp.atlassian.com/v2/mcp

Then, inside a claude session, run /mcp and follow the prompt to sign in. This one uses a browser sign-in (OAuth) and acts with your own Jira permissions. Atlassian's page for it is Get started with the Atlassian MCP server. Older addresses are being retired, so use the one on that page.

This one is optional. You need a Jira site to try it, and if it is your employer's, follow your employer's rules about connecting AI tools to it. The agent below files its bug in GitHub so that anyone can follow along. The shape is identical for Jira: the agent searches for a duplicate, then asks to create an issue. Only the tool names change.

3. The agent: a failed test becomes a drafted bug

The job: take a Playwright run's failures, check whether each is already reported, and propose a bug report for each new one. A person approves every report before it exists.

Step 1: get the failures out of Playwright

Playwright can write its results as JSON. Run your suite with the JSON reporter, writing to a file in the agents folder:

# macOS, Linux, or Git Bash
PLAYWRIGHT_JSON_OUTPUT_NAME=agents/report.json npx playwright test --reporter=json

# Windows PowerShell
$env:PLAYWRIGHT_JSON_OUTPUT_NAME='agents/report.json'; npx playwright test --reporter=json

Why an environment variable, not > report.json: in Windows PowerShell, > saves the file in a different text encoding, and Node then cannot read it as JSON. The variable tells Playwright to write the file itself. To get a failure to practise on, make one test expect something untrue, for example a search for "tent" expecting two cards when the store has one.

Step 2: read the report

import { readFileSync } from 'node:fs';

export type Failure = {
  title: string;
  file: string;
  line: number;
  error: string;
  attempts: number;
};

type Spec = {
  title: string;
  file: string;
  line: number;
  tests: { status: string; results: { error?: { message?: string } }[] }[];
};
type Suite = { specs?: Spec[]; suites?: Suite[] };

const ANSI_COLOURS = /\u001b\[[0-9;]*m/g;

// Reads the file that `npx playwright test --reporter=json` writes
export function readFailures(reportPath: string): Failure[] {
  const report = JSON.parse(readFileSync(reportPath, 'utf-8')) as { suites: Suite[] };
  const failures: Failure[] = [];

  const walk = (suite: Suite) => {
    for (const spec of suite.specs ?? []) {
      for (const t of spec.tests) {
        // 'expected' passed, 'flaky' passed on a retry, 'skipped' did not run
        if (t.status !== 'unexpected') continue;
        const last = t.results[t.results.length - 1];
        failures.push({
          title: spec.title,
          file: spec.file,
          line: spec.line,
          error: (last.error?.message ?? '').replace(ANSI_COLOURS, '').trim(),
          attempts: t.results.length,
        });
      }
    }
    (suite.suites ?? []).forEach(walk);
  };
  report.suites.forEach(walk);
  return failures;
}
Explain this code, line by line
  • The type declarations describe the part of Playwright's report this code uses. Suites can nest (a file contains groups, which contain tests), which is why Suite refers to itself.
  • ANSI_COLOURS is a pattern matching the colour codes Playwright puts in error messages for the terminal. In a file they appear as junk characters, so they are removed.
  • readFailures reads the file and walks every suite. walk calls itself on each nested suite, which is how it reaches tests at any depth.
  • t.status !== 'unexpected' skips everything that is not a failure. In Playwright's report, expected means passed as planned, flaky means passed on a retry, and skipped means it did not run. unexpected is a real failure. Skipping flaky here is a choice: a test that passed on retry is not a bug report yet.
  • t.results[t.results.length - 1] takes the last attempt, because a retried test has one result per attempt.

This file does no AI work at all. Why keep it separate: reading a report is a job for plain code. It is fast, free and identical every time. The agent is used only for what code cannot do.

Step 3: the approval gate

import { createInterface } from 'node:readline/promises';
import type { CanUseTool } from '@anthropic-ai/claude-agent-sdk';

// Called for every tool the agent wants that is NOT on its allowedTools list.
// Anything that is not a plain "yes" from a person is a "no".
export const askHuman: CanUseTool = async (toolName, input) => {
  console.log(`\nThe agent wants to use: ${toolName}`);
  console.log(JSON.stringify(input, null, 2));

  const terminal = createInterface({ input: process.stdin, output: process.stdout });
  const answer = await terminal.question('Allow this? (y/N) ');
  terminal.close();

  if (answer.trim().toLowerCase() === 'y') return { behavior: 'allow', updatedInput: input };
  return { behavior: 'deny', message: 'A person declined this action. Do not retry it.' };
};
Explain this code, line by line
  • CanUseTool is the shape of a function the SDK calls when the agent wants a tool that is not on its pre-approved list. It receives the tool's name and the exact inputs.
  • The function prints both, so you see precisely what would be created, not just "the agent wants to create an issue".
  • terminal.question(...) waits for you to type. Only y counts as yes. Anything else, including pressing Enter, is a no. Why default to no: an approval that is easy to give by accident is not a gate.
  • Returning { behavior: 'deny', message } refuses the action and tells the agent why, in words. The message says not to retry, so the agent does not keep asking.

Step 4: the agent

import { query } from '@anthropic-ai/claude-agent-sdk';
import { readFailures } from './failures.js';
import { askHuman } from './ask-human.js';

const reportPath = process.argv[2] ?? 'test-results/report.json';
const bugRepo = process.env.BUG_REPO;                 // for example "your-name/peakandpack-bugs"
const token = process.env.GITHUB_TOKEN;
if (!bugRepo || !token) throw new Error('Set BUG_REPO and GITHUB_TOKEN first.');

const failures = readFailures(reportPath);
if (failures.length === 0) {
  console.log('No failed tests in the report. Nothing to file.');
  process.exit(0);
}

const prompt = `You are helping a QA engineer triage failed Playwright tests for the PeakAndPack shop.
Bugs go in the GitHub repository ${bugRepo}.

Failed tests (from the Playwright JSON report):
${JSON.stringify(failures, null, 2)}

For each failed test:
1. Search the repository's open issues for the same test title. If one exists, say so and do not file another.
2. Otherwise, create one issue. Title: "Failing test: <test title>". Body: the file and line, the error text,
   and one sentence on what the test was checking. Say plainly that the cause is not yet known.
3. Do not guess whether this is a product bug, a changed feature or a bad test. That is the human's call.

When you are finished, list what you filed and what you skipped.`;

const run = query({
  prompt,
  options: {
    mcpServers: {
      github: {
        type: 'http',
        url: 'https://api.githubcopilot.com/mcp/',
        headers: { Authorization: `Bearer ${token}` },
      },
    },
    // Reading is allowed without asking. Creating an issue is not on this list,
    // so it goes to askHuman first.
    allowedTools: ['mcp__github__list_issues', 'mcp__github__search_issues', 'mcp__github__issue_read'],
    canUseTool: askHuman,
    maxTurns: 15,
    maxBudgetUsd: 1,
  },
});

for await (const message of run) {
  if (message.type === 'result') {
    console.log(`\n${message.subtype}: ${message.num_turns} turns, about $${message.total_cost_usd.toFixed(3)}`);
    if (message.subtype === 'success') console.log(message.result);
  }
}
Explain this code, line by line
  • The first lines read two settings from the environment, BUG_REPO (for example your-name/peakandpack-bugs) and GITHUB_TOKEN, and stop with a clear message if either is missing. Why: a missing token should fail at once, not halfway through a run.
  • If the report has no failures, the script exits before calling any model. Why: every model call costs money, and "nothing to do" needs no AI.
  • The prompt gives the agent the failures as data and a numbered procedure: search first, file only if new, and do not guess the cause. That last rule matters because a failing test could be a real bug, an intended change, or a bad test, and the agent cannot tell which.
  • mcpServers connects the GitHub server for this run only. The SDK's version of the claude mcp add command from section 2.
  • allowedTools lists the three read tools. Reading needs no question. Creating an issue is not on the list, so the SDK passes it to askHuman instead. That one list is the whole safety design: what the agent may do alone, versus what needs you.
  • maxTurns and maxBudgetUsd are the Phase 0 limits. A triage run is a handful of searches and one or two issues, so 15 turns and a dollar are generous.
  • The final loop prints how the run ended, the cost, and the agent's own summary of what it filed and skipped.
cd agents
npx tsx simple-mcp-agent.ts report.json

Set BUG_REPO and GITHUB_TOKEN first. In bash: export GITHUB_TOKEN=your_token. In PowerShell: $env:GITHUB_TOKEN='your_token'.

What to expect and what to do:

  1. The agent searches for an existing issue. No question is asked, because search is read-only.
  2. It then asks to create an issue and prints the title and body. Type n once. Check the agent accepted the refusal and did not try again, and that no issue exists.
  3. Run it again and type y. Check the issue in GitHub: title, body, and above all the cause line. It should say the cause is not yet known.
  4. Run it a third time. A good run finds the issue and skips it. Notice whether it did. The agent doing this check is the weakest part of the design, and you are about to see why.

What this agent can get wrong. It might file a duplicate, because "is this the same issue?" is a judgement made by a model reading titles. It might state a cause with more confidence than the evidence supports. It might write an issue that reads well and describes the wrong step. The approval gate catches these only if you read the proposal instead of pressing y. A tired reviewer is the real failure mode of every human gate, so keep proposals short enough to read.

4. An agent from outside, and one inside the tool

The agent above is external: it runs on your machine and reaches into GitHub or Jira through MCP. Atlassian's Rovo offers the opposite shape: agents that live inside Jira and Confluence and act there. Both can draft a bug report or a test case. They differ in who controls them.

External agent plus MCP (this phase)Agent inside the tool (Rovo)
Where it runsYour machine or a pipelineInside Jira and Confluence
Who sets its permissionsYou, in code and tool listsThe tool's administrators
What it can seeWhat its tools expose, plus your filesWhat the tool's own data holds
Triggered byA command, a pipeline, a scheduleEvents and actions inside the tool, such as a status change
Good fitWork that spans several systems, such as your test results and a trackerWork that lives entirely inside one tool and should follow that tool's access rules

Neither is better. Choose by where the data lives and who needs to control the agent. Check the details of your own Jira site's AI features against what your administrators have turned on, because that varies between organisations.

5. Test management: Zephyr Scale

If your team keeps test cases and run results in Zephyr Scale, a Jira app for test management, two things connect it to Playwright: reporting results, and creating test cases. Reporting is a Playwright reporter, playwright-zephyr, added in playwright.config.ts:

reporter: [
  ['playwright-zephyr/lib/src/cloud', {
    projectKey: 'YOUR-KEY',                         // your Zephyr project's key
    authorizationToken: process.env.ZEPHYR_AUTH_TOKEN,   // from the environment, never typed in the file
  }],
],

That is the cloud version, from the package's own instructions. A self-hosted Server install uses a different reporter name and a host option, which the package documents. Creating test cases from an agent's output comes up in Phase 4. This section is deliberately short: it needs a Zephyr instance to try, so treat it as a pointer until you have one.

6. Make your test repository easy for an agent to read

An agent finds its way by reading file names and a few instruction files. A repository an agent can navigate is also one a new teammate can navigate. Four habits help both:

  • Predictable folders. tests/shop/cart.spec.ts tells a reader what it covers before it opens. tests/new2.spec.ts does not.
  • One page of instructions at the root. Claude Code reads a file called CLAUDE.md at the start of a session. Put the commands and rules there so you do not repeat them in every prompt.
  • Stable hooks in the app. Role-based locators and test ids from Phase 2 of the Playwright series give the agent something solid to point at.
  • Small files with one job. Easier to read in full, and easier to review a change to.
# CLAUDE.md

This is the QA repository for the PeakAndPack shop. Tests are Playwright and TypeScript.

## Commands
- Run all tests: `npx playwright test`
- Run one file: `npx playwright test tests/shop/cart.spec.ts`
- Agent scripts live in `agents/`. Run them with `npx tsx` from that folder.

## Rules for any test you write
- Locators: getByRole, getByLabel, getByText. Test ids only when nothing else names the element.
- No `waitForTimeout`. Wait on an assertion or on `waitForResponse`.
- Each test creates its own customer through the API. Never the shared demo account.
- Every test states what change to the app would make it fail.

## Do not
- Edit anything outside `generated-tests/` unless asked.
- Commit secrets. Keys come from environment variables.

The CCAR-F for QA series explains CLAUDE.md and how teams share it in Domain 3.

7. Common mistakes

  • A token with too much reach. Scope it to one practice repository and one permission.
  • Trusting a tool list from a blog post. Read the names from /mcp on your own machine.
  • Pressing y without reading. The gate is only as good as the reading.
  • Using an agent to read a JSON file. Code reads files for free. Spend the model on judgement.
  • Committing .mcp.json with a token inside it.

8. Deliverables

  • mcp-setup.md: which servers you connected, with the exact commands, the token's scope, and the tools each exposed (copied from /mcp)
  • agents/simple-mcp-agent.ts: the agent above, working against your own practice repository
  • mcp-architecture.md: a diagram or short description of what talks to what, and where the approval gate sits
Assignment

Close the duplicate gap, and prove it

Run the agent twice against the same failure and note whether it files a duplicate. Then change one thing so a duplicate cannot be filed without a person noticing, and show it works. Write down what you changed and why you did not fix it by adding "do not file duplicates" in capital letters to the prompt.

Show solution: try it yourself first

Two sensible changes, and the reasoning that separates them:

  • Make the title predictable and the check mechanical. Have the agent always use Failing test: <exact test title>, and look for that exact string. An exact-match check is code, not judgement.
  • Move the duplicate check out of the model entirely. Search for the title in the script before the agent is asked to do anything, and only pass it failures with no open issue. Then a duplicate cannot be filed, whatever the model does.

Why not a stronger prompt: a prompt is a request. The model may follow it ninety-nine times and ignore it on the hundredth, and you cannot tell which run that is. A check written in code runs every time. Use the prompt for judgement and code for rules.

Show it works by running the agent twice on the same report and confirming one issue exists afterwards.

Bonus challenge

Read the tool list as an attacker would, and as a reviewer would. Open /mcp for the GitHub server and count how many tools it offers. For each one you did not allow, say what the worst case would be if the agent used it. Which of those would you be comfortable allowing without asking, and which never?
