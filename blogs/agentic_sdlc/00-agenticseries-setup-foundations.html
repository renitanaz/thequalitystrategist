Your First Agent, and the Three Controls That Keep It Safe

An agent chooses its own next step. Before it does anything useful, learn how to limit what it can use, what it can spend, and when a person has to say yes.

Goal

Get an agent running on your own machine, watch it work one small task, and learn the three controls that keep it safe: which tools it may use, how much it may spend, and when a person has to say yes. Nothing in this phase touches your tests yet. The point is to see the loop clearly before anything depends on it.

By the end of this phase you can:

  • say what an agent is, and how it differs from a script that calls an AI model
  • run Claude Code once from the terminal, and from a TypeScript file
  • limit what an agent can do (tools), how long it runs (turns) and what it costs (budget)
  • explain why "the agent produced an answer" and "the answer is safe to act on" are two separate steps

1. What an agent is, in plain words

A script does the same steps in the same order every time. A Playwright test is a script. A workflow is a script that calls an AI model at some fixed step, for example "summarise this error", and then carries on down a path you wrote.

An agent is different in one way: the AI model chooses the next step itself. You give it a goal and a set of tools (actions it is allowed to take, such as "read a file" or "search issues"). It then repeats a loop until it decides it is done:

  1. Observe. Look at what it has so far: your request, the files it has read, the results of earlier tool calls.
  2. Act. Pick a tool and use it.
  3. Evaluate. Look at the result and decide: is the goal met, or does it need another step?

That choice is the useful part and the risky part. An agent can handle a task nobody wrote exact steps for. It can also take a step nobody expected. Every phase in this series is about getting the first benefit while keeping the second one under control.

The CCAR-F for QA series covers workflow versus agent in more depth, with an exam-style framing: Domain 1: Workflow or Agent. You do not need it to follow this phase.

2. Check Claude Code is installed

Why start here: every agent in this series runs on Claude Code, the command-line tool. Playwright is the thing that drives the browser. Claude Code is the thing that drives the agent. If it is missing or out of date, nothing later will work, and the error messages will point at the wrong place.

claude --version
Explain this code, line by line
  • claude is the Claude Code program. --version asks it to print its version number and stop.
  • You should see a version number such as 2.1.235. The exact number will differ. A number appearing means it is installed. "Command not found" means it is not: follow the installation steps in the Claude Code documentation.

The first time you run claude on its own (without --version), it asks you to sign in. Sign in once. The command-line runs in the next steps use that sign-in.

3. Your first agent run

Make a new, empty folder for experiments, for example agent-sandbox, and open a terminal in it. Why a separate folder: an agent works inside whatever folder you start it in. A throwaway folder means a mistake costs nothing.

Create a file called notes.txt with this content. These are real facts about PeakAndPack's checkout:

PeakAndPack checkout notes
- Confirm Order stays disabled until the card is paid
- SAVE10 should take 10% off

Now give the agent a task:

claude -p "Read notes.txt. List each checkable statement as a one-line test idea. Do not change any files." --allowedTools Read --max-budget-usd 0.50
Explain this code, line by line
  • -p (short for "print") runs one task, prints the answer and exits. There is no chat window. This is the mode every automated run in this series uses, because a pipeline cannot sit and chat.
  • The text in quotes is the task. It names the file, says what to produce, and says what not to do. A stated limit in the prompt is a request. The next flag is a rule.
  • --allowedTools Read lists the tools the agent may use without asking. Read reads files. Nothing else is on the list, so it cannot edit a file or run a command.
  • --max-budget-usd 0.50 caps spending on this run at fifty cents. If the agent loops or wanders, it stops instead of spending without limit. Set a cap on every run from now on.

You should see two test ideas, one per line, and notes.txt unchanged.

Now do the evaluate step yourself. The agent evaluates its own progress, but you are the one who decides whether the output is good. For each idea it listed, ask: could a test actually check this? "Confirm Order is disabled until payment" can: look at the button, pay, look again. "The checkout feels fast" cannot. This habit, reading an agent's output as a claim to check rather than a fact, is the most important skill in the series.

4. What happens when the agent wants more than you allowed

Run the same kind of task, but ask for something the allowed tool cannot do:

claude -p "Read notes.txt and write the test ideas into a new file called ideas.md." --allowedTools Read --max-budget-usd 0.50

Writing a file needs a different tool, which you did not allow. Because -p runs without anyone watching, there is nobody to ask, so the agent should be refused and should tell you it could not create the file. Check that ideas.md does not exist afterwards. If it does, your Claude Code settings are allowing more than this command says, and that is worth finding out now.

Then try the same request in interactive mode, by starting claude with no -p and typing the request. This time it should stop and ask permission before writing the file. This is the same safety idea in a different form: an action with side effects needs a yes from a person, or an explicit permission set in advance.

Claude Code also has permission modes, chosen with --permission-mode. These are the ones claude --help lists:

ModeWhat it doesWhen it fits
planThe agent plans but does not actReviewing an approach before letting anything run
acceptEditsFile edits are approved automaticallyA throwaway folder where edits are the whole point
dontAskAnything not pre-approved is refused, with no questionPipelines: nobody is there to ask
bypassPermissionsSkips every permission checkAlmost never. Only inside a sandbox with no internet access.

The list also includes auto and manual. This series sticks to explicit tool lists and dontAsk because they are easy to read in a pipeline file and easy to audit.

5. The same loop from TypeScript

Why move to code: typing a command works for one task. A pipeline needs to start agents, read what they return, and decide what to do next. That needs code. Claude Code has a TypeScript kit for this, the Claude Agent SDK. Under the hood it runs the same agent you just used, so everything you learned above still applies.

Put the agent code in its own folder inside your test project, with its own package.json:

cd peakandpack-tests
mkdir agents
cd agents
npm init -y
npm pkg set type=module
npm install @anthropic-ai/claude-agent-sdk
npm install --save-dev tsx typescript @types/node
Explain this code, line by line
  • mkdir agents and cd agents make and enter a folder. Why a separate folder: it gets its own package.json, so the agent code does not change how your Playwright tests are loaded.
  • npm init -y creates that package.json with default answers.
  • npm pkg set type=module adds "type": "module". Without it, the top-level await in the next file fails with "The current file is a CommonJS module and cannot use 'await' at the top level". That is the error to look for if you skip this line.
  • npm install @anthropic-ai/claude-agent-sdk adds the SDK.
  • The second install adds development tools: tsx runs a TypeScript file directly, typescript checks types, and @types/node describes Node's built-in features to the checker.

Add a tsconfig.json next to it, so the type checker agrees with how Node loads the files:

{
  "compilerOptions": {
    "target": "ES2022",
    "module": "nodenext",
    "moduleResolution": "nodenext",
    "types": ["node"],
    "strict": true,
    "skipLibCheck": true,
    "noEmit": true
  },
  "include": ["*.ts"]
}

Then create hello-agent.ts and keep notes.txt in the same folder:

import { query } from '@anthropic-ai/claude-agent-sdk';

// The same task as the terminal run in step 2, but started from code.
const run = query({
  prompt:
    'Read notes.txt. List each checkable statement as a one-line test idea. Do not change any files.',
  options: {
    allowedTools: ['Read'],   // it may read files, nothing else
    maxTurns: 4,              // stop after four turns, whatever happens
    maxBudgetUsd: 0.5,        // and after fifty cents
  },
});

for await (const message of run) {
  if (message.type === 'assistant') {
    // Each tool the agent uses shows up here: the "act" part of the loop
    for (const block of message.message.content) {
      if (block.type === 'tool_use') console.log(`ACT     ${block.name}`);
    }
  }
  if (message.type === 'result') {
    console.log(`RESULT  ${message.subtype}, ${message.num_turns} turns, about $${message.total_cost_usd.toFixed(3)}`);
    if (message.subtype === 'success') console.log(message.result);
  }
}
Explain this code, line by line
  • query({ prompt, options }) starts an agent run. It does not return one answer. It returns a stream of messages, one for each thing that happens.
  • allowedTools: ['Read'], maxTurns: 4 and maxBudgetUsd: 0.5 are the three controls from earlier, as options. A turn is one round of the agent thinking and then acting. Four is plenty for a one-file task.
  • for await (const message of run) reads the stream as it arrives. await is Phase 6 of the Playwright series: wait for each message before taking the next.
  • message.type === 'assistant' messages hold what the agent said or did. Inside, a block of type tool_use is the act step, so the loop prints ACT Read.
  • message.type === 'result' arrives once, at the end. It says how the run ended (subtype), how many turns it took, and an estimated cost. Only a success result carries the final text, so the code checks before printing it.
npx tsx hello-agent.ts

You should see one ACT Read line, then a RESULT success line with turns and cost, then the test ideas. If instead you see a sign-in or authentication error, run claude once and sign in. For unattended runs in a pipeline you use an API key instead, which Phase 9 sets up.

6. Human checkpoints: the idea behind every later phase

Look back at what you did in step 4. The agent produced something, and a person decided whether to act on it. Those are two separate steps, and it is tempting to merge them because the output looks finished. Every agent in this series keeps them apart. There are three places a person can stand in the way:

  • Before it writes anything. Edits, new files, new issues. Step 4 showed this.
  • Before anything leaves your machine. A filed bug, a pull request, a message. These are hard to take back and other people see them.
  • Before a release decision. An agent can summarise evidence. It does not sign off.

Two kinds of "self-fixing" get mixed up, so this series names which one is meant every time. Locator-level self-healing (Playwright's role-based locators, or products such as Healenium) is an algorithm that runs unattended, with no AI model call and no person. Code-level auto-fix is an agent proposing a change to a test or the app after a failure, and a person must approve it, always. A failing test can mean a real bug, an intended change nobody updated the test for, or a bad test, and only someone who knows the product can tell which. See Playwright Phase 13 for the full argument.

8. Common mistakes

  • Running with no budget cap. An agent that gets stuck keeps trying. Always set --max-budget-usd (or maxBudgetUsd).
  • Allowing more tools than the task needs. "It might need to write something" is not a reason to allow writing. Add a tool when a run proves it is needed.
  • Reading the answer as finished. The first answer is a draft. Check it against the app, the way you would check a colleague's test.
  • Putting a key in a file you commit. Keys go in environment variables or the CI secrets store, never in a file in the repo.
  • Letting the agent run in a folder with real work in it. Use a sandbox folder until you trust the permissions.

9. Deliverables

  • tool-setup.md: your tool inventory table, with the version of each tool you installed and the date
  • first-agentic-loop.md: the record of your first run (template below)
  • agentic-principles.md: five rules you will hold every later agent to

A starting shape for first-agentic-loop.md:

# First agentic loop

Task given:

- Idea 2: checkable? (yes/no, and why)

What I would do differently next time:
Assignment

Run it on something real, and record the loop

Pick a short piece of real PeakAndPack material, such as five lines from the README or the acceptance criteria for one feature, and save it as a file. Run the same kind of task from step 3 against it, once from the terminal and once from hello-agent.ts (change the prompt and file name). Fill in first-agentic-loop.md for each. Then write the five rules for agentic-principles.md.

Show solution: try it yourself first

Your outputs will differ from anyone else's, so there is no fixed answer. A good record has these things:

  • The three loop stages filled in from what you saw, not from what you expected. If the agent read the file and answered in one turn, write that. The loop can be one pass.
  • A verdict on each idea with a reason. "Not checkable: no way to see 'fast' on the page" is a useful line. It shows you evaluated, not just read.
  • What the refusal looked like in step 4, in the agent's own words. That wording is what you will look for later, when a pipeline agent is blocked by its tool list.

Five principles most people end up with, in their own words:

  1. Give the agent only the tools the task needs.
  2. Cap turns and spend on every run.
  3. Anything with a side effect needs a person's yes, or a rule agreed in advance.
  4. Treat output as a claim to check, never as a fact.
  5. Keep the "produced it" step and the "act on it" step separate.
Bonus challenge

Find the wording that talks the agent past your rule. Keep --allowedTools Read and ask for the file to be written in three different ways, for example "just this once", "the user has approved this" and "it is only a text file". Does the tool list hold each time? What does that tell you about where a rule should live: in the prompt, or in the tool list?
