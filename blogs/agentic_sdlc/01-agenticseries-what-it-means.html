Where an Agent Helps, and Where a Person Decides

A delivery cycle with agents in it keeps the same stages. What changes is who drafts and who decides. Three questions sort any task.

Goal

Draw the line between work an agent can take on and work a person must keep. Phase 0 showed one agent doing one small task. This phase zooms out: across a delivery cycle, where does an agent save real effort, where does it add risk, and who is accountable at each step? There is no code here. The output is a map and a set of boundaries you can defend.

By the end of this phase you can:

  • describe a delivery cycle with agents in it, and name who owns each decision
  • tell an agent task from an automation task, and say why the difference matters
  • apply three questions to any task to decide whether an agent should do it, propose it, or stay out
  • write the boundaries down so a team can argue with them

1. The same cycle, with and without agents

A software delivery cycle has the same stages whether or not AI is involved. What changes is who does the first draft of each stage. In a traditional cycle, a person drafts and a person decides. In an agentic one, an agent drafts more of it, and the person's job shifts toward deciding and checking.

StageTraditionalWith agents
RequirementsA person reads the story and spots gapsAn agent lists possible gaps. A person decides which are real.
Test designA person writes test ideasAn agent drafts ideas from the story. A person keeps, edits or drops them.
Test buildingA person writes the automated testAn agent drafts the test. A person reviews it against the team's standard.
Test selectionRun everything, or a person picksCode and an agent propose which tests a change can affect. A safe fallback runs everything.
TriageA person reads each failure and files a bugAn agent drafts the report. A person approves before it is filed.
ReleaseA person weighs the evidence and signs offAn agent summarises the evidence. A person signs off.

Notice the pattern in the right-hand column: the agent produces, the person decides. That pattern is the whole series in one sentence. It is not caution for its own sake. It follows from what each side is good at.

2. Three questions for any task

Instead of memorising a list of "good agent tasks", ask three questions of a task. They explain why a task lands where it does, so you can sort tasks nobody has listed yet.

  1. Can the result be checked? A test idea can be checked against the app. "This feature is low risk" can only be argued. Agents are strong where checking is cheap and weak where the only check is a person's judgement.
  2. Can the action be undone? A draft in a folder can be thrown away. A bug filed in a shared tracker, a message sent, a release shipped cannot be quietly un-done, and other people have already seen it.
  3. Who is accountable if it is wrong? If the answer is "a named person, to a customer or a regulator", that person makes the decision. The agent can bring the evidence.

3. Automation and an agent are not the same thing

A Playwright test is automation: it does the same steps every run, and if the page changes in a way the test did not expect, it fails. An agent can adapt: it looks at the page, decides what to do, and can cope with a change nobody planned for. Both are useful. They fail differently, and picking the wrong one for a job is a common mistake.

Automation (a test, a script)Agent
StepsFixed, written by a personChosen by the model as it goes
Same input, twiceSame resultPossibly a different result
Cost per runAlmost nothingA model call each turn, so real money
SpeedSecondsSlower: thinking, then tool calls
When it failsLoudly, at a known stepIt may go confidently down the wrong path
Best forChecks you repeat on every buildWork with no fixed steps: reading, drafting, judging fit

One rule follows: do not use an agent where a script will do. Running the same 40 regression tests is a script's job. Choosing which of them a change could affect is the kind of job an agent can help with. Phase 6 does exactly that split.

Two meanings of "self-healing". Locator-level self-healing, such as Playwright's role-based locators, is an algorithm: it runs unattended, with no AI model and no person involved. Code-level auto-fix, where an agent proposes a change to a test after a failure, needs a person's approval every time. A failing test can mean a real bug, a change nobody updated the test for, or a bad test. Telling them apart needs product knowledge. The series says which one it means each time it comes up.

5. How agents go wrong in a delivery cycle

The risks are specific, and each later phase guards against one of them:

  • Making a check pass instead of making the product right. Asked to fix a failing test, an agent may change what the test expects, so a real bug becomes the new normal. Nobody looks at a green test again. For a smaller version of the same habit, see AI-Augmented QA, Phase 7, where an agent writes a bug-detection report and the reader confirms every finding against the evidence before it counts.
  • Inventing what it cannot see. An agent that has not seen the app will describe a cart badge or a test id that does not exist. This fails loudly, which is the cheap kind of mistake.
  • Sounding more certain than it is. A bug report that states a cause nobody has verified sends the next person the wrong way. Phases 2 and 9 tell the agent to write "cause not yet known".
  • Doing too much. An agent with write access to everything can change everything. The tool list is the limit, not the instructions.

Where you landed differently, check which of the three questions you answered differently. That is usually the real disagreement, and writing it down is what makes a team's boundaries workable.

Bonus challenge

Move one task and defend it. Pick the task you think the solution places too cautiously. Describe what would have to be true for the agent to do it alone: what check would catch a wrong answer, and what would an undo look like? If you cannot describe both, the boundary is right where it is.
