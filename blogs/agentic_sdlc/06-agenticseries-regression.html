Run the Tests a Change Can Affect, and Everything When Unsure

A mapping does most of the work, an agent covers the gaps, and one strict rule decides. When anything is unclear, the full suite runs.

Goal

Run the tests a change could affect, and fall back to running everything whenever that is not clear. This is the phase where "agent" and "script" split the work: code does the part that is a rule, the agent handles only the files no rule covers, and a safety net catches what the agent cannot place.

By the end of this phase you can:

  • explain why the QA pipeline works from a list of changed files, not the app's code
  • build a mapping from source files to the tests that cover them
  • use an agent for the gaps in the mapping, with a confidence score and a structured answer
  • write the rule that turns an agent's answer into a decision, and the fallback for when it is unclear
  • check the whole approach against your own project's history

1. The regression problem

Every change could break something that used to work, so in principle every change needs the whole suite. In practice a suite grows until running it on every change is slow, and teams start skipping it or running a hand-picked few. Either way, some risk goes unchecked without anyone deciding it should.

Choosing which tests a change can affect is a real skill: you read what changed, you know the product, you judge which areas it touches. It is also a task that fits an agent, if two conditions hold. A wrong answer must be caught (the full suite still runs on a schedule), and a wrong answer must be cheap (an extra test costs seconds, a missed one costs a bug in production). The rule that makes both true: when unsure, run everything.

2. Why a list of changed files, not the code

You might expect the agent to read the change itself, the code difference. In many companies the QA team cannot do that: the application lives in a repository QA has no access to. So the design here follows the realistic setup. The development pipeline, after it ships a change, sends QA only a list of the file names that changed. The agent maps names to tests.

It sounds like a weakness. It is also a constraint that keeps the agent honest. A file name and the names and contents of the tests are all it sees, so when a file's purpose is not clear from those, it has to say so. Phase 9 wires the real trigger. For now you supply the list by hand.

3. Three layers, in order

  1. A mapping, written by a person, applied by code. "When frontend/src/pages/Cart.js changes, run the cart and checkout tests." Free, instant, identical every time.
  2. An agent for files the mapping does not cover. A new file, a renamed one. It proposes tests, each with a confidence, or says it cannot judge.
  3. A decision rule in code that accepts only trusted proposals and otherwise runs the full suite.

The order is the lesson. Put as much as possible in layer 1, because rules are cheap and reliable. Use layer 2 only for the remainder. Make layer 3 strict, because it is the part you can trust.

Explain this code, line by line
  • Each line is one rule with three parts. match is a file path, or a folder path ending in / that covers everything inside it. tests lists the spec files to run. why is a short reason.
  • Why a why field: the reason ends up in the report. Six months from now, "run the checkout tests because the payment form changed" is something a person can argue with. A bare list of file names is not.
  • frontend/src/api.js maps to five spec files, because every page talks to the server through it. A change there could affect anything, so it maps to a wide set.
  • Rules overlap on purpose. A file can match several rules, and the selection is the union of all of them.

5. Applying the mapping, and the decision rule

import { readFileSync } from 'node:fs';

export type MappingRule = { match: string; tests: string[]; why: string };
export type Selection = {
  tests: string[];            // spec files to run
  unmapped: string[];         // changed files no rule covered
  reasons: Record<string, string[]>;   // spec file -> why it was chosen
};

// A rule's match is a path prefix or an exact file path.
const covers = (rule: MappingRule, file: string) =>
  file === rule.match || (rule.match.endsWith('/') && file.startsWith(rule.match));

export function selectFromMapping(changedFiles: string[], rules: MappingRule[]): Selection {
  const tests = new Set<string>();
  const unmapped: string[] = [];
  const reasons: Record<string, string[]> = {};

  for (const file of changedFiles) {
    const hits = rules.filter((rule) => covers(rule, file));
    if (hits.length === 0) unmapped.push(file);
    for (const rule of hits) {
      for (const test of rule.tests) {
        tests.add(test);
        (reasons[test] ??= []).push(`${file}: ${rule.why}`);
      }
    }
  }
  return { tests: [...tests].sort(), unmapped, reasons };
}

export function loadMapping(path = 'test-mapping.json'): MappingRule[] {
  return JSON.parse(readFileSync(path, 'utf-8')) as MappingRule[];
}

export type AgentPick = { file: string; test: string; confidence: number; reason: string };
export type AgentAnswer = { picks: AgentPick[]; cannot_judge: string[] };

export type Decision = {
  runAll: boolean;
  tests: string[];
  why: string[];
};

const ADD_AT = 0.7;   // below this, the agent's suggestion is noted but not trusted

// The rule that keeps the agent honest: when anything is unclear, run everything.
export function decide(
  selection: Selection,
  answer: AgentAnswer | null,       // null: the agent was not asked, or did not answer
  knownTests: string[],             // spec files that really exist
): Decision {
  const tests = new Set(selection.tests);
  const why = Object.entries(selection.reasons).map(([t, r]) => `${t}: ${r.join('; ')}`);

  if (selection.unmapped.length === 0) return { runAll: false, tests: [...tests].sort(), why };

  if (answer === null) {
    return { runAll: true, tests: [], why: [...why, `Unmapped files and no agent answer: ${selection.unmapped.join(', ')}`] };
  }
  if (answer.cannot_judge.length > 0) {
    return { runAll: true, tests: [], why: [...why, `The agent could not judge: ${answer.cannot_judge.join(', ')}`] };
  }
  const covered = new Set<string>();   // changed files that got at least one trusted pick
  for (const pick of answer.picks) {
    if (!knownTests.includes(pick.test)) {
      why.push(`Ignored ${pick.test}: no such spec file`);   // an invented file name
    } else if (pick.confidence < ADD_AT) {
      why.push(`Ignored ${pick.test}: confidence ${pick.confidence} is below ${ADD_AT}`);
    } else {
      tests.add(pick.test);
      covered.add(pick.file);
      why.push(`${pick.test}: agent, confidence ${pick.confidence}: ${pick.reason}`);
    }
  }

  // A changed file nobody could place is not "no tests needed", it is "we do not know"
  const unplaced = selection.unmapped.filter((file) => !covered.has(file));
  if (unplaced.length > 0) {
    return { runAll: true, tests: [], why: [...why, `No trusted pick for: ${unplaced.join(', ')}`] };
  }
  return { runAll: false, tests: [...tests].sort(), why };
}
Explain this code, line by line
  • covers says whether a rule covers a file: an exact match, or the file is inside the rule's folder.
  • selectFromMapping goes through each changed file, collects the tests of every matching rule, and notes the files nothing matched (unmapped). It also records, for each test, the reasons it was chosen.
  • decide is the rule that matters. With no unmapped files, the mapping's answer stands and the agent is not needed. With unmapped files and no agent answer, runAll is true. If the agent says it could not judge, runAll is true.
  • Each agent pick is checked three ways. A test file that does not exist is ignored: models invent file names. A pick below 0.7 confidence is noted but not trusted. Only trusted picks join the selection.
  • The last block is the one that is easy to forget. A changed file with no trusted pick is not "no tests needed". It is "we do not know", so the answer is to run everything. Without this, one unplaced file could quietly drop out.

Here is how the rule behaved on seven made-up situations, run with a fake agent answer in each case. Wishlist.js stands for a new page nobody has written a rule for:

SituationDecision
Every changed file is mappedRun the mapped specs. The agent is not asked.
A new file, and no agent answer (it was down)Run everything
The agent places it, with confidence 0.8, on a real specAdd that spec to the selection
The agent names a spec file that does not existIgnored, so the file is unplaced: run everything
The agent places it with confidence 0.4Ignored, so the file is unplaced: run everything
The agent says it cannot judge the fileRun everything
Two new files, and the agent places only oneThe other is unplaced: run everything

Read the right-hand column. Only one situation in the list lets the agent narrow the suite on its own, and it needs a real test, a high confidence and every unmapped file covered. Everything else widens. That asymmetry is deliberate: the agent can only make the run bigger or approve its own narrow pick under strict conditions. It cannot quietly drop a test.

6. The agent

import { readFileSync, readdirSync, writeFileSync } from 'node:fs';
import { sep } from 'node:path';
import { query } from '@anthropic-ai/claude-agent-sdk';
import { decide, loadMapping, selectFromMapping, type AgentAnswer } from './select-tests.js';

// The dev pipeline sends this list. This script never sees the app's code.
const changedFiles: string[] = JSON.parse(process.env.CHANGED_FILES ?? readFileSync('changed-files.json', 'utf-8'));

const testsDir = process.env.TESTS_DIR ?? '../tests';
const knownTests = readdirSync(testsDir, { recursive: true, encoding: 'utf-8' })
  .filter((f) => f.endsWith('.spec.ts'))
  .map((f) => `tests/${f.split(sep).join('/')}`);   // Windows paths use \ ; the mapping uses /

const selection = selectFromMapping(changedFiles, loadMapping());
let answer: AgentAnswer | null = null;

if (selection.unmapped.length > 0) {
  const run = query({
    prompt: `The PeakAndPack shop changed these files, and no mapping rule covers them:
${selection.unmapped.map((f) => `- ${f}`).join('\n')}

You cannot see the app's code, only these file paths and the test files in ${testsDir}.
Test files that exist:
${knownTests.map((t) => `- ${t}`).join('\n')}

For each changed file, decide which of those test files could be affected. Read the test files if you need to.
Each pick names the changed file it is about ("file"), the test file ("test") and a confidence from 0 to 1.
If a changed file's name and the tests give you no basis to judge,
put the file in cannot_judge instead of guessing.`,
    options: {
      cwd: process.cwd(),
      allowedTools: ['Read', 'Glob', 'Grep'],
      permissionMode: 'dontAsk',          // anything not allowed above is refused, with nobody to ask
      maxTurns: 10,
      maxBudgetUsd: 0.5,
      outputFormat: {
        type: 'json_schema',
        schema: {
          type: 'object',
          properties: {
            picks: {
              type: 'array',
              items: {
                type: 'object',
                properties: {
                  file: { type: 'string' },
                  test: { type: 'string' },
                  confidence: { type: 'number' },
                  reason: { type: 'string' },
                },
                required: ['file', 'test', 'confidence', 'reason'],
              },
            },
            cannot_judge: { type: 'array', items: { type: 'string' } },
          },
          required: ['picks', 'cannot_judge'],
        },
      },
    },
  });

  for await (const message of run) {
    if (message.type === 'result' && message.subtype === 'success') {
      answer = (message.structured_output as AgentAnswer | undefined) ?? null;
    }
  }
}

const decision = decide(selection, answer, knownTests);
writeFileSync('selection.json', JSON.stringify({ changedFiles, ...decision }, null, 2));
console.log(decision.runAll ? 'Run the full suite.' : `Run ${decision.tests.length} spec file(s):\n${decision.tests.join('\n')}`);
console.log('\nWhy:\n' + decision.why.map((w) => `- ${w}`).join('\n'));
Explain this code, line by line
  • The changed-file list comes from the CHANGED_FILES environment variable, or from a changed-files.json file. Why both: the pipeline will pass it in the environment, and while you are practising a file is easier.
  • knownTests lists the spec files that really exist, by reading the tests folder. The split(sep).join('/') turns Windows \ separators into the / the mapping uses. Without that line, no Windows path would ever match.
  • The agent is only called when something is unmapped. A run where every file is covered makes no model call, costs nothing and cannot vary.
  • The prompt shows the agent exactly what it can and cannot see, lists the real spec files, and tells it to use cannot_judge instead of guessing.
  • allowedTools is read-only (Read, Glob, Grep) and permissionMode: 'dontAsk' means anything else is refused without a question. Why: in a pipeline nobody is there to answer a question, so "refuse" is the only safe default.
  • outputFormat with a json_schema forces the answer into a fixed shape: a list of picks (each with the changed file, the test, a confidence and a reason) plus cannot_judge. Why a schema: code can only act on an answer it can read. Free text would need guesswork to parse.
  • The result arrives as structured_output. If it is missing, answer stays null, which decide treats as "run everything".
  • The final lines write selection.json (what Phase 9's pipeline reads) and print the decision with every reason.

The mapping layer needs no model, so you can run and read it today. From the agents folder, point TESTS_DIR at a folder that has the test layout (PeakAndPack's own e2e/tests folder works) and give it two changed files:

8. Check it against your own history

A design that looks sensible is not the same as one that works. Test it on changes that already happened. This small script prints the files one commit changed, in the format the pipeline will send:

import { execFileSync } from 'node:child_process';

// Prints the files one commit changed, as the JSON list the pipeline would send.
// Usage: npx tsx commit-files.ts C:/path/to/PeakAndPackShopDemo 75d1365
const [repoPath, sha] = process.argv.slice(2);
if (!repoPath || !sha) throw new Error('Usage: npx tsx commit-files.ts <path to the app repo> <commit sha>');

const output = execFileSync('git', ['diff', '--name-only', `${sha}~1`, sha], { cwd: repoPath, encoding: 'utf-8' });
const files = output.split('\n').filter((line) => line.trim() !== '');

console.log(JSON.stringify(files));
Explain this code, line by line
  • execFileSync('git', [...]) runs Git and waits for the answer. Passing the arguments as a list, not one string, avoids quoting problems with spaces in paths.
  • git diff --name-only <sha>~1 <sha> lists the files that differ between a commit and the one before it (~1 means "one before"). That is exactly "what this change touched".
  • The last lines drop empty lines and print the result as JSON, ready to use as CHANGED_FILES.

Read it as a tester would. Three of ten narrowed, and seven ran everything. Look at why the seven did:

  • backend/package.json changing is a good reason to run everything. A dependency upgrade (the database library here) can affect any test. The fallback gave the right answer without a rule. You could add an explicit rule to make that intention visible.
  • A 46-file commit is a "run everything" case anyway. The workflow and README files are unmapped, which is fine: they affect no test.
  • The first run showed a real gap. Before the rule for frontend/public/admin/ was added, the admin panel's copy served with the store was unmapped. Running the mapping over real commits is how you find rules you missed.
  • A real project would fall back to the full suite often. That is the safe direction. It means the time saved is smaller than a demo suggests. Measure it before you promise a number.

Green history cannot tell you whether the selection missed something, because if nothing failed there was nothing to miss. Use the deliberate-regression method in the assignment for that.

9. Common mistakes

  • Letting the agent do the whole job. A model re-deciding every file every run is slow, costs money and varies. Rules first.
  • No fallback. Selection without a safety net is a way to ship a regression the full suite would have caught.
  • Trusting a confidence number as if it were measured. A model's "0.9" is a rough feeling, not a probability. That is why the decision rule only uses it as a threshold and checks the rest in code.
  • Never running the full suite. Selection is a speed-up for the change run. A scheduled full run (Playwright Phase 12's nightly job) is what catches a selection error.
  • Letting the mapping rot. New files need rules. Review the "unmapped" list each week.

10. Deliverables

  • agents/regression-agent.ts, select-tests.ts and commit-files.ts: the three scripts
  • agents/test-mapping.json: the mapping, edited to match your repository
  • regression-report.md: your results from the retrospective and the deliberate-regression test, with the numbers
Assignment

Find out whether the selection would have missed anything

Part 1: take the last ten commits of PeakAndPackShopDemo, produce the changed-file list for each with commit-files.ts, and record the decision. Part 2: pick five source files. For each, make a small, deliberate change that would break a visible behaviour (for example change a label in Cart.js), run only the selected specs, and check whether the change is caught. Put both results in regression-report.md.

Show solution: try it yourself first

Your numbers will differ. This is what a useful report contains:

  • Part 1: the table, plus a count of narrowed against full-suite decisions and a one-line reason for each full-suite decision. Expect many "unmapped" results on a small project.
  • Part 2: for each of the five changes, "selected specs caught it" or "selected specs missed it". A miss is the most valuable result in the report, because it names a gap in the mapping. Add the missing rule and rerun to show it is closed.
  • The time column: specs selected against the total, and the run time of each. Do not claim a saving the table does not show.

A mapping that catches five of five deliberate regressions is a good sign, not proof. It means these five were covered. Say that in the report, in those words.

Bonus challenge

Add a rule that says "run everything". Extend the mapping so a change to backend/package.json or frontend/package.json always runs the full suite, and show the reason in the report. Is making the intention explicit better than letting the fallback produce the same result? Think about what happens when someone later adds a mapping rule for package.json without realising what it implies.
