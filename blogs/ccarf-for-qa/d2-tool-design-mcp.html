The Description, the Error, and the Scoped Tool: What D2 Actually Tests

Same PeakAndPack MCP tools, sharpened four ways: split descriptions that stop misrouting, structured errors instead of "operation failed," a scoped tool set per agent, and the MCP config that ships it.

CCAR-F for QA · ~8 min read

D2 doesn't test whether a tool works. It tests whether an agent can tell, from the description alone, which tool to call, what happens when the call fails, and whether it should even have access to that tool in the first place. All three questions get answered before a single tool actually runs.

Every example below is a real PeakAndPack tool, most reused from Post 01 and Post 03, sharpened against a specific D2 task statement instead of just working.

Four things D2 actually asks you to know

2.1 · Descriptions

The description is the primary way a model selects a tool. Ambiguous or overlapping descriptions cause misrouting, not model failure.

2.2 · Structured errors

isError plus a category (transient, validation, business, permission) plus a retryable flag, not a generic failure string.

2.3 · Scope & choice

Fewer tools per agent beats more. tool_choice forced only for a genuinely fixed first step.

2.4 / 2.5 · MCP & built-ins

Project vs. personal server scope, env var expansion for secrets. Grep, Glob, and when Edit falls back to Read + Write.

Part 1: a description is the interface

An agent never sees a tool's implementation, only its description. A vague one doesn't produce a vague tool call, it produces a confidently wrong one.

The exam's first Customer Support sample question tests exactly this. Try it before reading the explanation:

Exam sample question · Scenario: Customer Support Resolution Agent

Production logs show the agent frequently calls get_customer when users ask about orders (e.g., "check my order #12345"), instead of calling lookup_order. Both tools have minimal descriptions ("Retrieves customer information" / "Retrieves order details") and accept similar identifier formats. What's the most effective first step to improve tool selection reliability?

Tool descriptions are the primary mechanism LLMs use for selection. When descriptions are minimal, the model lacks the context to differentiate similar tools, B fixes the root cause directly, with the least effort. A adds token overhead without fixing the underlying issue. C is over-engineered and bypasses the model's own language understanding. D is a valid architectural choice, but it's more effort than a "first step" warrants when the immediate problem is just inadequate descriptions.

Deliverable, Part 1
  • d2-tool-descriptions.md: the full before/after, plus the four questions a description should always answer

How to use it: for any MCP tool description, check it states input format, output shape, when to use it, and when NOT to (naming the sibling tool). A description missing that last part is usually the one causing misrouting.

Part 2: an error that tells the agent what to do next

Task Statement 2.2's isError pattern isn't just a boolean. What turns a failure into something an agent can act on is the category attached to it.

Guess the four error categories the guide names, before you look
  • Transient: timeouts, service unavailability. Retryable, the same call will likely succeed shortly.
  • Validation: invalid input. Non-retryable, the same malformed request produces the same error again.
  • Business: a policy rule, not a technical failure. Non-retryable, but for a different reason, retrying doesn't change a real "no."
  • Permission: the requester isn't allowed to see this. Non-retryable, and the correct response to a missing or unverified requester ID, not a data leak.

A uniform "operation failed" response collapses all four into one undifferentiated signal, and an agent receiving it can't tell whether to retry, give up, or explain a policy to the user, it can only guess.

The permission category has a direct PeakAndPack stake: d2-error-responses.ts returns one for any orders lookup missing a verified requester ID, which is the correctly-built version of what BUG-010 gets wrong today, that endpoint currently returns every user's orders to anyone who asks, no permission check at all.

{
  "isError": true,
  "errorCategory": "permission",
  "isRetryable": false,
  "message": "Order lookups require a verified requester ID, none was provided"
}
Deliverable, Part 2
  • d2-error-responses.ts: all four categories implemented against real PeakAndPack failure modes, extending d1-triage-agent.ts's check_live_api

How to use it: replace any tool's plain throw or generic error string with an object carrying isError, errorCategory, and isRetryable. Not run against a live key here, the categorization logic is real and adaptable.

Part 3: how many tools, and who picks

Task Statement 2.3 is two decisions in one: how many tools any single agent can see, and when a caller forces a specific one instead of leaving the choice open.

Why scoped, not shared

An agent with tools outside its specialization tends to misuse them. Post 01's two subagents get 1 and 2 tools each, never the full three.

Why 18 tools degrade reliability

The guide's own number: 18 tools instead of 4-5 measurably worsens selection accuracy, not because the model gets confused, because the decision space grew.

The exam's Multi-Agent Research scenario asks this exact question about a synthesis agent needing occasional verification. Try it:

Exam sample question · Scenario: Multi-Agent Research System

The synthesis agent frequently needs to verify specific claims while combining findings. Currently it returns control to the coordinator, which invokes the web search agent, then re-invokes synthesis, adding 2-3 round trips per task. 85% of these verifications are simple fact-checks, 15% require deeper investigation. What's the most effective approach to reduce overhead while maintaining reliability?

A gives the synthesis agent only what it needs for the 85% common case, while preserving the existing coordination path for the harder 15%, least privilege applied correctly. B creates blocking dependencies, later synthesis steps may depend on earlier verified facts. C over-provisions the agent and violates separation of concerns, the exact anti-pattern 2.3 warns against. D relies on speculative caching that can't reliably predict what will actually need verification.

Deliverable, Part 3
  • d2-tool-scoping.md: why Post 01's subagent split isn't arbitrary, plus a forced tool_choice example for a fixed first step

How to use it: no script to run. Audit any agent's tool count, above 5-6 is worth questioning. Use forced tool_choice only for a genuinely fixed first step, not as a general ordering mechanism.

Part 4: the config, and the tools that already exist

2.4 and 2.5 are both about not building things that already exist: an MCP server config that's scoped correctly, and the built-in tools (Grep, Glob, Read, Write, Edit) that cover most of what a custom tool would otherwise need to.

Guess which built-in tool fits each job, before you look

Using D5's own scratchpad example (a checkout-drift investigation) as the material:

  • Finding every caller of computeSubtotal(): Grep, a content search across file contents, not a path match.
  • Finding every test file that should follow D3's Playwright conventions: Glob, a path-pattern match (**/*.spec.ts), no content involved yet.
  • Fixing the SAVE10 constant when the same literal value appears twice in one file: Edit fails on the non-unique anchor, fall back to Read the full file, then Write the corrected version back.
Deliverable, Part 4
  • d2-mcp-config/.mcp.json: a real project-scoped MCP server config with env var expansion
  • d2-built-in-tools.md: Grep vs. Glob vs. Edit-fallback, grounded in D5's own scratchpad example

How to use it: drop .mcp.json at your repo root, set PEAKANDPACK_API_TOKEN in your environment rather than the file, Claude Code expands it at connection time. Personal, experimental servers go in ~/.claude.json instead, never committed.

The QA angle: a tool boundary is a test boundary

Every distinction in this post has a testing mirror. A split tool description is testable in a way a merged one isn't, you can write a case that asserts the model picks the right tool for an ambiguous-sounding request. A structured error category is a thing you can assert on directly, instead of string-matching a message that might change wording. A scoped tool list is a thing you can enumerate and diff against what an agent is actually allowed to call. None of that is available when a tool is vague, a failure is a plain string, or an agent's tool list is "whatever's configured, we're not sure."

Blueprint tie · D2, 18%, Task Statements 2.1–2.5

D2 tests the boundary between an agent and the tools it calls, at the level of what the model can actually perceive: a description it reads, an error object it receives, a tool list it's scoped to, a server it discovers. Every one of those showed up as a real, checkable artifact in this post, not a description of a best practice.

What this does not solve

None of this post's code has run against a live key or a real MCP server connection, same methodology limits as every post in this capsule. It doesn't cover what happens when a tool description is accurate but the tool itself is buggy, that's closer to D5's error-propagation territory than D2's interface-design one. And the MCP server config here is illustrative, a real @example/peakandpack-mcp-server package doesn't exist, the shape of the config is what's real and adaptable.
