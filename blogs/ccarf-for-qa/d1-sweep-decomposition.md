# D1: Sweep Decomposition and Session State

**Reference note:** this is a worked-through reasoning document, not a file Claude Code loads. It covers Task Statements 1.6 (task decomposition strategies) and 1.7 (session state, resumption, forking), applied to PeakAndPack's bug catalog rather than a single triage call like Parts 1 to 3.

---

## Fixed pipeline: the pre-release regression sweep

Before every PeakAndPack release, the same 11 known bugs get re-verified against the live API, in the same order, every time. The steps are known in advance, the sequence doesn't change, and that predictability is the entire point.

1. `check_live_api("/api/products")` against BUG-001 (negative price), BUG-002 (empty product name), BUG-009 (discount total).
2. `check_live_api("/api/search")` against BUG-011 (search endpoint 500).
3. `check_live_api("/api/orders")` against BUG-010 (cross-user visibility), skipped if the sweep has no authenticated session available, same judgement call the agent in Part 1 made.
4. For each of the remaining catalogued bugs, the equivalent live-endpoint check against the field the bug describes.
5. Update the catalog's status field for anything that no longer reproduces, BUG-011 is the documented example: catalogued as open, not reproducing as of 16 August 2026.

This is prompt chaining, not adaptive decomposition. Each step is decided before the sweep starts, not by what the previous step found. That's correct here: the catalog is finite, known, and the goal is coverage, not discovery.

## Dynamic decomposition: an unfiled batch

A support inbox export lands with six new, unfiled reports. Nothing about them is known yet, not whether they're real, duplicates, or already-catalogued under different wording. A fixed pipeline can't be written for this because the second step depends on what the first one finds.

- Report 1 gets `search_bug_catalog` first. A match ends the investigation for that report, no live check needed.
- Report 2 has no catalog match, so it escalates to `search_past_reports`, the same tool the agent used to catch the RPT-014 duplicate in Part 1's Scenario 6.
- Report 3 matches nothing in either search. Only now does it reach `check_live_api`, the most expensive step, reserved for reports that survived the cheaper checks first.

The order isn't fixed in advance, it's generated by what each prior step actually returned. That's the adaptive half of Task Statement 1.6: the shape of the investigation matches the shape of what's actually unknown, instead of running every tool against every report regardless of whether earlier results already answered the question.

## Picking the sweep back up: session state

A full sweep across 11 catalogued bugs plus an unfiled batch rarely finishes in one sitting. Three situations, three different commands:

- **`--resume <session-name>`**, when nothing has changed since the sweep paused. The catalog is the same, the live API hasn't moved, prior tool results are still valid. Continuing the named session picks up exactly where it stopped, no re-verification needed.
- **A fresh session with a structured summary**, when the underlying system changed while the sweep was paused, a deploy landed, an endpoint's behaviour shifted. Resuming in this case means reasoning from tool results that are now stale, worse than starting clean. The structured summary (which bugs were already re-verified, which weren't, what changed) replaces the resumed history instead of trying to patch it.
- **`fork_session`**, when the sweep surfaces a bug worth two different remediation strategies, and both need investigating from the same baseline without re-running the whole sweep twice for each. Forking branches from the point where the sweep already established the shared facts, then diverges.

## Blueprint tie

D1, 27% of the exam. Task Statements 1.6 and 1.7 aren't about a single triage call, they're about what changes once the work is a catalog instead of one bug, and once it spans more than one sitting. Fixed pipeline versus dynamic decomposition is a choice made once, at the start, based on whether the scope is known. Resume versus fresh-with-summary versus fork is a choice made every time the sweep gets picked back up, based on whether the world underneath it moved.

## What this reference does not solve

It doesn't cover what happens when a fixed-pipeline sweep discovers something that should have been investigated adaptively, real sweeps sometimes need to switch strategy mid-run, and that decision isn't captured here. It also doesn't address session state for the multi-agent coordinator pattern from Part 2, resuming a coordinator with subagents that no longer hold isolated context is a different, harder problem than resuming a single-agent sweep.
