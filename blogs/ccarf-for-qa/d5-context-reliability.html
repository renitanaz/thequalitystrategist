The Case Facts, the Scratchpad, and the Calibrated Guess: What D5 Actually Tests

Same PeakAndPack QA setup, stretched across a long session: what survives context trimming, when to escalate instead of guess, what an interrupted investigation recovers from, and why a confidence score means nothing until it's calibrated.

CCAR-F for QA · ~8 min read

D5 is the lightest domain by weight, 15%, and the easiest to underrate because none of it is about getting an answer right. It's about what's still true, still attributed, and still legible after a session runs long enough to stop being a single clean exchange.

Every deliverable below reuses Post 01's triage agent and Post 01's own real finding, a live discrepancy the catalog didn't know about, because D5 isn't a new task, it's what happens to an existing one under pressure: more tool calls, more time, more sources that might disagree.

Four things D5 actually asks you to know

5.1 · What survives

A persistent case-facts block, placed first, holding exact values. Verbose tool output gets trimmed before it accumulates, not summarized after.

5.2 / 5.3 · Escalate or propagate

Explicit criteria beat sentiment or self-reported confidence. A failed tool call reports what actually happened, not a generic status.

5.4 · What outlives a restart

Scratchpad files, subagent delegation for verbose exploration, /compact between phases, a manifest for crash recovery.

5.5 / 5.6 · Calibrated, not just confident

Field-level confidence, stratified sampling. Conflicting sources get annotated, never silently resolved by picking one.

Part 1: the case-facts block

D1's triage agent appends every tool result to history verbatim, fine for three tools across six scenarios. It stops being fine once a live-API check starts returning full response bodies: the guide's own example is 40+ fields per lookup when five are relevant.

Guess what gets lost first when a long session gets summarized, before you look

Two separate risks the guide names under Task Statement 5.1, not one:

  • Progressive summarization condenses numerical values, percentages, dates, and stated expectations into vague prose. "The discount was wrong" survives a summary. "SAVE10 applied 100% instead of 10%" often doesn't.
  • The "lost in the middle" effect. Models reliably process the start and end of a long input, findings buried in the middle of a growing history are the ones most likely to get dropped or ignored, even though they're technically still there.

A case-facts block addresses both: exact values instead of summarized ones, and positioned first instead of buried mid-history.

Trim, don't summarize

Summarizing under context pressure flattens exact values. Trimming at extraction time keeps the numbers that matter and discards only what doesn't.

Position matters

The case-facts block goes at the start of the next prompt, not buried mid-history where the "lost in the middle" effect is worst.

Deliverable, Part 1
  • d5-case-facts.ts: extraction and case-facts-block functions, adaptable into d1-triage-agent.ts's tool loop

How to use it: call extractCaseFacts() after every tool result instead of appending the raw result to history untouched, then prepend caseFactsBlock()'s output to the next prompt. Not run against a live key here, the extraction logic is real and adaptable.

Part 2: escalate, or propagate what actually happened

5.2 and 5.3 are two sides of the same problem: when the agent itself can't resolve something, what does it do instead of guessing? Escalate to a human, or hand the coordinator enough information to decide.

The BUG-011 mistake, generalized: a 200 response with an empty result set is not the same event as a 503 or a network timeout, but a generic error handler often treats "nothing came back" identically regardless of why. Conflating "the endpoint answered and the answer was empty" with "the endpoint never answered" is the same category error as the catalog/live discrepancy from Post 01.

Escalation criteria run on the same principle as error handling: specific and explicit, not a vibe. The agent escalates when the live check contradicts the catalog, when a developer's test output explicitly asks for a human, or when two catalog entries match ambiguously, never on self-reported confidence or sentiment alone, both of which the guide names directly as unreliable proxies for actual complexity.

Deliverable, Part 2
  • d5-escalation-criteria.md: explicit escalate/don't-escalate criteria and a structured handoff shape
  • d5-error-propagation.ts: structured tool-error types, extending d1-coordinator-subagents.ts's verify-reproduction subagent

How to use it: swap d1-triage-agent.ts's plain file-new / link-existing / flag-flaky-retry verdict for the four-way version in the criteria doc, and replace check_live_api's raw fetch with checkLiveApiWithStructuredErrors() so failures carry a type instead of just throwing.

Part 3: the scratchpad that survives a restart

The triage task doesn't run long enough to need this. A regression investigation spanning cart, checkout, and shared pricing logic does. Past a certain point in an unaided session, the guide's own failure mode shows up: the agent starts referencing "typical patterns" instead of the specific line it found forty tool calls ago.

Guess what a session without a scratchpad starts doing wrong, before you look

Not hallucinating, exactly, degrading. The guide's own description: models in extended sessions "start giving inconsistent answers and referencing typical patterns rather than specific classes discovered earlier." The finding is technically still in the conversation history, it's just stopped being what the model actually reasons from.

A scratchpad file doesn't fix the model's attention, it routes around the problem: the specific finding lives on disk, referenced by path, instead of depending on staying salient in a growing history.

Not "the agent remembers more." What it needs to remember lives somewhere designed to hold it accurately, a file, written once, referenced by path, instead of somewhere that degrades under pressure.

Deliverable, Part 3
  • d5-scratchpad-investigation.md: the full worked investigation, why each step matters
  • d5-scratchpad-template.md: an actual scratchpad file, manifest section included

How to use it: no script to run. Have a real investigating session write findings to a scratchpad file as it goes, point follow-up questions back at that file instead of re-exploring, and run /compact once a phase's findings are safely on disk.

Part 4: a confidence score you calibrated, or didn't

"94% accurate" can still hide one category the system is systematically wrong on. Six scenarios is too small a sample to prove anything, which is exactly why it's a useful illustration: 100% correct on six scenarios looks identical to "got lucky on the one hard case" without stratifying by category first.

Guess why a 97% aggregate accuracy number can still be hiding a real problem, before you look

Because it's one number covering every document type and field, and a system can be excellent on the common cases while being quietly, consistently wrong on one rare one, the aggregate never separates the two.

The guide's fix: stratified random sampling, measuring error rates per document type and per field instead of trusting one blended percentage, specifically to catch the segment a single aggregate number would hide.

4/4clean catalog match, no discrepancy
1/1live check contradicted catalog, caught it
n=6too small to trust any one aggregate number

Verdict-level confidence hides the same thing aggregate accuracy does. Splitting it per field is more honest:

{
  "match": "BUG-011",
  "matchConfidence": "low",
  "liveReproductionConfidence": "high",
  "actionConfidence": "high"
}

High confidence in what was directly observed, low confidence in which catalog entry it belongs to. One collapsed number would have hidden that split entirely.

Provenance is the same discipline applied to sources instead of fields. The correct shape for the BUG-011 conflict never picks a winner:

{
  "claims": [
    { "source": "bug-catalog", "claim": "returns 500 on empty query" },
    { "source": "live-api-check", "claim": "returns 200, empty results" }
  ],
  "conflictDetected": true
}
Deliverable, Part 4
  • d5-confidence-calibration.md: stratified breakdown and a field-level confidence schema
  • d5-provenance-conflict.md: the BUG-011 conflict, structured correctly this time

How to use it: no script to run. Change any verdict schema to report confidence per field instead of one overall number, and any synthesis schema that draws on more than one source to carry a claims array plus a conflictDetected flag instead of collapsing to a single value.

The QA angle: reliability is a property of the session, not the answer

A single triage verdict can be correct and the system can still be unreliable, if getting there depended on context that happened not to overflow yet, or on a source conflict that happened not to come up. D5 is what a QA seat actually owns here: not whether one run got the right answer, but whether the same system stays right at call fifty, after a restart, and when two sources disagree.

Blueprint tie · D5, 15%, Task Statements 5.1–5.6

D5 is the lightest domain by weight and the one most likely to be treated as an afterthought once a system produces correct answers in testing. Every task statement here is really the same question asked from a different angle: what happens when the easy case (short session, one source, no failures) stops being the case you're in.
