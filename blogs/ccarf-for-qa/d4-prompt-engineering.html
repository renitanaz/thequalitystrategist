The Criteria, the Schema, and the Second Reviewer: What D4 Actually Tests

Same PeakAndPack triage and review flows, sharpened four ways: explicit criteria instead of "be conservative," a schema that can't fabricate a bug ID, a retry loop that knows when to stop, and a reviewer with no memory of writing the fix.

CCAR-F for QA · ~8 min read

D4 is the closing post in this capsule, and the domain most likely to be mistaken for "writing good prompts." It's narrower and more mechanical than that: specific criteria over vague adjectives, a schema over free text, a retry that uses the actual error, a reviewer with no stake in the answer already given.

Every example below is Post 01's triage agent or Post 02's CI reviewer, pushed one step further than either post needed to go on its own.

Four things D4 actually asks you to know

4.1 / 4.2 · Precision

Explicit categorical criteria beat "be conservative." Few-shot examples earn their place on ambiguous cases, not easy ones.

4.3 · Structured output

tool_use with a JSON schema eliminates syntax errors, not semantic ones. Nullable fields stop a model from fabricating a value to fill a gap.

4.4 · Validation loops

Retry with the specific error attached, not a repeat of the same prompt. Some failures aren't fixable by retrying at all.

4.5 / 4.6 · Batch & review

The Batch API is for latency-tolerant work only. An independent reviewer catches what a self-review instance won't.

Part 1: a criterion you can point to

"Be conservative" and "only flag high-confidence matches" sound like precision instructions. The guide's finding: neither actually improves precision, because neither says what confidence is built from.

Guess the specific criteria that replace "be confident," before you look

Applied to the triage verdict, a checkable version:

  • The failing endpoint matches the catalog entry exactly.
  • The error status code matches exactly.
  • The failure shares a specific mechanism with the catalog entry, not just a topic. A shared keyword like "price" or "order" is not sufficient on its own.

Flag a match only when at least two of the three hold. A reviewer who disagrees with a verdict can now name which condition the agent got wrong, instead of arguing about what "confident" was supposed to mean.

Few-shot examples earn their place the same way: not by padding a prompt with more instances of the case the model already gets right, but by walking through the case where a surface signal (a shared keyword, a similar-looking endpoint) is actually misleading.

Deliverable, Part 1
  • d4-explicit-criteria.md: the full before/after, applied to a real ambiguous BUG-007-vs-BUG-009 case
  • d4-few-shot-examples.md: two examples chosen for the mechanism they teach, not the count

How to use it: rewrite any confidence adjective in a prompt into a checklist of specific, checkable conditions. If a reviewer can't point to which condition failed when they disagree with a verdict, the criteria aren't explicit enough yet.

Part 2: a schema that can't lie by omission

Task Statement 4.3's core distinction: tool_use with a JSON schema eliminates syntax errors, a malformed brace, a missing quote, but it does nothing to stop a semantically wrong answer, a bug ID that doesn't exist, a total that doesn't sum.

{
  matchedBugId: { type: ["string", "null"] },  // nullable on purpose
  confidence: { enum: ["high", "medium", "low", "unclear"] },
  action: { enum: ["file-new", "link-existing",
                    "flag-flaky-retry", "escalate-to-human"] }
}

matchedBugId is explicitly nullable. A required, non-null field here would pressure the model to pick something from the catalog even when nothing actually matches, the exact fabrication the guide's 4.3 skill point warns against. "unclear" in the confidence enum is doing similar work, it's a real, distinct outcome (the tools couldn't resolve this) rather than a synonym for "low" (a match was found but it's shaky).

tool_choice: auto, then forced

Early turns stay "auto" so the model can still call search_bug_catalog or check_live_api freely. The final turn forces report_triage_verdict, guaranteeing schema-shaped output instead of drifting prose.

Syntax vs. semantics

The schema guarantees the JSON parses. It says nothing about whether matchedBugId: "BUG-099" refers to a bug that exists, that check still needs to happen downstream.

Deliverable, Part 2
  • d4-structured-verdict.ts: the full tool schema, nullable fields, and the forced-final-turn tool_choice pattern

How to use it: define the verdict as a tool with an input schema, force that tool only on the turn meant to be final, and make any field nullable where "I don't know" is a legitimate answer, not a validation failure.

Part 3: retrying with the actual error, and knowing when to stop

A validation failure is information. Re-sending the exact same prompt after a failed parse throws that information away.

Guess which triage verdict combination is invalid, before you look

{ action: "link-existing", matchedBugId: null }. Linking to an existing bug requires something to link to, the schema's types allow this combination (both fields are individually valid), but the cross-field logic doesn't hold. This is exactly the kind of semantic error tool_use's syntax guarantee doesn't catch on its own.

The fix is a validation pass after parsing, and a retry prompt that names the specific problem: "action is link-existing but matchedBugId is null", not a generic "please try again."

Retry has a ceiling. If the live API and the catalog both come back inconclusive, an endpoint that genuinely no longer exists, no amount of re-prompting produces information that isn't there. That's an escalate-to-human case, not another retry.

Deliverable, Part 3
  • d4-validation-retry.ts: cross-field validation, a specific-error retry prompt, and a retryable-vs-not check

How to use it: after parsing structured output, add validation for rules a JSON schema can't express (cross-field logic), and when retrying, always include the exact validation error and the original failed output, never just the original prompt again.

Part 4: overnight batches, and a reviewer who wasn't there

4.5 and 4.6 both come down to matching the tool to what the task actually tolerates: latency for batching, independence for reviewing.

Try the exam's own version of the batch question first:

Exam sample question · Scenario: Claude Code for Continuous Integration

Your team wants to reduce API costs for automated analysis. Real-time Claude calls power two workflows: a blocking pre-merge check that must complete before developers can merge, and a technical debt report generated overnight for review the next morning. Your manager proposes switching both to the Message Batches API for its 50% cost savings. How should you evaluate this proposal?

The Batch API's up-to-24-hour window with no guaranteed SLA is unsuitable for a blocking pre-merge check where a developer is waiting, but ideal for an overnight report already reviewed the next morning. B wrongly treats "often faster" as acceptable for a blocking workflow. C reflects a misconception, batch results correlate cleanly via custom_id. D adds complexity the simpler per-workflow split doesn't need.

PeakAndPack's version: d1-triage-agent.ts's live, tool-calling triage cannot batch at all, the Batch API doesn't support mid-request tool calls. Only a nightly sweep using the simpler d1-triage-workflow.ts shape, no tools, one call in, one verdict out, actually qualifies.

Now the multi-pass review question, extending Post 02's d3-ci-review.sh:

Exam sample question · Scenario: Claude Code for Continuous Integration

A pull request modifies 14 files. Your single-pass review analyzing all files together produces inconsistent results: detailed feedback for some files but superficial comments for others, and contradictory feedback, flagging a pattern as problematic in one file while approving identical code elsewhere in the same PR. How should you restructure the review?

Splitting into focused passes directly addresses the root cause, attention dilution across many files at once, while a separate integration pass still catches cross-file issues a local view can't see. B shifts the burden to developers without fixing the review system. C misunderstands that a larger context window doesn't fix attention quality. D would actually suppress real bugs caught only intermittently by requiring consensus across runs.

Deliverable, Part 4
  • d4-batch-triage.md: which PeakAndPack workflow qualifies for batching and which structurally can't
  • d4-multi-pass-review.md: per-file plus integration passes, applied to D5's own three-file checkout investigation

How to use it: before batching a workflow, check it needs no mid-request tool calls and tolerates real latency. Before reviewing multiple files in one pass, check whether depth is already inconsistent across files, if so, split into per-file passes plus one integration pass.

The QA angle: precision is testable, "sounds careful" isn't

Every D4 distinction produces something you can actually assert on. Explicit criteria let a test name which condition failed. A schema lets a test check for a specific null instead of parsing free text for an implied absence. A validation rule is a function you can call directly, independent of the model that triggered it. None of that exists when the standard is "the prompt sounds careful," which is the actual gap between prompt engineering as a craft and prompt engineering as something a QA seat can hold a system accountable to.

Blueprint tie · D4, 20%, Task Statements 4.1–4.6

D4 is tied for the second-heaviest domain on the exam, and every task statement in it resolves to the same question asked six ways: does this system's output survive being checked, by a specific criterion, a schema, a validator, or a second, independent instance, or does it only survive being read once and sounding plausible.

What this does not solve

None of this post's code has run against a live key, same methodology limits as the rest of this capsule. It doesn't measure whether the explicit criteria in Part 1 actually reduce false positives in practice, that requires production data this environment doesn't have. And it doesn't build a real Batch API submission end to end, the shape and constraints described are real and documented, the 500-report sweep is illustrative, not executed.
