The Criteria, the Schema, and the Second Reviewer: What D4 Actually Tests

PeakAndPack's triage and review flows, sharpened four ways: explicit criteria instead of "be conservative," a schema that can't fabricate a bug ID, a retry loop that knows when to stop, and a reviewer with no memory of writing the fix.

CCAR-F for QA · ~8 min read

D4 is the last of the five domain posts, and the domain most likely to be mistaken for "writing good prompts." It's narrower and more mechanical than that: specific criteria over vague adjectives, a schema over free text, a retry that uses the actual error, a reviewer with no stake in the answer already given.

Every example below is Post 01's triage agent or Post 02's CI reviewer, pushed one step further than either post needed to go on its own.

Structured output and few-shot examples, in plain terms: structured output means asking Claude to reply in a fixed, predictable shape, a JSON object with specific named fields, instead of free-form prose, so the reply can be parsed and acted on by code rather than just read by a person. A few-shot example is a worked sample included right in the prompt, a real input paired with the correct output for it, shown to the model before it's asked to handle a new case.

Four things D4 actually asks you to know

4.1 / 4.2 · Precision

Explicit categorical criteria beat "be conservative." Few-shot examples earn their place on ambiguous cases, not easy ones.

4.3 · Structured output

tool_use with a JSON schema eliminates syntax errors, not semantic ones. Nullable fields stop a model from fabricating a value to fill a gap.

4.4 · Validation loops

Retry with the specific error attached, not a repeat of the same prompt. Some failures aren't fixable by retrying at all.

4.5 / 4.6 · Batch & review

The Batch API is for latency-tolerant work only. An independent reviewer catches what a self-review instance won't.

Part 1: a criterion you can point to

"Be conservative" and "only flag high-confidence matches" sound like precision instructions. The guide's finding: neither actually improves precision, because neither says what confidence is built from.

Guess the specific criteria that replace "be confident," before you look

Applied to the triage verdict, a checkable version:

  • The failing endpoint matches the catalog entry exactly.
  • The error status code matches exactly.
  • The failure shares a specific mechanism with the catalog entry, not just a topic. A shared keyword like "price" or "order" is not sufficient on its own.

Flag a match only when at least two of the three hold. A reviewer who disagrees with a verdict can now name which condition the agent got wrong, instead of arguing about what "confident" was supposed to mean.

Few-shot examples earn their place the same way: not by padding a prompt with more instances of the case the model already gets right, but by walking through the case where a surface signal (a shared keyword, a similar-looking endpoint) is actually misleading.

When one category is the problem, fix that category, not everything: a criterion that's noisy on one specific case (say, flagging every discount-code mismatch, even correct ones) erodes trust in every other verdict too, a reviewer who's seen the agent cry wolf on discounts starts second-guessing its refund verdicts as well. Tightening that one criterion, or turning it off while it's reworked, protects trust in the categories that are already reliable. It's a cheaper fix than rewriting the whole prompt while the noisy category is still live.

Part 2: a schema that can't lie by omission

tool_use, in plain terms: instead of asking Claude to type out JSON in plain prose (which it might wrap in a markdown code fence, get syntactically wrong, or leave a field out of), you define the exact shape as a tool and let Claude "call" that tool with matching arguments. The reply arrives well-formed by construction, not because Claude promised to format it correctly. Post 01 hit the plain-prose version of this problem directly, a fenced JSON reply broke a plain JSON.parse call in production, the exact failure mode this pattern avoids.

Task Statement 4.3 (exam guide)'s core distinction: tool_use with a JSON schema eliminates syntax errors, a malformed brace, a missing quote, but it does nothing to stop a semantically wrong answer, a bug ID that doesn't exist, a total that doesn't sum.

{
  matchedBugId: { type: ["string", "null"] },  // nullable on purpose
  confidence: { enum: ["high", "medium", "low", "unclear"] },
  action: { enum: ["file-new", "link-existing",
                    "flag-flaky-retry", "escalate-to-human"] }
}

matchedBugId is explicitly nullable. A required, non-null field here would pressure the model to pick something from the catalog even when nothing actually matches, the exact fabrication the guide's 4.3 skill point warns against. "unclear" in the confidence enum is doing similar work, it's a real, distinct outcome (the tools couldn't resolve this) rather than a synonym for "low" (a match was found but it's shaky).

A fixed enum works here because the action space is genuinely closed, there are only four real verdicts. For a category that isn't closed, a fifth catalog might add a bug class this schema has never seen, the same nullable discipline applies differently: add an "other" value plus a free-text detail field alongside it, so the model can report something real without either fabricating a fit to an existing category or being blocked entirely.

tool_choice: auto, then forced

Early turns stay "auto" so the model can still call search_bug_catalog or check_live_api freely. The final turn forces report_triage_verdict, guaranteeing schema-shaped output instead of drifting prose.

Syntax vs. semantics

The schema guarantees the JSON parses. It says nothing about whether matchedBugId: "BUG-099" refers to a bug that exists, that check still needs to happen downstream.

Part 3: retrying with the actual error, and knowing when to stop

A validation failure is information. Re-sending the exact same prompt after a failed parse throws that information away.

Guess which triage verdict combination is invalid, before you look

{ action: "link-existing", matchedBugId: null }. Linking to an existing bug requires something to link to, the schema's types allow this combination (both fields are individually valid), but the cross-field logic doesn't hold. This is exactly the kind of semantic error tool_use's syntax guarantee doesn't catch on its own.

The fix is a validation pass after parsing, and a retry prompt that names the specific problem: "action is link-existing but matchedBugId is null", not a generic "please try again."

Retry has a ceiling. If the live API and the catalog both come back inconclusive, an endpoint that genuinely no longer exists, no amount of re-prompting produces information that isn't there. That's an escalate-to-human case, not another retry.

One field in d4-validation-retry.ts's TriageVerdict interface isn't for validation at all: detectedPattern. It records which specific criterion actually fired for this verdict, so that when a developer later dismisses a finding as wrong, there's something concrete to check, is this one criterion producing most of the false positives, or is it spread evenly across all three? Without it, a dismissed finding is just a data point, with it, dismissed findings become a pattern you can actually query.

Part 4: overnight batches, and a reviewer who wasn't there

The Batch API, in plain terms: instead of sending one request and waiting for one reply right away, you submit a large stack of requests at once and get all the results back later, often cheaper per request, but with no guarantee of a fast turnaround. It's the right fit only for work where "later today" is an acceptable answer, not for anything a user or another process is actively waiting on.

4.5 and 4.6 both come down to matching the tool to what the task actually tolerates: latency for batching, independence for reviewing.

PeakAndPack's version: d1-triage-agent.ts's live, tool-calling triage cannot batch at all, the Batch API doesn't support mid-request tool calls. Only a nightly sweep using the simpler d1-triage-workflow.ts shape, no tools, one call in, one verdict out, actually qualifies.

Running that sweep for real needs one more piece the qualify/disqualify decision above doesn't cover: each request in a batch carries a custom_id you choose, a scenario's failure text ID, say, so that when results come back unordered, each verdict can be matched to the failure it belongs to. If a handful of requests fail (a malformed input, a document too large), only those specific custom_ids get resubmitted, not the whole batch.

Part 4's second technique, multi-pass review, is really Part 1's attention-dilution problem restated for reviewers instead of criteria: reviewing many files in one pass produces the same file detailed feedback while another gets skimmed, and the same pattern flagged in one file waved through in another. d4-multi-pass-review.md covers the fix, per-file passes for local issues, then one separate integration pass for anything that only shows up looking across files together.

The QA angle

How to test: precision is testable, "sounds careful" isn't

Every D4 distinction produces something you can actually assert on:

  • Explicit criteria let a test name which condition failed.
  • A schema lets a test check for a specific null instead of parsing free text for an implied absence.
  • A validation rule is a function you can call directly, independent of the model that triggered it.

None of that exists when the standard is "the prompt sounds careful," which is the actual gap between prompt engineering as a craft and prompt engineering as something a QA seat can hold a system accountable to.

Applying what we learnt to your own projects

  • A prompt asks the model to "be careful" or "be conservative": that's a request a reviewer can't check, per Part 1, replace it with a short checklist of specific, checkable conditions so a disagreement can point to which one failed.
  • You're parsing a model's plain-text JSON reply with a try/catch and a generic fallback: that's the exact pattern Post 01 got burned by, per Part 2, a tool_use schema guarantees the shape parses, it just doesn't guarantee the content is right, which still needs checking downstream.
  • A retry loop re-sends the same prompt after a failure: per Part 3, that throws away the one piece of information the failure actually gave you, include the specific error, and know when to stop retrying and escalate instead.
  • The same session that wrote a fix is asked to review it: per Part 4, that's a self-review with no independent perspective, a fresh session with no memory of writing the code is more likely to actually question it.
Blueprint tie · D4, 20%, Task Statements 4.1–4.6 (exam guide)

D4 is tied for the second-heaviest domain on the exam, and every task statement in it resolves to the same question asked six ways: does this system's output survive being checked, by a specific criterion, a schema, a validator, or a second, independent instance, or does it only survive being read once and sounding plausible.
