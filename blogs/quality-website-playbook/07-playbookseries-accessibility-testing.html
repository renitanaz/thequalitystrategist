Accessibility testing

A developer builds an accessible template once. An editor breaks it, one missing alt attribute or one skipped heading level at a time, every time they publish, forever after. This post is about the checks that catch that ongoing content-side risk, and about the honest limits of the free tools that automate part of it.

Key takeaways
  • A template's accessibility is a one-time developer concern. Content's accessibility, alt text, heading structure, link wording, is a per-edit concern that never stops.
  • Automated scanners (Lighthouse, axe, WAVE) reliably catch roughly 30-40% of real WCAG issues. The rest need a human, deliberately.
  • A missing form label doesn't look broken. A screen reader announces it as an unlabeled field with no clue what to type.
  • Cross-check at least two automated tools, since they don't all catch the same things, then do one manual pass: keyboard-only, no mouse.

Two accessibility problems, on two different schedules

A template's accessibility, semantic HTML, ARIA where needed, logical tab order, gets built once and reviewed once. An editor's accessibility choices, whether they fill in alt text, whether they use headings in order, whether a link says "read more" or something that means anything out of context, happen every single time content is published, by someone who's rarely thought about screen readers at all.

Why this matters more here than a generic accessibility checklist

Testing a CMS site's accessibility once, at launch, only covers the template. The content layer needs the same ongoing attention Post 1 described for every other kind of content risk, because a perfectly accessible template still produces an inaccessible page the moment an editor uploads an image without alt text.

What automated tools actually catch

Automated tools catch roughly 30-40% of real WCAG issues. That's a strong first pass, not a pass/fail gate. Treat a clean automated scan as "nothing obvious," not "accessible."

The core checks

What a missing label actually sounds like

It's easy to read "missing form label" as a minor technicality. It isn't, once you hear what it actually does to someone using a screen reader.

FieldWith a proper labelWithout one (Grove & Bean's contact form)
Email field"Your email, edit text""Edit text, blank"
Message field"Your message, edit text""Edit text, blank"

Placeholder text disappears the moment someone starts typing, and most screen readers don't reliably announce it as a label in the first place. A sighted user glances at the greyed-out hint text and moves on. A screen reader user gets three identical, contentless "edit text, blank" announcements in a row and has to guess.

Try it: audit the demo site with two tools

Try it

Install the axe DevTools browser extension, and separately try WAVE. Run both against the Grove & Bean contact page and compare what each one flags.

Then close the mouse entirely. Using only Tab, Shift+Tab, and Enter, try to navigate from the homepage to the contact form and fill it in. Notice whether you can ever tell which element currently has focus.

Check your findings against demo-site/seeded-issues.md, the A11Y-1 through A11Y-6 entries.

Your deliverable

A short comparison: which of the six A11Y issues axe caught, which WAVE caught, and which one only showed up during the keyboard-only pass. Note any issue neither automated tool flagged.

Time: ~25 minutes.
