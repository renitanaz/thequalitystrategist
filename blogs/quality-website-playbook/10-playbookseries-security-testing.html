Security testing

Most of a CMS site's attack surface isn't code anyone on the team wrote. It's every plugin, theme, and integration installed with a single click, each one a separate codebase with its own vulnerabilities and its own update schedule, none of it reviewed the way the team's own code would be.

Key takeaways
  • Every installed plugin or theme is a separate codebase with its own vulnerabilities. "We didn't write it" doesn't mean the team isn't responsible for testing it.
  • Access control needs a security-level check beyond Post 2's workflow check: not just "is the button hidden" but "is the endpoint actually unreachable" for a role that shouldn't have it.
  • Any field that accepts rich text or raw HTML is a potential stored-injection point if it isn't sanitized on save or render.
  • Session handling deserves a QA-level check too: does logout actually invalidate the session, and are sensitive actions re-confirmed rather than trusted from an old login.
  • Missing HTTP security headers (CSP, X-Frame-Options, and similar) don't break anything visible, but a free scan catches them in about ten seconds.

The attack surface grows with every plugin

A hand-coded site has one codebase, reviewed by the team that owns it. A CMS site, especially WordPress, typically runs a dozen or more third-party plugins and a theme, each maintained independently, each capable of introducing a vulnerability the core CMS itself has nothing to do with.

Why this matters for QA, not just for whoever manages hosting

A plugin update landing without anyone testing it is exactly the same content/code separation problem from Post 1, except this time the "editor" publishing an untested change is the plugin's own maintainer, and the change ships to the site automatically the moment auto-update runs.

Access control: a security check, not just a workflow check

Post 2 tested whether a Contributor's publish button is genuinely absent. Security testing asks the sharper version of that question: even without the button, can that role still reach the underlying action directly?

CheckWhat it catches
Direct URL access to an admin screen while logged in as a lower roleA missing server-side permission check, relying only on the UI hiding the link
Direct API/REST endpoint calls with a lower-privilege tokenThe same gap, reachable programmatically instead of by URL
Editing or deleting another user's content by IDOwnership checks that verify the content type but not who created it

"The button isn't there" is a UI decision. "The action is rejected" is a security control. Only the second one is real access control. Test the underlying action directly, not just whether the UI offers it.

Content fields as an injection point

Any field that accepts rich text, or raw HTML, is a place where content and code blur together again, the same theme from Post 1, now with a security angle. If the CMS doesn't sanitize that field on save or on render, whatever an editor (or an attacker with editor-level access) enters can execute as real markup or script in every visitor's browser.

Why this is worth testing directly, not assuming the CMS handles it

Sanitization behavior varies by field type, by role, and by CMS version, a title field and a rich-text body field are often sanitized differently, and a change to either during an update can silently reintroduce a gap that was previously closed. The only way to know is to actually enter markup and check what comes back out, not to assume "modern CMS platforms handle this."

HTTP security headers: a ten-second check

Response headers like Content-Security-Policy, X-Frame-Options, and Strict-Transport-Security tell a browser how to treat a page defensively, whether it can be embedded in an iframe elsewhere, whether it will only load over HTTPS, what sources of script it will trust. A CMS's default hosting setup often ships with few or none of these configured.

Why this belongs in a QA pass, not just a hosting checklist

Missing headers don't break anything a functional test would catch, the page renders fine either way. They're a real gap all the same: a missing X-Frame-Options header, for instance, is what makes a page embeddable in a malicious iframe for a clickjacking attack. securityheaders.com checks a live URL against all of them in about ten seconds and grades the result, faster than checking each header by hand.

Try it: test access control, sanitization, and headers

Try it

In your WordPress Playground instance, log in as the Contributor account from Post 2. While logged in as that role, try navigating directly to wp-admin/plugins.php by typing the URL. Note whether you're blocked or whether the page partially loads.

Back in the admin account, create a new post and, in the body field, enter <script>document.title='test'</script> as literal text, then save and view the published post. Check whether the page title actually changed, which would mean the script executed, or whether it rendered as inert text or was stripped entirely.

Log out, then use the browser's back button to return to a page that required being logged in. Note whether it shows cached content or correctly forces a re-login.

Separately, since Playground's sandbox has no real public URL to scan, run securityheaders.com against any real site you maintain or have permission to test, and note which headers, if any, are missing.

Your deliverable

A short table: the four checks above (admin URL access as Contributor, script tag in post body, back-button after logout, security-headers scan), and for each, what actually happened versus what you expected.

Time: ~25 minutes.
