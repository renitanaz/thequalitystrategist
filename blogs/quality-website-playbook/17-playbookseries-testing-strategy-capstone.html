Bringing it together: the quality website strategy

Post 1 promised this diagram would turn into a full checklist by the end. Sixteen posts later, here it is: every check from this series, mapped onto the four SDLC phases where it actually has to happen to catch something before it matters.

By RN ~8 min read Capstone reference

Key takeaways
  • Content-layer risk concentrates in Pre-release and Post-release, exactly the phases a code-only test plan is least likely to cover on a recurring basis.
  • Plan and Build checks differ by CMS. Pre-release checks are close to identical regardless of what generated the page, that's what makes this strategy transferable.
  • This checklist isn't meant to be run once. Pre-release and Post-release checks recur every time meaningful content changes, not just at launch.
  • The underlying idea to keep, beyond any individual checklist item: a CMS site is two layers on two schedules, and most testing gaps live in the seam between them.

The strategy, by SDLC phase

Plan

  • Content model reviewed for required fields, especially ones that feed SEO and accessibility (alt text, meta description) (Post 2)
  • Roles and permissions defined and verified by logging in as each role, not read off a chart (Post 2)
  • URL structure and SEO strategy decided before content exists, redirect policy included (Post 6)

Build

  • Templates tested against content edge cases: empty fields, long text, special characters, zero and single-item lists (Post 3)
  • Shared components tested once, thoroughly, not once per page they appear on (Post 3)
  • Content API tested directly: status codes, response shape, pagination, auth on write endpoints (Post 4)
  • Webhooks tested for the receiver-down case, not just the happy path (Post 4)
  • Headless setups: preview integration verified, multi-channel content constraints checked, contract tested by changing a field and observing the front end (Post 5)
  • Access control tested at the endpoint level, not just the UI level; content fields tested for injection (Post 10)

Pre-release

  • Title uniqueness, meta descriptions, canonical tags, structured data (Post 6)
  • robots.txt and sitemap.xml checked directly, broken links crawled, favicon and social-share preview confirmed (Post 6)
  • Alt text, form labels, contrast, heading hierarchy, keyboard focus, cross-checked with two automated tools plus a manual keyboard pass (Post 7)
  • Core Web Vitals (LCP, INP, CLS), image dimensions set, third-party scripts reviewed for blocking behavior, load capacity considered separately from single-visitor speed (Post 8)
  • Analytics verified with DebugView or a network-request check, not just visual snippet presence; event tracking checked separately from page-view tracking (Post 9)
  • HTTP security headers scanned before launch (Post 10)
  • Layout checked at mobile, tablet, and desktop widths backed by real usage-share data, not just desktop (Post 11)
  • Forms tested for validation, spam handling, delivery, and error states, specifically what happens after submit (Post 12)
  • RTL and translation fallback tested on the actual front end; dates and times checked under a timezone override, not just the local one (Post 13)
  • Consent gates verified to block scripts before consent, not just display a banner; Privacy Policy link reachability checked (Post 14)

Post-release

  • Staging environments matched on representative content, not just code; content freeze observed during sign-off windows (Post 15)
  • Live URL checked directly before calling anything released, preview isn't proof (Post 15)
  • Old-domain URLs audited with an extractor before migrating, not just the CMS's own page list (Post 16)
  • Migrations reconciled by count, sampled across content age and type, not just the newest content (Post 16)

Why the phases carry unequal weight

Plan and Build differ meaningfully depending on the CMS: WordPress, a headless setup, and something in-house each carry different Plan and Build risks. Pre-release is where this strategy earns its platform-agnostic claim, SEO, accessibility, performance, analytics, and the rest are close to identical regardless of what generated the page.

Pre-release and Post-release deserve the most recurring attention. They're where content-layer risk concentrates, and they're the two phases a code-only test plan is least likely to cover on an ongoing basis, since nothing about a content edit triggers a build or a deploy.

One operational note worth carrying into how a team actually works, not just what gets tested: accessibility and analytics checks land more reliably when they're written into a user story's acceptance criteria up front, rather than treated as a separate audit bolted on after a feature is already built.

The one idea worth keeping

Every specific check in this series traces back to the same root idea from Post 1: a CMS splits a website into a code layer and a content layer, on two different schedules, owned by two different kinds of people, with no shared review gate between them.

A checklist goes stale. A new CMS feature, a new plugin category, a new regulation will eventually add a check this series didn't anticipate. The content/code split, and the SDLC map built on top of it, won't. Handed a CMS this series never mentioned, that's the framework that still tells you where to look first.
