Localization and multi-language testing

Adding a second language to a CMS site is rarely a clean, complete switch. It's usually a partial one: some pages translated, some not, an admin interface that flips direction cleanly while the actual site half-does. Testing localization means testing that gap, not just checking whether the words changed.

Key takeaways
  • A CMS's content model rarely has native per-locale fields by default, translation is usually bolted on by a plugin, with its own gaps.
  • What happens when a page hasn't been translated yet matters as much as the translation itself: a broken link, a blank page, or a silent fallback with no indication.
  • WordPress's admin dashboard flips to RTL automatically for RTL languages, a core feature. The public-facing site only does if the active theme explicitly supports it.
  • Dates, currency, and numbers format differently by locale. Content pulling raw values without locale-aware formatting shows the wrong format to the wrong audience.
  • Chrome DevTools' Sensors panel can override the browser's reported timezone directly, letting date and time formatting be tested for a specific zone without a second device.

Translation is usually bolted on, not built in

Most CMS platforms, WordPress included, aren't multilingual out of the box. Adding a second language typically means adding a plugin that duplicates content per language, with its own workflow for keeping translations in sync as the original changes.

RTL: the admin and the site test differently

WordPress core genuinely supports right-to-left languages, no plugin required. Switching the Site Language setting to Arabic or Hebrew flips the entire admin dashboard to RTL automatically. That's a real, built-in feature, and it's easy to test.

Why testing only the admin gives false confidence

It's easy to switch the site language, see the admin dashboard flip cleanly to RTL, and conclude "RTL works." That only proves WordPress core handles RTL, which was never in question. The actual visitor-facing site depends entirely on whether the theme includes RTL-specific CSS, and plenty of themes, especially simple or custom-built ones, don't. That gap only shows up by checking the public page directly, not the dashboard.

Try it: test the RTL gap directly

Try it

In your WordPress Playground instance, go to Settings → General and change Site Language to Arabic (العربية) or Hebrew (עברית). Save, and confirm the admin dashboard immediately flips to a right-to-left layout.

Then open the public-facing site (the front end, not the dashboard) in a new tab. Compare the text direction and layout mirroring against the admin. Note whether the theme actually followed, or whether the front end still reads left-to-right despite the language setting.

Dates and times: overriding the timezone directly

A date or timestamp rendered without locale awareness shows the wrong convention to the wrong audience, and a scheduled-publish time evaluated in the wrong timezone can put content live an hour early or late. Both are testable without needing a second physical device or account.

Why DevTools can test this directly

Chrome DevTools can override the browser's reported timezone entirely, so a page's date and time formatting can be checked as if the visitor were actually in that timezone, without changing the operating system's real clock.

Open DevTools (F12), open the Command Menu (Ctrl/Cmd+Shift+P), type "Sensors," and open the Sensors panel. Under Location, set a custom timezone (for example, America/New_York or Asia/Kolkata) and reload the page to see any date or time on it recalculated for that zone.

Your deliverable

A short note: whether the admin and the public site matched in RTL behavior, and if not, exactly which visual elements (navigation, text alignment, icon placement) stayed left-to-right when they shouldn't have. Separately, note one date or timestamp on any real site you test that would display differently, or ambiguously, under a different timezone override.

Time: ~20 minutes.
