API and integration testing

A CMS's content isn't only consumed by the page you're looking at. The same data usually reaches a mobile app, a partner integration, or a marketing tool through an API most testers never open. This post is about testing that contract directly, instead of only the one page that happens to render it.

Key takeaways
  • A CMS's content API is a separate contract from its rendered pages, consumed by mobile apps, integrations, and other front ends that a UI test never touches.
  • Test status codes, response shape, field types against the content model, pagination, and auth on write endpoints, directly against the API.
  • Webhooks are fire-and-forget by default: if the receiver is down, the event is often silently lost unless retries are explicitly configured.
  • An integration usually breaks from a content-side change, a renamed field or altered response shape, not from the integration's own code.

The page is not the only consumer

It's easy to test a CMS by testing the pages it renders and stop there. But most CMS platforms, headless or not, expose a content API alongside the pages: WordPress ships a REST API by default, Strapi's entire purpose is the API, and even a hand-built site often has a mobile app or a partner feed pulling the same content a different way.

Each of those consumers gets data straight from the API, with no template to catch or mask a problem. A bug that a page's CSS quietly hides can be a hard crash in a mobile app reading the raw JSON.

"Who else reads this API?" is worth asking before testing starts. A mobile app, a partner feed, and an internal dashboard can all depend on the same endpoint without any of them appearing in a sitemap.

What to test directly against the API

CheckWhat it catches
Status codesA 200 with an error message in the body, instead of an actual 4xx/5xx, breaks any consumer that checks status before parsing
Response shapeA field that's sometimes a string and sometimes an array (common when a field is optional) crashes strictly-typed consumers
Field types match the content modelA "required" field the model promises but the API returns as null anyway
PaginationAn endpoint that silently caps results at a default page size, with a consumer that assumed it got everything
Auth on write endpointsA create, update, or delete endpoint reachable without a valid token, or reachable with a token scoped for something else
Error response shapeWhether a 400 or 500 returns a consistent, parseable error body, or an inconsistent one depending on what failed
Why this needs its own test, not just a page-level check

A page that renders correctly proves the template handled whatever the API returned. It doesn't prove the API returned the right thing, only that the template was defensive enough to cover for it.

Testing the API directly, with a tool like Postman, curl, or Strapi's own admin panel, removes the template as a variable and shows exactly what every consumer actually receives.

Webhooks: fire, and rarely check what happened

A webhook is the CMS notifying another system the moment something happens, a post published, an entry updated, by sending it an HTTP request. It's how a CMS pushes data out instead of waiting for something to pull it.

Why "it worked when I tested it" doesn't cover webhooks

A webhook demo almost always tests the happy path: receiver is up, request succeeds, done. That proves the webhook fires. It says nothing about what happens the one time the receiving system is deploying, rate-limiting, or simply down.

Whether that failure is retried, logged anywhere visible, or silently dropped is a configuration detail, not a given, and it's usually the actual root cause when "the integration randomly misses events" gets reported weeks later.

Third-party integrations: what actually breaks them

An integration rarely breaks because its own code changed. It breaks because something upstream, in the content side, changed underneath it.

Change on the content sideHow the integration breaks
A field gets renamed in the content modelThe integration's mapping still references the old field name and silently gets null
A field's type changes (single value to a list)The integration's parser expects the old shape and throws, or worse, half-processes it
An API token expires or is regeneratedEvery request from that integration starts failing auth, often without a clear error surfaced to anyone
Rate limits are added or tightenedAn integration that used to sync fine starts silently dropping requests during high-traffic periods

Test integrations from the content side, not just the integration's side. Change a field name or type in a test environment and watch what happens downstream, rather than only testing the integration in isolation with data that never changes.

Try it: test a real content API

Try it

Install Strapi locally with its quickstart command, it sets up a free, self-hosted instance with a SQLite database, no separate server needed:

npx create-strapi-app@latest my-project --quickstart

In the admin panel, create a content type called "Article" with a title, a body, and a required featured image field. Publish two or three entries, then in Settings, enable public read access for the Article API under Roles.

Hit the REST endpoint directly in your browser or curl: http://localhost:1337/api/articles. Check the response against the table above: does the status code make sense, does every field match what the content type defines, and what happens if you request a page number past the last one?

Your deliverable

A short list of the real consumers (mobile app, partner feed, internal tool, or hypothetical ones if none exist yet) that would read a CMS's content API, and one specific thing each would break on if the API's response shape changed unexpectedly.

Time: ~25 to 35 minutes, most of it the Strapi setup.
