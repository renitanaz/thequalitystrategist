Six Capstone Projects

No new concepts in this phase, only application. Six independent projects against PeakAndPack, each one drawing on a different stretch of Phases 0 through 14. Do as many as are relevant to where you want to go next: automation engineer, SDET, or automation lead.

How to use this phase

Each earlier phase practised one skill on its own. A real suite needs them working together, and the gaps only show up where they meet. These projects are where that happens.

Each project names three things:

  • What to build
  • What "done" looks like
  • Which earlier phases it draws on most

None of them has a single correct answer the way earlier assignments did. There are approach notes for all six after the projects, but the point is applying judgment across a full project, not matching a reference answer.

1Full page-object-model rebuild
Draws on: Phase 9, Phase 2, Phase 1

Take every test you've written across the series and rebuild it on top of a proper page object layer: one class per PeakAndPack page (Product listing, Cart, Checkout, Login), each exposing actions and results while keeping its locators inside, so no test file touches a raw locator directly.

Done looks like: every spec file reads as user actions and assertions only, page objects hold all the locators, and adding a new test for an existing page needs zero new locator work.

2Visual regression coverage
Draws on: Phase 11, Phase 4

Add baseline screenshots for the product listing, cart, and checkout pages, at both desktop and mobile width. Capture the current state of the negative-price and unnamed-product bugs as part of the baseline. Don't wait for them to be fixed before tracking visual regressions elsewhere on the page.

Done looks like: a visual regression suite that fails on an unintended layout change and stays quiet on the two known, already-tracked bugs.

3CI pipeline with flaky-test quarantine
Draws on: Phase 12, Phase 4

Set up GitHub Actions to run the full suite on every PR, sharded for speed. Then make Phase 12's quarantine list automatic: a nightly job that counts how often each test was flaky, moves a test onto the list on its third time, never quarantines a @critical test, and opens an issue for each one it moves.

Done looks like: a PR can't merge on a genuine failure, but a known-flaky test doesn't block merges either, and every quarantined test has an open issue saying why.

4An AI-reviewed suite pass
Draws on: Phase 13

Run every spec file in your suite through the Phase 13 reviewer prompt, all six rules. Document every finding, which ones you fixed, and which ones you decided not to and why (not every finding deserves a fix; that judgment call is the point). For the tests you trust least, run the mutation check as well.

Done looks like: a written record showing the suite was reviewed against a stated standard, not just "looks fine to me."

5An accessibility-integrated test pass
Draws on: the Shift-Left Accessibility series, Phase 2

Add automated accessibility checks (axe-core, per the Shift-Left Accessibility series' Blog 32) to your PeakAndPack suite, running alongside the functional assertions, not as a separate suite. Check the product listing, login form, and checkout flow.

Done looks like: a CI run that fails on a genuine WCAG violation the same way it fails on a broken checkout, one pipeline, one bar.

6A capstone report on the suite's architecture
Draws on: Phase 14, all prior phases

Write the document you'd hand a new senior hire on day one: what the suite tests and why, the conventions from Phase 14, the known bugs it's designed to catch (with bug IDs), what's deliberately out of scope, and what you'd do differently starting over.

Done looks like: someone who has never seen this suite could read the report and know where to add their first test without asking you a single question.

Show approach notes for all six: try them yourself first

These notes come from building the six against PeakAndPack. Where a number appears, I ran it.

What tends to go wrong in each

Project 1: the most common mistake is a page object that just wraps locators one-to-one with no real actions (getEmailField() instead of login(email, password)). A good page object hides the steps, not just the selectors. Measure "done" instead of feeling it: count the locator calls inside tests/. The goal is zero.

# Git Bash, macOS or Linux: count the locator calls inside the tests folder
grep -rEo "\.(getBy[A-Za-z]+|locator)\(" tests | wc -l

# Windows PowerShell
(Get-ChildItem tests -Recurse -Filter *.ts | Select-String -Pattern '\.(getBy\w+|locator)\(' -AllMatches |
  ForEach-Object { $_.Matches.Count } | Measure-Object -Sum).Sum

PeakAndPack's own end-to-end suite has the page objects but not the zero: it has 43 locator calls inside its tests against 31 inside its page objects. Most are in the admin panel tests (10, the panel has no page object yet), the auth tests (12) and the browse tests (9). That list is the project's work, in the order to do it.

Project 2: baselining a bug feels wrong the first time you do it. It isn't: the baseline records current reality, and updating it when BUG-001 (the negative price) and BUG-002 (the empty name) get fixed is a one-line change, not a redesign. Assert that the bugs are on screen before the screenshot, so the baseline cannot silently start recording a page that has lost them. I ran the three pages at desktop width and on an emulated phone: each of the six baselines was written on the first run and passed on the second.

// tests/visual-pages.spec.ts: the three pages, with the two known data bugs on screen
import { test, expect } from '../fixtures';
import { stubImages } from '../helpers/visual';

test('product listing', async ({ page }) => {
  await stubImages(page);
  await page.goto('/');
  await expect(page.getByTestId('product-card').first()).toBeVisible();
  await expect(page.getByText('$-89.00')).toBeVisible();            // the negative price is part of the baseline
  await expect(page.getByText('(no name)').first()).toBeVisible();   // and so is the product with no name
  await expect(page).toHaveScreenshot('listing.png', { fullPage: true, maxDiffPixels: 100 });
});

test('cart page', async ({ seededCart, loggedInPage }) => {
  await stubImages(loggedInPage);
  await seededCart.goto();
  await expect(loggedInPage.getByText('Trekking Poles (Pair)')).toBeVisible();
  await expect(loggedInPage).toHaveScreenshot('cart.png', { fullPage: true, maxDiffPixels: 100 });
});

test('checkout page', async ({ seededCart, loggedInPage }) => {
  await stubImages(loggedInPage);
  await seededCart.goto();
  await seededCart.proceedToCheckout();
  await expect(loggedInPage.frameLocator('iframe[title="Payment form"]').getByLabel('Card number')).toBeVisible();
  await expect(loggedInPage).toHaveScreenshot('checkout.png', { fullPage: true, maxDiffPixels: 100 });
});

Three things from Phase 11 matter here. Baselines belong to an operating system, so make the ones CI uses in CI. Stub the product images, or the outside host decides what your baseline looks like. And keep the pixel allowance small: a percentage tolerance on a full page would let a whole card change colour and still pass.

Project 3: quarantine only works if something forces a review of what's in it. A quarantine list that only grows is worse than no quarantine: it hides real regressions behind old, ignored ones. That's why each quarantined test gets an issue. One way to build it, in two pieces:

A script that reads the JSON report after each nightly run (add ['json', { outputFile: 'results.json' }] to the config's reporters, and install tsx with npm install -D tsx to run it). One detail decides whether @critical tests are really protected: in the JSON report, a spec's tags are written without the @ (critical), and a test tagged with Phase 12's tag option has no tag in its title at all. A check like title.includes('@critical') never matches, so a flaky critical test would be quarantined. Read the tags instead:

// scripts/quarantine-flaky.ts
// Reads the JSON report from the last run, counts which tests were flaky,
// and moves any test that has now been flaky THRESHOLD times into quarantine.json.
import fs from 'fs';

const THRESHOLD = 3; // flaky runs before a test is quarantined

// In the JSON report, a spec's tags are written without the @: '@critical' appears as 'critical'
type Spec = { title: string; tags?: string[]; tests: { status: string }[] };
type Suite = { specs?: Spec[]; suites?: Suite[] };
type Flaky = { title: string; critical: boolean };

// 'flaky' is Playwright's status for a test that failed, then passed on retry
function flakyTests(suite: Suite): Flaky[] {
  const here = (suite.specs ?? [])
    .filter((spec) => spec.tests.some((t) => t.status === 'flaky'))
    .map((spec) => ({ title: spec.title, critical: (spec.tags ?? []).includes('critical') }));
  // Suites nest (file > describe > describe), so walk the children too
  return here.concat(...(suite.suites ?? []).map(flakyTests));
}

const report = JSON.parse(fs.readFileSync('results.json', 'utf8'));
const flaky: Flaky[] = report.suites.flatMap(flakyTests);

// Keep a running count per test, across CI runs, and remember which ones are critical
const historyFile = 'flaky-history.json';
const history: Record<string, { count: number; critical: boolean }> = fs.existsSync(historyFile)
  ? JSON.parse(fs.readFileSync(historyFile, 'utf8'))
  : {};
for (const { title, critical } of flaky) {
  history[title] = { count: (history[title]?.count ?? 0) + 1, critical };
}
fs.writeFileSync(historyFile, JSON.stringify(history, null, 2));

// Past the threshold goes into quarantine, except @critical tests:
// a flaky critical test keeps blocking, because someone needs to look at it now
const quarantineFile = 'quarantine.json';
const quarantine: string[] = fs.existsSync(quarantineFile)
  ? JSON.parse(fs.readFileSync(quarantineFile, 'utf8'))
  : [];
const newlyQuarantined = Object.entries(history)
  .filter(([title, { count, critical }]) => count >= THRESHOLD && !critical && !quarantine.includes(title))
  .map(([title]) => title);
fs.writeFileSync(quarantineFile, JSON.stringify([...quarantine, ...newlyQuarantined], null, 2));

// Print the new ones so the workflow can open an issue for each
console.log(JSON.stringify(newlyQuarantined));
Explain this code, line by line
  • THRESHOLD = 3 is how many flaky nights it takes to quarantine a test. Change it to suit your suite.
  • The type lines describe the shape of the JSON report: suites hold specs, specs have a title, tags and tests. tags? with the question mark means a spec may have none.
  • flakyTests walks the report and returns the title of every spec whose test status is flaky (failed, then passed on retry, Phase 4), with whether it is critical. It calls itself on the child suites, because a suite can hold suites.
  • history is a file that remembers a count per test between nightly runs. Each flaky test gets one more, and its critical flag is stored beside it.
  • The filter keeps a test only if its count has reached the threshold, it is not critical, and it is not already in the list. !critical is what keeps a flaky @critical test blocking merges.
  • console.log(JSON.stringify(newlyQuarantined)) prints the new titles as data, so the next workflow step can read them and open an issue for each.

I ran it on a report where three tests were flaky: two @regression tests and the @critical checkout test. After three nightly runs, the two regression tests were in quarantine.json and the checkout test, flaky three times, was left in the gate. The first run printed nothing new, the second nothing, and the third printed the two titles.

And a nightly job that runs it, saves the lists and opens the issues:

# In .github/workflows/playwright.yml, alongside the test jobs
  quarantine-check:
    if: github.event_name == 'schedule'  # nightly only
    runs-on: ubuntu-latest
    permissions:
      contents: write  # to commit the updated lists
      issues: write    # to open an issue per quarantined test
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test --project=gate
        continue-on-error: true  # still read the report when tests fail

      - name: Quarantine tests that keep flaking
        id: quarantine
        run: echo "new=$(npx tsx scripts/quarantine-flaky.ts)" >> "$GITHUB_OUTPUT"

      - name: Commit the updated lists
        run: |
          git config user.name "flaky-bot"
          git config user.email "flaky-bot@users.noreply.github.com"
          git add quarantine.json flaky-history.json
          git commit -m "Update flaky test quarantine" || echo "Nothing changed"
          git push

      - name: Open an issue for each newly quarantined test
        env:
          GH_TOKEN: ${{ github.token }}
          NEW: ${{ steps.quarantine.outputs.new }}
        run: |
          echo "$NEW" | jq -r '.[]' | while read -r title; do
            gh issue create --title "Quarantined flaky test: $title" \
              --body "Flaky in 3 nightly runs, so it no longer blocks merges. Find the root cause, fix it, and remove it from quarantine.json."
          done

The job pushes to your main branch, so branch protection has to allow the Actions bot to push, or you can have it open a pull request instead. I parsed this workflow as YAML and ran the script locally, but I have not run the job on GitHub: the first nightly run is the real test, including the git push, the jq step and the issue creation. It also assumes the gate and quarantine projects from Phase 12's config.

Project 4: use all six rules of Phase 13's reviewer prompt, and add the mutation check for the tests you trust least. The value is in the "decided not to fix" column as much as the fixes. A reviewer that agrees with every finding without pushback hasn't actually exercised judgment. Record, for each test you audited, the break you tried and whether it went red.

Project 5: the failure mode is running the accessibility check as a separate, ignorable job. If it doesn't block the same way a broken login blocks, it will get muted the first time it's inconvenient. I scanned the pages the project names, and added the register form and cart. Failing on serious and critical violations only:

PageSerious or criticalModerate (backlog)
Product listcolor-contrast on 9 elements: the grey line under each product is #888 on white, 3.54:1heading order, no main landmark, content outside landmarks
Login formlabel (critical) on 2 fieldsno main landmark, content outside landmarks
Register formlabel (critical) on 3 fieldssame
Cartnonesame
Checkoutnonesame

The login and register findings are the same defect that sent your tests to input[type="email"] back in Phase 2: the labels are not linked to their fields, so getByLabel can't find them, and a screen reader can't announce them either. A test hack and a real accessibility bug had the same cause. Each page that fails today becomes a test marked test.fail(), so the pipeline stays green while the bug exists and goes red when it is fixed:

// tests/a11y/forms.spec.ts: one scan per page, in the same run as everything else
import { test, expect } from '../../fixtures';
import AxeBuilder from '@axe-core/playwright';

for (const { name, path } of [{ name: 'login form', path: '/login' }, { name: 'register form', path: '/register' }]) {
  test(`the ${name} has no serious accessibility violations`, { tag: ['@a11y', '@known-bug'] }, async ({ page }) => {
    test.fail();   // the labels aren't linked to their fields: axe reports 'label' as critical
    await page.goto(path);
    await expect(page.getByRole('button').first()).toBeVisible();
    const results = await new AxeBuilder({ page }).analyze();
    const serious = results.violations.filter((v) => v.impact === 'critical' || v.impact === 'serious');
    expect(serious.map((v) => `${v.id} (${v.impact}): ${v.nodes.length} element(s)`)).toEqual([]);
  });
}

Project 6: the report is often written for yourself, dense with context only you have. Test it by having someone unfamiliar with the project read it and try to answer "where would my first test go" from the document alone. Here is an outline, filled in with the facts of PeakAndPack's suite so you can see the level of detail. Section 6 is the one only you can write:

# PeakAndPack end-to-end suite: architecture report

## 1. What the suite tests, and why
39 tests across eight areas: smoke (3), shop (13: browse 5, cart 4, checkout 4), auth (5), api (8), admin (2),
known-bugs (6), a11y (1), mobile (1). The weight is on the journeys where a bug costs money or trust: checkout,
login, and the cart. The API tests carry the rules (status codes, validation, who may see what), because a rule
belongs where it is enforced.

## 2. Conventions
See CONTRIBUTING.md. In short: role/label/text locators, no sleeps, every test tagged, every test owns its data.

## 3. What it is designed to catch: the known bugs
| Bug | Where | Test |
|---|---|---|
| BUG-008 no stock check | checkout | known-bugs: an out-of-stock product cannot be ordered |
| BUG-009 SAVE10 = 100% off | checkout | known-bugs: a 10% discount code takes 10% off |
| BUG-010 everyone's orders | /api/orders | known-bugs: a customer's order list shows only their own |
| Negative price, empty name | catalogue | known-bugs, plus the visual baseline |
| Colour contrast, unlinked labels | UI | a11y |

## 4. What is deliberately out of scope
Security testing beyond access control, performance, and the native app. Not because they don't matter: because
this suite answers "does the store work", and each of those needs its own approach.

## 5. Where to add your first test
A new journey: tests/<area>/, using the fixtures. A new rule: tests/api/. A new bug: tests/known-bugs/, marked test.fail().

## 6. What I would do differently
(Yours to write. This is the section that shows judgement.)

Series complete

Playwright: Zero to Architect is done. You've gone from a hardcoded URL and a CSS selector in Phase 0 to a suite with conventions, CI, AI-assisted review, and a documented architecture. Every phase built on the one before it: locators fed assertions, assertions fed debugging, page objects fed fixtures, and all of it fed the leadership and capstone work here. The bugs seeded into PeakAndPack (the negative price, the empty product name, the discount-code miscalculation tracked as BUG-009, the order-history authorization gap, the colour-contrast and unlinked-label accessibility defects) were never the point on their own, they were the proof, at every phase, that the tests you were writing could actually tell the difference between working and broken.
