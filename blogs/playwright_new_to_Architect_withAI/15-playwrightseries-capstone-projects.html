Six Capstone Projects

No new concepts in this phase, only application. Six independent projects against PeakAndPack, each one drawing on a different stretch of Phases 0 through 14. Do as many as are relevant to where you want to go next: automation engineer, SDET, or automation lead.

How to use this phase

Each project below names what to build, what "done" looks like, and which earlier phases it draws on most. None of them have a single correct solution the way earlier phases' assignments did, there's a suggested approach in each collapsible solution, but the point is applying judgment across a full project, not matching a reference answer.

1Full page-object-model rebuild
Draws on: Phase 9, Phase 2, Phase 1

Take every test you've written across the series and rebuild it on top of a proper page object layer: one class per PeakAndPack page (Product listing, Cart, Checkout, Login), each exposing actions and locators, no test file touching a raw locator directly.

Done looks like: every spec file reads as user actions and assertions only, page objects hold all the locators, and adding a new test for an existing page needs zero new locator work.

2Visual regression coverage
Draws on: Phase 11, Phase 4

Add baseline screenshots for the product listing, cart, and checkout pages, at both desktop and mobile width. Capture the real, current state of the negative-price and unnamed-product bugs as part of the baseline, don't wait for them to be fixed to start tracking visual regressions elsewhere on the page.

Done looks like: a visual regression suite that fails on an unintended layout change and stays quiet on the two known, already-tracked bugs.

3CI pipeline with flaky-test quarantine
Draws on: Phase 12, Phase 4

Set up GitHub Actions to run the full suite on every PR, sharded for speed. Add a quarantine mechanism: a test that fails intermittently gets tagged @quarantine and moves to a separate, non-blocking job instead of being deleted or ignored.

Done looks like: a PR can't merge on a genuine failure, but a known-flaky test doesn't block merges either, and there's a visible list of what's in quarantine and why.

4An AI-reviewed suite pass
Draws on: Phase 13

Run every spec file in your suite through the Phase 13 reviewer prompt. Document every finding, which ones you fixed, and which ones you decided not to and why (not every finding deserves a fix; that judgment call is the point).

Done looks like: a written record showing the suite was reviewed against a stated standard, not just "looks fine to me."

5An accessibility-integrated test pass
Draws on: the Shift-Left Accessibility series, Phase 2

Add automated accessibility checks (axe-core, per the Shift-Left Accessibility series' Blog 32) to your PeakAndPack suite, running alongside the functional assertions, not as a separate suite. Check the product listing, login form, and checkout flow.

Done looks like: a CI run that fails on a genuine WCAG violation the same way it fails on a broken checkout, one pipeline, one bar.

6A capstone report on the suite's architecture
Draws on: Phase 14, all prior phases

Write the document you'd hand a new senior hire on day one: what the suite tests and why, the conventions from Phase 14, the known bugs it's designed to catch (with bug IDs), what's deliberately out of scope, and what you'd do differently starting over.

Done looks like: someone who has never seen this suite could read the report and know where to add their first test without asking you a single question.

Show approach notes for all six — try them yourself first

What tends to go wrong in each

Project 1: the most common mistake is a page object that just wraps locators one-to-one with no real actions (getEmailField() instead of login(email, password)). A good page object hides the steps, not just the selectors.

Project 2: baselining a bug feels wrong the first time you do it. It isn't, the baseline records current reality, and updating it when BUG-011 gets fixed is a one-line change, not a redesign.

Project 3: quarantine only works if something forces a review of what's in it. A quarantine list that only grows is worse than no quarantine, it hides real regressions behind old, ignored ones.

Project 4: the value is in the "decided not to fix" column as much as the fixes. A reviewer that agrees with every finding without pushback hasn't actually exercised judgment.

Project 5: the failure mode is running the accessibility check as a separate, ignorable job. If it doesn't block the same way a broken login blocks, it will get muted the first time it's inconvenient.

Project 6: the report is often written for yourself, dense with context only you have. Test it by having someone unfamiliar with the project read it and try to answer "where would my first test go" from the document alone.

Series complete

Playwright: Zero to Architect is done. You've gone from a hardcoded URL and a CSS selector in Phase 0 to a suite with conventions, CI, AI-assisted review, and a documented architecture. Every phase built on the one before it: locators fed assertions, assertions fed debugging, page objects fed fixtures, and all of it fed the leadership and capstone work here. The bugs seeded into PeakAndPack (the negative price, the empty product name, the discount-code miscalculation tracked as BUG-009, the order-history authorization gap, the visual regression tracked as BUG-011) were never the point on their own, they were the proof, at every phase, that the tests you were writing could actually tell the difference between working and broken.
