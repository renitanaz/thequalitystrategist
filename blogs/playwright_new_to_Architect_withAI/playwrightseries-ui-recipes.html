UI Component Recipes

How to automate the controls a real store is full of: inputs, checkboxes, dropdowns, sliders, radio buttons, tooltips, date pickers and tables. Every recipe runs against a real PeakAndPack page.

Series: Playwright: Zero to Architect Demo: PeakAndPack 15 min read By: RN

Draft. Every recipe was run against a local copy of PeakAndPack. The filters, delivery options and out-of-stock product it uses are new, so these recipes only pass once the updated PeakAndPack is deployed. Run each one yourself when you reach this page.

Goal

  • Automate every form control PeakAndPack has, with the method that fits each one
  • Recognise the three ways a control makes automation harder: a hidden real input, a list that lives outside it, and a value that arrives late
  • Pick dates dynamically, so a test works next month too
  • Read, filter and loop through a table

The checkout recipes need a logged-in user with something in the cart. One small helper does that through the API, the same pattern as Phase 5, so each test starts straight on the checkout page:

// helpers.ts: used by the checkout recipes
import { Page, APIRequestContext } from '@playwright/test';

const API = 'https://peakandpackshopdemo.onrender.com';

// Log in through the API, put one item in the cart, and open the checkout page
export async function openCheckout(page: Page, request: APIRequestContext) {
  const login = await request.post(`${API}/api/auth/login`, {
    data: { email: 'test@peakandpack.com', password: 'password123' },
  });
  const { token, user } = await login.json();
  await request.post(`${API}/api/cart`, {
    headers: { Authorization: `Bearer ${token}` },
    data: { product_id: 1, quantity: 1 },
  });
  // The store keeps its session in localStorage: set it before the page loads
  await page.addInitScript(([t, u]) => {
    localStorage.setItem('token', t);
    localStorage.setItem('user', u);
  }, [token, JSON.stringify(user)]);
  await page.goto('/checkout');
}
Explain this code, line by line
  • export makes the function available to other test files (Part 4 of JavaScript for Testers).
  • openCheckout(page, request) takes the two things a test already has: the browser tab and the API request tool.
  • The first call logs in through the API and returns a token and the user. The second puts product 1 in that user's cart, using the token.
  • page.addInitScript(...) runs a small script in every page before the page's own code. Here it saves the token and the user in localStorage, which is where PeakAndPack keeps its login, so the checkout page opens already signed in.
  • page.goto('/checkout') goes straight there. baseURL from your config supplies the rest of the address.

2. Input fields

The product list's search box is a plain text input. These five methods cover almost everything you'll do with one.

test('search box: type, replace, clear and read', async ({ page }) => {
  await page.goto('/');
  const search = page.getByPlaceholder('Search gear...');

  await search.fill('headlamp');                  // click, clear what's there, type
  await expect(search).toHaveValue('headlamp');

  await search.fill('stove');                     // fill replaces: no need to clear first
  await expect(search).toHaveValue('stove');

  await search.clear();                           // empty it, and leave it empty
  await expect(search).toHaveValue('');

  await search.pressSequentially('tent', { delay: 100 });   // real key presses, 100 ms apart
  expect(await search.inputValue()).toBe('tent');           // read the value into a variable
  await expect(search).toHaveValue(/^te/);                  // part of the value: use a pattern

  expect(await search.getAttribute('placeholder')).toBe('Search gear...');
  expect(await search.textContent()).toBe('');              // an input's value is not its text
});
Explain this code, line by line
  • fill('headlamp') clicks the field, removes whatever is in it, and types the text. You never need to click first, or clear first.
  • clear() empties the field and leaves it empty. Use it when emptying is the point of the step.
  • pressSequentially('tent', { delay: 100 }) presses one key at a time, 100 milliseconds apart. Use it when the app reacts to each keystroke, like a live search. fill sets the whole text at once.
  • inputValue() reads what's in the field. The text inside an input isn't the page's text: textContent() returns an empty string for it.
  • toHaveValue(...) is the assertion for an input. A text value must match exactly; a pattern between slashes, like /^te/, matches part of it.
  • getAttribute('placeholder') reads any attribute of the element: here, the hint text.

3. Checkboxes

The product list's Category filters and "In stock only" are checkboxes. Try the obvious thing first:

await page.getByRole('checkbox', { name: 'Camping' }).check();

It fails, after waiting 30 seconds:

Error: locator.check: Timeout 30000ms exceeded.
Call log:
  - waiting for getByRole('checkbox', { name: 'Camping' })
  -   locator resolved to <input type="checkbox" name="category" value="Camping" class="visually-hidden"/>
  - attempting click action
  -   waiting for element to be visible, enabled and stable
  -   element is visible, enabled and stable
  -   <span class="mark"></span> intercepts pointer events
  - retrying click action ...

Why. The real checkbox is visually hidden, one pixel in size, and a styled box (the span) is drawn on top. That's a common pattern in design systems: the real input stays for screen readers and keyboards, and the span is what people see and click. Before clicking, Playwright checks that nothing else would receive the click. The span would, so Playwright keeps waiting, and eventually gives up.

There are two ways round it, and one proper fix:

  • { force: true } skips those checks and clicks anyway. It works, but it switches off the safety net that makes tests stable, so use it only when you know why the check fails, as here.
  • Click what the user sees: the visible text, page.getByText('Camping', { exact: true }).click().
  • The proper fix is in the app: ask the developers whether the styled box can be part of the clickable element. Until then, one of the two above.
test('category filters: check, uncheck, click', async ({ page }) => {
  await page.goto('/');
  const camping = page.getByRole('checkbox', { name: 'Camping' });

  await camping.check({ force: true });           // fix 1: skip the checks that fail
  await camping.check({ force: true });           // already checked: nothing happens
  await expect(camping).toBeChecked();
  await expect(page.getByTestId('result-count')).toHaveText('Showing 2 of 10 products');

  await camping.click({ force: true });           // click toggles, whatever the state was
  await expect(camping).not.toBeChecked();
  await expect(page.getByTestId('result-count')).toHaveText('Showing 10 of 10 products');

  await page.getByText('Camping', { exact: true }).click();   // fix 2: click what the user sees
  await expect(camping).toBeChecked();
  await camping.uncheck({ force: true });
  await expect(camping).not.toBeChecked();
});

test('in stock only hides the out-of-stock product', async ({ page }) => {
  await page.goto('/');
  await page.getByText('In stock only').click();
  await expect(page.getByTestId('result-count')).toHaveText('Showing 9 of 10 products');
  await expect(page.getByRole('heading', { name: 'Climbing Harness' })).toHaveCount(0);
});
Explain this code, line by line
  • check() makes sure the box is ticked. If it already is, nothing happens. uncheck() is the reverse. That's why they're safer than click(), which toggles whatever the state was.
  • { force: true } is the second argument of the action: an object of options.
  • toBeChecked() and not.toBeChecked() are the assertions for a checkbox. They retry until true, like every locator assertion.
  • getByTestId('result-count') reads the line "Showing 2 of 10 products", which proves the filter worked, not just that the box ticked. PeakAndPack's second test ID, after product-card.
  • getByText('Camping', { exact: true }): exact matches the whole text. Without it, any text containing "Camping" would match, such as the category line on a product card.
  • The second test shows the new product state: the Climbing Harness is out of stock, so "In stock only" hides it.

Because check and uncheck don't care about the starting state, you can loop over every checkbox on a page:

test('every checkbox on the filter bar, in a loop', async ({ page }) => {
  await page.goto('/');
  // The filter bar appears once products have loaded, and all() doesn't wait
  await expect(page.getByTestId('product-card').first()).toBeVisible();

  const boxes = await page.getByRole('checkbox').all();    // a list of locators
  expect(boxes).toHaveLength(6);                           // five categories + "In stock only"

  for (const box of boxes) {
    await box.check({ force: true });
    await expect(box).toBeChecked();
  }
  for (const box of boxes) {
    await box.uncheck({ force: true });
    await expect(box).not.toBeChecked();
  }
});
Explain this code, line by line
  • await expect(page.getByTestId('product-card').first()).toBeVisible() waits for the products to load first. The filter bar only appears once they have, and all() doesn't wait: it returns whatever exists at that instant, possibly an empty list.
  • all() turns a locator that matches several elements into a list of separate locators you can loop over with for...of (Part 4 of JavaScript for Testers).
  • toHaveLength(6) checks the list's size: five categories and "In stock only".
  • Looping checks then unchecks every box, and asserts each state, so the test also proves every box responds.

4. Native dropdowns

"Sort by" on the product list is a plain HTML <select>. Its options are inside it, so Playwright can choose one without opening it.

test('native dropdown: sort by', async ({ page }) => {
  await page.goto('/');
  const sort = page.getByRole('combobox', { name: 'Sort by' });

  await sort.selectOption('price-asc');                   // pick by value
  await expect(sort).toHaveValue('price-asc');
  await expect(page.getByTestId('product-card').first()).toContainText('Sleeping Bag');   // -$89 comes first

  await sort.selectOption({ label: 'Price: high to low' });   // pick by the text people read
  await expect(page.getByTestId('product-card').first()).toContainText('Insulated Water Bottle');

  await page.getByLabel('Sort by').selectOption({ index: 3 });   // pick by position
  await expect(sort).toHaveValue('name');
});
Explain this code, line by line
  • getByRole('combobox', { name: 'Sort by' }): a <select> has the role combobox. The name comes from its label, which is correctly linked here, so getByLabel('Sort by') works too.
  • selectOption('price-asc') chooses by the option's value, the code behind it. There's no need to click the dropdown first.
  • selectOption({ label: 'Price: high to low' }) chooses by the label, the text people read. { index: 3 } chooses by position, counting from 0.
  • toHaveValue('price-asc') checks the chosen option's value, not its visible text.
  • toContainText('Sleeping Bag') on the first card proves the list really changed order: the -$89 bug sorts first.

5. Sliders

The product list's price slider is a custom one: a knob on a track. It has the role slider, and its position is published in aria-valuenow, the number a screen reader would read out. Two ways to move it:

  • The keyboard is the most reliable. Focus the knob and press the arrow keys, exactly as a keyboard user would.
  • The mouse works when there's no keyboard support. It needs coordinates, so it's more fragile.
test('price slider: keyboard', async ({ page }) => {
  await page.goto('/');
  const slider = page.getByRole('slider', { name: 'Maximum price' });
  await expect(slider).toHaveAttribute('aria-valuenow', '500');     // the far right means "any price"

  await slider.focus();
  await slider.press('Home');                                       // jump to the start
  await expect(slider).toHaveAttribute('aria-valuenow', '0');
  await expect(page.getByTestId('product-card')).toHaveCount(1);    // only the -$89 sleeping bag

  for (let i = 0; i < 10; i++) {
    await slider.press('ArrowRight');                               // 10 per press
  }
  await expect(slider).toHaveAttribute('aria-valuenow', '100');
  await expect(page.getByTestId('result-count')).toHaveText('Showing 6 of 10 products');
});

test('price slider: drag with the mouse', async ({ page }) => {
  await page.goto('/');
  const track = page.locator('.slider-track');
  const knob = page.getByRole('slider', { name: 'Maximum price' });
  await track.scrollIntoViewIfNeeded();                  // the mouse can only reach what's on screen

  const trackBox = (await track.boundingBox())!;         // { x, y, width, height } on the screen
  const knobBox = (await knob.boundingBox())!;

  await page.mouse.move(knobBox.x + knobBox.width / 2, knobBox.y + knobBox.height / 2);   // knob centre
  await page.mouse.down();                                                                // press
  await page.mouse.move(trackBox.x + trackBox.width * 0.2, trackBox.y + trackBox.height / 2, { steps: 5 });
  await page.mouse.up();                                                                  // release

  await expect(knob).toHaveAttribute('aria-valuenow', '100');
  await expect(page.getByText('Price: up to $100')).toBeVisible();
});
Explain this code, line by line
  • getByRole('slider', { name: 'Maximum price' }) finds the knob by its role and its aria-label.
  • toHaveAttribute('aria-valuenow', '500') reads the slider's position from its attribute. Attribute values are text, so the number is in quotes. The far right, 500, means "any price" in PeakAndPack.
  • focus() puts the keyboard on the knob. press('Home') jumps to the start; press('ArrowRight') moves one step, which is $10 here.
  • boundingBox() returns the element's rectangle on the screen: x and y are its top-left corner, measured from the top-left of the visible page, plus width and height.
  • To grab the knob, move the mouse to its centre: its x plus half its width, its y plus half its height.
  • mouse.down() presses the button, mouse.move(x, y, { steps: 5 }) drags to a point in five small moves (so the page sees movement, not a jump), and mouse.up() lets go.
  • The target is 20% along the track: trackBox.x + trackBox.width * 0.2. With a range of 0 to 500, 20% is 100.
  • scrollIntoViewIfNeeded() comes first because the mouse can only reach what's on screen.
  • A native slider (<input type="range">), which PeakAndPack doesn't have, is easier: fill('300') sets it.

6. Radio buttons

Checkout's "Delivery method" is a group of radio buttons built the same way as the checkboxes: a hidden real input with a styled circle on top. So the obvious call fails the same way:

Error: locator.check: Timeout 30000ms exceeded.
Call log:
  - waiting for getByRole('radio', { name: 'Express (2 days)' })
  -   locator resolved to <input type="radio" name="delivery" value="express" class="visually-hidden"/>
  - attempting click action
  -   <span class="mark round"></span> intercepts pointer events
  - retrying click action ...

The fixes are the same, too: { force: true }, or click the visible text.

test('delivery method: choose, switch, and the disabled option', async ({ page, request }) => {
  await openCheckout(page, request);
  const express = page.getByRole('radio', { name: 'Express (2 days)' });
  const standard = page.getByRole('radio', { name: 'Standard (5 days)' });

  await expect(standard).toBeChecked();                   // Standard is the default

  await express.check({ force: true });                   // fix 1: skip the failing checks
  await expect(express).toBeChecked();
  await expect(standard).not.toBeChecked();               // choosing one clears the other

  await page.getByText('Standard (5 days)').click();      // fix 2: click what the user sees
  await expect(standard).toBeChecked();

  await expect(page.getByRole('radio', { name: /store pickup/i })).toBeDisabled();
});

test('isChecked reads a status, it does not check one', async ({ page, request }) => {
  await openCheckout(page, request);
  const express = page.getByRole('radio', { name: 'Express (2 days)' });

  const status = await express.isChecked();     // just true or false, right now
  expect(status).toBe(false);                   // fine for logic, but it never waits or retries

  await expect(express).not.toBeChecked();      // the real assertion: retries until true, or times out
});
Explain this code, line by line
  • openCheckout(page, request) is the helper from the top of the page.
  • getByRole('radio', { name: 'Express (2 days)' }) finds one option by its role and its label.
  • Standard is selected by default, so the first assertion proves the starting state before changing anything.
  • check({ force: true }) selects an option. Checking one radio button clears the others in its group, which the next assertion proves with not.toBeChecked().
  • There's no uncheck for radio buttons: you can only choose a different one.
  • toBeDisabled() asserts that an option can't be chosen. Trying to check a disabled radio waits for it to become enabled, then fails.
  • isChecked() returns true or false right now. It's useful when your test needs to decide something, but it isn't an assertion: it doesn't wait or retry. To check a state, use toBeChecked().

7. Custom dropdowns

Checkout's "Delivery time" looks like a dropdown, but it isn't a <select>. It's a button, and the list of options is built and added to the very bottom of the page when you click it, outside the button. Open DevTools and look in the Elements panel to see it for yourself. So there's no selectOption: do what a user does, click, then choose, then check.

test('custom dropdown: delivery time', async ({ page, request }) => {
  await openCheckout(page, request);
  const timeButton = page.getByRole('button', { name: /delivery time/i });
  await expect(timeButton).toHaveText('Delivery time: Morning (8-12)');

  await timeButton.click();                               // open the list, like a user
  await page.getByRole('listbox').getByRole('option', { name: 'Afternoon (12-17)' }).click();
  await expect(timeButton).toHaveText('Delivery time: Afternoon (12-17)');   // text, not a value

  await timeButton.click();                               // open it again to read every option
  await expect(page.getByRole('option').first()).toBeVisible();   // wait: allTextContents() doesn't
  const options = await page.getByRole('option').allTextContents();
  expect(options).toEqual(['Morning (8-12)', 'Afternoon (12-17)', 'Evening (17-21)']);

  await page.keyboard.press('Escape');                    // close the list
  await expect(page.getByRole('listbox')).toHaveCount(0);
});
Explain this code, line by line
  • getByRole('button', { name: /delivery time/i }): the control is a button, named by its text. The pattern ignores capital letters and matches part of the name, which changes with the chosen time.
  • toHaveText('Delivery time: Morning (8-12)') asserts the button's text. A custom control has no value to check, so the visible text is the result.
  • getByRole('listbox').getByRole('option', { name: ... }) narrows to the options inside the list. The list isn't inside the button, so you scope to the list itself.
  • await expect(page.getByRole('option').first()).toBeVisible() waits for the list. allTextContents() doesn't wait, so reading it too early can return an empty list.
  • allTextContents() returns the text of every matching element as a list of strings. toEqual([...]) compares the list's contents.
  • keyboard.press('Escape') presses a key without targeting an element. The list closes, which toHaveCount(0) confirms: zero matches is how you assert something is gone.

8. Tooltips

A tooltip exists only while you hover, which makes it hard to inspect: the moment the mouse moves to DevTools, it vanishes. Freeze the page instead. Open DevTools, go to the Sources tab, hover the element so the tooltip shows, then press F8 (or Ctrl+\; Cmd+\ on a Mac) to pause the page. The Elements panel then shows the tooltip, so you can see what it's made of. In PeakAndPack it's a div with role="tooltip", added to the bottom of the page.

test('tooltips appear on hover and go away', async ({ page, request }) => {
  await openCheckout(page, request);

  await page.getByRole('button', { name: 'Discount code help' }).hover();     // hover, not click
  await expect(page.getByRole('tooltip')).toHaveText('Codes are case-sensitive');

  await page.getByRole('button', { name: 'Delivery date help' }).hover();
  await expect(page.getByRole('tooltip')).toHaveText('The earliest delivery date is tomorrow');

  await page.mouse.move(0, 0);                            // move away: the tooltip is removed
  await expect(page.getByRole('tooltip')).toHaveCount(0);
});
Explain this code, line by line
  • hover() moves the mouse onto the element without clicking, which is what shows a tooltip.
  • getByRole('button', { name: 'Discount code help' }) finds the little "i" button by its aria-label, since its visible text is just the letter i.
  • getByRole('tooltip') finds the tooltip, because the app gives it that role. If yours doesn't have a role, use an ordinary locator for whatever the tooltip is.
  • toHaveText(...) is a locator assertion, so it waits for the tooltip to appear.
  • mouse.move(0, 0) moves the mouse to the top-left corner of the page, away from everything. toHaveCount(0) then confirms the tooltip was removed.

9. Date pickers

Checkout's "Delivery date" opens a calendar. Two things make calendars awkward:

  • A calendar always shows whole weeks, so it includes days from the previous and next month. A "30" in the grid might be this month's or last month's. PeakAndPack gives those days an extra class, bounding-month, which you can exclude.
  • Text matching matches part of the text by default, so getByText('2') also matches 12, 20, 21 and so on.
test('date picker: neighbouring months, exact text, disabled days', async ({ page, request }) => {
  await openCheckout(page, request);
  await page.getByLabel('Delivery date (optional)').click();

  await expect(page.locator('.day-cell')).toHaveCount(42);              // always six weeks of cells

  // Without exact, "2" matches 2, 12, 20, 21 ... : text is matched as a part
  const loose = await page.locator('.day-cell:not(.bounding-month)').getByText('2').count();
  expect(loose).toBeGreaterThan(1);

  // exact: true matches the whole text, and the class leaves out neighbouring months
  const second = page.locator('.day-cell:not(.bounding-month)').getByText('2', { exact: true });
  await expect(second).toHaveCount(1);

  // Days before tomorrow are disabled
  const today = new Date().getDate().toString();
  await expect(page.locator('.day-cell:not(.bounding-month)').getByText(today, { exact: true })).toBeDisabled();
});
Explain this code, line by line
  • getByLabel('Delivery date (optional)') finds the field by its label, which is linked to it. Clicking it opens the calendar.
  • .day-cell is a CSS locator: the dot means "has this class". Each day is a button with that class, and toHaveCount(42) checks the six weeks of cells.
  • :not(.bounding-month) means "without that class", so only days from the displayed month. Chaining .getByText(...) after a locator searches inside the matches.
  • getByText('2') without exact matches any day whose text contains a 2, which is why the count is more than one.
  • { exact: true } matches the whole text, "2" and nothing else. Together with the class, it leaves exactly one cell.
  • new Date().getDate() is today's day of the month, as a number; .toString() turns it into text for matching. PeakAndPack disables every day before tomorrow, which toBeDisabled() confirms for today.

A test that picks a date must still work next month. So don't type a date: work it out from today with JavaScript's Date object, which handles month lengths and year ends for you.

test('date picker: pick a date 40 days from today, in any month', async ({ page, request }) => {
  await openCheckout(page, request);

  const date = new Date();                         // right now
  date.setDate(date.getDate() + 40);               // move it 40 days on; JavaScript fixes the month and year
  const day = date.getDate().toString();
  const monthShort = date.toLocaleString('en-US', { month: 'short' });   // Nov
  const monthLong = date.toLocaleString('en-US', { month: 'long' });     // November
  const year = date.getFullYear();
  const expectedDate = `${monthShort} ${day}, ${year}`;                  // Nov 10, 2026

  const dateField = page.getByLabel('Delivery date (optional)');
  await dateField.click();

  // Flip to the right month first
  let shown = await page.locator('.calendar-title').textContent();
  while (!shown!.includes(`${monthLong} ${year}`)) {
    await page.getByRole('button', { name: 'Next month' }).click();
    shown = await page.locator('.calendar-title').textContent();
  }

  await page.locator('.day-cell:not(.bounding-month)').getByText(day, { exact: true }).click();
  await expect(dateField).toHaveValue(expectedDate);
});
Explain this code, line by line
  • new Date() is the current date and time. date.setDate(date.getDate() + 40) moves it 40 days later. If that crosses into another month or year, JavaScript adjusts for you, so you never calculate month lengths yourself.
  • getDate() is the day of the month, getFullYear() the year. toLocaleString('en-US', { month: 'short' }) gives the month's name in a chosen format: short is Nov, long is November. 'en-US' fixes the language, so the test gives the same answer on any computer.
  • `${monthShort} ${day}, ${year}` builds the exact text the field will show, with a template literal (Part 1 of JavaScript for Testers).
  • The while loop repeats while its condition is true: while the calendar's title doesn't contain the month we want, click "Next month" and read the title again. It stops once the right month is showing.
  • !shown!.includes(...): the first ! means "not". The second, after shown, is TypeScript's way of saying "this isn't empty", because textContent() may return nothing.
  • toHaveValue(expectedDate) checks the field: PeakAndPack's date picker is an input, so its text is a value.

10. Tables

PeakAndPack's admin panel lists every product in a table. A table is rows, and rows are cells; there's no locator for a whole column, so you find a row first, then work inside it. The admin panel signs in through its own form, so these tests start with this helper:

// The admin panel lives on the API server and keeps its login in memory,
// so every admin test signs in through the panel's own form
const ADMIN = 'https://peakandpackshopdemo.onrender.com/admin/';

async function signInAsAdmin(page: Page) {
  await page.goto(ADMIN);
  await page.getByPlaceholder('admin@peakandpack.com').fill('admin@peakandpack.com');
  await page.getByPlaceholder('Password').fill('adminpass123');
  await page.getByRole('button', { name: 'Sign in as admin' }).click();
  await expect(page.getByRole('heading', { name: 'Products' })).toBeVisible();
}

Find a row, read its cells

test('admin table: find a row, read its cells', async ({ page }) => {
  await signInAsAdmin(page);
  const row = page.getByRole('row', { name: /Headlamp/ });       // the row whose text mentions Headlamp
  await expect(row).toBeVisible();

  await expect(row.getByRole('cell')).toHaveCount(6);            // handle, name, price, stock, category, actions
  await expect(row.getByRole('cell').nth(2)).toHaveText('$24.99');   // columns count from 0
  await expect(row.getByRole('cell').nth(3)).toHaveText('60');
  await row.getByRole('button', { name: 'Delete' }).count();     // buttons inside the row are scoped to it
});

test('admin table: filter rows by one column', async ({ page }) => {
  await signInAsAdmin(page);
  await expect(page.getByRole('row', { name: /Headlamp/ })).toBeVisible();

  // Rows whose Stock cell is exactly 0. Searching the row text for "0" would match prices too
  const outOfStock = page.getByRole('row').filter({ has: page.getByRole('cell', { name: '0', exact: true }) });
  await expect(outOfStock).toHaveCount(1);
  await expect(outOfStock).toContainText('Climbing Harness');
});
Explain this code, line by line
  • getByRole('row', { name: /Headlamp/ }) finds the row whose text mentions Headlamp. Rows are named by all the text inside them.
  • row.getByRole('cell') finds the cells inside that row only. toHaveCount(6) counts them: a drag handle, name, price, stock, category and the actions column.
  • .nth(2) picks one cell by position, counting from 0: 0 is the handle, 1 the name, 2 the price, 3 the stock. Positions are fragile if columns move, so use them for tables whose columns are stable.
  • getByRole('cell', { name: '0', exact: true }) finds a cell whose whole text is 0. Searching the row's text for "0" would match prices like $1450.00 too. filter({ has: ... }) keeps only the rows that contain the cell you describe.
  • The row's own buttons, such as Delete, are found through the row, so they're the right row's buttons even when every row has one.

Wait, then read every row

The admin table first shows a single "Loading..." row, then the real rows arrive. all() doesn't wait, so reading the rows too early gives you the loading row. On a fast server you might never notice. To prove it, the test below slows the API down by a second:

test('admin table: wait for the data before reading every row', async ({ page }) => {
  // Make the product list answer slowly, so the race is easy to see
  await page.route('**/api/admin/products', async (route) => {
    await new Promise((resolve) => setTimeout(resolve, 1000));
    await route.continue();
  });
  await signInAsAdmin(page);

  const tooEarly = await page.locator('#products-tbody tr').all();   // all() doesn't wait
  expect(tooEarly).toHaveLength(1);                                  // just the "Loading..." row

  await expect(page.getByRole('row', { name: /Trekking Poles/ })).toBeVisible();   // wait for real data
  const rows = await page.locator('#products-tbody tr').all();
  expect(rows).toHaveLength(10);
});

test('admin table: no product has a negative price', async ({ page }) => {
  test.fail();    // expected to fail while BUG-001 exists: remove this line once it is fixed
  await signInAsAdmin(page);
  await expect(page.getByRole('row', { name: /Trekking Poles/ })).toBeVisible();

  const rows = await page.locator('#products-tbody tr').all();
  const prices: number[] = [];
  for (const row of rows) {
    const text = await row.locator('td').nth(2).textContent();   // e.g. "$24.99"
    prices.push(Number(text!.replace('$', '')));                 // remove the $ before converting
  }
  expect(prices.filter((price) => price < 0)).toHaveLength(0);   // finds the -$89 sleeping bag
});
Explain this code, line by line
  • page.route('**/api/admin/products', ...) intercepts that API call (Phase 7 covers this properly). The handler waits one second with setTimeout inside a promise, then route.continue() lets the real request go ahead.
  • all() straight after sign-in returns one row: the "Loading..." placeholder. toHaveLength(1) proves it.
  • expect(row).toBeVisible() on a real product waits until the data has arrived. After that, reading all the rows is safe.
  • The second test loops down the Price column: row.locator('td').nth(2) is each row's price cell, textContent() reads text like "$24.99", and replace('$', '') removes the dollar sign so Number(...) can convert it (Part 3 of JavaScript for Testers).
  • test.fail() tells Playwright this test is expected to fail. The seeded -$89 sleeping bag fails the check, so the test is reported as passing. When BUG-001 gets fixed, the test would start passing, Playwright would report that as a failure, and you'd remove the line.
