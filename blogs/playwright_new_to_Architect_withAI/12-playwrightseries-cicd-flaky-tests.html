CI/CD, Reporting and Flaky Test Management

Fast feedback on every PR. Tag tests so the right ones run at the right time. Shard for speed. Track flaky tests as quality debt.

By RN~5 hours Series: Playwright: Zero to Architect Demo: PeakAndPack

Goal

Build a CI pipeline that gives fast, reliable feedback on every pull request. Tag tests so the right tests run at the right time. Shard the suite for speed. Build a custom reporter for actionable failure output. Track and enforce flaky test health.

Before: a naive CI pipeline

Before: slow, no tagging, poor failure output
# Runs every test on every PR. No tagging, no sharding.
# A 200-test suite takes 15 minutes. PRs sit waiting.
# Failure output: "Test failed at line 42." No context.

name: Tests
on: [push]
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - run: npm ci
      - run: npx playwright install
      - run: npx playwright test
After: tagged, sharded, fast feedback
# PRs run only @critical tests (fast feedback).
# Full suite runs nightly (complete coverage).
# Sharded across 4 machines (4x faster).
# Failure output includes screenshot link and expected vs actual.

name: PR checks
on: pull_request
jobs:
  critical:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install chromium
      - run: npx playwright test --grep @critical
      - uses: actions/upload-artifact@v4
        if: failure()
        with:
          name: report
          path: playwright-report/

Test tagging strategy

Tags control which tests run when. Add them directly to test names and filter with --grep:

// Tag in the test name
test('checkout completes @critical', async ({ page }) => { ... });
test('discount code applies correctly @critical @regression', async ({ page }) => { ... });
test('admin CSV export @admin', async ({ page }) => { ... });

// Run only critical tests (on PR)
// npx playwright test --grep @critical

// Run critical and regression (extended PR check)
// npx playwright test --grep "@critical|@regression"

// Exclude admin tests
// npx playwright test --grep-invert @admin
TagWhen it runsWhat it covers
@criticalEvery PRCore user journeys: login, add to cart, checkout
@regressionPre-releaseFull coverage of all known bug fixes
@visualNightlyScreenshot comparisons (slow, stable)
@adminOn demandAdmin panel features

Sharding: run faster with multiple machines

Sharding splits the test suite across multiple CI workers. Each worker runs a subset:

# .github/workflows/playwright.yml -- sharded across 4 machines
jobs:
  test:
    runs-on: ubuntu-latest
    strategy:
      matrix:
        shard: [1/4, 2/4, 3/4, 4/4]
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install chromium
      - run: npx playwright test --shard=${{ matrix.shard }} --reporter=blob
      - uses: actions/upload-artifact@v4
        with:
          name: blob-report-${{ matrix.shard }}
          path: blob-report/

  merge-reports:
    needs: test
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
      - run: npm ci
      - uses: actions/download-artifact@v4
        with: { path: all-blob-reports, pattern: blob-report-* }
      - run: npx playwright merge-reports --reporter html ./all-blob-reports
      - uses: actions/upload-artifact@v4
        with:
          name: html-report
          path: playwright-report/

Custom reporter: actionable failure output

The default reporter tells you a test failed. A custom reporter tells you exactly what to look at:

// reporters/custom-reporter.ts
import { Reporter, TestCase, TestResult } from '@playwright/test/reporter';

class ActionableReporter implements Reporter {
  onTestEnd(test: TestCase, result: TestResult) {
    if (result.status === 'failed') {
      console.log('
 FAILED:', test.title);
      // Print the first error with expected vs actual
      const error = result.errors[0];
      if (error?.message) {
        console.log('  Error:', error.message.split('
').slice(0,3).join(' | '));
      }
      // Print screenshot path if captured
      const screenshot = result.attachments.find(a => a.name === 'screenshot');
      if (screenshot?.path) {
        console.log('  Screenshot:', screenshot.path);
      }
    }
  }
}

export default ActionableReporter;

// playwright.config.ts
reporter: [
  ['html'],
  ['./reporters/custom-reporter.ts'],
],

Flaky test management

A flaky test is a quality debt that compounds. Track every flaky test in a register and enforce a health gate:

# flaky-register.md
| Test | File | Root cause | Status | Fixed date |
|------|------|------------|--------|------------|
| cart shows item count | cart.spec.ts | Missing await on goto | Fixed | 2026-01-15 |
| checkout completes | checkout.spec.ts | Shared cart between workers | In progress |: |

Quality gate: if flaky rate exceeds 5% of the suite, block the merge. A 200-test suite with more than 10 flaky tests is not a test suite: it is noise.

# playwright.config.ts
retries: process.env.CI ? 1 : 0, // one retry in CI to catch genuine intermittency
// Track: if a test passes only on retry, it is flaky. Add to the register.

The flaky rate is a quality metric. Report it alongside test pass rate in your sprint review. "95 tests passing, 3 flaky (1.5%)" is honest. "98 tests passing" when 3 of them only pass on retry is not. The flaky register makes invisible quality debt visible.

Common mistakes in Phase 12.

  • Running the full suite on every PR. A 200-test suite at 10 seconds per test is 33 minutes. Tag and run only critical tests on PRs. Run the full suite nightly.
  • Sharding without merging reports. Each shard writes its own blob report. Without the merge step, you get 4 partial HTML reports and no unified view of what passed and failed.
  • Not uploading artifacts on failure. If CI fails and you have no artifact, you have no trace, no screenshot, and no way to debug remotely. Always upload the report.
  • Treating retries as a fix. A retry that makes a flaky test pass hides the problem. Track every test that passes only on retry in the flaky register.

Show solution -- try it yourself first

PR pipeline with critical tag and nightly full run

name: Playwright tests
on:
  pull_request:
  schedule:
    - cron: '0 2 * * *'  # nightly at 2am UTC

jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - run: npm ci
      - run: npx playwright install chromium

      # On PRs: only critical. On nightly: everything.
      - name: Run tests
        run: |
          if [ "${{ github.event_name }}" = "pull_request" ]; then
            npx playwright test --grep @critical
          else
            npx playwright test
          fi

      - uses: actions/upload-artifact@v4
        if: always()
        with:
          name: playwright-report
          path: playwright-report/
          retention-days: 7

Why upload on always(), not only on failure. Uploading only on failure means you never have a passing run's report to compare against. Uploading always (with a short retention) means you can look at any run's report, passing or failing.
