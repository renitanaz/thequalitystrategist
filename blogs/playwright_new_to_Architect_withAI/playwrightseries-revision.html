Phase 0: Intro & Setup Open phase
1 · Setting up
Why does Playwright need Node.js, and which minimum version?
What is npm, and what is a package?
Which five things does npm init playwright@latest put in your project?
Why does node_modules never go into Git?
Why should you cd into a projects folder before mkdir?
RecapHide
  • Playwright is written in JavaScript, and Node.js runs JavaScript outside a browser. It needs version 18 or higher.
  • npm is Node's package manager, installed with Node. A package is ready-made code someone else wrote and shared.
  • package.json (the project's ID card), package-lock.json (exact versions), node_modules/ (the packages), playwright.config.ts (settings), tests/example.spec.ts (a demo you delete). Plus .gitignore, and the browsers go to a shared folder outside the project.
  • It's large, and it can be rebuilt from package.json at any time.
  • A terminal can open in a system folder, such as C:\WINDOWS\system32 when run as administrator. The project would end up there.

Phase 1: Test Design Thinking Open phase
1 · The test pyramid
Name the three layers of the pyramid and what each one tests.
Why do most tests belong near the bottom?
What is the rule for choosing a layer?
Why does PeakAndPack have no unit layer to test directly?
What three costs does every test carry?
RecapHide
  • Unit: a single function or component, in milliseconds. API (integration): the server and its responses, in seconds. UI or end-to-end: a full journey through a real browser, 10 to 60 seconds.
  • The lower layers are fast and rarely fail for reasons unrelated to the bug. Only journeys that genuinely need a browser belong at the top. It is a guide for where to put effort, not a strict rule.
  • Put each test at the lowest layer that still gives you confidence. A calculation does not need a browser. A user journey does.
  • The logic sits inside the server routes. The API layer is those routes, which Playwright can call with no browser, and the UI layer is the React store.
  • Time to write it, time it adds to every future run, and effort to keep it working when the app changes.
→ See: Phase 1, section 1
2 · Design principles
What does "one test, one scenario" mean for a journey with several steps?
Why not write 99 tests for a quantity from 1 to 99, and what replaces them?
What does a decision table show you?
What does "assert behaviour, not implementation" mean?
RecapHide
  • A journey may need several steps just to reach the thing under test. What it must not do is verify unrelated things on the way, such as login, cart and email under one name.
  • Boundary value analysis: test the edges and one value in the middle, and test them below the UI layer.
  • Every combination of conditions and what should happen, so you can see which combinations are separate cases and which only repeat another.
  • Check what the user sees, such as the order confirmation heading, not a CSS class, a function call or the exact payload of a request.
→ See: Phase 1, section 3
3 · Running the design against the app
Which quantities did the BVA table test, and which should have been rejected?
Which row of the checkout decision table was a repeat, and why?
Why could clicking through the page never find the quantity bug?
The app disagrees with your table. What do you do?
RecapHide
  • 0, 1, 50, 99 and 100. The rule says 0 and 100 are rejected. PeakAndPack accepted both, and also accepted -1, 1000, 2.5 and "abc".
  • No valid code and an empty cart. An empty cart is refused before the code is looked at, so it is the same case as a valid code with an empty cart.
  • The page has no quantity box, so a tester who only clicks never tries 0 or -1. The cart API accepts them, and a test at the API layer finds the problem in seconds.
  • Treat it as a finding. Decide whether the table or the app is wrong, and if it is the app, mark the test test.fail() with a comment.

Phase 2: Locators Open phase
1 · Reading a page, and the priority list
Why do locators care about parents, children and siblings?
What is the difference between an id and a class?
List the locator priority from best to last resort.
Why does getByRole survive a restyle?
Why can't PeakAndPack's login inputs be found by label, and what does the series use instead?
RecapHide
  • They often describe an element by its relationships, such as "the button inside this card".
  • An id is meant to be unique and names one element. A class is shared by many elements, usually for styling. Both are chosen for styling and scripts, so refactors change them.
  • getByRole, getByLabel, getByPlaceholder, getByText, getByTestId, then locator('css') as the last resort.
  • A role and an accessible name describe what an element is and says, not how it looks, so renaming a class or moving a div changes nothing the locator uses.
  • The visible labels are not linked to the inputs, and there is no aria-label or placeholder. It uses input[type="email"] and input[type="password"], and the missing names are also an accessibility defect.

4 · Tools, AI output and "self-healing"
Name two ways Playwright suggests a locator.
What must you do with a suggested or generated locator?

RecapHide

Phase 5: Test Data & State Open phase
1 · Coupled and independent tests
Why can two "before" tests that share the demo account pass in one order and fail in the other?

Why must the browser be signed in as well as the API user created?
RecapHide
  • Test 2 depends on what test 1 left in the shared cart. Run the other way round it meets an empty cart.

2 · API setup and hooks
Why set up data through the API and keep the UI for what the test is about?
Name the four hooks and what each is for.
