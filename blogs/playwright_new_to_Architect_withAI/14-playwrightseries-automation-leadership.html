Phase 14 of 15 · Automation Leadership

Leading a Test Automation Practice

Everything so far made you good at writing tests. This phase is about the suite as a shared asset: conventions other people follow, a review process that catches drift, and the judgment to say no to a test that shouldn't exist.

Goal for this phase

Produce two documents most solo-written suites never have: a written conventions standard, and a PR review checklist that enforces it. Leave able to answer "should this new test exist at all" as confidently as "is this test written well."

Before: conventions that only live in one person's head

A suite written entirely by one disciplined engineer can look excellent and still fail the moment a second person contributes to it, because the standard was never written down anywhere a new contributor could find it.

Before: two contributors, two styles
// contributor-a.spec.ts (Phase 2-3 conventions)
test('checkout completes', async ({ page }) => {
  await page.getByRole('button', { name: /checkout/i }).click();
});

// contributor-b.spec.ts (never read Phase 2-3, no one told them)
test('checkout completes', async ({ page }) => {
  await page.locator('#checkout-btn').click();
  await page.waitForTimeout(1500);
});
After: one standard, enforced at review, not just known
// CONTRIBUTING.md, section 2: Locators and waits
// - getByRole/getByLabel/getByText only, CSS selectors
//   need a comment explaining why nothing else worked.
// - No waitForTimeout. Ever. PR review blocks on it.
// Both contributors' PRs are checked against this file,
// not against whatever the reviewer happens to remember.

The difference isn't that contributor B is careless, it's that the standard existed only as contributor A's personal habit. Writing it down is what makes it enforceable by anyone, including someone reviewing a PR from a person more senior than them.

Suite-wide conventions worth writing down

ConventionWhy it needs to be explicit
Locator priority (Phase 2's table)Without it written down, "resilient" means whatever each contributor was taught last
File and test namingA test named test1 or a file named misc.spec.ts is unfindable six months later
Tagging convention (@smoke, @regression)Phase 12's CI sharding and selective runs depend on tags being applied consistently, not just by whoever remembers
Where fixtures live and how they're sharedPhase 10 patterns only pay off if everyone uses the shared fixture instead of writing their own login flow per file
What earns a data-testid requestWithout a rule, every missing role/label becomes a testid request, and the app fills up with test-only attributes

A PR review checklist for new tests

A checklist turns "does this look right" (which varies by reviewer and by how tired they are) into a fixed set of yes/no checks anyone on the team can apply the same way.

  • Every locator is role, label, or text-based, or has a comment explaining why not
  • No waitForTimeout anywhere in the diff
  • Every assertion checks something a user would actually see or experience
  • The test is tagged correctly for CI sharding (Phase 12)
  • If the test is new coverage for a known bug (check the bug list), it's written to fail until the bug is fixed, not adjusted to match current broken behaviour
  • Test name describes the behaviour, not the implementation ("checkout blocks empty cart," not "test 14")

The checklist is also the onboarding doc. A new engineer joining the project doesn't need a separate "how we write tests" conversation if the PR checklist already states the rules and the reviewer applies them consistently. The first PR review they get is the training. This is worth more than a wiki page nobody reads before their first contribution.

Measuring suite health

"How's the suite doing" needs a real answer, not a feeling. Three numbers matter more than raw test count:

  • Flake rate. Tests that fail and pass on rerun with no code change, tracked per test, not suite-wide. A suite with a 2% overall flake rate can still have five tests that fail one run in three, and those five are where trust erodes fastest.
  • Runtime, and its trend. Not just today's number, whether it is climbing. Phase 12's sharding buys you headroom, it doesn't fix a suite that adds five minutes every month with no offsetting cleanup.
  • Coverage by user journey, not by line. "80% code coverage" says nothing about whether checkout, the highest-risk flow per Phase 1's risk ranking, actually has a test. Track coverage against the risk map from the requirements, not against a percentage a linter reports.

When to say no to a new E2E test

Phase 1 introduced the test pyramid: put a test at the lowest layer that still gives confidence. Automation leadership means enforcing that at review time, not just knowing it. A PR that adds a full browser test for a pure calculation, exactly the "before" example from Phase 1, is a test the suite would be healthier without.

Ask this at review, every time: "Could this be a unit or API test instead, and lose nothing?" If yes, that's the conversation to have before the PR merges, not a retrospective six months later when the suite has grown slow and nobody remembers why half of it is E2E.

Common mistakes in Phase 14.

  • Writing the standard once and never updating it. A conventions doc that doesn't reflect a rule the team actually started enforcing last month trains people to ignore it.
  • Measuring suite health only by pass/fail count. A suite that's 100% green with a 15% flake rate people have learned to just rerun is not healthy, it's a suite nobody trusts and everyone routes around.
  • Applying the PR checklist inconsistently by seniority. The moment a senior engineer's PR skips the checklist "because they know what they're doing," the checklist stops being a standard and becomes a suggestion for juniors only.
  • Saying no to new E2E tests without offering the alternative. "Don't test this at the UI layer" without "here's how to test it at the unit/API layer instead" just discourages testing the behaviour at all.

Deliverables

  • CONTRIBUTING.md: locator, wait, naming, and tagging conventions, written for a new contributor
  • pr-checklist.md: the review checklist, ready to paste into a PR template
  • suite-health.md: current flake rate, runtime trend, and journey coverage against the Phase 1 risk map
Assignment

Review a real PR against the checklist

Take any spec file you wrote in an earlier phase (before you knew this checklist existed) and review it as if it were a teammate's PR. List every checklist item it fails. Then fix it. This is the fastest way to feel how much the checklist changes what "good enough" means once it's written down.

Bonus challenge

Draft the "no" conversation. Write out, as if messaging a teammate, how you'd explain declining to add a full E2E test for validating that a discount percentage calculates correctly, and what you'd suggest instead. The goal is a response that doesn't just say no, it hands them a better path.

Example PR checklist, as a template

## New test checklist

- [ ] Locators: getByRole/getByLabel/getByText only (or a comment explaining
      why not)
- [ ] No waitForTimeout anywhere in this diff
- [ ] Assertions check what a user sees, not internal state or a status
      code alone
- [ ] Tagged correctly (@smoke / @regression / @slow)
- [ ] If this covers a known bug, it fails until the bug is fixed
- [ ] Test name describes behaviour, not implementation
- [ ] Could this be a unit or API test instead, with no loss of confidence?

Why "tagged correctly" is on a leadership-phase checklist, not just a technical one. Tagging is easy to skip because an untagged test still runs and still passes review by every other line item. It's exactly the kind of small omission that only costs something later, when Phase 12's selective CI runs quietly miss it. A checklist's job is to catch the things that are easy to forget precisely because they don't fail anything today.
