29 Lighthouse: Accessibility Scores and What They Actually Mean

Lighthouse gives you a score out of 100. The score is not a conformance statement. Here is what the score measures, what it misses, and how to use it without being misled.

1. What Lighthouse Is

Lighthouse is an open-source automated auditing tool built into Chrome DevTools. It produces scores across five categories: Performance, Accessibility, Best Practices, SEO, and Progressive Web App. The accessibility score is powered by axe-core: the same engine as axe DevTools and Accessibility Insights.

Lighthouse is built into every Chrome browser. No installation required. It also runs via the Node CLI and integrates with CI/CD pipelines via lighthouse-ci. It is the most widely distributed accessibility scanning tool available.

2. The Accessibility Score: What It Measures

The Lighthouse accessibility score is a weighted average of the axe-core rules it runs. A score of 100 does not mean the page is accessible. It means the page passed all automated axe-core checks that Lighthouse runs.

Automated tools catch approximately 30 to 50 percent of WCAG 2.1 AA failures. A score of 100 is the floor for accessibility, not the ceiling. A page with a score of 100 can still fail WCAG on keyboard navigation, screen reader announcements, cognitive load, and dozens of manual criteria.

The score weights violations by impact. A missing image alt text reduces the score more than a missing label for a decorative element. This means two pages with different failure patterns can have the same score despite having different severity of real-world impact.

3. How to Run Lighthouse

In Chrome DevTools

  • Open Chrome DevTools (F12)
  • Go to the Lighthouse tab
  • Select Accessibility: deselect others to speed up the run
  • Choose Mobile or Desktop mode
  • Click Analyse Page Load
  • Lighthouse runs, reloads the page, and returns the report

In the Node CLI

  • Install: npm install -g lighthouse
  • Run: lighthouse https://example.com --only-categories=accessibility --output=json
  • Output: JSON report with full violation details, scores, and passing audits
Run Lighthouse in an incognito window or with browser extensions disabled. Extensions including WAVE and axe DevTools can interfere with page load and affect the score.

How to Test With Lighthouse

Tier 1: Pipeline automation

Use lighthouse-ci to run Lighthouse on every build and fail when the accessibility score drops below a threshold. Set "categories:accessibility": ["error", {"minScore": 0.9}] in your lighthouserc.json. Track score trends across releases. Never let the score regress.

Tier 2: Semi-automated: Lighthouse in Chrome DevTools

  • Open Chrome DevTools (F12), go to the Lighthouse tab
  • Select Accessibility only. Choose Desktop or Mobile mode.
  • Run in an incognito window with all extensions disabled for an accurate baseline
  • Review every flagged violation. Note the WCAG criterion and fix guidance.
  • Re-run after fixing violations to confirm the score improvement
  • Platforms: Chrome DevTools on Windows and Mac. Lighthouse CLI runs on any OS headlessly. Lighthouse Mobile mode simulates a mobile viewport but does not test native apps.

Where to practise: Open any of the A11y Test Playgrounds from this series in Chrome and run Lighthouse against them. The playgrounds contain deliberate violations: verify Lighthouse catches them and note which ones it misses.

  • Axe DevTools Playground: contains Critical and Serious violations
  • Dynamic Content Playground: live region failures Lighthouse cannot catch
  • Forms Playground: mix of automated and manual failures

Tier 3: Manual: what Lighthouse cannot catch

  • Keyboard navigation: Tab through every interactive element. Lighthouse cannot navigate.
  • Screen reader testing: NVDA + Firefox on Windows, VoiceOver + Safari on Mac. Lighthouse score of 100 does not mean screen readers work correctly.
  • iOS VoiceOver: Physical iPhone + Safari.
  • Android TalkBack: Physical Android device + Chrome.
  • Dynamic content: Trigger interactions after page load. Re-run axe DevTools: Lighthouse does not re-scan post-interaction.

6. Lighthouse in CI/CD

Lighthouse CI (lhci) integrates Lighthouse into CI pipelines and can fail builds when the accessibility score drops below a defined threshold.

{
  "ci": {
    "assert": {
      "assertions": {
        "categories:accessibility": ["error", {"minScore": 0.9}]
      }
    }
  }
}

A threshold of 0.9 (90) is a reasonable starting point. The goal should be 1.0 (100). Never allow the score to regress. A Lighthouse score threshold in CI is a floor, not a ceiling: meeting the threshold does not mean the page is accessible.

7. WCAG 2.1 AA Coverage

Lighthouse covers the same automated subset of WCAG 2.1 AA as axe DevTools because it runs the same axe-core rules. Its value is in CI integration and historical score tracking.

Use Lighthouse for score tracking in CI and catching regressions across releases. Use axe DevTools in the browser for detailed per-component violation investigation. Lighthouse for the trend, axe DevTools for the detail.
How to use Lighthouse without being misled
  • A score of 100 is the minimum bar, not a passing grade for accessibility.
  • Use Lighthouse CI to prevent score regression between releases.
  • Never report a Lighthouse score to stakeholders as evidence of WCAG conformance.
  • Run Lighthouse in incognito with all extensions disabled for an accurate baseline.

Mobile Testing: What These Tools Cannot Do

Browser-based tools like axe DevTools, WAVE, and Lighthouse run on desktop browsers. They cannot test native mobile apps, and they cannot replicate the experience of a screen reader user on a phone. The issues these tools catch still need to be verified on mobile. Use these apps to test the same failure patterns in a native mobile context.
