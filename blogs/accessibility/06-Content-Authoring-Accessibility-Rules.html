Testing Content for Accessibility

Tier 1: Pipeline automation

axe-core catches some content failures: missing image alt text, empty links, colour contrast on text. It does not catch plain language quality, reading level, vague link text, or logical heading structure. Content accessibility is predominantly a manual concern.

Tier 2: Semi-automated tools

WAVE Structure tab gives the fastest visual overview of heading hierarchy. Its Links panel lists all link text for review. Use the Alt Text Playground and Headings Playground to practise identifying failures.

Tier 3: Manual

Platform coverage: Test on Windows (Chrome + Firefox), Mac (Safari + Chrome), iOS (Safari on physical iPhone), and Android (Chrome on physical device). Platform differences in keyboard handling and screen reader behaviour mean a bug on one platform does not guarantee the same behaviour on another.

Read every alt text aloud: if it sounds meaningless, it fails. Tab through all links and read only the link text: if the destination is unclear, it fails. Read headings in sequence: if the structure is illogical without surrounding content, it fails. On mobile: verify content scales correctly with iOS Dynamic Type enabled and Android font size at Large.

1. Who This Is For

This blog is for anyone who puts content into a product: text, images, links, forms, or media. CMS author, developer, UX writer, or QA reviewing it. The rules apply regardless of how the content gets in.

The content layer is not a CMS feature. It is a phase of delivery. Every project has one.

2. Alt Text: Meaningful, Not Missing

Every image that conveys information needs alt text that describes what the image communicates, not what it looks like. A decorative image needs an empty alt attribute so the screen reader skips it entirely. A missing alt attribute means the screen reader reads the filename aloud: which is never useful and occasionally embarrassing.

ALT
Alt text rules
WCAG 1.1.1
Informative images need alt text that describes the purpose, not the visual. A photo of someone signing a document used as a CTA should have alt text describing the action, not the scene.

Decorative images need alt="" so screen readers skip them. A background flourish or a divider line communicates nothing. Making a screen reader announce it is noise.

Image links must have alt text describing the destination, not the image. A logo that links to the homepage should read "Go to homepage": not "Company logo."
Fail
"image"
"img_final_v3.jpg"
"photo of team"
alt attribute missing
Pass
"Download the 2024 annual report"
"Team members at the 2024 conference"
alt="" (decorative)
alt="Go to homepage" (logo link)
CMS enforcement
The alt text field must be separate from the description field and required for non-decorative images. Add a decorative flag checkbox: when checked, alt is set to empty automatically. Authors who cannot find the alt text field will put it in the wrong field. Every time.
Non-CMS enforcement
Use eslint-plugin-jsx-a11y to enforce the alt prop as required on all img elements. Fail the build on missing alt text. UX annotates alt text in Figma before handoff so developers are never guessing.

3. Headings: One H1, No Skipped Levels

Screen reader users navigate by headings the same way sighted users scan a page visually. A broken heading structure is the equivalent of a document with random bold text instead of a table of contents: technically readable, practically useless.

  • One H1 per page.
  • Heading levels must be sequential: H1 then H2 then H3, no skipping.
  • Heading levels must reflect content hierarchy, not visual size preferences.
H1
Heading rules
WCAG 1.3.1 · 2.4.6
One H1 per page: the page title. H2 for main sections. H3 for subsections. Never skip a level. Never choose a heading level for its size.
The CSS vs heading problem: real example
A designer wants a section label to look large and bold. An author or developer picks H2 because it renders big: not because it is a section heading in the document structure. The correct fix is one line of CSS:

.section-label { font-size: 1.4rem; font-weight: 600; } /* no heading element needed */
The heading element is for structure. CSS is for size. Mixing them breaks screen reader navigation on every page that inherits the pattern.
Fail
H1: Homepage
H3: Latest news (H2 skipped)
H1: About us (second H1)
Bold text used as a subheading
Pass
H1: Homepage
H2: Latest news
H3: Individual article title
H2: About us
CMS enforcement
Restrict heading levels in the rich text editor. H1 should not be available in body content: that is the page title field. Allowed levels in body: H2 and H3 only. This prevents the most common failure without requiring author training.
Non-CMS enforcement
Heading levels defined in component hierarchy. The page title component renders H1. Section headers render H2. The developer does not choose the level: the component does.

4. Link Text: No "Click Here"

Screen reader users can pull up a list of all links on a page and navigate by them directly. If your link list reads "Click here, Read more, Click here, Learn more, Click here": that list is completely useless. Each link must describe its destination from the link text alone.

LNK
Link text rules
WCAG 2.4.4
Link text must describe the destination or action from the link text alone, not the surrounding paragraph. Not the page heading. The link text itself: because that is all a screen reader announces when listing links.

Click here
Read more
Learn more
Download
Here
Pass
Download the 2024 accessibility report

CMS and non-CMS enforcement
This one is harder to enforce with a field rule: it requires author awareness. The most effective CMS intervention is a validation warning when a link field contains "click here", "read more", or "here" as the complete link text. In coded products, link text comes from the author or from a data model: an accessibility linting rule cannot check the meaning, only the presence.

5. Error Messages: Descriptive, Not Vague

Error messages are not a developer's responsibility to write. They are content, and they must be written by someone who understands what the user needs to do to fix the problem. "Invalid input" tells a screen reader user precisely nothing. "Enter a valid UK phone number, for example: 07700 900000" tells them exactly what to do.

Error message comparison: vague vs descriptive
Field Vague: Fail Descriptive: Pass
EmailInvalid inputEnter a valid email address, for example: you@domain.com
PasswordPassword errorPassword must be at least 8 characters and include one number
Date of birthInvalid dateEnter your date of birth in DD/MM/YYYY format, for example: 15/06/1990
Phone numberRequired fieldEnter a UK phone number, for example: 07700 900000
PostcodeErrorEnter a full UK postcode, for example: SW1A 1AA

Error messages must be written at design stage (Blog 05 covers this), stored in CMS fields or data models: not hardcoded by developers: and programmatically associated with the input they describe.

6. Media: Captions, Transcripts, No Autoplay

VID
Media rules
WCAG 1.2.1 · 1.2.2 · 2.2.2
Captions: Every prerecorded video with audio must have synchronised captions. Auto-generated captions (YouTube, Teams) do not meet this requirement: they are frequently inaccurate and do not meet WCAG 1.2.2. Human-reviewed captions only.

Transcripts: Audio-only content (podcasts, voice recordings) must have a full text transcript. The transcript must be available near the media, not buried in a separate page.

Autoplay: Any media that autoplays audio must have a mechanism to pause, stop, or mute it within the first three elements. Autoplay audio that cannot be stopped fails WCAG 1.4.2 and is deeply disruptive to screen reader users.
Fail
Video published with no captions
Auto-generated captions only
Podcast with no transcript
Background video autoplays with audio
Pass
Human-reviewed captions uploaded
Full transcript linked below media
Autoplay off by default
Pause control visible and keyboard-operable
CMS enforcement
Require a captions file field and a transcript URL field on every video entry. Make them required before publishing. Set autoplay to off in the component default and require a deliberate override to enable it: not the other way around.

7. Colour Is Not Enough on Its Own

Colour alone cannot convey meaning. This applies to error states, status indicators, required field markers, data charts, and anything else where colour is the only signal. Approximately 8% of men have some form of colour vision deficiency: for them, red and green are often indistinguishable.

CLR
Colour-only communication
WCAG 1.4.1
Every use of colour to convey meaning must be paired with a text label, an icon, a pattern, or another non-colour visual indicator. A red border on a form field error is not enough: there must also be an error icon and error text. A green "Available" status is not enough: there must also be the word "Available."

(no icon, no text)

Green dot = available
Red dot = unavailable
(no text label)
Pass
Red border + error icon + "Enter a valid email"

Green dot + "Available"
Red dot + "Unavailable"

8. CMS Rules That Prevent Authoring Defects

The most effective accessibility governance in a CMS is not training. It is enforcement. A field rule that requires alt text is more reliable than an author who remembers to add it. A heading restriction that removes H1 from the rich text editor is more reliable than a style guide that says to avoid it.

CMS field rules that enforce accessibility at the authoring layer
Content area CMS rule What it prevents
ImagesAlt text field required. Decorative flag available. Alt field separate from description.Missing alt text. Alt text in wrong field.
HeadingsH1 removed from rich text editor. Only H2 and H3 allowed in body content.Multiple H1s. Skipped heading levels.
LinksValidation warning on link text containing "click here", "read more", "here".Generic link text that fails in screen reader link lists.
VideoCaptions file field required. Transcript URL field required. Autoplay off by default.Videos published without captions or transcripts.
FormsError message field required per validation rule. Label field required per input.Vague or missing error messages. Unlabelled inputs.
Page languageLocale field required. Maps to HTML lang attribute on publish.Missing or incorrect page language declaration.
If publishing is allowed, the system has approved the content. CMS rules are not optional extras: they are the accessibility governance layer.

9. Non-CMS Projects: Where the Content Layer Lives

In a project without a CMS, the content layer does not disappear: it moves. Here is where each authoring responsibility sits in a non-CMS project:

Content layer responsibilities in non-CMS projects
Content area Where it lives Who enforces it
Alt textComponent props, JSON data model, or Figma annotationDeveloper (required prop) + UX (Figma annotation)
Heading levelsComponent hierarchy: the component determines the levelDeveloper (component design) and UX (Figma annotation)
Link textComponent props or JSON content fieldContent owner + Developer (build warning for generic text)
Error messagesValidation schema or JSON copy fileContent owner writes copy. Developer implements.
CaptionsVideo component configuration or WebVTT file path in data modelDeveloper (required config) + Content owner (provides file)
Page languageHTML template or framework configDeveloper: set once, applies globally

The key difference from a CMS project: in a non-CMS project there is no authoring UI to add field-level validation. Enforcement happens through component design, required props, and build-time linting. Blog 04 covers who owns each lane in detail.

10. How QA Catches Content Defects

Content defects look different from code defects, but the testing approach is the same. QA looks for the failure, identifies the root cause phase, and assigns the defect to the right owner.

What to check manually

  • WAVE: red icons flag missing alt text instantly
  • Open Accessibility Insights heading visualiser: broken hierarchy is immediately visible
  • Use NVDA Insert+F7 to open the links list: "click here" and "read more" appear in isolation
  • Tab to every form field: listen for what the screen reader announces as the label
  • Play every video: check for captions and confirm they are human-reviewed
  • Check every use of colour as a signal: look for a paired text or icon indicator

How to write the defect

Content defects belong to the content phase, not the development phase. The defect goes to the content author, with a note that the CMS model should enforce the field. Two fixes from one defect: the individual instance, and the systemic cause.

The bottom line

Every authoring mistake in this blog is preventable before QA sees it. CMS field rules, required props, build linting, and UX annotations are all cheaper than a QA defect. The question is not whether to enforce it: it is which layer does the enforcing.
