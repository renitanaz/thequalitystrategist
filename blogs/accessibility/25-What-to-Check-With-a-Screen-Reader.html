25 What to Check With a Screen Reader: The Operational Checklist for Every Session

This is the checklist you open before every screen reader testing session. It works with NVDA, VoiceOver, and TalkBack.

1. The Checklist

This blog is the operational companion to the individual screen reader guides (Blogs 20–24). Use it during every screen reader testing session regardless of which screen reader and platform you are testing on. The checks below apply to NVDA, VoiceOver, and TalkBack.

The core principle: close your eyes after the first few minutes. Navigate only by keyboard (desktop) or gesture (mobile). If you cannot complete any task by listening alone, that is an accessibility defect.

2. Page Structure

  • Page title: Load the page. The first thing announced must be a meaningful page title that identifies both the page and the site. "Home: Example Company" is correct. "Page" is not.
  • Skip link: Before any other content, a skip to main content link must be the first focusable element. Tab once: the skip link must be announced and operable.
  • Landmarks: Navigate landmarks (NVDA: D, JAWS: R, VoiceOver: VO+Cmd+L, rotor on mobile). Main, navigation, search, banner, contentinfo (footer) must all be present and labelled if there is more than one of the same type.
  • Heading hierarchy: Navigate headings. H1 must be present and unique. Heading levels must not skip (H1 to H4 with no H2 or H3 is a failure). All visible headings must be semantic heading elements.
  • Reading order: Read from the top continuously (NVDA: Insert+Down, JAWS: Insert+Down, VoiceOver: VO+A). The reading order must match the visual order. Content that appears visually first must be announced first.

3. Interactive Elements

  • Every interactive element is reachable: Tab through all interactive elements (links, buttons, inputs, custom controls). Nothing should be unreachable by Tab. No focus traps without an Escape mechanism.
  • Every interactive element has a label: When focus lands on a button, link, or input: the screen reader must announce a meaningful name. "Button" with nothing else is a failure. "Submit, button" is correct.
  • Role is announced: The element type must be announced. Button, link, checkbox, radio, combobox, tab: if the role is not announced, ARIA is missing or wrong.
  • State is announced: Expanded/collapsed for accordions and menus. Checked/unchecked for checkboxes. Selected/not selected for radio buttons and tabs. Required for required form fields. Invalid when in an error state.
  • Links describe their destination: Navigate the links list. Every link must make sense when read in isolation. "Read more" is a failure. "Read our 2024 accessibility report" is correct.

4. Images

  • Meaningful images have descriptive alt text: Navigate graphics. Each meaningful image must announce content that conveys the same information a sighted user gets. A chart with alt="bar chart" is a failure.
  • Decorative images are silent: Decorative images must be skipped entirely. If a background swoosh is announced as "decorative wave graphic": it has non-empty alt text and should use alt="".
  • Functional images describe the action: A linked icon must announce the destination or action, not the visual appearance. "Shopping cart icon, link" is a failure. "Go to checkout, link" is correct.

5. Forms

  • Every field has a label: Tab to each input. "Edit text, blank" means no label. "Email address, edit text" is correct.
  • Required fields are announced: "Email address, required, edit text": required must be in the announcement, not only indicated by a visual asterisk.
  • Errors are announced without requiring navigation: Submit the form with errors. Error messages must be announced immediately via role="alert". The user must not need to Tab to find out what went wrong.
  • Error descriptions are re-announced on field refocus: Tab back to an error field. The error description must be announced via aria-describedby alongside the label and invalid state.
  • Radio button groups announce the group question: Tabbing to a radio button must announce the group question (from the fieldset legend) before the option label.

6. Dynamic Content

  • Status messages are announced without focus moving: Navigate focus away from live regions. Trigger each dynamic update (add to cart, filter, load, toast). Every update must be announced without the user navigating to it.
  • Alerts interrupt immediately: Role="alert" content must interrupt whatever the screen reader is reading. If an error summary appears silently, it has no role="alert".
  • Loading completion is announced: Trigger an async action. The loading state may be announced. When loading completes, a completion message must be announced.

7. Tables

  • Table structure is announced: Navigate to a table. The screen reader must announce the number of rows and columns.
  • Column headers are announced per cell: Navigate cell by cell using Ctrl+Alt+arrow (desktop). Each cell must announce its column header before the data.
  • Complex tables have captions or descriptions: Tables with multiple header levels or complex relationships must have a caption or aria-describedby to explain the structure.

The 10-minute structural audit
  • Load page. Listen to page title. Tab once to skip link.
  • Navigate landmarks. Are main, nav, search, and footer all present?
  • Navigate headings. Is the hierarchy logical and complete?
  • Open elements/links list. Are all link texts descriptive?
  • Tab through form fields. Does every field announce a label?
  • Submit form empty. Are errors announced immediately?
  • Navigate graphics. Does every meaningful image have useful alt text?
  • Move focus, trigger dynamic updates, listen for announcements.
