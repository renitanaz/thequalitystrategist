32 Pa11y in CI/CD: Command-Line Accessibility Testing for Pipelines

Pa11y runs from the command line, outputs JSON, and integrates into any CI pipeline without a browser extension or GUI. It is the fastest way to add accessibility gates to a build.

1. What Pa11y Is

Pa11y is a free, open-source command-line accessibility testing tool. It launches a headless browser, loads a URL, runs accessibility checks using axe-core or HTML_CodeSniffer as the underlying engine, and returns results as JSON, CSV, or CLI output. It requires no browser extension and no GUI: making it the cleanest tool for integrating accessibility into a CI pipeline without adding browser dependencies.

2. Install and First Run

npm install -g pa11y

# Run against a URL
pa11y https://example.com

# Run with WCAG 2.1 AA standard
pa11y --standard WCAG2AA https://example.com

# Output as JSON
pa11y --reporter json https://example.com > results.json

Pa11y outputs each issue with: type (error, warning, notice), message, context (the HTML element), and the WCAG criterion reference.

3. Configuration and WCAG 2.1 AA Targeting

Pa11y accepts a configuration file (.pa11yrc) or inline options. For WCAG 2.1 AA compliance testing:

# .pa11yrc
{{
  "standard": "WCAG2AA",
  "reporters": ["json"],
  "threshold": 0,
  "ignore": [
    "notice",
    "warning"
  ],
  "chromeLaunchConfig": {{
    "args": ["--no-sandbox"]
  }}
}}
  • standard WCAG2AA: Targets WCAG 2.1 AA rules specifically
  • threshold 0: Fails if any errors are found. Increase to allow a known number of violations during remediation.
  • ignore notice/warning: Focus the gate on errors only: the definite failures.
  • chromeLaunchConfig no-sandbox: Required for running in most CI environments (GitHub Actions, Jenkins, Docker).

4. Integrating Pa11y in CI

Pa11y exits with code 2 when violations are found: CI tools treat a non-zero exit code as a build failure. No additional configuration needed to fail the build.

# GitHub Actions example
- name: Run Pa11y accessibility check
  run: |
    npm install -g pa11y
    pa11y --standard WCAG2AA --reporter json       https://staging.example.com > pa11y-results.json
    
- name: Upload Pa11y results
  uses: actions/upload-artifact@v3
  with:
    name: pa11y-results
    path: pa11y-results.json

For multiple pages, use pa11y-ci which accepts a list of URLs and runs Pa11y against each:

npm install -g pa11y-ci

# pa11y-ci.json
{{
  "urls": [
    "https://staging.example.com/",
    "https://staging.example.com/about",
    "https://staging.example.com/contact"
  ],
  "defaults": {{
    "standard": "WCAG2AA",
    "ignore": ["notice", "warning"]
  }}
}}

pa11y-ci --config pa11y-ci.json

5. Pa11y Dashboard for Multi-Page Monitoring

Pa11y Dashboard is a web interface for scheduling and monitoring Pa11y runs across multiple URLs over time. It stores historical results and shows trend data: useful for tracking accessibility improvement or regression across a site over weeks and sprints.

Pa11y Dashboard requires a MongoDB database and a Node server. It is most useful for teams managing large sites with many pages where per-page tracking in CI output becomes unwieldy.

How to Test: Tiers and Platform Coverage

Tier 1: Pipeline automation

Pa11y is a Tier 1 tool by design. It runs from the command line or CI pipeline and exits with a non-zero code on violations. Key setup for WCAG 2.1 AA:

  • Set "standard": "WCAG2AA" in .pa11yrc to target WCAG 2.1 AA rules
  • Set "threshold": 0 to fail on any error: increase temporarily during active remediation
  • Ignore notices and warnings in CI gates: focus errors only for build failures
  • Use pa11y-ci with a URL list to scan multiple pages per build
  • Add --chromeLaunchConfig: args: ["--no-sandbox"] for Docker/CI environments
  • Platforms: Runs on any OS with Node.js: Linux, Mac, Windows. No browser installation required separately (uses bundled Chromium).

Tier 2: Semi-automated tools

Pa11y has no browser extension equivalent. After a Pa11y CI failure, use axe DevTools or WAVE in the browser to visually inspect and locate the element. Pa11y uses axe-core by default: violations reported in CI can be reproduced immediately with axe DevTools on the same page.

Tier 3: Manual: what Pa11y cannot catch

  • Post-interaction states: Pa11y scans page load only. Modals, accordions, form errors, and filter results after interaction require manual or scripted testing.
  • Keyboard navigation: Pa11y cannot Tab. Navigate every interactive element manually.
  • Screen reader testing: NVDA + Firefox on Windows, VoiceOver + Safari on Mac, VoiceOver on iOS (physical device), TalkBack on Android (physical device).
  • Alt text quality: Pa11y confirms alt attribute exists: meaningful description requires human review.
  • Mobile browsers: Pa11y does not run on mobile. Pa11y CI scanning a mobile-rendered viewport is not the same as testing on a physical device.

7. What Pa11y Catches and Misses

Pa11y catches the same automated subset as axe DevTools and Lighthouse: missing labels, contrast failures, invalid ARIA, empty buttons: because it uses the same axe-core engine by default. It misses the same things: keyboard navigation logic, screen reader announcements, focus order, alt text quality, and interaction-state violations unless scripted explicitly.

When to choose Pa11y
  • You want to scan a list of public URLs in CI without modifying your test suite.
  • You need a simple CLI tool that fails the build and outputs JSON without browser extension setup.
  • You are monitoring a staging environment's accessibility across multiple pages between releases.
  • Your team does not yet have Playwright or Cypress: Pa11y is the fastest accessibility gate to add to any pipeline.

Mobile: What Pipeline Tools Cannot Test

Pipeline automation tools run on desktop CI servers and scan web pages. They cannot test native mobile apps and cannot replicate screen reader experience on a phone. The failures they catch still need to be verified on physical devices. These apps provide real broken implementations to test against:
