23 VoiceOver on iOS: Screen Reader Testing on iPhone and iPad

VoiceOver on iOS is used by millions. Testing on a physical device takes 20 minutes. Not testing it is not an option.

1. Why VoiceOver on iOS

VoiceOver on iOS is Apple's built-in screen reader for iPhone and iPad. It is the primary assistive technology for iOS users and is used by a significant proportion of the screen reader user population on mobile. Testing must be done on a physical device: iOS Simulator does not replicate gesture behaviour, touch exploration, or focus management accurately.

Always test on a physical iPhone or iPad. The iOS Simulator cannot replicate how VoiceOver handles gestures, touch exploration, or how apps announce dynamic content changes.

2. Enabling and Configuring VoiceOver

  • Enable: Settings, Accessibility, VoiceOver, Toggle ON
  • Shortcut: Triple-click the side button (or Home button) if configured at Settings, Accessibility, Accessibility Shortcut, VoiceOver
  • Speech rate: Settings, Accessibility, VoiceOver, Speaking Rate: drag slider. Start slow when learning gestures.
  • Recommended browser: Safari on a physical device
  • Tip: Connect a Bluetooth keyboard to use keyboard shortcuts alongside touch gestures: useful for desk-based testing sessions

4. The Rotor on iOS

The rotor is VoiceOver's navigation control. Rotate two fingers on the screen to open it. The rotor appears and announces a category. Continue rotating to cycle through: Headings, Links, Form Controls, Images, Landmarks, Characters, Words, Lines.

Once a rotor category is selected, swipe up or down to navigate between items of that type. This is the fastest way to navigate page structure on iOS:

  • Headings: navigate page structure. Listen for heading level.
  • Links: test link text. Any "read more" is immediately findable.
  • Form Controls: navigate form fields. Listen for label, type, required state.
  • Images: test alt text. Listen for what VoiceOver announces.

5. What to Test and What to Listen For

Navigation and structure

Set rotor to Headings. Swipe down through all headings. Is the hierarchy logical? Are there any missing heading levels? Do all headings announce a level?

Forms on iOS

Navigate to each form field using the Form Controls rotor category. When focus lands on a field, VoiceOver announces the label, field type, and required state. Double-tap to activate and enter text. After submitting with errors, role="alert" content is announced immediately. Navigate back to error fields: the error description should be re-announced.

Correct: "Email address, required, text field" | Failure: "text field" with no label

Custom components

Double-tap to activate buttons and links. For toggles and checkboxes, double-tap toggles the state and VoiceOver announces the new state. For custom components using ARIA, the role and state must be explicitly set: VoiceOver does not infer state from visual styling.

Live regions on iOS

Navigate focus to a heading. Trigger a dynamic content change. VoiceOver should announce role="status" content when idle and role="alert" content immediately. If VoiceOver is silent after a dynamic update, the live region is missing or the container was created simultaneously with its content.

The testing flow
  • Rotor, Headings: swipe through the full heading structure
  • Rotor, Form Controls: verify every field announces a label
  • Rotor, Images: verify every meaningful image announces alt text
  • Rotor, Links: check for non-descriptive link text
  • Navigate away from live regions, trigger updates, listen
