13 Colour Contrast Testing: Web, Android, iOS and Colour Blindness Simulation

The numbers are exact. The tools are free. There is no excuse for a contrast failure reaching production.

1. The Ratios: What You Are Testing Against

Contrast testing is not subjective. The WCAG requirements are precise numbers. Either the ratio meets the threshold or it does not.

4.5:1
Normal text: body copy, labels, links. Under 18pt regular or 14pt bold.
WCAG 1.4.3 · Level AA
3:1
Large text (18pt+ regular or 14pt+ bold) and UI component boundaries: input borders, focus rings, button outlines.
WCAG 1.4.3 / 1.4.11 · Level AA
7:1
Enhanced: WCAG AAA. Not required for AA compliance but worth flagging where ratios are close to the minimum.
WCAG 1.4.6 · Level AAA
Decorative text and text in logos are exempt from contrast requirements. Everything else is in scope: including placeholder text, disabled state labels, and tooltip text. These are commonly missed.

2. What Fails Contrast and Why It Matters

The most common contrast failures in production are not bad design decisions: they are untested assumptions. A colour combination that looks fine on a calibrated designer monitor at 100% brightness can fail for users with low vision, on budget screens, in bright sunlight, or with age-related contrast sensitivity loss.

What the examples above show: the same yellow brand colour that fails on white passes easily with dark text on it. Contrast failures are almost always fixable by adjusting one colour token, not redesigning the component.

3. How to Test: Automation, Tools, and Platform Coverage

🎯
Practice these yourself
Interactive contrast failure examples are available in the Colour Contrast Playground. Mobile testing steps are in the Mobile Testing Guide.

Tier 1: Pipeline automation

These run in CI/CD without human involvement. They catch failures on every pull request before code merges.

  • axe-core in Playwright or Cypress: flags text colour against background colour failures where both are solid, computed CSS values. Also catches large text failing 3:1 and UI component boundary failures where the boundary colour is in the stylesheet.
  • Pa11y: runs the same axe-core ruleset in a headless browser. Useful for scanning pages that require no authentication and for nightly regression scans across large sites.

Tier 2: Semi-automated tools

A human opens these and runs them on a live page. They automate the measurement work but need a person to trigger them, review results, and investigate flagged elements.

  • WAVE: open the Contrast tab for an instant visual map of all contrast failures on the page. Shows ratio, required minimum, and highlights the failing element in place.
  • axe DevTools: run a full page scan and filter by color-contrast. Shows exact element, computed ratio, and required minimum. Export to CSV for defect logging.
  • WebAIM Contrast Checker: takes two hex values and returns the ratio with AA and AAA pass/fail. Use it to verify a specific combination or propose a passing fix colour.
  • Chrome DevTools colour picker: select any text element, click the colour swatch in Styles. Contrast ratio and AA pass/fail displayed inline. No extension needed.

Tier 3: Manual checks only

No tool can detect these. They require a human looking at the rendered page.

  • Text over images or gradients: pipeline automation reads the CSS background-color property. If the visual background is an image or gradient, the computed value is wrong or absent. Check visually with the Chrome DevTools eyedropper on the actual rendered pixel.
  • Placeholder text contrast: many automated tools skip ::placeholder pseudo-elements. Inspect the element in DevTools, find the placeholder rule, and check its colour manually.
  • Disabled state contrast: WCAG exempts genuinely disabled controls. Check whether elements styled to look disabled are actually using the disabled attribute or just CSS styling.
  • Colour blindness simulation: no tool checks whether meaning is lost for colour-blind users. Use Chrome DevTools Rendering panel (Emulate vision deficiencies) and walk through the UI manually.
  • Dynamic states: hover, focus, active, error, selected. Trigger each state manually and check contrast at that moment with the DevTools colour picker.
  • Native mobile screens: pipeline automation cannot reach native iOS or Android UI. Use Accessibility Scanner (Android) or DAC Color Contrast Checker and Accessibility Checker - AI EAA (iOS) per platform.

4. Testing on Web: Tools and Steps

WAVE Contrast tab

Open WAVE on the page. Click the Contrast tab. Every text element with a contrast failure is listed with its ratio, the required ratio, and a link to the element. This is the fastest first pass: it covers all visible text on the page in one scan.

axe DevTools

axe DevTools flags contrast failures as Critical violations. Run a full page scan. Filter by "color-contrast" to isolate contrast issues. The panel shows the exact element, the computed ratio, and the required minimum. Export to CSV for defect logging.

WebAIM Contrast Checker

WebAIM Contrast Checker at webaim.org/resources/contrastchecker/ takes two hex values and returns the ratio with AA and AAA pass/fail for normal text, large text, and UI components. Use it when you need to verify a specific colour combination or propose a fix with a passing ratio.

Colour Contrast Analyser (desktop app)

Colour Contrast Analyser by TPGi is a free desktop application for Windows and Mac. It includes an eyedropper tool to sample colours directly from any screen content: including images, PDFs, and native apps. Download from tpgi.com/color-contrast-checker/. Essential for testing contrast in non-browser contexts.

Chrome DevTools colour picker

In Chrome DevTools, select any text element. In the Styles panel, click the colour swatch next to the text colour. The colour picker shows the contrast ratio against the current background inline. A AA pass/fail indicator appears immediately. No extension needed.

5. Colour Blindness Simulation

Approximately 8% of men and 0.5% of women have some form of colour vision deficiency. The most common type is red-green colour blindness (deuteranopia and protanopia), where red and green appear similar. This directly affects error states, success indicators, and any interface that uses colour as the only signal.

Web: Chrome DevTools colour blindness simulation

In Chrome DevTools, open the Rendering panel (More tools → Rendering). Scroll to "Emulate vision deficiencies." Select from: Blurred vision, Protanopia, Deuteranopia, Tritanopia, Achromatopsia. The page re-renders immediately. Walk through the UI with each simulation active and check whether any meaning is lost when colour is removed.

Figma: Stark plugin

Stark in Figma runs colour blindness simulation across all eight deficiency types before a design is handed off. Blog 05 covers Stark at the design phase.

6. Testing on iOS

Display Accommodations

iOS has built-in display accessibility settings that simulate how users with visual impairments experience your app. Settings, Accessibility, Display and Text Size:

  • Increase Contrast: darkens borders and separates visual elements more strongly. If your UI breaks or becomes unclear when this is enabled, contrast is likely borderline.
  • Differentiate Without Colour: removes colour from UI controls. Anything that relied on colour alone becomes a blank square or loses meaning. This directly tests WCAG 1.4.1.
  • Reduce Transparency: solidifies translucent backgrounds. Tests whether layered UI elements maintain readable contrast when glass effects are removed.

Colour filters for colour blindness simulation

Settings, Accessibility, Display and Text Size, Colour Filters. Enable colour filters and select: Greyscale, Red/Green filter (Protanopia), Green/Red filter (Deuteranopia), Blue/Yellow filter (Tritanopia). Navigate through the app with each filter active. Any meaningful information that disappears or becomes ambiguous is a failure.

DAC Color Contrast Checker app

DAC Color Contrast Checker (by Digital Accessibility Centre) overlays contrast ratio measurements directly on screenshots of your app. Useful for native app screens where browser-based tools cannot reach. Download from the App Store.

Accessibility Checker - AI EAA

Accessibility Checker - AI EAA by Accessible Developer Ltd scans your screen for accessibility issues including colour contrast failures. Point it at any app screen and it reports contrast ratios with WCAG pass/fail status.

7. Testing on Android

Display settings

Settings, Accessibility, Display. Key options:

  • High Contrast Text: forces text to render with a stronger contrast outline. If text becomes hard to read with this enabled, the original contrast was insufficient.
  • Colour Correction: Settings, Accessibility, Colour and Motion, Colour Correction. Deuteranomaly, Protanomaly, Tritanomaly modes available. Equivalent to iOS colour filters.
  • Colour Inversion: inverts all colours. Useful for quick identification of elements where contrast depends entirely on a colour relationship that inverts poorly.

Accessibility Scanner

Accessibility Scanner is a free Android app that scans app screens and flags contrast failures with exact ratios. It requires no code access: it analyses the rendered screen. Download from the Play Store, enable it in Accessibility settings, then navigate through the app. A floating button appears; tap it to scan.

DAC Color Contrast Checker app

DAC Color Contrast Checker is also available on Android and provides the same screenshot-based contrast analysis as on iOS. Download from the Play Store.

8. Writing Contrast Defects

A contrast defect needs to be specific and reproducible. "Text is hard to read" is not a defect. "Body text #aaaaaa on background #ffffff measures 2.3:1, fails WCAG 1.4.3 AA (minimum 4.5:1)" is a defect.

Every contrast defect must include:

  • Foreground colour (hex or RGB): the exact text or UI component colour
  • Background colour (hex or RGB): the exact background colour behind it
  • Measured ratio: e.g. 2.3:1
  • Required ratio: 4.5:1 for normal text, 3:1 for large text or UI boundaries
  • WCAG criterion: 1.4.3 for text, 1.4.11 for UI components
  • Element and location: "placeholder text in search input, homepage header"
  • Tool used: axe DevTools, WAVE, WebAIM Checker, Colour Contrast Analyser
Always include a suggested fix. "Foreground colour changed to #767676 achieves 4.5:1 on #ffffff" saves a design round-trip and gets the defect resolved faster.
The fast check

Run WAVE Contrast tab and axe DevTools on every page before sign-off. Then open Chrome DevTools Rendering panel and run Deuteranopia simulation. Walk through the UI. Anything that loses meaning under the simulation is a WCAG 1.4.1 failure: colour used as the only signal.
