1. What axe DevTools Is

axe DevTools is a browser extension built on axe-core, the open-source accessibility rules engine maintained by Deque Systems. The same engine that runs in the extension runs in your CI pipeline via the axe-core npm package. This means a violation flagged in the browser during development is the same violation that fails a build in CI: no rule differences, no score drift between environments.

The free extension is available for Chrome and Firefox. It runs a rules-based scan on the current page state and returns structured violations with impact level, WCAG criterion, DOM element reference, and remediation guidance. The Pro version adds guided testing workflows and more rules, but the free version covers the majority of automated detectable violations.

axe DevTools is a Tier 2 semi-automated tool. It scans the rendered DOM and returns structured violations. It does not replace keyboard testing, screen reader testing, or visual judgment: but it covers more WCAG criteria with more precision than any other browser-based tool.

2. Impact Levels: Critical, Serious, Moderate, Minor

axe DevTools categorises every violation by impact. Unlike WAVE which distinguishes errors from alerts, axe uses four levels that indicate the severity of the user experience barrier.

Critical
Blocks access entirely for users with disabilities. Fix before any release. Examples: missing form labels, empty buttons, keyboard traps.
Serious
Significant barrier, difficult to work around. Fix before release. Examples: colour contrast failures, missing landmark regions, invalid ARIA.
Moderate
Some users will find a workaround but the experience is degraded. Fix before release where possible. Examples: redundant alt text, missing table headers.
Minor
Best practice violations with minimal user impact. Fix in the next available sprint. Examples: redundant title attributes, empty table summary.
For WCAG 2.1 AA compliance, treat Critical and Serious violations as release blockers. Moderate violations should be fixed before the sprint closes. Minor violations go in the backlog with a defined resolution date.

3. How to Use axe DevTools in the Browser

  1. Install: axe DevTools Chrome extension or Firefox Add-on from Deque.
  2. Open DevTools: F12 then find the axe DevTools panel in the DevTools tabs.
  3. Run a scan: Click Analyse. axe scans the current DOM state and returns all violations, passes, and incomplete checks.
  4. Review violations: Each violation shows: rule ID, impact level, WCAG criterion, affected element (with highlight on page), and remediation guidance.
  5. Use the element highlight: Click any violation to highlight the affected element in the browser. This is the fastest way to locate the issue without reading DOM selectors.
  6. Check incomplete results: axe returns an "incomplete" category for rules it cannot automatically determine: these require manual verification. Never ignore the incomplete list.
  7. Trigger interactions then re-scan: Open a modal, submit a form, expand an accordion. Run axe again on the updated DOM. axe only scans the current DOM state.

The incomplete list matters

axe returns three categories: violations (definite failures), passes (confirmed passing), and incomplete (needs manual check). The incomplete list includes colour contrast on images, ARIA labels that exist but may not be descriptive, and focus order. These are not false positives: they are genuine checks axe cannot resolve programmatically. Review every incomplete item.

How to Test With axe DevTools

Tier 1: Pipeline automation

Add axe-core to your Playwright or Cypress test suite. Run with withTags(['wcag2a','wcag2aa']) scoped to WCAG 2.1 AA. Fail builds on Critical and Serious violations only. Run axe after every significant interaction state: not just page load. See Blog 31 for full CI setup.

Tier 2: Semi-automated: axe DevTools in the browser

  • Install the axe DevTools Chrome extension
  • Open DevTools, go to the axe DevTools panel, click Analyse
  • Work through violations by impact: Critical first, then Serious
  • Review the Incomplete list: every item needs manual verification
  • Trigger interactions (open modal, submit form, apply filter), then re-run axe on the updated DOM
  • Use the element highlight to locate each violation on the page without reading DOM selectors

Platforms: Chrome and Firefox on Windows and Mac. axe-core also runs headlessly in CI on any OS. Mobile browser support is limited: use native testing tools for iOS and Android.

Tier 3: Manual: what axe cannot catch

  • Keyboard navigation: Tab through every interactive element. axe cannot determine whether the focus order is logical.
  • Screen reader announcements: NVDA + Firefox on Windows, VoiceOver + Safari on Mac. ARIA attributes present does not mean announcements are correct.
  • Alt text quality: axe confirms alt exists: read every alt text manually to verify it is meaningful.
  • iOS VoiceOver: Physical iPhone + Safari. axe does not run on iOS screen readers.
  • Android TalkBack: Physical Android device + Chrome. Same limitation.

6. axe-core in the Pipeline

The axe-core npm package brings the same rules engine into automated test suites. Install it as a dependency and integrate with Playwright, Cypress, or Jest to run accessibility scans as part of every build.

Playwright + axe-core example
import { checkA11y } from 'axe-playwright';

test('homepage has no critical violations', async ({ page }) => {
  await page.goto('/');
  await checkA11y(page, null, {
    runOnly: { type: 'tag', values: ['wcag2a', 'wcag2aa'] },
    includedImpacts: ['critical', 'serious']
  });
});
  • runOnly wcag2aa: Scope the scan to WCAG 2.1 AA rules only: avoids best-practice noise in CI
  • includedImpacts critical/serious: Fail the build only on Critical and Serious: prevents minor issues from blocking deployments
  • Scope to a component: Pass a CSS selector as the second argument to scan only a specific component rather than the full page
  • Run after interactions: Call axe after opening modals, submitting forms, and expanding accordions: not just on page load
The right workflow: axe-core in CI catches failures at build time before they reach testers. axe DevTools in the browser gives developers immediate feedback during development. Same engine, two touchpoints, consistent results.

The axe workflow
  • Run axe on page load. Fix all Critical and Serious violations before committing.
  • Trigger every interactive state: modals, accordions, form submissions, filters. Re-run axe on each.
  • Review the incomplete list. Every item in incomplete requires a manual check: it is not safe to ignore.
  • Add axe-core to CI with wcag2aa scope and critical/serious impact filter. Zero violations = green build.

Mobile Testing: What These Tools Cannot Do

Browser-based tools like axe DevTools, WAVE, and Lighthouse run on desktop browsers. They cannot test native mobile apps, and they cannot replicate the experience of a screen reader user on a phone. The issues these tools catch still need to be verified on mobile. Use these apps to test the same failure patterns in a native mobile context.
