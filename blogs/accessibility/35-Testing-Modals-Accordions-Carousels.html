35 Testing Modals, Accordions and Carousels: How to Test the Components That Break Most Often

Modals, Accordions, Carousels auto-advance with no pause. These three components fail accessibility more often than any others.

Series: Shift-Left Accessibility ·Blog 35 of 38 ·9 min read
In this blog
  1. Modals and dialogs
  2. Accordions and disclosure widgets
  3. Carousels and slideshows
  4. Common failure patterns across all three

1. Modals and Dialogs

A modal dialog must: move focus inside the modal when it opens, trap focus within the modal while it is open (Tab cycles only inside), return focus to the trigger element when it closes, and be announced as a dialog with its title when focus enters.

What to test

  • Focus moves on open: Click the trigger. Focus must move inside the modal immediately: usually to the heading, the first focusable element, or the close button depending on the design. If focus stays on the trigger, the modal is not announced.
  • Focus is trapped: Tab through all focusable elements in the modal. Focus must cycle within the modal: it must not escape to the page behind. If Tab reaches the last element and jumps to the browser chrome, the focus trap is broken.
  • Shift+Tab works: Reverse Tab also traps within the modal. If Shift+Tab escapes the modal, the trap is one-directional.
  • Escape closes: Press Escape. The modal must close. Focus must return to the element that triggered the modal.
  • Close button is labelled: An X icon button with no accessible name fails WCAG 4.1.2. It must have aria-label="Close" or equivalent.
  • Role is announced: NVDA must announce "dialog" and the modal title when focus enters. If it announces nothing, role="dialog" is missing or aria-labelledby is not pointing to the modal heading.

ARIA requirements

  • role="dialog" on the modal container
  • aria-modal="true" to inform screen readers the background is inert
  • aria-labelledby pointing to the modal heading ID
  • Focus management via JavaScript on open and close
The most common modal failure: the modal opens visually but NVDA announces nothing because focus did not move. The screen reader user is still on the trigger button, reading the page behind the modal.

2. Accordions and Disclosure Widgets

An accordion trigger must be a button, must announce its expanded or collapsed state, must control the visibility of its panel, and must move focus to the panel content when appropriate.

What to test

  • Trigger is a button: Tab to the accordion header. NVDA must announce it as "button": not "heading" or "link" alone. A heading wrapping a button is valid: "Shipping information, collapsed, button."
  • State is announced: NVDA must announce "expanded" or "collapsed" with the button. If only the label is announced with no state, aria-expanded is missing.
  • Activate and verify: Press Space or Enter on a collapsed accordion. NVDA must announce "expanded." The panel content must become visible and reachable by keyboard.
  • Collapse and verify: Press Space or Enter on an expanded accordion. NVDA must announce "collapsed." The panel content must become hidden.
  • Panel content is reachable: After expanding, Tab into the panel. All content inside the expanded panel must be focusable and readable.
  • Focus does not move unexpectedly: Activating an accordion trigger must not move focus into the panel. Focus stays on the trigger. The user can Tab into the panel manually.

ARIA requirements

  • Trigger: <button aria-expanded="false" aria-controls="panel-id">
  • Panel: <div id="panel-id" hidden>: use the hidden attribute or display:none, not just visibility:hidden
  • On expand: set aria-expanded="true" and remove hidden from the panel
  • On collapse: set aria-expanded="false" and add hidden back

3. Carousels and Slideshows

Carousels are among the most frequently failed components in accessibility audits. Auto-advancing content, insufficient controls, and missing announcements make them a consistently high-risk component.

What to test

  • Auto-advance has a pause control: If the carousel auto-advances, a pause button must be visible and operable by keyboard. WCAG 2.2.2 requires that moving content can be paused, stopped, or hidden.
  • Auto-advance respects prefers-reduced-motion: Enable Reduce Motion in OS settings. The carousel must stop auto-advancing or significantly reduce motion.
  • Previous/Next controls are labelled: Arrow icon buttons must have accessible names: "Next slide" and "Previous slide," not just arrow icons with no aria-label.
  • Current slide is announced: When navigating between slides, NVDA must announce the slide content or at minimum the slide position ("2 of 5"). If slide changes silently, a live region is missing.
  • All slide content is reachable: Use keyboard to navigate to every interactive element across all slides. Content on non-active slides must not be keyboard-reachable while hidden.
  • Role and structure: The carousel region should have aria-label (e.g. "Featured products"). Slide items should be in a list structure so screen reader users know there are multiple items.

ARIA requirements

  • Carousel container: aria-label="[name]" aria-roledescription="carousel"
  • Each slide: role="group" aria-roledescription="slide" aria-label="[n] of [total]"
  • Live region for announcements: aria-live="polite" on the slide container when auto-advancing
  • Pause button: visible and keyboard operable, with aria-label="Pause slideshow"

How to Test: Tiers and Platform Coverage

Tier 1: Pipeline automation

axe-core in CI catches some component failures automatically: missing dialog role, missing aria-expanded, empty button names in carousels. Run axe after opening each component state: not just page load.

// Open the modal, then scan
await page.click('#open-modal-btn');
await page.waitForSelector('[role="dialog"]');
const results = await new AxeBuilder({ page }).withTags(['wcag2a','wcag2aa']).analyze();
expect(results.violations.filter(v => ['critical','serious'].includes(v.impact))).toHaveLength(0);

Tier 2: Semi-automated tools

  • Accessibility Insights Tab Stops: Enable Tab Stops before opening the modal. Open it. Watch whether arrows move inside, and whether Escape closes it and returns focus. Tab Stops makes focus management visible without needing a screen reader.
  • axe DevTools: Run axe with the modal open, accordion expanded, and carousel mid-slide. Each state may reveal different violations.
  • ANDI Focusable Elements: Step through all focusable elements in the component. Verify role and state are announced correctly for each.

Tier 3: Manual: keyboard and screen reader

  • Keyboard (all platforms): Test every component with Tab, Enter, Space, Escape, and arrow keys. No mouse. Document every stuck point.
  • NVDA + Firefox (Windows): Open each component. Verify role announcement, state changes (expanded/collapsed, selected), and that focus returns correctly on close.
  • VoiceOver + Safari (Mac): Same component walkthrough. Use VO+U rotor to check form controls and landmarks inside components.
  • VoiceOver on iOS: Swipe through modal, accordion, and carousel. Verify aria-expanded, dialog role, and slide announcements. Test on physical iPhone: simulator does not replicate VoiceOver accurately.
  • TalkBack on Android: Swipe navigation through each component. Verify state announcements and focus management. Physical device required.

The 3-step component test
  • Keyboard only: can you open, navigate, and close the component using only Tab, Enter, Space, and Escape?
  • NVDA: does it announce the role, state, and content correctly at each interaction point?
  • Screen reader off: can you operate the component fully with keyboard without hearing anything?
