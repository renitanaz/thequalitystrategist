33 Automated Tools Only Catch 30 to 50 Percent: Why Automation Is the Floor, Not the Ceiling

axe gets a score of zero violations. WAVE shows no errors. Lighthouse hits 100. The page still fails WCAG. Here is why: and what to do about it.

1. The 30 to 50 Percent Figure

The most cited statistic in accessibility testing is that automated tools catch between 30 and 50 percent of WCAG failures. The figure comes from research by Deque Systems, WebAIM, and others comparing automated scan results against manual expert audits of the same pages. The number varies by page type, component complexity, and which tool is used: but the range is consistent across multiple studies.

What this means in practice: a page with a perfect automated score: zero axe violations, 100 Lighthouse score, no WAVE errors: can still fail WCAG 2.1 AA on more than half its applicable criteria.

A Lighthouse score of 100 is not a WCAG 2.1 AA conformance statement. It is evidence that the page passed the automated checks that Lighthouse runs. These are not the same thing.

2. What Automation Catches Well

Automated tools are excellent at catching structural and attribute-level failures: things that exist in the DOM and can be evaluated against a rule without human interpretation.

  • Missing alt text: The alt attribute is absent or empty on a non-decorative image
  • Missing form labels: An input has no associated label element, aria-label, or aria-labelledby
  • Colour contrast failures: Foreground and background colours compute below 4.5:1 for normal text
  • Invalid ARIA: An aria-role has invalid value, or required aria-* attributes are missing
  • Empty interactive elements: Buttons, links, or form controls with no accessible name
  • Missing document properties: No page title, no language attribute, no landmark regions
  • Structural violations: Skipped heading levels, duplicate IDs, invalid HTML nesting

3. What Automation Cannot Catch

Automated tools cannot evaluate anything that requires human judgement, runtime interaction, or listening to a screen reader. This is the majority of WCAG 2.1 AA.

4. The Gap Between Score and Conformance

The gap is not a failure of the tools: it is a fundamental limitation of what can be evaluated programmatically. No tool will close this gap because the missing checks require human perception, context, and interaction. The tools are doing everything they can do. The rest is ours to do.

The gap is also not uniform. A simple marketing page with static content, clear headings, and no custom components may have 70 percent of its failures catchable by automation. A complex single-page application with custom widgets, dynamic content, and video may have 20 percent of its failures catchable by automation. The 30 to 50 percent figure is an average: not a guarantee for any specific page.

How to Test: Building the Full Three-Tier Stack

Tier 1: Pipeline automation

Covers the 30 to 50 percent that automated tools can catch. Run axe-core in Playwright or Cypress on every commit. Scope to WCAG 2.1 AA, fail on Critical and Serious only. Add Pa11y CI if you want broader URL-based scanning alongside component-level tests.

  • Platforms: Linux/Mac/Windows in CI. Chromium + Firefox. Headless.
  • What it covers: Missing labels, invalid ARIA, contrast failures, empty buttons, landmark structure, duplicate IDs
  • What it does not cover: Everything in the table in Section 3 of this blog

Tier 2: Semi-automated tools

Use WAVE and axe DevTools in the browser on each feature before it ships. These add visual context to the same violations: helping developers locate and understand failures faster than reading JSON output. Use Accessibility Insights Tab Stops to visualise focus order. None of these tools expand the 30 to 50 percent ceiling: they make it faster to act on what automation finds.

Tier 3: Manual: the remaining 50 to 70 percent

Every item in Section 3 of this blog is Tier 3. The complete manual coverage requires:

  • Keyboard testing: Tab through all interactive elements. Check focus order, indicators, and traps.
  • NVDA + Firefox: Windows screen reader testing: headings, links, forms, images, live regions
  • VoiceOver + Safari: Mac screen reader testing: rotor walkthrough, form labels, dynamic content
  • VoiceOver on iOS: Physical iPhone: gestures, rotor, form interactions, live regions
  • TalkBack on Android: Physical Android: reading controls, swipe navigation, explore by touch
  • Visual checks: 320px reflow, 400% zoom, Reduce Motion, colour independence
  • Media: Captions, transcripts, audio descriptions, media player keyboard access

6. Communicating This to Stakeholders

The most common misuse of accessibility scores is presenting them to stakeholders as conformance evidence. A Lighthouse score of 100 presented in a compliance report without qualification is misleading: it implies conformance that has not been established.

  • What to say: "Automated checks pass. Manual testing covering keyboard navigation, screen reader behaviour, and content review is in progress."
  • What not to say: "Lighthouse 100: the page is accessible."
  • In defect reporting: Distinguish automated violations from manual findings. Both are valid defects. The mix tells you about the balance between structural failures and interaction failures.
  • In sprint reviews: Report both the automated score and the number of open manual testing defects. The score alone is not the accessibility status.
The right framing
  • Automation is the floor: it prevents the most common structural failures from reaching production.
  • Manual testing is the ceiling: it is what separates a compliant product from an accessible one.
  • A zero-violation automated scan is the minimum bar for a release. It is not the release criterion for accessibility.

Mobile: The Biggest Gap in Automated Testing

Automated tools run on desktop CI servers. They produce zero coverage of native mobile accessibility. Every native iOS and Android app needs its own testing pass: there is no pipeline equivalent. These apps contain real broken implementations to practise on:
