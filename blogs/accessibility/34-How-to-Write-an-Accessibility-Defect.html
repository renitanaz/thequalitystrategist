34 How to Write an Accessibility Defect: Defect Reports That Can Be Actually Acted On

Most accessibility defect reports say "screen reader does not read this." That is not a defect. This is how to write one that a developer can fix on the first read.

1. Anatomy of an Accessibility Defect

Every accessibility defect must contain these fields:

Required fields in an accessibility defect
FieldWhat to include
TitleComponent + failure + WCAG criterion. Example: "Email input field: missing programmatic label (WCAG 1.3.1)"
LocationPage URL, page name, and component name. Example: "/contact: Contact form: Email field"
Current behaviourWhat happens now. For screen reader defects: what the screen reader announces in quotes.
Expected behaviourWhat should happen. For screen reader defects: what the screen reader should announce.
WCAG criterionNumber, name, and level. Example: "1.3.1 Info and Relationships: Level A"
ImpactCritical / Serious / Moderate / Minor and which users are affected
Steps to reproduceNumbered steps from page load. Include tool and browser/screen reader version.
Fix guidanceThe code change that would fix it. Not always possible to specify: but include when you can.

How to Test: Writing Defects at Each Tier

Tier 1: Pipeline automation

Pipeline tools (axe-core, Pa11y) surface automated violations: missing labels, contrast failures, invalid ARIA. These are the easiest defects to write because axe provides the rule ID, WCAG criterion, impact, and DOM selector. Copy this directly into the defect. The axe JSON output gives you everything except steps to reproduce and fix guidance, which you add manually.

Tier 2: Semi-automated tools

Browser tools (axe DevTools, WAVE, ANDI) give visual context. Use the element highlight in axe DevTools to locate the affected element and capture its selector. Use ANDI to get the exact accessible name and source attribute: this is what goes in the "current behaviour" field. WAVE alerts add the WCAG criterion and a summary of the issue type.

Tier 3: Manual: screen reader and keyboard defects

Manual defects require the most care. The critical requirement: capture the exact screen reader announcement in quotes.

  • Windows NVDA + Firefox: Tab to the element. Write down exactly what NVDA announces: word for word in quotes. This is your "current behaviour."
  • Mac VoiceOver + Safari: Same: exact VO announcement in quotes. Note the VO version and macOS version.
  • iOS VoiceOver: Swipe to the element. Record the announcement. Note iPhone model, iOS version, Safari version.
  • Android TalkBack: Swipe to the element. Record the announcement. Note Android version and Chrome version.
  • Keyboard defects: Document the exact key sequence: Tab count from page load, key pressed, what happened vs what should have happened.

2. Worked Examples

Example 1: Missing form label

Bad: "Email field is not accessible."

Good:

Title: Email input: missing programmatic label (WCAG 1.3.1 / 3.3.2)
Location: /contact: Contact Us form: Email address field
Current: NVDA announces "edit text, blank" when focus lands on the input. No label is announced.
Expected: NVDA should announce "Email address, required, edit text"
WCAG: 1.3.1 Info and Relationships: Level A / 3.3.2 Labels or Instructions: Level A
Impact: Critical: screen reader users cannot determine the purpose of the field
Reproduce: 1. Enable NVDA + Firefox. 2. Navigate to /contact. 3. Tab to the email input. Listen.
Fix: Add <label for="email">Email address</label> associated with the input via matching id, or add aria-label="Email address" to the input element.

Example 2: Colour contrast failure

Bad: "The text colour doesn't pass contrast."

Good:

Title: Card subtitle text: colour contrast 3.2:1 fails WCAG minimum 4.5:1 (WCAG 1.4.3)
Location: /products: Product card: subtitle text below card title
Current: Subtitle text (#9ca3af on #ffffff) has a contrast ratio of 3.2:1
Expected: Minimum 4.5:1 for normal text at this font size (14px / 400 weight)
WCAG: 1.4.3 Contrast (Minimum): Level AA
Impact: Serious: affects users with low vision and those in bright environments
Reproduce: 1. Open /products in Chrome. 2. Activate WAVE extension. 3. Purple contrast icon visible on subtitle text. Ratio: 3.2:1.
Fix: Change subtitle text colour from #9ca3af to #6b7280 (4.62:1 ratio) or darker.

Example 3: Missing live region

Bad: "The toast notification isn't read."

Good:

Title: Add to cart toast: not announced by screen reader, missing live region (WCAG 4.1.3)
Location: /products: Product detail page: "Add to cart" button toast
Current: NVDA announces nothing when the toast appears. Toast is visually visible for 3 seconds. No screen reader announcement.
Expected: NVDA should announce "Item added to cart" without focus moving to the toast.
WCAG: 4.1.3 Status Messages: Level AA
Impact: Major: screen reader users do not know the cart action succeeded
Reproduce: 1. Enable NVDA + Chrome. 2. Navigate to any product page. 3. Focus on the product description paragraph. 4. Click "Add to cart". 5. Listen. No announcement.
Fix: Add a pre-existing empty container with role="status" aria-live="polite" aria-atomic="true" to the page on load. On cart add, update its text content to "Item added to cart".

3. Severity and WCAG Mapping

Severity levels and their characteristics
SeverityDefinitionRelease impact
CriticalBlocks access entirely for one or more disability groups. No workaround exists.Release blocker
MajorSignificant barrier. A workaround may exist but it is difficult or undiscoverable.Release blocker
ModerateDegraded experience. A workaround exists. Some users will find it.Fix before sprint close
MinorBest practice violation. Minimal real-world impact.Backlog with resolution date

4. Screen Reader Defects: The Extra Requirements

Screen reader defects require three additional pieces of information that other defect types do not:

  • Screen reader and version: NVDA 2024.4.1, VoiceOver macOS 14.6, TalkBack Android 14. Different versions may produce different announcements.
  • Browser and version: NVDA + Firefox 132. NVDA + Chrome may behave differently for the same element.
  • Exact announcement in quotes: Not "NVDA does not read the label." Write: NVDA announces "edit text, blank." This is the only way a developer can reproduce and verify the fix.

5. The Defect Template

Title: [Component]: [failure description] (WCAG [x.x.x]) Location: [URL]: [page name]: [component name] Current behaviour: [What happens now. For SR defects: "[SR] announces: '[exact text]'"] Expected behaviour: [What should happen. For SR defects: "Should announce: '[exact text]'"] WCAG criterion: [x.x.x] [Name]: Level [A/AA] Impact: [Critical / Major / Moderate / Minor] Affected users: [screen reader users / keyboard users / low vision / colour blind / all] Steps to reproduce: 1. [Start from page load] 2. [Each action clearly numbered] 3. [Include tool, browser, SR version] Fix guidance: [The code change. Include the HTML/CSS/ARIA attribute needed.]
The test for a good accessibility defect
  • Can a developer reproduce it without asking you a single question?
  • Does it tell them what the code should do differently?
  • Does it include the exact WCAG criterion so it can be prioritised correctly?
  • For screen reader defects: does it include the exact announcement in quotes?
