04 Who Owns Accessibility?

A responsibility matrix for every role, and what breaks when each lane is dropped.

Testing Ownership in Practice

Tier 1: Pipeline automation

Who reviews violations? Who can block a release on a Critical violation? If the answer is always "QA," the distributed ownership model has not been implemented. The pipeline gate should be a delivery team responsibility.

Tier 2: Semi-automated tools

At each phase gate, a semi-automated scan should be run by whoever owns that phase. Designers run axe DevTools or Stark on prototypes. Developers run it on components. QA runs it on integrated features. The tool is the same: the owner changes per phase.

Tier 3: Manual

Manual testing requires trained testers. Assign ownership explicitly: NVDA + Firefox on Windows, VoiceOver + Safari on Mac, VoiceOver on iOS (physical device), TalkBack on Android (physical device). Accessibility testing isn't complete without hands-on screen reader testing on a real device.

1. The Problem With Shared Ownership

Every team that has struggled with accessibility has said some version of the same thing at some point: "Accessibility is everyone's responsibility."

Shared responsibility with no named lanes is just a polite way of saying no one is accountable.

The fix is simple. A matrix that names who owns what, before work starts. Not paperwork: a practical agreement that stops the most expensive rework: the kind that happens after launch.

This blog gives you that matrix: each role, what they own, and what goes wrong when they drop it.

2. The Responsibility Matrix: Role by Role

Six roles. Six phases. Each has a clear lane: and a clear cost when it is dropped.

PM
Product Owner / PM
Phase 0: Discovery and strategy
Owns:
  • Identifying legal and regulatory obligations
  • Defining the WCAG conformance target (minimum WCAG 2.1 AA)
  • Writing accessibility into acceptance criteria before design begins
  • Assigning a named accessibility owner: not a team, a person
  • Documenting the sign-off model across all phases
What good looks like
The user story reads: "All interactive elements must be keyboard-operable and pass WCAG 2.1 AA 2.1.1." The PM has named an accessibility lead. The sign-off criteria for each phase are documented in Confluence before sprint 1.
What breaks when this lane is dropped
No target is defined. Developers guess what accessible means. QA has nothing to test against. The product ships with no audit trail and finds out about its legal exposure from a user complaint.
UX
UX / Designer
Phase 1: UX research and design
Owns:
  • Validating colour contrast across all text and UI components before handoff (4.5:1 for body text, 3:1 for large text and UI components)
  • Specifying focus indicators
  • Annotating tab order in Figma
  • Defining heading hierarchy in page templates
  • Writing error message copy at design stage: not leaving it to developers to invent
  • Running Stark or Zımmer in Figma before any handoff
What good looks like
Every Figma component has contrast ratio noted. Tab order is annotated with numbered arrows on interactive flows. The error state for every form field has copy written: not a placeholder saying "error message here." Stark has been run and all failures resolved before the design review.
What breaks when this lane is dropped
The brand colour palette ships with a 2.8:1 contrast ratio on body text, failing WCAG 1.4.3. Fixing it post-development means updating the design system, regenerating components, and retesting every screen. I have seen this turn a one-hour Figma fix into a three-sprint remediation.
CA
Content Author / Developer (Phase 2)
Phase 2 (CMS) or Phase 3 (non-CMS): Content layer ownership
Owns: The content layer: but who holds it depends on the project type. This lane exists in every project. The owner changes.
CMS projects (Contentful, WordPress, Sanity)
Content Author / Strategist owns this lane. Write meaningful alt text in the correct field (not the description field). Use heading levels correctly: no skipping. Write descriptive link text, not "click here." Provide captions and transcripts for video. Flag decorative images so screen readers skip them.
Non-CMS projects (React, Angular, static, component-based)
This lane moves to the Developer in Phase 3. Alt text must be enforced as required component props. Heading structure is defined in templates. Link text is authored in code or JSON. UX owns the copy and alt text definitions at design stage: the developer implements them. If neither defines it, nobody does.
Headless and API-driven projects
The backend developer must enforce accessible data models: a separate alt text field, required labels, heading hierarchy in schema. Content arriving via API with no alt text field cannot be made accessible at the frontend layer alone. The data model is the content model.
What good looks like (CMS)
The image field requires alt text. The rich text editor restricts heading levels: no H1 in body content. "Click here" is blocked by CMS validation. Every video entry has a captions field and transcript URL that must be populated before publishing.
What good looks like (non-CMS)
The React image component has a required alt prop: the build fails if it is missing. UX has defined alt text for every image in Figma annotations before handoff. The data model has a separate altText field. Heading structure is enforced through component hierarchy, not guessed at runtime.
What breaks when this lane is dropped
CMS: alt text in the wrong field, H1 on every paragraph, "click here" across hundreds of pages: all requiring individual correction after migration. Non-CMS: no alt prop enforcement means images ship without alt text silently. No UX annotation means developers guess or skip. Both scenarios end up in QA as the same defect. The cause is different. The cost is identical.
Dev
Developer
Phase 3: Development
Owns:
  • Using semantic HTML: <button> not <div onclick>, <nav> not <div class="nav">
  • Applying ARIA only when native HTML is insufficient
  • Making sure every interactive element works with a keyboard
  • Running eslint-plugin-jsx-a11y in the IDE
  • Adding axe-core to CI/CD and failing builds on Critical violations
  • Managing focus on modals, SPAs, and dynamic content
What good looks like
The modal uses a native <dialog> element. Focus moves into it on open, cycles within it while open, and returns to the trigger on close. The ESLint plugin flags a missing alt attribute before the PR is even raised. The CI pipeline fails when axe-core detects a Critical violation: so it never reaches QA.
What breaks when this lane is dropped
The dropdown menu is built with <div> and JavaScript click handlers. It works perfectly with a mouse. Keyboard users cannot open it. Screen reader users get no announcement of state. The component is used in 14 places across the product. QA finds it in week 8 of testing. All 14 need rework.
QA
QA / Accessibility Lead
Phase 4: Testing and validation
Owns:
  • Running manual keyboard testing across all user journeys
  • Running screen reader testing (NVDA on Windows, VoiceOver on Mac, VoiceOver on iOS, TalkBack on Android)
  • Running axe DevTools, WAVE, and Accessibility Insights scans
  • Validating phase exit criteria before sign-off
  • Logging defects with the WCAG criterion, severity, and steps to reproduce
  • Pushing upstream issues back to the right owner: with evidence
What good looks like
The defect reads: "Contrast ratio on body text is 2.8:1, failing WCAG 1.4.3 (minimum 4.5:1). Affects all body copy across all pages. Severity: Major. Root cause: design phase: colour palette not validated before handoff." The defect is assigned to design, not development. Phase exit criteria are not signed off until it is resolved.
What breaks when this lane is dropped
Without QA holding the exit gate, upstream failures compound. A design that was never contrast-checked, content that was never heading-validated, and code that was never keyboard-tested all ship together. The first accessibility audit: often commissioned after a complaint: finds everything at once. That audit costs more than all the upstream work that was skipped.
Ops
Maintenance / Operations
Phase 5: Live and post-launch
Owns:
  • Running Pa11y or axe-core nightly on production to catch regressions
  • Triaging and resolving user-reported accessibility issues within a defined SLA
  • Maintaining the VPAT if required for enterprise procurement
  • Keeping an audit trail as compliance evidence
  • Ensuring new content published post-launch meets the same standards as launch content
What good looks like
A nightly Pa11y run detects that a third-party chat widget introduced a keyboard trap in the last deployment. An alert fires. The widget is rolled back within hours. The accessibility regression never reaches users for more than a day.
What breaks when this lane is dropped
A third-party script update silently breaks keyboard navigation across the entire site. Nobody notices for three months: until a user files a formal complaint. By then the issue has been live long enough to constitute a legal liability in some jurisdictions.

3. What Breaks When Each Lane Is Dropped

The table below maps each role to the specific defect type that appears in QA when that role has not held its lane. This is useful when writing defects: it tells you where the root cause actually sits, not just where the symptom was found.

Defects that appear in QA when each upstream role drops their lane
Role that dropped the lane Defect found in QA Root cause phase Cost to fix
PM / PO No acceptance criteria for accessibility : QA has nothing to test against Phase 0 Medium: governance rework mid-project
UX / Designer Contrast failures across brand palette, missing focus indicators, no error copy Phase 1 High: design system rework, component rebuild
Content Author (CMS) or Developer (non-CMS) Missing alt text, heading hierarchy broken, "click here" links, videos without captions Phase 2 (CMS) or Phase 3 (non-CMS) Medium: content re-authoring at scale
Developer Keyboard traps, div soup, broken ARIA, missing semantic structure, focus not managed Phase 3 High: component rework, retest across all instances
QA All of the above reach production Phase 4 Critical: legal risk, emergency sprint, audit cost
Operations Regressions accumulate silently post-launch Phase 5 Critical: complaints, legal exposure, reputation

4. Myths About Accessibility Ownership

"Accessibility is QA's job."
QA is the last gate, not the only gate. When accessibility arrives in QA untouched by design, content, and development, QA becomes a remediation team. The defect volume is unmanageable and the cost multiplier is at its highest. QA verifies: it cannot retroactively fix decisions made four phases earlier.
"Developers handle accessibility when they write the code."
Developers can implement accessibility correctly: but only if the design gave them a contrast-validated palette, the content model enforced alt text, and the acceptance criteria specified what "accessible" means. You cannot code your way out of a design that was never accessibility-reviewed.
"We run automated tests, so we're covered."
Automated tools catch 30–50% of accessibility issues. Focus visibility, keyboard usability, screen reader context, and cognitive load require human testing. Automated tests are the floor, not the ceiling. A 100% Lighthouse score is not an accessibility sign-off.
"The client owns accessibility: it's their legal obligation."
The client carries the legal obligation, but the delivery team carries the quality responsibility. Shipping an inaccessible product and pointing to the contract is not a defence. Dual ownership is required: a named owner on the delivery team and a named owner on the client side. Without both, decisions stall and accountability disappears.

5. The One Thing Most Teams Get Wrong

Of everything in the responsibility matrix, the single most impactful thing a team can do is name one person as the accessibility owner, not a team, not a role: a person.

"The accessibility team owns it" means nobody does. "Sarah owns it" means Sarah gets the call when a decision needs making, a gate needs holding, or a third-party tool needs challenging.

The second thing: dual ownership. The delivery team needs a named owner, and so does the client. Without both, decisions stall. I have seen accessibility sign-off sit in email threads for weeks: not because anyone disagreed, but because nobody on the client side had authority to approve.

Accessibility ownership is not a title. It is a commitment to hold a lane for the entire lifecycle: from the first user story to the first production regression.

Name the person. Document the lane. Hold the gate.
