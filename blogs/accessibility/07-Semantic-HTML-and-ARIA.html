Testing Semantic HTML and ARIA

Tier 1: Pipeline automation

axe-core in CI is the primary gate for ARIA and semantic HTML: invalid roles, missing required ARIA attributes, aria-required-children violations, role/name/value failures. Run with withTags(['wcag2a','wcag2aa']). Use the Axe-Core CI Playground to test your pipeline against real violations.

Tier 2: Semi-automated tools

ANDI Focusable Elements module is the most precise tool for inspecting accessible name computation: it shows exactly which attribute provides the name and flags conflicts between aria-label and visible text. axe DevTools element highlight locates ARIA violations in the rendered DOM faster than reading source code.

Tier 3: Manual

ARIA presence does not mean ARIA works. Test every custom widget with NVDA + Firefox on Windows and VoiceOver + Safari on Mac. Verify: role announced correctly, state changes announced (expanded/collapsed, selected, checked), accessible name matches what a sighted user sees. Mobile: VoiceOver on physical iPhone, TalkBack on physical Android device.

1. Why Semantic HTML Is the Foundation

Semantic HTML means using elements that carry meaning. <button> for buttons, <nav> for navigation, <main> for main content. The element tells the browser, the screen reader, and the accessibility tree what the thing is: not just what it looks like.

This matters because assistive technologies do not read the visual presentation of a page. They read the DOM. A <div> styled to look like a button is invisible to a screen reader as a button. It has no role, no keyboard support, no state. It is a box with text in it.

ARIA can patch missing semantics. But the correct fix is always the right HTML element in the first place. No amount of ARIA makes a <div> as reliable as a <button>.

QA cannot fix semantic HTML issues by writing a defect and moving on. This requires a code change, a redeploy, and a retest. This is Phase 3 work: and the earlier it is caught, the cheaper it is. Blog 02 has the cost multiplier.

2. The Div Soup Problem

"Div soup" is the nickname for codebases where almost every element is a <div> or <span> regardless of its semantic meaning. It is extremely common in React and Angular applications where component libraries are built with generic containers and visual styling rather than semantic elements.

Same visual result. Completely different accessibility tree. The screen reader output tells the whole story: one version announces a navigation landmark with three links. The other announces nothing.

3. The Semantic Elements to Check

These are the elements most commonly replaced with generic divs. Catch them early: in code review or a dev build: not after they have shipped.

4. What ARIA Is and What It Is Not

ARIA: Accessible Rich Internet Applications: is a set of attributes that extend HTML to communicate role, state, and property information to assistive technologies. It fills gaps where native HTML does not have an equivalent semantic element.

The most important thing to know about ARIA:

ARIA does not add functionality. It adds description. A button with role="button" on a <div> is announced as a button: but it still does not respond to keyboard events unless JavaScript adds that too. Native elements come with behaviour built in. ARIA-patched divs do not.

The W3C ARIA specification has one guiding principle that summarises the correct approach: No ARIA is better than bad ARIA. A missing ARIA attribute is a screen reader announcement gap. A wrong ARIA attribute actively misdirects screen reader users. Bad ARIA is worse than no ARIA.

5. The Five ARIA Rules That Matter

The W3C ARIA specification publishes five rules of ARIA use. These are the practical ones for a QA engineer to know: because violations of them are what you find in code review and testing.

01
Use native HTML first. If a native HTML element or attribute already has the semantics you need, use it. Do not add role="button" to a <div> when <button> exists.
02
Do not change native semantics unless necessary. Do not add role="presentation" or role="none" to elements that have meaningful semantics unless there is a specific reason to remove them.
03
All interactive ARIA controls must be keyboard-operable. If you give a <div> role="button", it must also respond to Enter and Space keypresses: exactly like a native button. ARIA announces the role. JavaScript must provide the behaviour.
04
Do not hide focusable elements. Do not use aria-hidden="true" on an element that can receive keyboard focus. This creates a keyboard trap: the element receives focus but the screen reader announces nothing.
05
All interactive elements must have an accessible name. Every button, link, input, and control must have a name that screen readers can announce. This comes from visible text content, aria-label, aria-labelledby, or a linked <label>.

6. Common ARIA Patterns and How to Check Them

These are the ARIA patterns used most frequently in real applications, what correct implementation looks like, and how to verify them.

aria-label and aria-labelledby

Used to give an element an accessible name when visible text is insufficient or absent. aria-label provides the name directly. aria-labelledby points to the ID of an existing element whose text becomes the name.

Fail
<button> <svg>...</svg> </button> <!-- SR: "button" - no name -->
Pass
<button aria-label="Close modal"> <svg aria-hidden="true">...</svg> </button> <!-- SR: "Close modal, button" -->

How to check: Open Chrome DevTools Accessibility panel. Inspect the element. The "Computed Properties" section shows the accessible name. If it is empty on an interactive element, that is a defect.

aria-expanded

Used on a trigger element (button, link) to communicate whether the controlled content is expanded or collapsed. Common in accordions, dropdown menus, and disclosure widgets.

Fail
<button>Show more</button> <div class="content hidden"> ... </div> <!-- No state communicated -->
Pass
<button aria-expanded="false" aria-controls="content-1"> Show more </button> <div id="content-1" hidden> ... </div>

How to check: Tab to the accordion or dropdown trigger. Open NVDA or VoiceOver. The announcement should include "collapsed" or "expanded." Activate the control. The announcement must update. If it does not, the state is not being toggled in the DOM.

aria-live regions

Used to announce dynamic content changes to screen readers without moving focus. role="status" (polite: waits for user to finish) and role="alert" (assertive: interrupts immediately) are the two most common patterns.

Fail
<div id="message"></div> <!-- JS injects text here --> <!-- SR: silent -->
Pass
<div role="status" aria-live="polite" aria-atomic="true"> </div> <!-- SR: announces injected text -->

How to check: With NVDA running, trigger the dynamic update (form submit, filter, search result). Listen for the announcement. If nothing is announced, the live region is missing or the container was not present in the DOM on page load.

aria-describedby

Links a form input to additional instructional text that supplements the label. Different from aria-labelledby: the label names the control, the description provides context.

Fail
<label for="pw">Password</label> <input id="pw" type="password"> <p>Must be 8+ chars with a number</p> <!-- hint not linked to input -->
Pass
<label for="pw">Password</label> <input id="pw" type="password" aria-describedby="pw-hint"> <p id="pw-hint"> Must be 8+ chars with a number </p>

7. ARIA Misuse Patterns Found Across Every Phase

These patterns show up at every stage: in code review, in staging, and yes, sometimes in production when the earlier gates are missed. Each one is a real defect pattern. The earlier it is caught, the cheaper the fix.

Common ARIA misuse patterns and their impact
Pattern What it looks like Impact
aria-hidden on focusable element <button aria-hidden="true"> Button receives keyboard focus but screen reader announces nothing. Invisible keyboard trap.
role="button" without keyboard support <div role="button" onclick="..."> Screen reader announces "button" but Enter and Space do nothing. Mouse-only control with a button label.
aria-label overriding visible text <button aria-label="X">Close</button> Screen reader announces "X" not "Close." Sighted users see "Close." Screen reader users hear "X." Mismatch fails WCAG 2.5.3.
Missing aria-expanded toggle Accordion trigger does not update aria-expanded on click Screen reader cannot determine whether content is open or closed. State is invisible.
Duplicate landmark roles Two <nav> elements with no aria-label Screen reader announces "navigation" twice with no distinction. Both are inaccessible as separate regions.
Empty aria-label <button aria-label=""> Element has no accessible name. Screen reader may announce nothing or the element type only.
role="presentation" on interactive element <table role="presentation"> containing links Removes table semantics: acceptable for layout. But if the table contains interactive elements, their context is lost.

8. What QA Checks for in the Development Phase in Shift-Left A11y

QA at Phase 3 is not waiting for the build to complete and then running a scan. It is reviewing code patterns, checking the accessibility tree, and verifying that what the developer implemented matches what the design annotated. Here is the checklist.

01
All interactive elements use native HTML. Every button is a <button>. Every link is an <a href>. No <div onclick> or <span onclick> used as interactive controls.
02
Page landmark structure is present. <header>, <nav>, <main>, <footer> all present. Exactly one <main>. Multiple navs have distinct aria-label values. Check with WAVE Structure tab.
03
All interactive elements have an accessible name. Inspect every button, link, input, and icon control in Chrome DevTools Accessibility panel. Computed name must not be empty.
04
Dynamic state is communicated. Accordions, dropdowns, and disclosure widgets update aria-expanded on toggle. Modal dialogs set aria-modal="true" and manage focus correctly. Live regions announce dynamic updates.
05
No focusable elements are hidden with aria-hidden. Search the codebase for aria-hidden="true" on any element that can receive focus: <a>, <button>, <input>, elements with tabindex.
06
Form inputs have programmatic labels. Every <input>, <textarea>, and <select> has a linked <label> or an aria-label. Placeholder text alone is not a label. Check with axe DevTools.
07
Run axe DevTools and WAVE. Resolve all Critical and Serious violations before moving to Phase 4. These tools catch structural and ARIA issues automatically. Manual testing covers what they miss.
The bottom line

Semantic HTML and ARIA are Phase 3 responsibilities. QA verifies them: it does not implement them. The earlier a structural issue is caught, the simpler the fix. A missing landmark found in code review is a comment. The same landmark missing from a live page is a defect, a deploy, and a retest.
