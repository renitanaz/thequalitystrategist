How to Verify Phase Exit Criteria

Tier 1: Pipeline automation

The development phase exit criterion: zero Critical and Serious violations in the axe-core CI pipeline. This is a binary gate. Configure axe-core in Playwright or Cypress with withTags(['wcag2a','wcag2aa']) and includedImpacts: ['critical','serious']. The build passes or it does not.

Tier 2: Semi-automated tools

QA phase entry check: run axe DevTools and WAVE on all new pages before beginning manual testing. Violations present here that the pipeline should have caught indicate the gate is not working. Fix the gate before proceeding.

Tier 3: Manual

QA phase exit criterion: all Sprint-Ready Checklist items (Blog 37) verified. Critical and Major defects resolved. Moderate and Minor logged with target sprints. Screen reader testing completed on NVDA + Firefox (Windows), VoiceOver + Safari (Mac). Mobile: VoiceOver on iOS and TalkBack on Android on physical devices.

1. What a Phase Exit Criterion Is

A phase exit criterion is a specific, testable condition that must be true before work moves to the next phase. Each phase has a named owner. That owner holds the gate.

A defect caught at Phase 1 costs a Figma edit. The same defect at Phase 4 costs a sprint. Blog 02 has the numbers.

If publishing is allowed, the system has approved the content. Phase exit criteria are the governance layer, not a retrospective checklist.

Phase 4 is QA's primary gate. It covers manual testing that no automated tool can replicate: keyboard navigation, screen reader testing, and full user journey validation.

Phase 4 does not close until all Critical and Major defects are resolved and retested. QA holds this gate. It is not a negotiation.

7. Phase 5: Live and Production

Going live does not close the accessibility loop. Regressions happen. Third-party scripts update. New content gets authored. Phase 5 is ongoing governance, not a one-time check.

Phase 5
Live and Production
Owner: DevOps / QA / Operations
☐
Nightly automated scan in place using Pa11y or axe-core. Alerts fire on Critical violations. Regressions caught within 24 hours.
Multiple
☐
New content published post-launch meets the same standards as launch content. CMS rules enforced on an ongoing basis.
All
Catch a regression the next morning via automated scanning. Not from a user complaint three months later.

8. How to Use These in a Real Project

These criteria are most useful when they are agreed before Phase 0 begins, not presented to a team for the first time at Phase 4. Here is how to introduce them without friction:

At project kickoff

Share the Phase 0 criteria with the PM and get named owners assigned before sprint 1. Without named ownership, the criteria have no one to enforce them.

At each phase handoff

The phase exit criteria for the next phase become the acceptance criteria for the handoff. Design does not hand off to development until Phase 1 criteria are confirmed. Development does not hand off to QA until Phase 3 criteria are confirmed.

When holding a gate

The criteria give QA formal leverage. "Phase 3 exit criterion 06 is not met: the CI/CD pipeline does not fail on Critical axe-core violations": this is a named, documented condition: not an opinion. It is harder to override a specific criterion than a vague concern.

When a deadline is under pressure

Critical and Major defects do not get waived under deadline pressure. The criteria exist precisely because that conversation happens on every project. Having them documented before the deadline arrives is the only way to hold the line when it matters.

The one thing

Agree the criteria at kickoff. Assign a named owner per phase. Review at every handoff. The conversation that happens when you introduce phase exit criteria is worth more than any post-launch audit.
