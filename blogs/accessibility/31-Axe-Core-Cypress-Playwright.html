31 Axe-Core in Cypress and Playwright: Accessibility Testing Built Into Every Test Run

Axe-core does not need a separate testing pass. It runs inside your existing Playwright and Cypress suites on every build.

1. Why axe-Core in the Pipeline

Browser-based scanning with axe DevTools finds violations in the browser. Pipeline automation with axe-core finds the same violations on every commit, on every branch, before any human sees the code. The difference is not capability: it is timing. Catching a missing form label in CI is cheaper than catching it in a QA session, and far cheaper than catching it in production.

axe-core integrates directly into Playwright and Cypress test suites as an additional assertion. No separate scanning tool. No separate test run. Accessibility checks run alongside your existing functional tests on every build.

axe-core in the pipeline catches the same violations as axe DevTools in the browser: same engine, same rules. The pipeline adds timing: violations are caught at commit, not at release.

2. axe-Core with Playwright

The @axe-core/playwright package provides the checkA11y helper that runs an axe scan on the current page state.

npm install --save-dev @axe-core/playwright
import {{ test, expect }} from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('homepage has no critical accessibility violations', async ({{ page }}) => {{
  await page.goto('/');
  const results = await new AxeBuilder({{ page }})
    .withTags(['wcag2a', 'wcag2aa'])
    .analyze();
  expect(results.violations.filter(v =>
    ['critical','serious'].includes(v.impact)
  )).toHaveLength(0);
}});
  • withTags: Scope to WCAG 2.1 AA rules only. Avoids best-practice rules that produce noise in CI.
  • filter by impact: Fail only on critical and serious. Moderate and minor go in the backlog.
  • results.violations: Array of violations: each has rule ID, impact, WCAG criterion, and affected elements with DOM selectors.

3. axe-Core with Cypress

The cypress-axe package adds cy.checkA11y() as a Cypress command.

npm install --save-dev cypress-axe axe-core
// cypress/support/commands.js
import 'cypress-axe';

// cypress/e2e/accessibility.cy.js
describe('Accessibility', () => {{
  it('homepage passes axe wcag2aa', () => {{
    cy.visit('/');
    cy.injectAxe();
    cy.checkA11y(null, {{
      runOnly: {{ type: 'tag', values: ['wcag2a', 'wcag2aa'] }},
      includedImpacts: ['critical', 'serious']
    }});
  }});
}});
  • cy.injectAxe(): Injects axe-core into the page. Must be called after page load, before cy.checkA11y().
  • First argument null: Scans the full page. Pass a CSS selector to scope to a component.
  • includedImpacts: Same impact filtering as Playwright: fail on critical and serious only.

4. Scoping Scans: Page, Component, Interaction State

The most common mistake in pipeline accessibility testing is scanning only the page load state. Most violations live in interaction states: open modals, expanded accordions, submitted forms with errors, filter results. Scope your scans to match your functional test flows.

When to run axe scans within a test flow
Test pointWhat to scanWhy
Page loadFull pageCatches structural issues: missing landmarks, heading hierarchy, page title, language
Modal openModal selector or full pageCatches missing dialog role, missing close button label, focus management violations
Form submit with errorsFull page or form selectorCatches error identification violations, missing aria-describedby on invalid fields
After filter or searchResults container selectorCatches dynamic content violations on updated DOM
After accordion expandAccordion selectorCatches aria-expanded state violations, revealed content with missing labels

5. Configuration: wcag2aa, Impact Filtering, Exclusions

  • runOnly: WCAG 2.1 AA: Targets WCAG 2.1 AA rules. Add wcag21aa for WCAG 2.1-specific rules beyond 2.0.
  • Included impacts: Critical and Serious: Critical and Serious violations fail the build immediately. Moderate and Minor are written to a separate JSON artifact in CI: they are visible to the team but do not block the pipeline. Route them to the backlog with a target sprint.
  • Exclude selectors: Pass an exclude array to skip known third-party components you cannot fix. Document the exclusion and review it each sprint.
  • Baseline file: Some teams use a baseline file to suppress known existing violations and catch only new regressions. Use this as a temporary measure: not as a permanent exemption mechanism.

6. Failing Builds on Violations

The test assertion must cause the build to fail when violations are found. A scan that logs violations without failing the build is not a gate: it is a log that nobody reads.

  • Playwright: Use expect(violations).toHaveLength(0) or expect(critical).toHaveLength(0). Test fails, build fails.
  • Cypress: cy.checkA11y() throws on violations by default. The test fails, the build fails.
  • Report output: Log the full violations array to a JSON file and attach it to the CI artifact. Developers need the rule ID, WCAG criterion, and DOM selector to fix the issue without running the suite locally.

How to Test: Tiers and Platform Coverage

Tier 1: Pipeline automation

This entire blog is Tier 1. axe-core in Playwright or Cypress is the pipeline accessibility gate. Key configuration for WCAG 2.1 AA compliance:

  • Scope with withTags(['wcag2a', 'wcag2aa']): targets WCAG 2.1 AA rules only
  • Filter with includedImpacts: ['critical', 'serious']: only Critical and Serious fail the build
  • Run axe after every meaningful interaction state: not just page load
  • Log the full violations array to a CI artifact as JSON so developers can reproduce without re-running the suite
  • Platforms: Runs headlessly on any OS in CI (Linux, Mac, Windows). Playwright and Cypress both support cross-browser: run on Chromium and Firefox at minimum.

Tier 2: Semi-automated tools

Use axe DevTools browser extension for interactive validation of what the pipeline flags. Developers can reproduce a pipeline violation in the browser, see the highlighted element, and verify the fix before pushing. This is the feedback loop between Tier 1 and Tier 3.

Tier 3: Manual: what axe-core in CI cannot catch

  • Keyboard navigation: Tab through every interactive element. Focus order logic cannot be automated.
  • Screen reader announcements: NVDA + Firefox on Windows, VoiceOver + Safari on Mac. ARIA attributes present in the DOM does not mean screen readers announce correctly.
  • Alt text quality: axe confirms alt exists: a human must verify it is meaningful.
  • iOS VoiceOver: Physical iPhone + Safari. Pipeline tests do not cover native mobile.
  • Android TalkBack: Physical Android device + Chrome.
  • Visual overlaps and reflow: Requires viewport testing: not detectable by axe-core.
🎯
Practice on real violations
Point your Playwright or Cypress test at the Axe-Core CI Playground: it contains deliberate Critical, Serious, and Moderate violations plus passing examples. Verify your pipeline catches the failures and passes the correct implementations.

Pipeline axe-core catches the same issues as browser axe DevTools: missing labels, invalid ARIA, colour contrast, empty buttons. It misses the same issues too: keyboard navigation logic, screen reader announcements, focus order, alt text quality, and any violation that only appears in an interaction state not covered by your test suite.

The pipeline is the automated floor. Manual testing, keyboard testing, and screen reader testing are still required. The pipeline prevents regressions: it does not replace human testing.

The minimum viable pipeline setup
  • Add axe-core to your existing Playwright or Cypress suite: not a separate suite.
  • Scope to wcag2aa rules and critical/serious impact only.
  • Run axe after page load AND after every significant interaction state in your test flow.
  • Fail the build on any critical or serious violation. Zero exceptions without a documented exclusion.

Mobile: What Pipeline Tools Cannot Test

Pipeline automation tools run on desktop CI servers and scan web pages. They cannot test native mobile apps and cannot replicate screen reader experience on a phone. The failures they catch still need to be verified on physical devices. These apps provide real broken implementations to test against:
