Before You Start: What a CI/CD Pipeline Actually Is

New to CI/CD? Read this section first: everything after it assumes these terms.

CI/CD (Continuous Integration and Continuous Delivery, or Deployment) means one thing for a QA tester in practice: automated steps that run every time someone pushes code, without a person triggering them by hand.

A pipeline is that set of steps. On GitHub it's called a workflow: a YAML file in .github/workflows/. GitHub watches that folder and runs any .yml file there automatically on its own servers, once its trigger conditions are met, not on your laptop.

A build is one run of that workflow.

The rest of this blog assumes you can already write and run a Playwright or Cypress test locally. If not, do that first: everything here adds an accessibility check on top of a test suite that already runs.

1. Why axe-Core in the Pipeline

axe-core integrates directly into Playwright and Cypress test suites as an additional assertion: no separate scanning tool, no separate test run. Accessibility checks run alongside your existing functional tests on every commit, before any human sees the code.

2. axe-Core with Playwright

The @axe-core/playwright package provides the AxeBuilder class: construct it with the current page, then call .analyze() to run an axe scan on the current page state.

npm install --save-dev @axe-core/playwright
Playwright test file — show code 
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

test('homepage has no critical accessibility violations', async ({ page }) => {
  await page.goto('/');
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa'])
    .analyze();
  expect(results.violations.filter(v =>
    ['critical','serious'].includes(v.impact)
  )).toHaveLength(0);
});
  • withTags: Scope to WCAG 2.1 AA rules only. Avoids best-practice rules that produce noise in CI.
  • filter by impact: Fail only on critical and serious. Moderate and minor go in the backlog.
  • results.violations: Array of violations: each has rule ID, impact, WCAG criterion, and affected elements with DOM selectors.

3. axe-Core with Cypress

The cypress-axe package adds cy.checkA11y() as a Cypress command.

npm install --save-dev cypress-axe axe-core
Cypress commands and test file — show code 
// cypress/support/commands.js
import 'cypress-axe';

// cypress/e2e/accessibility.cy.js
describe('Accessibility', () => {
  it('homepage passes axe wcag2aa', () => {
    cy.visit('/');
    cy.injectAxe();
    cy.checkA11y(null, {
      runOnly: { type: 'tag', values: ['wcag2a', 'wcag2aa'] },
      includedImpacts: ['critical', 'serious']
    });
  });
});
  • cy.injectAxe(): Injects axe-core into the page. Must be called after page load, before cy.checkA11y().
  • First argument null: Scans the full page. Pass a CSS selector to scope to a component.
  • includedImpacts: Same impact filtering as Playwright: fail on critical and serious only.

4. Scoping Scans: Page, Component, Interaction State

The most common mistake in pipeline accessibility testing is scanning only the page load state. Most violations live in interaction states: open modals, expanded accordions, submitted forms with errors, filter results. Scope your scans to match your functional test flows.

When to run axe scans within a test flow
Test pointWhat to scanWhy
Page loadFull pageCatches structural issues: missing landmarks, heading hierarchy, page title, language
Modal openModal selector or full pageCatches missing dialog role, missing close button label, focus management violations
Form submit with errorsFull page or form selectorCatches error identification violations, missing aria-describedby on invalid fields
After filter or searchResults container selectorCatches dynamic content violations on updated DOM
After accordion expandAccordion selectorCatches aria-expanded state violations, revealed content with missing labels

5. Configuration: wcag2aa, Impact Filtering, Exclusions

  • runOnly: WCAG 2.1 AA: Targets WCAG 2.1 AA rules. Add wcag21aa for WCAG 2.1-specific rules beyond 2.0.
  • Included impacts: Critical and Serious: Critical and Serious violations fail the build immediately. Moderate and Minor are written to a separate JSON artifact in CI: they are visible to the team but do not block the pipeline. Route them to the backlog with a target sprint.
  • Exclude selectors: Pass an exclude array to skip known third-party components you cannot fix. Document the exclusion and review it each sprint.
  • Baseline file: Some teams use a baseline file to suppress known existing violations and catch only new regressions. Use this as a temporary measure: not as a permanent exemption mechanism.

6. Failing Builds on Violations

The test assertion must cause the build to fail when violations are found. A scan that logs violations without failing the build is not a gate: it is a log that nobody reads.

  • Playwright: Use expect(violations).toHaveLength(0) or expect(critical).toHaveLength(0). Test fails, build fails.
  • Cypress: cy.checkA11y() throws on violations by default. The test fails, the build fails.
  • Report output: Log the full violations array to a JSON file and attach it to the CI artifact. Developers need the rule ID, WCAG criterion, and DOM selector to fix the issue without running the suite locally.

7. The GitHub Actions Workflow File

Everything above runs the test locally. To run it automatically on every push, it needs to live inside a GitHub Actions workflow file: not just the test command by itself. This is the piece that is usually missing for anyone setting this up for the first time.

Create the file at .github/workflows/accessibility.yml. GitHub only picks up workflows from that exact folder at the root of the repository.

.github/workflows/accessibility.yml — show code 
# .github/workflows/accessibility.yml
name: Accessibility Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]

jobs:
  a11y:
    runs-on: ubuntu-latest
    steps:
      - name: Check out the code
        uses: actions/checkout@v4

      - name: Set up Node.js
        uses: actions/setup-node@v4
        with:
          node-version: 20

      - name: Install dependencies
        run: npm ci

      - name: Install Playwright browsers
        run: npx playwright install --with-deps chromium

      - name: Run accessibility tests
        run: npx playwright test

      - name: Upload test report
        if: always()
        uses: actions/upload-artifact@v4
        with:
          name: playwright-report
          path: playwright-report/
What each step does — show explanation
  • name: The label shown for this workflow in the repository's Actions tab. Purely cosmetic, but useful once you have more than one workflow.
  • on: push / pull_request, branches main: Decides when the workflow runs. This runs it on every push to main and on every pull request targeting main, so a violation is caught before it merges, not after.
  • runs-on: ubuntu-latest: GitHub gives you a fresh, empty Linux virtual machine for each run. Nothing from your local machine exists on it, which is why every following step has to set that machine up from scratch.
  • actions/checkout@v4: Without this step, the runner has no copy of your code at all. This step pulls your repository onto the runner so later steps have something to test.
  • actions/setup-node@v4: Installs Node.js on the runner so npm and npx commands work. node-version: 20 pins the version so a future Node release cannot silently change CI behaviour.
  • npm ci: Installs dependencies from package-lock.json exactly as locked, rather than npm install, which can resolve to slightly different versions. CI should be reproducible.
  • npx playwright install --with-deps chromium: The runner does not have a browser installed. This downloads Chromium and the OS-level libraries Playwright needs to run it headlessly.
  • npx playwright test: Runs the actual test suite, including the axe-core assertion from Section 2. If a critical or serious violation is found, this step exits with a non-zero code and fails the job.
  • Upload test report, if: always(): By default, a failed step skips the steps after it. if: always() overrides that so the HTML report still gets uploaded even when the tests fail, since that is exactly when you need to look at it. It is downloadable from the run's summary page in the Actions tab.

8. Try It: Point This at the Playground

Sections 2 and 3 above assume a project that already runs. This section is the missing first mile: from nothing installed to a passing (well, correctly failing) axe-core test against the Axe-Core CI Playground, which contains deliberate Critical, Serious, and Moderate violations plus passing examples to check your setup against.

The playground is already hosted on GitHub Pages, so Playwright can open the live URL directly: no dev server, no local file path to resolve, and no repo checkout required just to run this one test. The same test runs unchanged on your machine or inside the GitHub Actions runner from Section 7.

  1. Install, if you have not already: npm install -D @playwright/test @axe-core/playwright, then npx playwright install --with-deps chromium.
  2. Save the test next to where you'd keep other playground checks. Create it at A11y-Test-Playground/axe-core-ci-playground.spec.ts: co-locating it with the rest of this series' playground tests makes it easy to find later, even though the test itself targets the hosted page, not a local file.
  3. Run it: npx playwright test A11y-Test-Playground/axe-core-ci-playground.spec.ts
A11y-Test-Playground/axe-core-ci-playground.spec.ts — show code 
import { test, expect } from '@playwright/test';
import AxeBuilder from '@axe-core/playwright';

const playgroundUrl = 'https://renitanaz.github.io/thequalitystrategist/blogs/accessibility/A11y-Test-Playground/31%20A11y%20Test%20Playground%20-%20Axe%20Core%20CI.html';

test('Axe-Core CI Playground has the expected violations', async ({ page }) => {
  await page.goto(playgroundUrl);
  const results = await new AxeBuilder({ page })
    .withTags(['wcag2a', 'wcag2aa'])
    .analyze();

  // This page is deliberately broken: the assertion checks that the gate
  // CATCHES violations, not that there are none. On a real page under test,
  // use the fail-the-build pattern from Section 6 instead.
  expect(results.violations.length).toBeGreaterThan(0);
});

Read the output: axe-core lists every violation it found, grouped by rule ID and impact. Compare that list against the labelled Critical, Serious, and Moderate scenarios on the playground page itself.

To see the other half of the pattern, point the fail-the-build assertion from Section 6 at the Axe-Core CI Playground: Clean Page instead: the same scenarios, implemented correctly. It should report zero Critical or Serious violations, confirming your pipeline gate does not fail on a page that is actually fine. Once you trust both directions, point the same test at a real page.

The minimum viable pipeline setup
  • Add axe-core to your existing Playwright or Cypress suite: not a separate suite.
  • Scope to wcag2aa rules and critical/serious impact only.
  • Run axe after page load AND after every significant interaction state in your test flow.
  • Fail the build on any critical or serious violation. Zero exceptions without a documented exclusion.
  • Runs headlessly on any OS in CI (Linux, Mac, Windows), on Chromium and Firefox at minimum.
