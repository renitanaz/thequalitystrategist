15 Forms, Labels, Errors and Instructions: How to Test Form Accessibility

A form without a label is a locked box. An error message without a description is just a red box. Both are testable in under five minutes.

1. Labels: The Non-Negotiable Baseline

Every form input must have a visible, programmatically associated label. There are four valid ways to associate a label with an input. Only one is wrong.

Correct: explicit for/id association
<label for="email"> Email address </label> <input type="email" id="email" autocomplete="email" />
Fails: placeholder only, no label
<input type="email" placeholder="Email address" /> /* Placeholder disappears on type. Not announced as a label. Fails 1.3.1 and 3.3.2 */

Placeholder text is not a label. It disappears when the user starts typing. Screen readers do not reliably announce it as the field's purpose. It fails both visually and programmatically.

The four valid labelling methods

Four valid ways to associate a label with an input
MethodWhen to useExample
for / id associationStandard. Use this by default.<label for="name"> + <input id="name">
Wrapping <label>When label and input are naturally grouped.<label>Name <input type="text"></label>
aria-labelWhen no visible label is possible (icon buttons, search inputs).<input aria-label="Search">
aria-labelledbyWhen the label is existing text elsewhere on the page.<input aria-labelledby="heading-id">
aria-placeholder is not a label. title attribute is not a reliable label. Visually positioned text with no programmatic association is not a label. Run axe-core: if it passes with no label violations, the association is correct. If it does not, the screen reader cannot find the label.

2. Error Messages: Identify, Describe, Suggest

WCAG requires three things from an error message: it identifies which field is in error, it describes what went wrong, and (where possible) it suggests how to fix it. A red border alone fails all three. "Invalid input" fails the description. "Please enter a valid email" is the minimum: it identifies the field and describes the format required.

Fails 3.3.1 and 3.3.3
<input type="email" class="error" aria-invalid="true" /> <span class="error-msg"> Invalid input </span> /* No aria-describedby linking input to error message. Error text too vague. */
Passes 3.3.1, 3.3.2, 3.3.3
<label for="email"> Email address </label> <input type="email" id="email" aria-invalid="true" aria-describedby="email-err" /> <span id="email-err" role="alert"> Enter a valid email address, e.g. name@example.com </span>

The critical elements: aria-invalid="true" signals to screen readers that the field is in an error state. aria-describedby links the field to its error message so the message is announced when focus enters the field. role="alert" on the error span announces the message immediately when it appears without requiring the user to Tab back to the field.

3. Required Fields and Instructions

Required fields must be marked in a way that does not rely on colour alone. A red asterisk (*) with no programmatic meaning fails WCAG 1.4.1. The requirement must be conveyed in text or via aria-required="true" or the HTML required attribute.

Fails 1.4.1: colour only
<label for="name"> Full name <span style="color:red">*</span> </label> <input id="name" /> /* Asterisk has no meaning to a screen reader. No required attribute set. */
Passes 1.4.1 and 3.3.2
<label for="name"> Full name <span aria-hidden="true">*</span> <span class="visually-hidden"> required </span> </label> <input id="name" required aria-required="true" />

Instructions that apply to the whole form: "Fields marked with * are required", date format guidance, password rules: must appear before the first field they apply to, not after. A screen reader user who has already passed the instruction cannot easily go back to it when they reach the relevant field.

4. Autocomplete Attributes

WCAG 1.3.5 requires that inputs collecting personal data include the appropriate autocomplete attribute. This helps users with cognitive disabilities, motor impairments, and anyone using a password manager. It is also one of the most commonly missed form requirements.

Setting autocomplete="off" on fields that collect personal data fails WCAG 1.3.5. This is common in banking and healthcare forms where teams assume it improves security. It does not: and it actively harms users with cognitive disabilities who rely on autofill.

5. How to Test: Automation, Tools, and Platform Coverage

🎯
Practice these yourself
All failure patterns are available as interactive demos in the Forms Playground. Mobile testing steps are in the Mobile Testing Guide.

Tier 1: Pipeline automation

axe-core in Playwright or Cypress, and Pa11y, will catch:

  • Inputs with no label and no aria-label or aria-labelledby
  • Inputs with aria-invalid="true" but no associated error message via aria-describedby
  • Missing autocomplete attributes on personal data fields
  • Form fields inside a group with no <fieldset> and <legend> (e.g. radio button groups)

Tier 2: Semi-automated tools

  • axe DevTools: run a full page scan after triggering a form validation error. Filter by label and color-contrast rules. Shows exact element and fix guidance.
  • WAVE: the Errors tab highlights missing labels with red flags. The Structural view shows form elements and their associated labels. Run after submitting the form with empty fields.
  • Chrome DevTools accessibility tree: select any input, check the computed accessible name and description. Confirms what the screen reader will announce and whether the error message is linked.

Tier 3: Manual checks only

  • Placeholder used as label: automation may not flag this if the placeholder text matches a label elsewhere. Tab to the input and check the DevTools accessibility tree: if the name is empty or comes only from placeholder, it is a failure.
  • Error message is vague: automation confirms the error is linked. Only a human can judge whether "Invalid input" meets the 3.3.3 requirement to suggest a fix.
  • Required field marked by colour only: automation does not check whether the asterisk has a programmatic meaning. Inspect the markup.
  • Instructions appear after the fields they apply to: automation cannot check reading order in context. Walk through the form with a screen reader.
  • Error announced on submit: trigger the form submission with invalid data. Verify the error messages are announced without requiring the user to Tab to the error.

Windows: NVDA

Tab into the form. For each field, NVDA should announce: label, field type, and any instructions or constraints. Submit the form with errors. NVDA should announce the error messages via role="alert" immediately. Tab back to any error field: NVDA should re-announce the error description via aria-describedby. Press Insert+F7 to open the elements list and select Form Fields: lists all inputs and their labels.

Mac: VoiceOver

Enable VoiceOver with Cmd+F5. Use Safari. Press VO+U to open the rotor and select Form Controls: all inputs listed with their labels. Tab through the form: VoiceOver announces "Email address, required, edit text" for a correctly marked required field. Submit the form with errors: error messages with role="alert" are announced immediately.

iOS: VoiceOver

Enable VoiceOver: Settings, Accessibility, VoiceOver, Toggle ON. Use Safari. Open the rotor and set it to Form Controls. Swipe through each field. VoiceOver announces the label, type, and required state when focus enters. Trigger validation errors by double-tapping Submit without completing the form. Error messages with role="alert" are announced immediately.

Android: TalkBack

Enable TalkBack: Settings, Accessibility, TalkBack, Toggle ON. Use Chrome. Open reading controls (swipe up then right) and select Controls. Navigate through each form field. TalkBack announces the label and type. Submit with errors: role="alert" messages are announced. For each error field, focus it again: TalkBack should re-announce the error description.

6. WCAG Requirements for Forms

WCAG success criteria for form accessibility
Criterion Level Requirement
1.3.1 Info and RelationshipsALabels are programmatically associated with their inputs. Field groups use <fieldset> and <legend>.
1.3.5 Identify Input PurposeAAInput fields collecting personal data have correct autocomplete attributes.
2.4.6 Headings and LabelsAALabels are descriptive. "First name" is descriptive. "Name" alone may not be.
3.3.1 Error IdentificationAIf an error occurs, the item in error is identified and described in text.
3.3.2 Labels or InstructionsALabels or instructions are provided when content requires user input.
3.3.3 Error SuggestionAAIf an error is detected and suggestions are known, the suggestion is provided.
3.3.4 Error PreventionAAFor legal, financial, or data submissions: reversible, checkable, or confirmable.
4.1.3 Status MessagesAASuccess and error messages are announced to screen readers without moving focus.

7. Writing Form Accessibility Defects

Form accessibility defects with WCAG reference, severity, and reproduction steps
Defect WCAG Severity Reproduction
Input has no label1.3.1 / 3.3.2CriticalInspect element: no <label for>, no aria-label, no aria-labelledby. NVDA announces "edit text, blank."
Placeholder used as only label1.3.1 / 3.3.2MajorTab to the input. Type a character. Placeholder disappears. NVDA no longer announces the field purpose.
Error indicated by colour only1.4.1 / 3.3.1MajorSubmit form with invalid data. Red border appears. No text error message. NVDA announces no error state.
Error message not programmatically linked3.3.1MajorSubmit form. Error message appears visually but aria-describedby is absent. NVDA does not announce the error when field is refocused.
Error message too vague3.3.3ModerateSubmit form with invalid data. Error text is "Invalid" or "Error" with no description or suggestion.
Required field marked by asterisk only1.4.1 / 3.3.2ModerateInspect label: asterisk has no aria-hidden and no visually hidden "required" text. required or aria-required absent on input.
Missing autocomplete on personal data field1.3.5ModerateInspect input: no autocomplete attribute on name, email, address, or phone field.
Radio group missing fieldset/legend1.3.1ModerateTab to first radio button. NVDA announces the option label but not the group question. No <fieldset> and <legend> wrapping the group.
The two fast checks
  • Tab through every field. NVDA should announce label, field type, and any constraints. If you hear "edit text, blank" on any field, the label is missing.
  • Submit the form with empty required fields. Every error must be announced immediately without requiring the user to Tab back. If errors are silent, role="alert" or aria-describedby is missing.
