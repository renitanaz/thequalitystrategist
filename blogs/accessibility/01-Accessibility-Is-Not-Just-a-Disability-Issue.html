How This Blog Connects to Testing

Tier 1: Pipeline automation

Automated tools cannot verify whether a team treats accessibility as a quality concern. But a missing pipeline gate is itself evidence of the problem. Add axe-core to CI as the minimum signal that accessibility is a build criterion: not a post-release check.

Tier 2: Semi-automated tools

Run axe DevTools or WAVE on any page before a sprint review. If violations exist and nobody flagged them, the gap is not tooling: it is ownership and priority. These tools make that gap visible in seconds.

Tier 3: Manual

Platform coverage: Test on Windows (Chrome + Firefox), Mac (Safari + Chrome), iOS (Safari on physical iPhone), and Android (Chrome on physical device). Platform differences in keyboard handling and screen reader behaviour mean a bug on one platform does not guarantee the same behaviour on another.

The most important check for this blog is a process check, not a tool check: who is responsible for accessibility at each phase? If the answer is "QA at the end," use Blog 04 for the ownership model and Blog 09 for phase exit criteria to change it.

🎯 1. What Accessibility Actually Means

Accessibility means designing websites, apps, and content so that everyone: including people with disabilities: can use them.

That definition is correct but incomplete. It creates the mental model that accessibility is a niche concern: something you do for the 15–20% of people who have a declared disability. That framing is why accessibility gets deprioritised.

The more accurate definition:

Accessibility is designing so that every person, in every context, can use what you build.

The moment you accept that definition, accessibility stops being a checkbox and becomes a quality standard: the same way performance or security is a quality standard.

👥 2. The Situational Impairment Model

Disabilities are not binary. They exist on a spectrum: and they are not always permanent. Microsoft's Inclusive Design Framework categorises impairment into three types.

👁
Visual
Permanent Blind, low vision, colour blindness
Temporary Eye surgery, eye infection
Situational Forgot glasses, screen glare
🤚
Motor

Temporary Broken wrist, RSI
Situational Holding a baby, bumpy train
👂

Permanent Deaf, hard of hearing
Temporary Ear infection, swimmer's ear
Situational Noisy environment, no headphones
🧠
Cognitive
Permanent Dyslexia, ADHD, memory impairment
Temporary Concussion, post-illness fatigue
Situational Distracted, stressed, new language
Takeaway

When you build for the permanent impairment case, you solve for everyone. Ramps built for wheelchair users are used daily by parents with prams, delivery workers, people with knee injuries, and the elderly. Captions built for deaf users are now used by millions watching videos in public without headphones. Accessibility features are usability features.

🔷 3. The Microsoft Inclusive Design Framework

Microsoft's framework makes the impairment model concrete with three design principles:

01
Recognise exclusion

Exclusion happens when we solve for the average user and ignore the edges. The edges are larger than most teams assume.

02
Learn from diversity

Constraints drive better design. Designing for keyboard-only users forces clarity that benefits everyone.

03
Solve for one, extend to many

Solutions for permanent impairments extend naturally to temporary and situational cases. One solution, every context.

A keyboard-accessible form benefits a permanent motor impairment user, someone with a broken wrist, a power user who prefers keyboard, and anyone whose mouse just stopped working. One solution. Every context.

Failure mode 1: QA is the only accessibility gate

Everything lands in QA for accessibility to be checked. Every defect was created upstream and is now expensive to fix. QA becomes a remediation team, not a quality gate.

Failure mode 2: QA is excluded entirely

Accessibility is declared a "developer responsibility" and QA is not given the tools, time, or mandate to test it. Defects reach production.

The correct model: QA is the last line of defence: not the only line. QA validates that upstream gates were enforced, runs checks that tools cannot replicate, logs defects precisely, and holds the sign-off gate.

📋 5. The Shared Responsibility Model

Accessibility is not one person's job. It fails when it becomes one person's job.

Accessibility ownership by role and delivery phase
Role Phase Primary responsibility
Product Owner / PMDiscoveryIdentify regulatory obligations, define WCAG conformance target, sign off on accessibility acceptance criteria
UX / DesignerDesignValidate colour contrast, specify focus indicators, annotate tab order, define heading hierarchy
Content AuthorAuthoringEnsure alt text, headings, and link text are correct in the CMS

When one role drops their responsibility, the defect moves to the next phase and becomes more expensive to fix. A missing alt text at authoring costs seconds. Found in QA it needs a content fix, deploy, retest, and sign-off. In production it carries legal risk.

✗ 6. Common Misconceptions

"Accessibility is only for blind users."
False. It covers visual, motor, hearing, and cognitive impairments: permanent, temporary, and situational. Keyboard accessibility has nothing to do with vision.
"We have a small disabled user base so it doesn't matter."
False. You cannot measure your disabled user base: users do not declare impairments. Situational impairments apply to everyone. In many jurisdictions it is a legal requirement regardless of audience size.
"Automated tools handle accessibility testing."
False. Automated tools catch 30–50% of accessibility issues. Focus visibility, keyboard usability, screen reader context, and cognitive load require human testing. This is the primary reason QA exists in this process.
"Accessibility is a one-time fix."
False. Content changes, components are rebuilt, integrations update. Accessibility requires ongoing governance: not a single audit.

📐 8. What WCAG 2.1 AA Is

The Web Content Accessibility Guidelines (WCAG) 2.1 is the W3C standard defining what an accessible digital product looks like. It is organised around four principles: Perceivable, Operable, Understandable, Robust (POUR). Level AA is the conformance level required by most legal frameworks. Blog 03 covers WCAG 2.1 AA in full: every criterion and how to test it.

📖 9. Key Terms Glossary

WCAG
Web Content Accessibility Guidelines
ARIA
Accessible Rich Internet Applications: markup that describes UI to assistive technologies
Semantic HTML
HTML elements that carry meaning (<button>, <nav>) vs generic <div>
Screen reader
Software that reads content aloud: NVDA, JAWS, VoiceOver, TalkBack
Keyboard trap
A UI component you can Tab into but cannot Tab out of
Contrast ratio
Luminance difference between foreground and background: min 4.5:1 for body text
Focus indicator
The visual outline showing which element has keyboard focus
AT
Assistive technology: any tool users with disabilities rely on
A11y
Numeronym for accessibility: A + 11 letters + y
POUR
Perceivable, Operable, Understandable, Robust: the four WCAG principles
