1. The Problem With Shift-Right

Most teams treat accessibility as a testing activity. It gets added to the sprint near the end, or more commonly it appears in a post-launch audit, and then the question becomes: how do we fix all this?

That question is expensive to answer. Not because fixing accessibility is inherently hard, but because the further you find a defect from its origin, the more work surrounds the fix itself.

A defect found at discovery costs 1× to fix. The same defect found in production costs 30–100×. Accessibility is no different from any other quality dimension.

This isn't a theory. It comes from decades of software defect cost research — and it applies directly to accessibility because accessibility defects have the same root cause structure as any other defect: a decision made without the right constraint in mind.

The rule

Every phase gate you hold saves multiples of the cost at the next phase. Catching something in design instead of development is a 2–5× saving. Catching it in development instead of QA is a 2–3× saving. Catching it before production is anywhere from a 2–7× saving, plus legal risk avoided.

3. Learnings From Experience

The multiplier table above is not theoretical. Here are two situations where I saw this cost play out firsthand: one avoidable, one not.

01
Phase 2: CMS Modelling

Not restricting heading types in the CMS: discovered too late

On one project, the CMS rich text editor was left open (authors could use any heading level, including H1, anywhere in the body). No restrictions were set during the content modelling phase.

By the time this was flagged — during QA — a significant volume of content had already been migrated. Every migrated page that contained an incorrect heading structure needed to be identified, reviewed, and corrected individually. The content model then had to be updated to restrict heading levels, which required re-validation of all previously published entries.

The fix itself (restricting heading levels in the CMS) was straightforward and would have taken a few hours at the modelling stage. The remediation after migration took days across multiple people. A Phase 2 decision left unaddressed became a Phase 4 crisis.

The lesson Heading level restrictions, alt text field requirements, and CMS content rules must be defined and enforced before any content is authored or migrated. Not after.
02
Phase 1: Design

Colour contrast validated at design, and what the alternative looked like

On one team, the design lead ran contrast checks in Figma — using Stark — before any handoff. The brand colour palette was validated against WCAG 1.4.3 and 1.4.11 before a single component was built. Contrast issues were caught and corrected in hours at the design stage.

I understood the value of this only when I worked with a different team that did not do it. The website's brand theme (primary colours, typography, button states) had never been validated for contrast. By the time it reached QA, the contrast failures were not isolated to a component. They were baked into the design system itself.

Fixing a contrast failure in a component is straightforward. Fixing a contrast failure in a brand theme means revisiting colour tokens, updating the design system, regenerating components, retesting every screen. The rework is enormous, and it was all avoidable with a Figma plugin check during Phase 1.

The lesson Colour contrast is not a QA check. It is a design constraint. The brand theme must meet WCAG contrast requirements before any component is designed against it.

The multiplier isn't arbitrary. Each phase adds layers of work around the fix itself. Here's what the cost actually comprises at each stage:

5. A Real Defect Traced Through Every Phase

Take a missing alt text on an image that is a call-to-action button. Here is exactly what it costs at each phase:

Cost of a missing alt text defect traced through every delivery phase
Phase How it's caught What the fix requires Cost
Discovery Acceptance criteria review Add "All image CTAs must have descriptive alt text" to AC 1×
Design Figma annotation review Add alt text annotation to component in Figma, re-handoff 3–5×
CMS Modelling Field audit Add alt text field to image component, migrate existing entries 4–6×
Development axe-core linting or PR review Add alt attribute, fix aria-label, PR, re-deploy 10–15×
QA axe DevTools scan + NVDA test Log defect, dev fix, retest, screen reader retest, sign off 20–30×
Production User complaint / external audit All of QA costs + legal review, emergency sprint, VPAT update 30–100×

The defect is identical at every phase. The work surrounding the fix is what multiplies. The fix itself (writing the alt text) takes 30 seconds. The process that wraps it at production can take days.

6. The Hidden Costs Nobody Talks About

The multiplier table covers the direct cost of fixing a defect. It does not cover the indirect costs that accumulate when accessibility is treated as an afterthought:

  • Team velocity loss: emergency accessibility sprints kill planned feature work. Teams that fix accessibility late are always in catch-up mode.
  • Regression risk: a fix applied under pressure in production often creates new issues. Rushed patches without regression testing introduce more defects.
  • Legal exposure: in the US, EU, UK, and Australia, non-compliant digital products are legal liabilities. ADA lawsuits cost significantly more than any remediation sprint.
  • Reputational damage: public accessibility failures are visible. A screen reader user sharing a broken experience on social media is a brand problem, not just a technical one.
  • VPAT burden: if your product requires a Voluntary Product Accessibility Template (VPAT) for enterprise sales, a production accessibility failure blocks deals.
  • Audit cost: a third-party accessibility audit commissioned after a complaint costs far more than the internal testing that would have caught the same issues.

7. How to Make the Case to Your Team

The cost multiplier is your most powerful tool for getting accessibility taken seriously upstream. Here's how to use it with different audiences:

PM
With a PM or product owner
"Adding accessibility acceptance criteria to the user story takes 10 minutes. Finding the same issue in QA adds 2–3 days to the sprint. Which one do you want?"
UX
With a designer
"Running Stark or Zımmer on your Figma file takes 5 minutes. A contrast failure caught in QA means a design rework, a dev rework, and a retest cycle. The plugin is faster."
Dev
With a developer
"eslint-plugin-jsx-a11y flags missing alt text as you type. Catching it in QA means a code change, a PR, a redeploy, and a retest. The linter is faster and cheaper."
Exec
With a stakeholder or client
"Accessibility built in from day zero costs approximately 10–20% of the effort of retrofitting it post-launch. And it avoids the legal risk entirely."

8. What Prevention Looks Like in Practice

Shift-left accessibility is not a single action. It is a set of gates (one per phase) that together make sure defects never compound:

Shift-left prevention actions by phase
Phase Prevention action Who
Discovery Add accessibility acceptance criteria to every user story. Define WCAG 2.1 AA as the conformance target. PM / PO
Design Run Stark or Zımmer on Figma files. Annotate tab order. Specify focus indicators. Write error copy at design stage. UX / Designer
CMS Modelling Add alt text fields. Restrict heading levels in rich text. Require captions on video. Make decorative image flag explicit. CMS / Backend Lead
Development Use semantic HTML. Run eslint-plugin-jsx-a11y. Add axe-core to CI/CD pipeline. Fail builds on Critical violations. Developer
QA Run keyboard testing, screen reader testing, axe DevTools, WAVE. Hold phase exit criteria. Log defects with WCAG reference. QA
Production Run Pa11y nightly. Monitor for regressions. Maintain VPAT if required. Act on user-reported issues within SLA. DevOps / QA
The point

Each of these actions costs a fraction of finding the same issue one phase later. The sum of all prevention actions across all phases is still less than a single production remediation sprint. Shift-left accessibility is not idealism; it is basic cost management.
