08 ESLint and Axe-Core: Catching Accessibility Issues Before They Reach QA

The two tools that sit between a developer's keyboard and a QA defect.

1. The Three Automated Layers

Automated accessibility checking happens at three points in the development workflow. Each catches different things. None replaces the others.

IDE / Code time
eslint-plugin-jsx-a11y
Flags issues as the developer writes JSX. Instant feedback, zero delay. Catches structural issues before the code is even saved.
Missing alt, invalid ARIA, non-interactive elements with event handlers.
Test suite
axe-core (jest-axe, Cypress, Playwright)
Runs accessibility checks against rendered components and full user journeys. Catches issues that only appear when the component is actually rendered in the DOM.
Contrast failures, landmark issues, focus management, ARIA state problems.
CI/CD pipeline
axe-core + Pa11y / Lighthouse
Runs on every pull request or deployment. Fails the build on Critical or Serious violations. The last automated gate before QA.
Any Critical or Serious violation that escaped the IDE and test suite.
Together these three layers catch a significant proportion of structural and ARIA issues automatically. What they cannot catch: focus visibility, keyboard usability, screen reader context, cognitive load: is where manual testing begins. Blog 07 covers what developers must get right before these tools even run.

2. eslint-plugin-jsx-a11y: Catching Issues as You Type

eslint-plugin-jsx-a11y is an ESLint plugin that adds accessibility rules to the standard JavaScript linting workflow. It analyses JSX statically: without rendering anything: and flags violations inline in the IDE as the developer writes code.

The practical effect: a missing alt attribute gets a red underline before the file is saved. A <div> with an onClick handler and no keyboard support gets flagged before it reaches a pull request. The defect is caught at the cheapest possible moment.

Installation

Terminal
npm install --save-dev eslint-plugin-jsx-a11y
.eslintrc.js or eslint.config.js
{ "plugins": ["jsx-a11y"], "extends": ["plugin:jsx-a11y/recommended"] }

The recommended config enables all rules at warn or error level. Use strict for a higher bar. Most teams start with recommended and tighten rules over time.

3. What It Catches: The Key Rules

These are the rules that fire most frequently on real codebases. Each maps directly to a WCAG failure.

4. Axe-Core: Catching Issues in Tests and CI/CD

axe-core is the accessibility testing engine used by axe DevTools, Accessibility Insights, and many CI/CD integrations. It runs against a rendered DOM: not static code: which means it catches issues that only appear when the component is actually mounted: contrast failures, missing landmarks, focus management problems, and ARIA state issues.

Axe-core reports violations at four severity levels:

  • Critical: Blocks access entirely for some users. Must fix before release.
  • Serious: Makes content very difficult to use. Should fix before release.
  • Moderate: Creates friction but does not block access. Fix in next sprint.
  • Minor: Best practice. Address when convenient.

The CI/CD gate should fail on Critical and Serious. Moderate and Minor violations should be tracked and addressed but should not block a release without a deliberate team decision.

Axe-core with jest-axe (component level)

Install
npm install --save-dev jest-axe
Button.test.jsx
import { render } from '@testing-library/react'; import { axe, toHaveNoViolations } from 'jest-axe'; import Button from './Button'; expect.extend(toHaveNoViolations); test('Button has no accessibility violations', async () => { const { container } = render( <Button onClick={() => {}}>Submit</Button> ); const results = await axe(container); expect(results).toHaveNoViolations(); });

This test renders the component and runs the full axe-core ruleset against it. If the button has no accessible name, no keyboard support, or invalid ARIA, the test fails. The developer sees the failure before the PR is raised.

5. Axe-Core in Cypress and Playwright

Component-level tests catch individual component issues. Integration tests with Cypress or Playwright test full user journeys: the login flow, the checkout process, the form submission: and can catch issues that only appear when components interact.

Cypress with cypress-axe

Install
npm install --save-dev cypress-axe axe-core
cypress/support/e2e.js
import 'cypress-axe';
login.cy.js
describe('Login page accessibility', () => { it('has no Critical or Serious violations', () => { cy.visit('/login'); cy.injectAxe(); cy.checkA11y(null, { includedImpacts: ['critical', 'serious'] }); }); it('form is accessible after error state', () => { cy.visit('/login'); cy.injectAxe(); cy.get('[data-cy=submit]').click(); // trigger errors cy.checkA11y(); // check error state too }); });

Playwright with axe-playwright

Install
npm install --save-dev @axe-core/playwright
login.spec.ts
import { test, expect } from '@playwright/test'; import AxeBuilder from '@axe-core/playwright'; test('login page has no Critical violations', async ({ page }) => { await page.goto('/login'); const results = await new AxeBuilder({ page }) .withTags(['wcag2a', 'wcag2aa']) .analyze(); expect(results.violations .filter(v => v.impact === 'critical')).toHaveLength(0); });
Test the error state too

Most accessibility tests check the happy path. The error state (form validation failures, API errors, empty states): is where accessibility issues hide. Always test the states that appear after user interaction, not just the initial page load.

6. Setting Up a CI/CD Accessibility Gate

The accessibility gate runs on every pull request and fails the build if Critical or Serious violations are present. Here is a minimal GitHub Actions setup using Pa11y:

.github/workflows/accessibility.yml
name: Accessibility check on: [pull_request] jobs: a11y: runs-on: ubuntu-latest steps: - uses: actions/checkout@v3 - uses: actions/setup-node@v3 with: node-version: '18' - run: npm ci - run: npm run build - run: npx serve -s build & - run: sleep 3 - run: | npx pa11y-ci \ --standard WCAG2AA \ --reporter cli \ http://localhost:3000

For Cypress-based pipelines, the cy.checkA11y() call in the test suite is the gate. The Cypress run in CI fails if any violations above the threshold are found.

The key principle: Critical and Serious violations fail the build. They do not get merged. This is a team agreement, not a tool setting: the tool enforces what the team has agreed.

7. What These Tools Miss

Automated tools: including eslint-plugin-jsx-a11y, axe-core, and Pa11y combined: catch approximately 30 to 50% of accessibility issues. The rest require manual testing.

What automated tools miss and why manual testing is required
Issue type Why automation misses it How to catch it
Focus visibilityTools check that a focus indicator exists in the stylesheet, not whether it is actually visible against the background in contextManual keyboard testing
Keyboard usabilityTools check that elements are focusable, not whether the interaction flow makes senseManual keyboard testing
Screen reader contextTools check that labels exist, not whether the announcement sequence makes sense to a screen reader user navigating the pageNVDA, VoiceOver, TalkBack
Meaningful alt textTools check that alt text is present and non-empty, not whether it is accurate or usefulManual content review
Cognitive loadNo tool measures whether content is clear, consistent, or easy to understandManual review + readability tools
Error announcementTools check that live regions exist, not whether the announcement fires at the right time with the right contentScreen reader testing
Mobile gesture supportTools do not run on real devices or test touch interactionVoiceOver on iOS, TalkBack on Android

8. How QA Uses This Layer

QA does not own the eslint or axe-core setup: that is a developer and DevOps responsibility. But QA has a direct interest in whether these tools are in place and working, for one reason: when they are not, the volume of structural and ARIA defects in QA testing increases significantly.

What QA should verify at Phase 3 exit

  • eslint-plugin-jsx-a11y is installed and configured in the project
  • No open Critical or Serious violations in the axe-core test suite
  • CI/CD pipeline fails on Critical accessibility violations
  • Axe-core tests cover key user journeys, not just component-level rendering
  • Error states and dynamic content states are covered by test cases

How to check the CI gate is working

Ask the developer to intentionally introduce a Critical violation: remove an alt attribute, add a div with no keyboard support: and verify the build fails. If the build passes, the gate is not working. This is a 5-minute check that has caught misconfigured pipelines more than once.

The bottom line

These two tools together are the cheapest accessibility investment a development team can make. eslint-plugin-jsx-a11y costs nothing to run and catches issues at the keyboard. axe-core in CI costs nothing to run and catches issues before merge. Both together still only cover half the problem. The other half is what the rest of this series covers.
