Testing the 12 Most Commonly Missed WCAG Criteria

Tier 1: Pipeline automation

Automation covers a subset of the 12 criteria: 1.1.1 (alt text present), 1.3.1 (info and relationships), 1.4.3 (contrast), 2.4.2 (page title), 3.1.1 (language), 4.1.1 (parsing), 4.1.2 (name/role/value). Run axe-core with withTags(['wcag2a','wcag2aa']). Use the Axe DevTools Playground to see these flagged in a real scan.

Tier 2: Semi-automated tools

Accessibility Insights Assessment provides a guided walkthrough of every WCAG 2.1 AA criterion including the ones automation misses. It records pass/fail per criterion and exports an HTML report. Use it for the non-automatable criteria in this blog.

Tier 3: Manual

The 12 missed criteria that require manual verification: 1.3.3 (sensory characteristics), 1.4.1 (use of colour), 2.1.1 (keyboard), 2.4.3 (focus order), 2.4.4 (link purpose), 2.4.7 (focus visible), 3.2.1 (on focus), 3.3.1 (error identification), 3.3.2 (labels or instructions). Test with keyboard, NVDA + Firefox (Windows), VoiceOver + Safari (Mac and iOS), TalkBack on Android.

1. What WCAG 2.1 Actually Is

The Web Content Accessibility Guidelines (WCAG) 2.1 is the W3C standard that defines what an accessible digital product looks like. It is published by the World Wide Web Consortium and is the basis for accessibility law in the US, EU, UK, Australia, and most other jurisdictions.

WCAG 2.1 has 78 success criteria across four principles. The version number matters: WCAG 2.1 added 17 new criteria on top of WCAG 2.0, primarily covering mobile, cognitive, and low-vision needs. WCAG 2.2 has since been published with further additions, but 2.1 AA is still the legal baseline in most jurisdictions.

2. Level A, AA and AAA: What the Difference Means

Each WCAG success criterion is assigned one of three conformance levels:

A
Minimum
The most critical requirements. Failing these makes content inaccessible to many users entirely.
Required baseline
AA
Standard
The legal target in most jurisdictions. Covers the majority of real-world accessibility needs.
Legal requirement
AAA
Enhanced
The highest level. Not required by law: often not achievable for all content types.
Best practice

When your project says "WCAG 2.1 AA compliant," it means every Level A and Level AA criterion is met. Level AAA criteria are aspirational: worth pursuing where possible, but not the legal threshold.

3. The Four POUR Principles

All 78 criteria sit under four principles: POUR. Every accessibility requirement flows from one of these four. Understanding POUR gives you a mental model for why each criterion exists.

P
Perceivable
Content and UI components must be presentable in ways users can perceive. If someone cannot see the screen, they must be able to hear it or feel it. Information cannot be conveyed by sight alone.
Covers: alt text, captions, contrast, text resize, audio descriptions
O
Operable
UI components and navigation must be operable. If someone cannot use a mouse, they must be able to use a keyboard. No interaction should require a physical action the user cannot perform.
Covers: keyboard access, no traps, skip links, focus visibility, timing
U
Understandable
Information and UI operation must be understandable. Content must be readable, UI must behave predictably, and users must be helped to avoid and correct mistakes.
Covers: page language, readable text, error messages, consistent navigation
R
Robust
Content must be robust enough to be interpreted by current and future assistive technologies. Code must be valid and semantic so screen readers, voice control, and other AT can parse it reliably.
Covers: valid HTML, ARIA roles, name/role/value for all UI components

4. The 12 Requirements That Catch Teams Off Guard

These are the requirements that appear most frequently as defects in real projects. Every item here maps to a real defect pattern seen in production. Use this as your rapid pre-release sanity check: regardless of role.

01
Perceivable
Headings: one H1, no skipped levels
Every page must have exactly one H1. Heading levels must be sequential (H1 → H2 → H3). Skipping from H1 to H3 breaks screen reader navigation and document structure.
1.3.1 · 2.4.6
02
Operable
Skip link: exists and is keyboard-focusable
A "Skip to main content" link must be the first focusable element on every page. It allows keyboard users to bypass repeated navigation. It must be visible on focus: not permanently hidden.
2.4.1
03
Perceivable
Landmarks: header, nav, main, footer present; one <main>
HTML landmark elements structure the page for screen reader users. A page must have one <main> only. Multiple <nav> elements must have distinct aria-labels to distinguish them.
1.3.1
04
Operable
Keyboard: fully operable, no traps
Every interactive element must be reachable and operable by keyboard alone. A keyboard trap: where focus enters a component and cannot leave: is a Critical defect. Disconnect your mouse and test every flow.
2.1.1 · 2.1.2
05
Operable
Focus: visible indicator, logical order
Every focusable element must show a visible focus indicator when active. The focus order must match the visual reading order. CSS outline:0 or outline:none removes the focus indicator entirely and is a defect.
2.4.3 · 2.4.7
06
Perceivable
Images: alt text present, or decorative flag set
Every informative image needs descriptive alt text. Decorative images must use alt="" (empty) so screen readers skip them. An image used as a link must have alt text describing the link destination, not the image.
1.1.1
07
Operable
Links: purpose clear, no "click here"
Each link must describe its destination from the link text alone, or from its immediate context. "Click here," "Read more," and "Learn more" used without context are failures. Screen readers list all links out of context: the link text must make sense standalone.
2.4.4
08
Understandable
Forms: visible labels, descriptive error messages
Every form input must have a visible, programmatically associated label. Placeholder text is not a label. Error messages must identify what is wrong and how to fix it, not just flag the field as invalid.
3.3.1 · 3.3.2
09
Robust
Dynamic messages: announced to assistive technology
Status updates, error messages, and AJAX content changes must be announced to screen readers via ARIA live regions. A form submission result that appears visually but is not announced is a failure for screen reader users.
4.1.3
10
Perceivable
Media: captions and transcripts, no autoplay
Prerecorded video must have synchronised captions. Auto-generated captions do not meet this requirement. Audio-only content requires a transcript. Any media that autoplays must have a mechanism to pause, stop, or mute it.
1.2.1 · 1.2.2 · 2.2.2
11
Understandable
Language: page language declared
The HTML lang attribute must be set correctly on the <html> element (e.g. lang="en"). Screen readers use this to select the correct language engine and pronunciation rules. A missing or incorrect lang attribute causes mispronunciation for every user.
3.1.1
12
Robust
Embeds: iframe titles required
Every <iframe> must have a meaningful title attribute describing its content. A YouTube embed without a title is announced as "frame" by screen readers: no information about what is inside. Hidden iframes must use aria-hidden="true".
4.1.2

5. Pass and Fail Examples for Each Requirement

Each example below shows three things: what it looks like visually, what the HTML looks like, and which tool to use to catch it. Start with the visual: if you can spot it without touching the code, you already have the instinct. The HTML and tool confirm the defect.

Requirement 01: Headings

Open any page and check the heading structure. A page that uses H1 twice, or jumps from H1 to H3, breaks screen reader navigation.

Fail (HTML)
<h1>Homepage</h1>
<h3>Latest news</h3>
<h1>About us</h1>
Pass (HTML)
<h1>Homepage</h1>
<h2>Latest news</h2>
<h3>Article title</h3>
How to catch it
  • WAVE Structure tab shows heading hierarchy visually.
  • axe DevTools Flags duplicate H1 and skipped levels.
  • Accessibility Insights Heading visualiser in FastPass.

Requirement 02: Skip link

Keyboard users must be able to skip past repeated navigation on every page. The skip link must be the first focusable element and must be visible when focused. Tab once on any page and see if it appears.

Fail (HTML)
<!-- No skip link -->
<nav>...</nav>
<main>...</main>
Pass (HTML)
<a href="#main" class="skip">
Skip to main content
</a>
<nav>...</nav>
How to catch it
  • Manual Press Tab once on page load. Skip link must appear.
  • Accessibility Insights FastPass checks for skip link presence.
  • axe DevTools Flags missing bypass block mechanism.

Requirement 03: Landmarks

Screen reader users navigate by landmarks the same way sighted users scan layout. A page without landmarks forces a screen reader user to read every word from the top to find the main content.

Fail (HTML)
<div class="header">
<div class="nav">
<div class="content">
Pass (HTML)
<header>
<nav aria-label="Main">
<main>
<footer>
How to catch it
  • WAVE Structure tab shows all landmarks on the page.
  • axe DevTools Flags missing landmark regions.
  • Chrome DevTools Accessibility tree lists all landmark roles.

Requirement 04: Keyboard: fully operable, no traps

Disconnect your mouse. Every action available to mouse users must be achievable by keyboard alone. If you Tab into a component and cannot Tab out, that is a Critical defect called a keyboard trap.

Fail
Modal opens.
Tab loops inside forever.
Escape key does nothing.
No way out without mouse.
Pass
Modal opens: focus moves in.
Tab cycles within modal only.
Escape closes and returns
focus to the trigger element.
How to catch it
  • Manual Disconnect mouse. Tab through every interactive element.
  • Accessibility Insights Tab stops visualiser shows focus path.
  • axe DevTools Flags some keyboard accessibility issues automatically.

Requirement 05: Focus indicator

Press Tab through the page. Every focusable element must show a visible outline or highlight when focused. If focus disappears, that is a defect.

Fail (CSS)
a:focus { outline: none; }
button:focus { outline: 0; }
Pass (CSS)
a:focus-visible {
outline: 2px solid #60a5fa;
outline-offset: 3px;
}
How to catch it
  • Manual Press Tab: watch for disappearing focus.
  • Accessibility Insights Tab stops visualiser shows every focus stop.
  • axe DevTools Flags outline:none on focusable elements.

Requirement 06: Alt text

Images that convey information need descriptive alt text. Decorative images need an empty alt attribute. A missing alt attribute means the screen reader reads the filename aloud.

Fail (HTML)
<img src="cta.jpg">
<img src="hero.jpg" alt="image">
Pass (HTML)
<img src="cta.jpg"
alt="Download the 2024 report">
<img src="divider.png" alt="">
How to catch it
  • WAVE Red icon on images with missing or empty alt.
  • axe DevTools Critical: "Image alternative text" rule.
  • Chrome DevTools Accessibility tree shows alt value (or none).

Requirement 07: Link text

Screen reader users navigate by links. When a list of links contains "Click here" five times, there is no way to distinguish them. Every link must describe its destination.

Fail (HTML)
<a href="/report">Click here</a>
<a href="/news">Read more</a>
Pass (HTML)
<a href="/report">
Download 2024 annual report</a>
<a href="/news">Read accessibility news</a>
How to catch it
  • WAVE Alerts tab flags "Suspicious link text."
  • axe DevTools "Links must have discernible text" rule.
  • Manual NVDA Insert+F7 opens links list: scan for duplicates.

Requirement 08: Form labels

Placeholder text disappears when you type. If the only label is the placeholder, the user loses all context mid-form. Every input needs a visible, persistent label above or beside it.

Fail (HTML)
<input type="text"
placeholder="Enter email">
Pass (HTML)
<label for="email">Email</label>
<input id="email" type="email"
placeholder="you@example.com">
How to catch it
  • axe DevTools "Form elements must have labels": Critical rule.
  • WAVE Red icon on unlabelled inputs.
  • Manual Tab to input. Listen for what NVDA announces.

Requirement 09: Dynamic messages

When content updates dynamically: form submissions, error messages, loading states, AJAX results: screen readers are not automatically notified. Without ARIA live regions, the update is silent for screen reader users.

Fail (HTML)
<div id="msg">
You're subscribed!
</div>
<!-- Silent to screen readers -->
Pass (HTML)
<div role="status"
aria-live="polite">
You're subscribed!
</div>
How to catch it
  • Manual NVDA open: trigger the update: listen for announcement.
  • Chrome DevTools Accessibility tree: check for aria-live on message containers.
  • axe DevTools Some live region issues flagged automatically.

Requirement 10: Media: captions, transcripts, no autoplay

Video must have synchronised captions: not auto-generated ones, which are frequently inaccurate. Audio-only content needs a full transcript. Any media that starts playing automatically must have a visible pause or stop control.

Fail
Video autoplays on load.
Captions are auto-generated.
No transcript provided.
No pause control visible.
Pass
Video paused on load.
Human-reviewed captions.
Full transcript below video.
Visible pause/stop control.
How to catch it
  • Manual Load page: check for autoplay. Play video: check CC quality.
  • WAVE Alerts for missing captions on embedded media.
  • axe DevTools Flags autoplay and missing media alternatives.

Requirement 11: Page language

The lang attribute on the <html> element tells the screen reader which language engine to use. Without it, pronunciation is wrong for every user relying on speech output.

Fail (HTML)
<html>
<!-- No lang attribute -->
Pass (HTML)
<html lang="en">
<!-- Correct engine selected -->
How to catch it
  • axe DevTools "HTML element must have a lang attribute": Critical.
  • WAVE Alerts section flags missing page language.
  • Chrome DevTools Inspect <html> element, check lang attribute in DOM.

Requirement 12: Embeds: iframe titles required

Every iframe on a page must have a meaningful title attribute. Without it, a screen reader user hears "frame" with no indication of what is inside: a YouTube video, a map, a form, or a payment widget.

Fail (HTML)
<iframe src="https://youtube.com/...">
</iframe>
<!-- No title. SR says "frame." -->
Pass (HTML)
<iframe
src="https://youtube.com/..."
title="Accessibility testing demo">
</iframe>
How to catch it
  • axe DevTools "Frames must have an accessible name": Critical rule.
  • WAVE Flags iframes with missing or empty title attributes.
  • Chrome DevTools Inspect iframe element: check title attribute in DOM.

6. Beyond the 12: The Full Checklist

The 12 requirements above are the highest-frequency defects. WCAG 2.1 AA has 50 Level A and AA criteria in total. The full checklist is essential for:

  • Formal accessibility audits
  • VPAT (Voluntary Product Accessibility Template) completion
  • Legal compliance sign-off
  • Procurement accessibility assessments

The official source is the WCAG 2.1 specification at w3.org. For a structured quick reference, the How to Meet WCAG quick reference lets you filter by principle, level, and technique. Blog 35 in this series covers the full sprint-ready checklist and the formal audit checklist side by side: when to use which, and how to structure your reporting.

The starting point

Start with the 12. Get them right on every sprint. Then expand to the full set for formal sign-off. Do not try to learn all 78 criteria at once. The 12 above account for the majority of real-world defects found in production. Master these first.
