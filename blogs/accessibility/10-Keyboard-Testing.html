1. Why Keyboard Testing Matters

Keyboard accessibility is not a nice-to-have. It is the foundation that every other input method builds on. Screen readers use the keyboard event model. Switch access devices use it. Voice control uses it. If something is not keyboard accessible, it is inaccessible to every user who cannot operate a mouse: including users with motor impairments, users on mobile keyboards, and users who simply prefer not to use a mouse.

It is also the most direct test available. There is no interpretation involved. Either you can reach and operate every interactive element using only the keyboard, or you cannot. If you cannot, that is a defect. You do not need a screen reader to find it. You do not need an automated tool. You need Tab, Enter, Space, Escape, and five minutes.

Everything a mouse user can do, a keyboard user must be able to do too. That is the complete rule. The rest of this blog is how to verify it.

2. How to Start: The Only Setup You Need

Unplug your mouse, or on a laptop, commit to not touching the trackpad. Open the page you want to test. Press Tab.

That is the full setup. No extensions, no configuration, no special tools.

One thing to check first on macOS: by default, Safari and Firefox on Mac only tab to text fields and lists, not all interactive elements. To fix this, go to System Settings, Keyboard, and turn on "Use keyboard navigation to move focus between controls." In Safari, also enable it under Safari Preferences, Advanced.

3. Essential Keyboard Shortcuts

These are the keys used in keyboard testing. Know them before you start.

Essential keyboard shortcuts for accessibility testing
Action Key What to check
Move forward Tab Focus moves to the next interactive element. Focus indicator visible.
Move backward Shift + Tab Focus moves to the previous interactive element in reverse order.
Activate link or button Enter The action fires. Navigation happens. Form submits.
Activate button, toggle checkbox, expand dropdown Space Buttons respond to Space as well as Enter. Checkboxes toggle.
Navigate within a component ↑ ↓ ← → Radio buttons, dropdowns, tabs, sliders, menus. All use arrow keys internally.
Close modal, collapse menu, cancel Escape Modal closes and focus returns to the trigger. Menu collapses.
Jump to top of page Home Focus or scroll position moves to the start of the page or component.
Jump to bottom of page End Focus or scroll position moves to the end.

4. Element Interaction Table

Every interactive element has specific expected keyboard behaviour. Deviations are defects. This is the complete reference.

Expected keyboard behaviour for each interactive element type
Element Keys What to verify
Link Enter to activate Navigates to destination. Announces destination text, not "click here."
Button Enter or Space Both keys activate. Announces name and role. role="button" on a div must also respond to both.
Checkbox Space to toggle Announces checked/unchecked state on toggle.
Radio button group Space to select, ↑↓ to navigate group, Tab to leave Only one selectable per group. Group label announced on entry.
Select / Dropdown Space to expand, ↑↓ to navigate, Enter or Escape to select Options announced as navigated. Selection confirmed on collapse.
Text input Tab to reach, type to enter Label announced on focus. Placeholder is not a substitute for a label.
Dialog / Modal Escape to close Focus moves into modal on open. Stays trapped inside while open. Returns to trigger on close.
Accordion Enter or Space to toggle Announces expanded/collapsed state. Panel content reachable after expanding.
Tab panel Tab to enter/exit group, ←→ to switch tabs Active tab announced as selected. Panel content updates and is reachable.
Carousel Tab to controls, ←→ between slides Pause/stop control present if auto-advancing. Slide change announced.
Slider ↑↓ or ←→ to adjust, Home/End for min/max Current value announced on change. Range and step size clear.
Date picker Tab to reach, arrow keys to traverse, Enter to select Selected date announced. Fully operable without mouse.
Menu bar ↑↓ within menu, ←→ to expand/collapse submenu, Enter to select Submenus announced on expand. Escape collapses and returns focus one level up.

5. What a Keyboard Trap Looks Like

A keyboard trap is when focus enters a component and cannot leave using standard keyboard keys. The user is stuck. They cannot Tab out, cannot Escape, cannot Shift+Tab back. Their only option is to reload the page.

WCAG 2.1.2 requires that focus can always be moved away from a component using standard keys. The only exception is a modal dialog, which must trap focus intentionally while open, but must release it when closed with Escape.

Common keyboard trap locations:

  • Modal dialogs with no working Escape key
  • Custom dropdown menus that do not release focus on Escape
  • Date pickers that open a calendar widget with no keyboard exit
  • Embedded maps or media players that absorb Tab focus
  • Chat widgets fixed to the bottom of the screen

How to Test: Tiers and Platform Coverage

Tier 1: Pipeline automation

Keyboard accessibility cannot be fully automated. axe-core in CI catches: keyboard traps (WCAG 2.1.2), scrollable regions not keyboard accessible, and missing focusable elements on interactive components. It cannot test focus order logic, the visibility of focus indicators, or whether all actions are achievable by keyboard. The pipeline is the floor: keyboard testing is always required on top.

Tier 2: Semi-automated tools

Accessibility Insights Tab Stops mode visualises the keyboard focus path without needing to remember each Tab stop. Enable it before starting keyboard testing: the arrows make focus order failures immediately visible. Use it alongside the 6-step sequence in this blog.

Tier 3: Manual: keyboard testing on all platforms

  • Windows: Chrome and Firefox. Tab, Shift+Tab, Enter, Space, Escape, arrow keys. Every interactive element.
  • Mac: Safari (enable full keyboard access in System Settings first), Chrome, Firefox.
  • iOS: External keyboard connected to iPhone. Tab navigation in Safari. Verify all interactive elements are reachable.
  • Android: External keyboard or TalkBack with keyboard. Verify Tab order in Chrome.

6. The 6-Step Test Sequence

Run this sequence on every page and every interactive component. It is the minimum keyboard test for a release sign-off.

01
Tab reach verification
Tab through the entire page. Every button, link, input, dropdown, and custom control must receive focus. If a control is reachable by mouse but not by Tab, that is a defect.
02
Tab order validation
The tab sequence must follow the visual reading order: left to right, top to bottom. No illogical jumps: footer before header, middle of page before navigation. Form fields must follow logical completion order.
03
Focus visibility check
A visible focus indicator must appear on every focusable element. Minimum 3:1 contrast between the indicator and the background. The indicator must not be obscured by sticky headers, overlapping elements, or z-index stacking.
04
Activation testing
Buttons must activate with both Enter and Space. Links activate with Enter only. Checkboxes toggle with Space. Radio buttons select with Space or arrow keys. If any of these do not work, that is a defect.
05
Component interaction testing
Test every interactive component against the element interaction table in Section 4. Modals must trap focus and release on Escape. Accordions must announce state. Dropdowns must be navigable by arrow keys. Deviations are defects.
06
Keyboard trap verification
Can you Tab into every component? Can you Tab out? Press Escape anywhere you feel stuck. If focus is trapped with no exit, that is a Critical defect. Log it immediately with the component name, the WCAG criterion (2.1.2), and reproduction steps.

7. Zero-Install Chrome DevTools Trick

No extension needed. This is built into every Chromium browser.

Press Ctrl+Shift+P (Windows) or Cmd+Shift+P (Mac) in Chrome DevTools to open the command palette. Search for "accessibility" and select "Enable Full Page Accessibility Tree."

The DOM tree is replaced with a full ARIA accessibility tree: exactly what a screen reader sees for every element. Role, name, state, and properties all visible without opening a screen reader. Useful for quickly checking whether a component's ARIA is wired up correctly before committing to a full screen reader session.

8. Where to Practice

The most effective way to build keyboard testing muscle memory is to practice on intentionally broken components, not production sites. The Actum Digital inaccessible components playground has broken accordions, modals, carousels, and more: specifically designed for training.

For everyday practice: pick one page of a site you use regularly and navigate it entirely by keyboard. You will find a defect within ten minutes on almost any site. That is not pessimism: it is the current state of the web.

The rule

Unplug the mouse. Press Tab. If you get stuck, log a defect. Keyboard testing is the fastest accessibility test you can run: and it requires nothing except the keyboard you are already using.
