11 Focus Indicators: Visible, Logical, Never Suppressed

The one CSS line that breaks keyboard accessibility for millions, and what to do instead.

1. What a Focus Indicator Is

A focus indicator is the visible mark that shows which element currently has keyboard focus. It is the keyboard user's cursor: the only way to know where you are on a page when you are not using a mouse.

Without a visible focus indicator, keyboard users are navigating blind. They press Tab and have no way to tell which element is active. They cannot see which link they are about to activate, which button they are about to press, or which field they are about to type into. The page is technically keyboard-accessible, but practically unusable.

A focus indicator is not a nice visual detail. It is navigation infrastructure. Removing it is the equivalent of removing the cursor from a text editor.

2. The outline:none Problem

The single most common focus indicator failure is this CSS line:

Fails WCAG 2.4.7
/* in a global stylesheet */ *:focus { outline: none; } /* or per component */ button:focus { outline: 0; }
Passes WCAG 2.4.7 and 2.4.11
/* remove browser default, replace with custom */ *:focus { outline: none; } *:focus-visible { outline: 3px solid #005fcc; outline-offset: 3px; }

The reason this appears so often in production: browser default focus rings are visually inconsistent, sometimes ugly, and frequently clash with a brand's design. Designers ask for them removed. Developers comply. Nobody replaces them. The result is a page that looks cleaner and is inaccessible to every keyboard user.

The fix is :focus-visible, a CSS pseudo-class that shows the focus ring only when the browser determines keyboard navigation is in use. Mouse clicks do not trigger it. Keyboard presses do. This solves the aesthetic concern without removing the indicator for keyboard users.

3. WCAG Requirements: 2.4.7 and 2.4.11

WCAG focus indicator requirements
Criterion Level Requirement What fails
2.4.7 Focus Visible AA Any keyboard-operable UI must have a visible focus indicator. outline: none with no replacement. Invisible indicator.
2.4.11 Focus Appearance AA (WCAG 2.2) Focus indicator must have minimum area, minimum 3:1 contrast against adjacent colours, and must not be entirely hidden by other content. Low-contrast ring. Ring hidden behind sticky header. Indicator too small to see.
1.4.11 Non-text Contrast AA UI components (including focus indicators) must have 3:1 contrast against adjacent background. White focus ring on light background. Brand-colour ring with insufficient contrast.
2.4.11 was introduced in WCAG 2.2. Many teams are still testing only against 2.1. If your target is WCAG 2.1 AA, 2.4.7 is the primary criterion. If your target is WCAG 2.2 AA, both 2.4.7 and 2.4.11 apply.

4. What Good Looks Like

A good focus indicator is three things: visible, high contrast, and not suppressed by overlapping content. Here is the CSS pattern that covers all three:

Recommended pattern
/* suppress browser default only when replacing it */ *:focus { outline: none; } /* show only on keyboard nav */ *:focus-visible { outline: 3px solid #005fcc; outline-offset: 3px; border-radius: 2px; }
Component-level override
/* custom per component when default is insufficient */ .card:focus-visible { outline: 3px solid #005fcc; outline-offset: 4px; box-shadow: 0 0 0 6px rgba(0,95,204,0.15); } /* dark background variant */ .dark .card:focus-visible { outline-color: #60a5fa; }

The key decisions: the outline colour must achieve 3:1 contrast against the adjacent background. The outline-offset separates the ring from the element edge, making it visible even on elements with matching background colours. The border-radius softens the ring to match rounded components.

5. Focus Indicators That Pass But Still Fail

These are the cases where a focus indicator technically exists but is still a practical failure. All are testable during a keyboard walkthrough.

🎯
Practice these yourself
All five failure patterns below, plus a passing example, are available as an interactive keyboard-only test in the Focus Indicator Playground. Unplug your mouse and find each one.
Focus indicator failure patterns that are not caught by automated tools
Pattern What happens WCAG
Hidden by sticky header Focus moves to an element that scrolls beneath a fixed header. The ring is there but visually obscured. The user cannot see it. 2.4.11
Hidden by z-index stacking A modal overlay, dropdown, or cookie banner sits above the focused element, covering the ring. 2.4.11
Low-contrast ring on matching background A grey ring on a grey card. A white ring on a light page. Passes 2.4.7 (ring exists) but fails 1.4.11 (ring is invisible). 1.4.11
Ring only visible on one state Focus ring designed for the default state but disappears when the component is in an active, selected, or error state. 2.4.7
Programmatic focus without visual indicator JavaScript moves focus to an element using .focus() but the element has no visible style for the focused state. 2.4.7

How to Test: Tiers and Platform Coverage

Tier 1: Pipeline automation

axe-core does not check focus indicator visibility: CSS :focus styles cannot be evaluated programmatically. The pipeline cannot catch this. The only automated signal is if an element has outline: none without a replacement: some linting rules flag this but it is not reliable. Focus indicator testing is Tier 3.

Tier 2: Semi-automated tools

Accessibility Insights Tab Stops draws the focus path. It does not evaluate whether the indicator is visible enough: but it shows you where focus goes so you can check each stop visually. Combine Tab Stops with manual visual inspection of each focused element.

Tier 3: Manual: platform coverage

  • Windows Chrome/Firefox: Tab through every interactive element. Every focus state must be visible. Check against the 3:1 contrast minimum for focus indicators (WCAG 1.4.11).
  • Mac Safari: Enable full keyboard access. Same walkthrough. Safari has different default focus styles to Chrome.
  • iOS Safari: External keyboard connected to iPhone. Tab through interactive elements. Verify focus indicator visible on each.
  • Android Chrome: External keyboard. Same check.

6. How to Test Focus Indicators

🎯
Practice these yourself
All failure patterns are available as interactive demos in the Focus Indicators Playground. For mobile testing steps, see the Mobile Testing Guide.

What automation catches

axe-core (in Playwright, Cypress, or axe DevTools) and Pa11y will flag these automatically:

  • Elements with outline: none and no replacement focus style (WCAG 2.4.7)
  • Interactive elements with no accessible focus style in the stylesheet
  • Elements with :focus styles that fail the 3:1 contrast requirement against the adjacent background (WCAG 1.4.11)

What automation misses: manual check required

  • Focus ring hidden by sticky header or overlay: automation checks the stylesheet, not whether the ring is visually obscured at runtime. Only a manual scroll-while-tabbing test reveals this.
  • Ring disappears in a specific component state: error state, selected state, active state. Automation tests the default state. You must trigger each state and Tab to the element.
  • Programmatic focus with no ring: automation does not trigger JavaScript interactions. Open modals, submit forms, navigate SPA routes, and verify focus lands visibly each time.
  • Ring present but too small to see: technically passes WCAG 2.4.7 (ring exists) but fails in practice. Only a human can judge practical visibility.

Desktop browsers

Tab through the page. For every focusable element ask: is the ring visible, does it have 3:1 contrast, is it obscured. Test in at least Chrome and Safari: default focus styles differ significantly between them.

Windows: NVDA

With NVDA running, Tab through the page. NVDA announces each element as focus moves, confirming focus is moving even when the ring is invisible. If NVDA announces an element but no ring is visible, that is a failure. Use Insert+F7 to open the elements list and navigate directly to interactive elements.

Mac: VoiceOver

Enable VoiceOver with Cmd+F5. Use Safari. VoiceOver draws a black focus rectangle around the currently focused element: this is separate from the CSS focus ring. Use VO+→ to move forward. Check both that VoiceOver highlights the element AND that the CSS ring is visible. A missing CSS ring next to VoiceOver's black rect is still a WCAG failure.

iOS: VoiceOver

Enable VoiceOver: Settings, Accessibility, VoiceOver, Toggle ON. Single-finger swipe right to navigate. VoiceOver draws a black rect around the focused element on iOS: useful for confirming programmatic focus landed correctly on a modal or dynamic content. Check that the rect appears and that focus does not land on an element with no visual indicator when VoiceOver is off.

Android: TalkBack

Enable TalkBack: Settings, Accessibility, TalkBack, Toggle ON. Single-finger swipe right to navigate. TalkBack draws a green focus rect around the focused element. The same programmatic focus failures visible on desktop are visible here: open a modal, confirm the green rect appears on the correct heading or first interactive element inside it.

Mobile testing must use a physical device. Xcode Simulator and Android Emulator do not reliably render focus rect behaviour for VoiceOver and TalkBack.

Testing programmatic focus across all platforms

Trigger every dynamic state: open modals, submit forms with errors, navigate SPA routes, fire toast notifications. On each platform, confirm that focus moves to the correct element AND that a visible indicator is present. The failure looks different per platform but the root cause is always the same: .focus() called on an element with no :focus style.

Testing across browsers

Browser default focus styles differ. Chrome, Firefox, and Safari each render their defaults differently. A custom focus style that passes in Chrome may be invisible in Safari. Test in at least two browsers before signing off.

Real focus indicator defect examples with WCAG reference and severity
Defect WCAG Severity How to reproduce
Global outline:none with no replacement 2.4.7 Critical Tab through the page. No focus ring visible on any element.
Focus ring hidden by sticky nav 2.4.11 Major Tab to elements in the upper section of the page. Focus moves under the sticky header and is obscured.

The rule

Tab through the page. If you cannot see where focus is at any point, that is a defect. It is that simple. Blog 10 has the full keyboard testing sequence if you need the complete walkthrough.
