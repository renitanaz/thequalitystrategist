1. Why the Design Phase Is the Cheapest Place to Fix Anything

A contrast failure caught in Figma costs a designer five minutes and a colour token update. The same failure caught in QA costs a design rework, a development update, a redeploy, and a retest. The same failure in production carries legal risk on top.

The cost multiplier is 3–5× at design stage vs 20–30× at QA. Blog 02 covers the full phase-by-phase multiplier table if you need the numbers to make the case to your team.

The design phase is not just cheaper: it is the only phase where some issues can be fixed without touching code. Heading hierarchy defined in a Figma template costs nothing to change. The same hierarchy missing from a live page requires a content audit, a CMS update, and a retest across every page that inherited the wrong structure.

The best accessibility defect is the one that never becomes a defect. Design is where that happens.

2. What QA can Be Doing at the Design Stage

Most QA engineers wait for a build. That is understandable: it is how the role has traditionally been defined. It is also how accessibility debt accumulates silently through an entire design phase before anyone looks at it.

Practically, QA can:

  • Raise missing tab order annotations, unspecified focus states, or placeholder error copy as defects: because they are defects, just at Phase 1 instead of Phase 4
  • Confirming the Phase 1 exit criteria are met before the project moves to development

This is QA thinking systemically. It is also the most direct way to reduce the volume of defects that reach testing later.

3. Colour Contrast: Validate the Brand Before the Components

Contrast is the most common accessibility failure in production. It is also one of the most preventable, because it is a design decision, not a development one.

The rules are precise:

  • 4.5:1 minimum for normal body text (under 18pt regular or 14pt bold): WCAG 1.4.3
  • 3:1 minimum for large text (18pt+ regular or 14pt+ bold): WCAG 1.4.3
  • 3:1 minimum for UI component boundaries and focus indicators: WCAG 1.4.11

The critical thing most teams miss: validate the colour palette before you build any components. Every button, card, label, and input inherits from the brand tokens. If the primary text colour on the primary background fails contrast, every component built on that palette fails too. One token update in Figma fixes everything. One token update after development fixes nothing without a full component rebuild.

Fail: WCAG 1.4.3
Body text on brand purple
Ratio: 2.0:1. Required 4.5:1. On-trend tonal palette. Fails hard.
Pass: WCAG 1.4.3
Body text on brand purple
Ratio: 4.9:1, passes AA. Same brand purple. White text instead of tonal lavender.
The failing palette might look good. Designers might prefer it. That is exactly why contrast needs to be checked with numbers, not eyes.

4. Focus Indicators: Designed, Not Defaulted

Browser default focus styles are inconsistent across browsers and often invisible against design backgrounds. They cannot be relied on. The designer owns specifying an explicit focus state for every interactive component before handoff: this is not a developer decision to make on the fly, and it is not QA's job to catch its absence after the fact.

What the focus state must have:

  • Visible outline on every interactive element when focused: WCAG 2.4.7
  • 3:1 contrast minimum between the focus indicator and the adjacent background: WCAG 1.4.11
  • Not obscured by sticky headers, overlapping components, or z-index stacking
  • Enhanced indicator where possible: a 2px+ outline with offset is the standard good practice

The most common design failure is not missing focus states. It is designs that specify outline: none in the design notes or CSS comments to "clean up" the default browser ring, with no replacement specified. What reaches the developer is a suppressed focus indicator and nothing to replace it with.

Specify the focus ring explicitly. Colour, width, offset. In Figma. Before handoff.

5. Tab Order Annotation: The Handoff Nobody Does

Tab order is the sequence in which keyboard users move through a page. It should follow the visual reading order and must be logical and predictable.

The problem: tab order is invisible in Figma unless someone annotates it. Without annotation, developers implement whatever feels natural to them: which is usually the DOM order of elements as they were stacked in the design, which is often not the visual reading order, which is frequently wrong.

What to annotate:

  • Every interactive element in reading order, numbered sequentially
  • Modal open and close flow: where focus goes on open, where it returns on close
  • Form submission: where focus moves after success or error
  • Dynamic content that appears after an action: where focus lands

6. Heading Hierarchy: Defined in Templates, Not Left to Content

Heading structure is how screen reader users navigate a page. Without a logical hierarchy, they are navigating blind: pressing H to jump between headings and landing on content out of order or out of context.

The rules are straightforward. One H1 per page, no skipped levels, heading levels reflecting content hierarchy. Defining this structure in Figma is the designer's responsibility, not a gap for QA to find later. The problem is not that designers do not know the rules: it is that heading structure is frequently not annotated in the design file at all. It appears as visual styling (big bold text) with no semantic label attached, and that label is the designer's to add.

What must be in the design file before handoff:

  • Heading level annotated on every heading element in page templates
  • H1 identified on each page or view type
  • Heading levels consistent across all instances of a component (a card title that is H2 on one page must be H2 everywhere)

The consequences of skipping this are significant. Blog 04 covers the CMS example in detail: heading restrictions not set at modelling stage led to hundreds of pages requiring individual correction post-migration. The same applies to coded templates: a missing heading annotation means the developer picks a level, and it is rarely consistent.

7. Error Message Copy: Written at Design, Not Invented by Devs

Error messages are an accessibility requirement, not a UX nicety. WCAG 3.3.1 requires that input errors are identified and described in text. WCAG 3.3.3 requires that suggestions for correction are provided where possible. Writing this copy belongs to design or UX writing, not development and not QA.

What this means in practice: every form field that can produce an error must have its error copy written by the design or content team at design stage. Not "error message here." Not "validation text TBD." The actual copy, owned and delivered before handoff.

What good error copy looks like:

Error copy comparison: vague vs descriptive

EmailInvalid inputEnter a valid email address, for example: you@domain.com

If error copy is not in the design file, the gap belongs to the design phase, not to the developer who fills it in. Developers are not copywriters, and they should not be expected to act as one. The result of skipping this step is "Invalid input" on every field, which tells a screen reader user precisely nothing about what to fix.

8. Touch Targets: 24x24px Minimum, Designed In

WCAG 2.5.8 requires a minimum touch target size of 24x24 CSS pixels for all interactive elements. This applies to buttons, links, icons, close buttons, checkboxes, radio buttons, and anything else a user taps or clicks.

The most frequent failures are icon-only buttons: close icons, hamburger menus, social share buttons: designed at 16x16px or smaller because that is the icon size, not the target size. The target must be at least 24x24px even if the visible icon is smaller.

This must be specified in Figma. Post-development, adding padding to hit areas is straightforward, but only if the developer knows it is required. Without a design annotation specifying minimum target size, it will not happen.

Testing in the Design Phase

Tier 1: Pipeline automation

Automation does not exist at the design phase: the pipeline enters at development.

Tier 2: Semi-automated tools

Colour contrast in design files can be checked with the Stark or A11y Annotation Kit Figma plugin before any code is written. Export a clickable prototype to HTML and run axe DevTools against it: structural violations appear even at the prototype stage.

Tier 3: Manual

Platform coverage: Test on Windows (Chrome + Firefox), Mac (Safari + Chrome), iOS (Safari on physical iPhone), and Android (Chrome on physical device). Platform differences in keyboard handling and screen reader behaviour mean a bug on one platform does not guarantee the same behaviour on another.

Design review is manual. Walk through the checklist in this blog against every design file before sign-off. Check: colour contrast ratios, touch target sizes (44x44px minimum), focus order in the prototype, heading structure, form label placement, and error state designs. On mobile: verify designs account for iOS Dynamic Type and Android font scaling up to 200%.

Design phase checklist: what to catch and with what tool

Stark and Zimmer reliably catch contrast and touch-target sizing because those are mathematical checks. Everything else on this list: structure, content quality, missing states, annotations: depends on human judgment or, at best, a plugin that helps you document the check rather than automatically detect the failure.

9. The Phase 1 Exit Checklist

Nothing moves to development until every item below is confirmed. The design lead owns sign-off on this checklist, since this is the design phase and the design phase has a named owner. QA verifies the checklist is genuinely complete, not the other way around: holding the gate is design's job, checking that the gate was actually held is QA's.

01
Accessible personas and AT user journeys documented
Inclusive personas include screen reader users, keyboard-only users, and users with cognitive or motor impairments. AT user journeys mapped explicitly for key flows.
1.3.1
02
Colour contrast validated across all text and UI components
Brand palette validated before components are built. 4.5:1 for body text, 3:1 for large text and UI boundaries. Stark or Zimmer run and all failures resolved.
1.4.3 · 1.4.11
03
Keyboard navigation and tab order annotated on all interactive flows
Tab order numbered in Figma for every interactive flow including modals, forms, and dynamic content states. No hover-only interactions.
2.1.1 · 2.4.3
04
Focus indicators designed and specified for every interactive component
Explicit focus state defined for every interactive element. Not browser default. Minimum 3:1 contrast. Not obscured by overlapping elements.
2.4.7 · 2.4.11
05
Heading hierarchy defined in all page templates
H1 identified per view. Heading levels annotated on all heading elements. No skipped levels. Consistent across all instances of shared components.
1.3.1 · 2.4.6
06
Error message copy written for every form field error state
Descriptive, actionable error copy defined for every validation state. No placeholder text. Copy specifies what is wrong and how to fix it.
3.3.1 · 3.3.3
07
Touch and pointer targets sized at minimum 24x24 CSS px
All interactive elements including icon-only buttons annotated with minimum target size. Hit area specified separately from icon size where needed.
2.5.8
08
No colour-only communication in any component
Every use of colour to convey meaning (error states, status indicators, links) is paired with a text label, icon, or other visual cue. Colour blindness simulation passed.
1.4.1
09
Design accessibility approval signed off before development begins
Design lead has confirmed all checklist items and owns the sign-off. QA has independently verified the checklist is complete. No Critical or Major accessibility gaps open. Development does not start until this gate is held.
All
The bottom line

Everything in this checklist is faster and cheaper to do in Figma than in a sprint. The question is not whether your team has time to do this. It is whether they have time not to. Blog 02 has the numbers if you need them.
