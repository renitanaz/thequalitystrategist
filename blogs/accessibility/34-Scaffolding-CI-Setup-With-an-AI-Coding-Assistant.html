1. Why This Setup Is Scaffoldable

Every CI setup in this series follows the same three-step shape: install the tool, add a config file scoped to WCAG 2.1 AA, and write a GitHub Actions workflow that fails the build and uploads a report on every push and pull request to main. That shape is mechanical, well-documented boilerplate: exactly what an AI coding assistant (Claude Code, Cursor, GitHub Copilot Workspace, and similar) can scaffold correctly from one specific prompt, instead of you assembling it section by section from Blog 32, Blog 33, Blog 29, and Blog 30 by hand.

The four prompts below are scoped to each tool's own conventions from its own blog. Fill in the <placeholders> for your project.

2. axe-core with Playwright or Cypress

Set up accessibility testing in CI for this project. My Playwright tests live in <your test folder, e.g. tests/ or e2e/> and run against <your app's local or staging URL>.

1. Install @axe-core/playwright as a dev dependency.
2. Add an axe-core accessibility check to <a new test file, or each existing test file>, scoped to WCAG 2.1 A and AA rules only (withTags(['wcag2a', 'wcag2aa'])), run after the page has fully loaded.
3. Fail the test only on critical and serious impact violations. Log moderate and minor violations to a JSON file without failing the build.
4. Create a GitHub Actions workflow at .github/workflows/accessibility.yml that runs this suite on every push and pull request to main, and uploads the test report as a build artifact even when the tests fail.

Show me the code before running anything, and explain what each part of the generated workflow file does.

Encodes the choices Blog 32 makes: WCAG 2.1 AA scope, a critical/serious fail threshold with everything else logged not blocked, and an artifact upload that survives a failed run.

3. Pa11y

Which prompt to use depends on whether axe-core is already running elsewhere in your pipeline. See Blog 33 for the full reasoning: the axe runner duplicates coverage you already have, the default runner adds a genuinely different engine.

3a. Pa11y as your only CI tool: axe runner

Set up accessibility testing in CI for this project using Pa11y. My site is reachable at <your staging or deployed URL>, and it has more than one page to check: <list your page paths>.

1. Install pa11y-ci as a dev dependency (not global).
2. Create a pa11y-ci.json listing each URL, with defaults standard: "WCAG2AA", runners: ["axe"], and ignore: ["notice", "warning"]: only errors should fail the build.
3. Create a GitHub Actions workflow at .github/workflows/accessibility.yml that runs on every push and pull request to main, installs Node and pa11y-ci, runs pa11y-ci against the config file, and uploads the JSON report as a build artifact even when the run fails.

Show me the code before running anything, and explain what each part of the generated workflow file does.

Encodes the choices Blog 33 makes: WCAG2AA standard, the axe-core runner instead of Pa11y's HTML_CodeSniffer default, notices and warnings ignored so only errors gate the build, and pa11y-ci for scanning more than one URL in a single run. Use this when Pa11y is the only automated accessibility tool in your pipeline.

3b. Pa11y alongside an existing axe-core setup: default runner

Set up accessibility testing in CI for this project using Pa11y. My site is reachable at <your staging or deployed URL>, and it has more than one page to check: <list your page paths>. I already run axe-core separately in this pipeline, so Pa11y should run its own default rule engine, not axe-core again.

1. Install pa11y-ci as a dev dependency (not global).
2. Create a pa11y-ci.json listing each URL, with defaults standard: "WCAG2AA" and ignore: ["notice", "warning"]: only errors should fail the build. Leave the runners option unset so Pa11y uses its default HTML_CodeSniffer engine, not axe-core.
3. Create a GitHub Actions workflow at .github/workflows/accessibility.yml that runs on every push and pull request to main, installs Node and pa11y-ci, runs pa11y-ci against the config file, and uploads the JSON report as a build artifact even when the run fails.

Show me the code before running anything, and explain what each part of the generated workflow file does.

Same WCAG2AA standard and error-only gate as 3a, but the runners key is deliberately left out so Pa11y stays on HTML_CodeSniffer: a second, genuinely different rule engine running alongside axe-core, the same "second opinion" case as IBM Equal Access. Use this when axe-core already runs elsewhere in your pipeline.

4. Lighthouse CI

Set up accessibility testing in CI for this project using Lighthouse CI. My site is reachable at <your staging or deployed URL>.

1. Install @lhci/cli as a dev dependency.
2. Create a lighthouserc.json that asserts categories:accessibility with a minimum score of 0.9, and fails the build below that threshold.
3. Create a GitHub Actions workflow at .github/workflows/accessibility.yml that runs on every push and pull request to main, installs Node and lhci, runs the Lighthouse CI assertion against the target URL, and uploads the Lighthouse report as a build artifact even when the run fails.

Show me the code before running anything, and explain what each part of the generated workflow file does.

Encodes the choices Blog 29 makes: a 0.9 score threshold as a starting point, not the eventual 1.0 goal, since a score threshold alone is a floor, not proof of conformance.

5. IBM Equal Access

Set up accessibility testing in CI for this project using IBM Equal Access. My site is reachable at <your staging or deployed URL>, and it has more than one page to check: <list your page paths>.

1. Install accessibility-checker as a dev dependency (not global).
2. Create an .achecker.yml scoped to the WCAG_2_1 policy, with failLevels set to violation and potentialviolation only.
3. Create a text file listing each URL to scan, one per line.
4. Create a GitHub Actions workflow at .github/workflows/accessibility.yml that runs on every push and pull request to main, installs Node and accessibility-checker, runs achecker against the URL list, and uploads the results folder as a build artifact even when the run fails.

Show me the code before running anything, and explain what each part of the generated workflow file does.

Encodes the choices Blog 30 makes: the achecker binary rather than the package name, a text file of URLs rather than a single URL argument, and running it alongside axe-core rather than instead of it, since the two engines catch different violations.

Where to Start if You Are New to This

New to CI/CD or accessibility automation? Start here, not with the prompts above.

  1. Repo access: you need push access to add a file under .github/workflows/. Actions is already enabled, nothing to turn on.
  2. Pick one tool, not four: axe-core and Pa11y is the recommended pair (Section 6), or axe-core alone for the smallest first step.
  3. Read the tool's own blog first: Blog 32 for axe-core, Blog 33 for Pa11y. The prompts encode those choices, they do not explain them.
  4. Check the prerequisite: axe-core needs an existing Playwright or Cypress suite. Pa11y just needs a reachable URL, so it is the easier starting point with nothing else running yet.
  5. Run one prompt, merge it, watch it pass on a real PR before adding a second tool.

6. Running axe-core and Pa11y Together, Selectable From One Workflow

The recommended combination is axe-core plus Pa11y on the default runner: axe-core catches interaction and authenticated-state violations no scanner-only tool reaches, and Pa11y's default HTML_CodeSniffer engine adds a genuinely different rule set for almost no extra setup, with no tests to write. Add Lighthouse CI or IBM Equal Access to the same pattern below only if you need score-trend tracking or Section 508 coverage: neither adds much new detection on top of this pair, since Lighthouse runs the same axe-core engine underneath (Blog 29).

Combine the axe-core and Pa11y setups above into a single GitHub Actions workflow at .github/workflows/accessibility.yml, with these rules:

1. On every push and pull request to main, run both as independent parallel jobs. For Pa11y, use the default HTML_CodeSniffer runner, not the axe-core runner: axe-core already runs as its own job, so Pa11y should add a different rule engine, not duplicate it.
2. Also support a manual trigger (workflow_dispatch) with a dropdown input named "tool" that defaults to "all" and offers "axe-core" and "pa11y" as choices, so a manual run can target just one tool.
3. Each job should only run when the trigger is push/pull_request, or when workflow_dispatch was used and the selected tool matches that job (or "all" was selected).
4. Keep each tool's own install, config, and fail-the-build behaviour exactly as scoped in its own prompt.
5. Each job uploads its own report as a separate build artifact, even when it fails.

Show me the code before running anything, and explain how the conditional logic on each job decides whether to run.
The shape this produces — show example 
name: Accessibility Tests

on:
  push:
    branches: [main]
  pull_request:
    branches: [main]
  workflow_dispatch:
    inputs:
      tool:
        description: 'Which tool to run (defaults to all on push/PR)'
        required: false
        default: 'all'
        type: choice
        options: [all, axe-core, pa11y]

jobs:
  axe-core:
    if: github.event_name != 'workflow_dispatch' || inputs.tool == 'all' || inputs.tool == 'axe-core'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 24 }
      - run: npm ci
      - run: npx playwright install --with-deps chromium
      - run: npx playwright test
      - if: always()
        uses: actions/upload-artifact@v7
        with: { name: axe-core-report, path: playwright-report/ }

  pa11y:
    if: github.event_name != 'workflow_dispatch' || inputs.tool == 'all' || inputs.tool == 'pa11y'
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-node@v7
        with: { node-version: 24 }
      - run: npm ci
      - run: npx pa11y-ci --config pa11y-ci.json

The if condition on each job is what makes the tool selectable: on an ordinary push or pull request, github.event_name != 'workflow_dispatch' is true, so every job runs regardless of the input. On a manual run, that first clause is false, so the job only runs if inputs.tool matches its own name or equals all. The two jobs also run in parallel by default, rather than one job that runs both tools in sequence: a broken axe-core step does not stop Pa11y from still reporting its own results. Adding Lighthouse CI or IBM Equal Access later is the same pattern: a new job, a new if clause, and a new option in the tool dropdown.

7. Troubleshooting What the Assistant Gets Wrong

An assistant produces working YAML far more often than it produces the right YAML for your project. These are the failure modes worth checking for specifically, because they fail quietly rather than throwing an error.

Common problems when an AI assistant scaffolds this CI setup, and their fixes
SymptomLikely causeFix
Every build fails, including on trivial changesThe assistant failed the build on all impact levels, not just critical and seriousCheck the filter explicitly: for @axe-core/playwright that's a manual results.violations.filter(v => ['critical','serious'].includes(v.impact)) as Blog 32 does, not an includedImpacts option (that belongs to cypress-axe); for Pa11y, check the ignore list excludes moderate and minor
The job fails with a connection error, not a violationThe workflow scans a URL that is not actually running in the CI runner, such as a hardcoded localhost address with no server startedAdd a step that builds and starts the app first, or point the config at a real, already-deployed staging URL
Pa11y's Chromium fails to launch in CI, but works locallyMissing the sandbox flag GitHub Actions' containers requireAdd chromeLaunchConfig: { args: ["--no-sandbox"] } to the Pa11y config, as Blog 33 does
A failed run has no report to downloadThe artifact upload step is missing if: always(), so it gets skipped whenever the job it depends on failsAdd if: always() to the upload step: this is the run you actually need to inspect
Lighthouse CI never fails the build, even on a clearly broken pageThe assertion is set to warn instead of error, or the score is written as a percentage (90) instead of a 0 to 1 decimal (0.9)Check both: the assertion level must be error, and the threshold must be a decimal between 0 and 1
Pa11y only checks one page despite asking for severalThe prompt's page list was vague, so the assistant scaffolded a single-URL pa11y config instead of pa11y-ci with a URL arrayList the actual page paths in the prompt, not just "more than one page"
CI behaviour changes on its own weeks laterNo Node version was pinned in actions/setup-nodeAdd an explicit node-version, matching the pattern in every workflow file across this series
IBM Equal Access reports violations but the build still passesThe assistant left failLevels out of .achecker.yml, or set it to an empty listSet failLevels explicitly to violation and potentialviolation, as Blog 30 does
IBM Equal Access scans nothing, or errors immediatelyThe assistant passed a URL directly on the command line instead of a text file listing URLs, which is the only input achecker acceptsConfirm the workflow writes each URL to a file first, then runs achecker <file>

8. Reviewing the Output

Review what any of these generate against the relevant blog's own sections before trusting it. An assistant will produce working YAML, but it does not know your team's risk tolerance for what should fail a build, and a generic prompt can default to failing on every impact level, scanning only one page, or skipping the artifact upload entirely.
Before you trust what it generated
  • Confirm the fail threshold matches your tool's blog: critical/serious for axe-core and Pa11y, a 0.9 starting score for Lighthouse, failLevels: violation, potentialviolation for IBM Equal Access.
  • Confirm the artifact upload step has if: always(), so a failed run still leaves you a report.
  • Confirm the target URL is actually reachable from inside the CI runner, not just from your own machine.
  • If you combined more than one tool, confirm the jobs run in parallel and that the manual tool input actually gates each one.
