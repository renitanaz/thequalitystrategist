Network conditions

A fast office WiFi connection is the one network condition most testing never leaves. This post is about the ones your users are actually on: a train, a basement, a phone with two bars, and whether PeakAndPack's UI holds up when the network doesn't cooperate.

What's actually being simulated

Proxyman's Network Conditions tool doesn't just delay a response uniformly. It models three separate, more realistic dimensions at once: download and upload bandwidth, a packet-drop rate, and added delay, with presets for 2G, 3G, 4G, WiFi, and rougher Bad/Medium profiles. The bandwidth within a profile isn't fixed either, it randomizes within a range each time, closer to what a real cell connection actually does than a single fixed number would be.

Turning it on

Right-click a domain in the source list, choose Tools → Network Conditions, and pick a preset, or set custom values if you want to push past what the presets offer. It applies per-domain, so you can throttle just PeakAndPack's API while your own tooling stays fast, or apply it system-wide if that's closer to what you're testing.

Practical: three things a fast connection never tells you

Try it

Enable the 3G preset on peakandpackshopdemo.onrender.com, then work through PeakAndPack's checkout flow again, the same one from Post 3, and watch specifically for these:

  1. Double submission. Click "place order" and, while it's clearly still loading, click it again. Does the UI disable the button after the first click, or can a slow response tempt a real user into placing the same order twice?
  2. Loading state honesty. Is there a visible loading indicator at all during the slow request, or does the page just look frozen with no feedback that anything is happening?
  3. Partial page load order. On the product listing, do images and data appear in a sensible order, or does something render broken-looking mid-load, like a price appearing before its product name?
Why the double-submission check matters more than it sounds

On a fast connection, the window between click and response is small enough that almost nobody double-clicks fast enough to hit it. Slow the network down and that window opens wide, which is exactly why "double order" bugs disproportionately show up in the field on bad connections and almost never in testing done on office WiFi.

Throttling makes everything feel broken if you leave it on by habit. It's easy to enable a profile for one test and forget it's still active twenty minutes later, wondering why every page suddenly feels sluggish. Same discipline as breakpoints and Map Local: turn it off the moment the specific test is done.

Your deliverable

A short note on each of the three checks above: pass, fail, or "couldn't tell," since "couldn't tell" is itself useful information about whether the UI gives any feedback at all under bad network. Save it as peakandpack-network-conditions-findings.md.

Time: ~15 minutes to run the throttled checkout once and note what you saw.
