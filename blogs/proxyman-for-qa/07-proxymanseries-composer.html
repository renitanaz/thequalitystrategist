Composer

Every other post so far starts from a request the app already made. Composer is for the question that comes after: "what if I sent this slightly differently?", answered in seconds, without clicking back through the UI each time.

Three ways to send a request that isn't a breakpoint

Breakpoints, from Post 4, pause a request the app is already making. These three tools are for when there's no app action to pause, you just want to send something and see what comes back.

ToolStarts fromUse it when
RepeatA request already in the flow listYou just want to see if the exact same request gives the exact same result twice, useful for spotting flakiness.
Edit & RepeatA request already in the flow listYou want to change one thing, a query param, a header, a body value, and resend, without leaving Proxyman or re-clicking through the app.
ComposeA blank template, or a pasted curl commandYou want to send a request the app itself has never made, testing an endpoint or a parameter combination directly.

Practical: explore the search endpoint's edges

PeakAndPack's search has a known rough edge: a missing query parameter has, at various points, returned a server error instead of a clean validation response, exactly the kind of boundary a UI's own search box will never let you actually hit, since it never submits an empty query on your behalf.

Try it

Find a real GET /api/search?q=... request in the flow list from using the search box normally, right-click it, and choose Edit & Repeat. Then try each of these, sending after each change:

  1. Remove the q parameter entirely and send. Read the actual status code and body, not what you assume it should be.
  2. Set q to an empty string, q=, and send. Is that treated the same as a missing parameter, or differently?
  3. Set q to something with special characters a search box might reject client-side, like q=%25%27, and send. Does the server handle it as cleanly as the client would have?

Three variations, three real responses, all without touching the PeakAndPack UI once after the first capture.

Why Edit & Repeat beats starting fresh in Compose here

The captured request already has the right host, the right auth headers, and the right base structure. Compose is for when none of that exists yet, testing an endpoint from nothing. Edit & Repeat is for when 90% of a real request is already correct and you only want to vary one thing, which describes most exploratory API testing far better than starting from a blank template does.

When Compose is the right call instead

Reach for Compose specifically when there's no existing request close enough to start from: testing an endpoint the UI never calls at all, rebuilding a request from a bug report that only included a curl command (Compose imports curl directly), or constructing a request with a completely different method or content type than anything you've captured yet.

Your deliverable

The three search-endpoint responses from the practical above, each with the exact request sent and the exact status/body received. Save it as peakandpack-search-edge-cases.md. If any of the three don't match sane, expected behavior, that's a candidate for Post 8's bug-evidence workflow.

Time: ~10 minutes once you have the first real search request captured to start from.
