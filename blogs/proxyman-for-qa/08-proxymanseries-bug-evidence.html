Capturing evidence for bug reports

A screenshot proves the UI looked wrong. It doesn't prove why. Every practical exercise since Post 3 has produced a real request and response, this post is about turning one of those into evidence a developer can act on immediately, not evidence they have to reverse-engineer first.

Why a screenshot alone invites a "can't reproduce"

A screenshot of a broken checkout page tells a developer the UI was wrong. It doesn't tell them what request produced that state, what the server actually sent back, or whether the client mishandled a correct response or the server sent a wrong one in the first place. Without that, "can't reproduce" is the honest, likely reply, not a brush-off.

A captured request and response answers exactly the question a screenshot can't: here is what was sent, here is what came back, here is where the two stop matching.

Two export formats, two audiences

HARCopy as curl
What it isA structured file (right-click a request → Export → HAR) containing the full request and response, headers, body, and timing.A single executable shell command (right-click → Copy as curl) that reproduces the exact request.
Best forHanding off to someone who'll open it in their own proxy or network analyzer tool, preserving everything, including timing.A developer who just wants to run the exact request themselves, right now, without installing anything.
LimitationNot human-readable on its own, needs a tool to open. Not appropriate to attach if it contains another user's real session data.Only captures the request, not the response, since a curl command is something you run, not something you receive.

Check what's in the export before you attach it to a bug report. Both formats include every header on the request, which usually means an Authorization token or session cookie. Fine for a demo app like PeakAndPack, not fine to paste into a shared ticket for anything touching real user data without scrubbing it first.

Practical: turn a real finding into a proper bug report

Try it

Pick one finding from an earlier post's deliverable, the breakpoint exercise in Post 4, the Map Local states in Post 5, or the search edge cases in Post 7. Whichever one actually surfaced unexpected behavior.

Export that request as curl, and write it up in the same Steps / Expected / Actual / Severity / Evidence format used throughout the AI-Augmented QA series on this site, with the curl command as your Evidence field instead of a screenshot description. Notice how much less interpretation the developer reading it has to do.

AI-assisted: drafting the report from the capture

The same pattern used across the AI-Augmented QA series on this site applies directly here: paste the exported curl command, or the key request/response fields, into an AI tool along with what you expected to happen, and ask for a first-draft bug report in the Steps / Expected / Actual / Severity format.

What it's good at: turning "here's a curl command and it returned a 500 when I expected a 400" into properly structured prose in seconds, faster than typing the template out by hand every time.

What it can't do for you: confirm the steps actually reproduce the issue (only running them again proves that), or judge severity against your specific business context (a "minor" API inconsistency might be a contract-breaking change for a partner integration, and no AI reading the request in isolation knows that). Review the draft the same way Post 4 of the AI-Augmented QA bug-detection phase does: as a fast first pass, not a final answer.

Think before pasting a capture into a third-party AI tool. The same headers-and-cookies caution from earlier applies with more force here: a capture handed to an external service leaves your machine. Fine for PeakAndPack's demo credentials, not something to do by habit with a capture containing a real user's session token or personal data without checking your organization's data-handling policy first.

Your deliverable

One complete bug report, peakandpack-proxyman-bug-report.md, evidence included, either handwritten or AI-drafted and reviewed. If nothing from earlier posts turned up a real discrepancy, that's fine, write up the search endpoint's missing-parameter behavior from Post 7 instead, since PeakAndPack's search has a documented rough edge worth confirming against the live app either way.

Time: ~15 minutes handwritten if you already have a finding from an earlier post, ~5 to 10 with AI-assisted drafting plus review, ~25 either way if you're capturing a fresh finding first.
