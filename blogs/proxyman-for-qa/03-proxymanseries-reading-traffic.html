Reading traffic

Everything from Post 4 onward, breakpoints, mocked responses, network conditions, assumes you can already find the request you care about and read what's actually in it. That's this post: one real PeakAndPack flow, read end to end.

The three panes

Proxyman's window is always the same three areas, left to right: which app or domain the traffic came from, the list of individual requests, and the full detail of whichever one is selected.

Why the source list matters once you have more than one app open

Once SSL proxying covers more than one domain, or you're testing on a device that has other apps generating background traffic, the source list is what keeps the flow list from turning into noise. Click a source to see only its traffic, without changing what's actually being captured.

Filtering: the difference between skimming and searching

The flow list can filter by protocol, content type, URL, request or response header, and body, each with contains, not-contains, prefix, suffix, or regex matching. For a checkout flow with a dozen requests, typing /api/cart into the filter does more to speed up reading traffic than any other single habit in this post.

Practical: read a real checkout, request by request

Try it

With Proxyman capturing and PeakAndPack open, add an item to the cart, go to checkout, and place the order. Then find these three requests in the flow list and open each one's Body tab:

  1. POST /api/cart, the add-to-cart call. Confirm the body sent matches the product you clicked, not just that the call succeeded.
  2. GET /api/cart, right before checkout loads. This is what the cart page actually renders from, not what you assume it renders from.
  3. POST /api/orders/checkout, the order itself. Check the response body's total field against what the UI displayed. This is exactly the discrepancy that exposes the SAVE10 bug in the AI-Augmented QA series, the UI and the API don't have to agree, and only reading the actual response proves whether they do.

Headers matter for a different reason than Body does. Body tells you what data moved. Headers tell you what the app assumed about the request: which Authorization token it sent, what Content-Type it claimed, whether a session Cookie went along. A bug where the right data reaches the wrong user is a headers bug, not a body bug, since the body can be perfectly correct while the authorization behind it is wrong.

Your deliverable

A short annotated capture: for the three requests above, one line each noting the method, path, status, and the one field you checked in the body. Save it as peakandpack-checkout-trace.md. This is the same habit Post 8 turns into formal bug evidence, starting it now means Post 8 is a formatting exercise, not a new skill.

Time: ~15 minutes to complete the checkout flow and annotate the three requests.
