Proxyman for QA

Browser DevTools shows you what one tab did. Proxyman shows you what's actually crossing the network, from any app on the machine or device, including the requests DevTools never sees. This series is the traffic-level half of testing that most QA workflows skip.

By RN 9 posts Demo: PeakAndPack Prerequisite: None

Why a proxy tool, when DevTools already shows network requests

The Network tab in browser DevTools only sees traffic from that one tab, in that one browser. It can't see a native mobile app's traffic, a background sync call, or a request made by a tool outside the browser entirely. It also can't change anything: you can watch a request happen, but you can't pause it mid-flight, edit the body before it reaches the server, or swap in a fake response to see how the UI reacts to an error state that's hard to trigger for real.

A proxy tool sits below the browser, at the network layer, so it sees every app's traffic on the machine or device, and it can intercept and modify that traffic, not just observe it. That's the difference this series is about: reading traffic is step one, but the real testing value is in the tools that let you shape what the app under test actually receives.

Every step comes with a reason. This series doesn't just say "turn on SSL proxying" or "set the proxy port to 9090." It explains what that setting actually does, why it's off by default, and what breaks if you skip it. The goal is that by the end you understand Proxyman well enough to solve a problem it doesn't have a tutorial for, not just repeat the steps in one.

The demo app: PeakAndPack

Where a technique needs a real app to demonstrate against, this series uses PeakAndPack, the same demo app used across the Playwright and AI-Augmented QA series on this site: a live e-commerce app with login, a product listing, a cart, and a checkout flow, at peakandpack-ui.onrender.com. It's web-only, so the mobile-specific parts of this series (device setup, mobile troubleshooting) use a generic target rather than force PeakAndPack into a context it doesn't have. A dedicated native mobile testing series, with its own demo app, is planned separately.

Who this is for

  • QA engineers who test through the browser or app UI today and have never looked at what's actually crossing the network underneath it.
  • Anyone who's hit a bug that "only happens sometimes" and suspects it's network-related but doesn't have a way to prove it.
  • Testers who want to simulate error states, slow networks, or malformed responses without needing a developer to change the backend first.

No prerequisite series, though a basic sense of HTTP (requests, responses, status codes) will make posts 3 onward easier. The API basics primer from the AI-Augmented QA series covers everything needed.
