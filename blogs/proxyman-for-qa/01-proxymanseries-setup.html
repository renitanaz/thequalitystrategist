Setup, web and mobile

Everything after this post assumes Proxyman is installed, HTTPS traffic is readable, and at least one target, a browser or a device, is actually sending its traffic through it. This post gets you there, and explains what each step is actually doing so the next post's troubleshooting makes sense instead of feeling like magic.

Why HTTPS traffic needs a certificate before it's readable at all

Every request PeakAndPack's UI makes to its API travels over HTTPS, encrypted end to end between the browser and the server. By default, a proxy sitting between the two sees only ciphertext: a request happened, roughly when, to which host, but not what was actually in it.

Proxyman gets around this the only way any tool can: by sitting in the middle as a trusted party to both sides.

Nothing about this is a vulnerability in HTTPS, it's exactly what a company's own network security tools do to inspect employee traffic. It only works because you explicitly told your machine to trust Proxyman's certificate, which is also why every setup guide makes a point of having you remove that trust when you're done debugging.

Why this matters before you touch a single setting

Every install step below exists to satisfy one of two requirements: get your traffic routed through Proxyman in the first place, and get your browser or device to trust Proxyman's certificate so HTTPS traffic isn't just ciphertext. If a later step doesn't work, it's almost always because one of those two things didn't actually happen, not because of something exotic.

Install Proxyman

Download it from proxyman.com for macOS, Windows, or Linux. On first launch it asks to install a small helper tool.

Why the helper tool

The helper is what lets Proxyman automatically set itself as your machine's system HTTP/HTTPS proxy the moment it opens, and cleanly revert that setting if Proxyman quits or crashes. Without it you'd have to manually point your OS's proxy settings at Proxyman every time, and manually undo it after, which is exactly the kind of step that gets forgotten and leaves your machine routed through a proxy that isn't running anymore.

On macOS, the certificate installs into the System Keychain, and the automatic option installs and trusts it in one step (it will ask for your password, since trusting a new certificate authority is a system-level, admin-privileged change). On Windows, the same certificate installs via Proxyman's Certificate menu into Windows' own Certificate Manager, with an equivalent automatic script available. Either platform also offers a manual, step-by-step install for anyone who wants to see exactly what's being added instead of running the one-click option.

Turn on SSL proxying, scoped to what you're testing

SSL proxying is not on for every domain by default. You choose what to decrypt, by app or by domain (including wildcards like *.onrender.com), in Proxyman's Include/Exclude list, then enable it for that scope.

Why it's opt-in instead of everything, all the time

Your machine talks to dozens of domains you have no interest in testing: OS update checks, other apps phoning home, browser telemetry. Decrypting all of it by default would bury PeakAndPack's traffic in noise, and would mean Proxyman is silently intercepting HTTPS traffic for things you never intended to inspect, including anything sensitive unrelated to your testing. Scoping SSL proxying to just the domains under test keeps the traffic list readable and keeps interception deliberate.

For this series, scope it to peakandpack-ui.onrender.com and peakandpackshopdemo.onrender.com, the UI and API PeakAndPack runs on.

Verify it's actually working, before moving on

Try it: 60-second check

Open peakandpack-ui.onrender.com in a browser on the same machine Proxyman is running on.

Watch the traffic list as the page loads. You should see requests appear in real time, and clicking one should show readable headers and a JSON body, not a wall of encrypted-looking bytes.

Requests show up, but the body looks like garbage, not readable JSON? That's the certificate-trust step, not the proxy-routing step. Traffic is reaching Proxyman (routing works), but Proxyman can't decrypt it (trust doesn't). Re-run the certificate install, and confirm on macOS specifically that the certificate isn't just present in Keychain Access but marked "Always Trust" for SSL, since installed and trusted are two different states. Post 2 goes into this failure mode and several others in more depth.

Connect a device: WiFi or USB

Everything above covers traffic from the same machine Proxyman is running on. Testing a mobile app, or a mobile browser, means getting a separate device's traffic routed through Proxyman instead, and that has more than one path depending on what you're testing and how much control you have over the app.

WiFi: the one that works on any app, any device

This is the standard path, and it works regardless of whether you have the app's source code, because it operates at the network level rather than inside the app.

  1. Put the device on the same WiFi network as the computer running Proxyman.
  2. On the device, open WiFi settings for that network and manually configure an HTTP proxy: the server is your computer's IP address on that network, the port is Proxyman's (9090 by default).
  3. With that proxy config in place, open a browser on the device and visit http://proxy.man/ssl or http://cert.proxyman.io to download Proxyman's certificate.
  4. Install and trust it. This step differs by platform and version: on iOS 12.2 and later it's a two-part process, install the downloaded profile under Settings → Profiles Downloaded, then separately flip it on under Settings → General → About → Certificate Trust Settings, since profile installation and certificate trust are handled by two different iOS settings screens. On Android 11 and later, you install it manually under Settings → Security → Encryption & Credentials → Install a Certificate; on Android 10 and earlier, visiting the certificate URL installs it automatically.
Why two separate certificate steps on iOS

Installing a configuration profile and trusting a certificate as a root authority are different levels of access on iOS, by design, so that a profile can't silently grant itself full certificate authority just by being installed. Skipping the second step is the single most common reason "I installed the certificate" still doesn't produce readable HTTPS traffic on an iPhone.

USB and no-WiFi-config alternatives: real, but narrower than they sound

Proxyman also offers ways to capture traffic without manually configuring a device's WiFi proxy, but it's worth being precise about what these actually are, since "USB setup" undersells how different they are from the WiFi path above.

OptionWhat it actually isWhen it applies
Atlantis (iOS)An SDK you add to an iOS app's own source code, then launch the app via Xcode. It captures the app's traffic over USB or WiFi with no manual proxy or certificate setup on the device.Only when you (or your dev team) have the app's source and build it yourself. Not usable against a third-party app, or an already-built app you only have as an installed binary, which is most black-box QA testing.
Proxyman for iOSA standalone app, installed on the device itself from the App Store, that runs a local VPN to capture the device's traffic without needing a Mac or Proxyman desktop at all.Useful when you want on-device capture independent of a computer, but it's a genuinely different tool with its own setup, not an extension of the desktop app's USB support.

For most QA work, testing an app you didn't build, against a device you control, the WiFi path is the one that actually applies. Treat Atlantis and Proxyman for iOS as options worth knowing exist, not defaults to reach for first.

When the app under test needs a VPN

VPN and Proxyman's proxy fight for the same job. By default, a VPN app forces all of a device's traffic through the VPN's own tunnel, which happens at a lower network layer than the HTTP proxy setting you just configured. That means the WiFi proxy setup above can be completely correct and Proxyman can still see nothing, because the VPN took the traffic first. Proxyman's own documentation is direct about this: disable VPN apps on both the device and the computer while debugging.

If the app you're testing genuinely requires a VPN to reach its backend at all, for instance an internal corporate app that isn't reachable from the open internet, there's no clean way to run both at once through the standard setup. The practical options are: use a test device or account that reaches the target over a network that doesn't require VPN in the first place, or ask whoever manages the VPN whether it supports split-tunneling in a way that leaves the app's traffic on the untunneled path where Proxyman's proxy can still see it. Neither is a Proxyman setting, they're network-architecture questions worth raising with IT or platform engineering before you sink time into a setup that can't work as configured.

Your deliverable

A short setup log, not a script: which platform you set up (browser, iOS device, Android device, or more than one), the exact steps that worked, and anything that didn't work on the first try. Save it as proxyman-setup-notes.md. This isn't busywork, it's the thing you'll actually reach for the next time you set up a new machine or device, faster than re-reading this post.

Time: ~15 to 30 minutes for a browser on the same machine; add 10 to 15 minutes per mobile device for the certificate trust steps.
