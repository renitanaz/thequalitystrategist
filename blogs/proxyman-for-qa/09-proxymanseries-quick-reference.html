API test case categories to run through Proxyman

Not every category below got its own dedicated exercise earlier in the series, but every one is directly reachable with the tools covered. Treat this as a checklist for a new endpoint, not just a recap.

CategoryWhat you're checkingTool
Status code correctnessNot just success vs. failure, the right status for the right condition: a missing required field is a 400, not a 500. A missing search query on PeakAndPack has been exactly this kind of mismatch.Reading traffic, Breakpoints
Boundary and invalid inputNegative numbers, zero, empty strings, values far outside any sane range, wrong data types in a field the server should validate.Breakpoints, Composer
Authorization, not just authenticationBeing logged in and being allowed to see this specific resource are different checks. Strip or swap the Authorization header on a request for another user's data, one bug in this exact category is real and confirmed on PeakAndPack's orders endpoint.Breakpoints (edit headers), Edit & Repeat
Error response data leakageDoes an error response ever include a stack trace, an internal file path, or other implementation detail that shouldn't reach a client?Reading traffic, Composer
IdempotencyDoes submitting the same request twice, on purpose or from a slow-network double click, create a duplicate side effect, or is the second one safely a no-op?Network Conditions, Repeat
Empty and missing-data statesZero results, a null field, a missing optional parameter, all realistic states a fast connection to a full database rarely produces on its own.Map Local
Degraded network behaviourLoading states, timeout handling, and whether the UI gives any feedback at all when a response is slow rather than absent.Network Conditions

The Authorization row is the one worth re-reading. It's the single highest-value category on this list and the easiest to skip, since a UI that only ever shows you your own data will never accidentally demonstrate the bug for you. It has to be deliberately tested by editing the request, which is exactly what a proxy tool is for and a UI-only test plan structurally cannot do.

Setup, condensed

  • Install Proxyman, install the helper tool when prompted
  • Trust the certificate (macOS: Keychain, "Always Trust" for SSL; Windows: Certificate Manager)
  • Enable SSL Proxying, scoped to the domains under test, not everything
  • Mobile: same WiFi network, manual proxy config pointing at your computer's IP and port 9090, then visit cert.proxyman.io on-device and trust it (two separate steps on iOS)
  • Verify: open the app, confirm traffic appears with a readable body, not ciphertext

Troubleshooting, condensed

SymptomLikely cause
Nothing shows up at allDifferent network, wrong IP/port, firewall, or a VPN silently taking the traffic first
Shows up, body unreadableCertificate installed but not trusted (check "Always Trust for SSL" on macOS)
One specific app errors or crashes, others work fineSSL pinning, not fixable from Proxyman's side for an app you don't own
Android app won't decrypt even with the cert installedThe app's own network_security_config.xml doesn't opt in to trusting user certificates

What this series covered

Nine posts, one real app, moving from "can I even see the traffic" to "here's a formal bug report with a developer-runnable repro attached." The throughline: everything after Post 2 depends on traffic actually being readable, and everything after Post 3 depends on being able to read what's in it. Skipping ahead to breakpoints or mocking without those two solid tends to produce confusing, hard-to-debug results.
