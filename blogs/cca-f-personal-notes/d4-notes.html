Prompt Engineering & Structured Output

Task Statements 4.1–4.6

Source: Claude Certified Architect – Foundations Certification Exam Guide, Domain 4 section, official sample Questions 11 and 12.

Topics Mind Map

1Topic Keywords

4.1 · Explicit Criteria

Explicit criteria
Precise, categorical rules beat vague instructions like "be conservative" - the latter doesn't actually improve precision.
False-positive trust cost
A high false-positive category undermines developer trust even in the categories that are accurate - e.g. if a reviewer's "security" findings are wrong 40% of the time, developers start skimming past all of its findings, including its accurate "bug" and "style" flags.
Severity criteria
Explicit per-level criteria with concrete code examples, for consistent classification.

4.2 · Few-Shot

Few-shot prompting
The most effective technique for consistently formatted, actionable output when instructions alone produce inconsistency - the guide's own number is 2–4 targeted examples per ambiguous scenario, each showing the reasoning for the chosen action.
Ambiguous-case examples
Few-shot examples that demonstrate handling of edge cases, so the model generalizes judgment instead of matching only pre-specified cases.

4.3 · Structured Output

tool_use for structure
The most reliable approach for guaranteed schema-compliant output - eliminates JSON syntax errors (not semantic ones).
tool_choice modes
"auto" may skip the tool, "any" forces some tool, forced selection names one exact tool.
Nullable required fields
Field must exist in the schema, but its value may be null - prevents the model fabricating data to satisfy a required field.
"other" + detail pattern
Extensible enum categorization: pick "other" plus a free-text detail field when nothing else fits.

4.4 · Validation & Retry

Retry-with-error-feedback
Append the specific validation error to the prompt on retry, along with the original doc and the failed extraction.
Limits of retry
Ineffective when the required information is simply absent from the source - no amount of retrying invents a fact that isn't there.
detected_pattern
Field tracking which code construct triggered a finding, to analyze dismissal/false-positive patterns systematically.
Semantic vs. schema errors
Schema syntax errors are eliminated by tool use. Semantic errors (values don't sum, wrong field) still need validation.

4.5 · Batch Processing

Message Batches API
~50% cost savings, up to a 24-hour processing window, no guaranteed latency SLA.
Blocking vs. non-blocking
Batch fits non-blocking, latency-tolerant work (overnight reports); wrong for blocking workflows (pre-merge checks).
No mid-batch tool calling
The batch API cannot execute a tool mid-request and return results within that same request.
custom_id
Correlates each batch response back to its original request; also used to resubmit only failed documents.

4.6 · Multi-Pass Review

Self-review limitation
A model retains its own generation reasoning, making it less likely to question its own decisions in the same session.
Independent review instance
A separate Claude call without the generator's reasoning context catches subtler issues than self-review.
Multi-pass review
Per-file local analysis passes, plus one separate cross-file integration pass - avoids attention dilution and contradictions.

Diagram: A Real Extraction, Annotated

How this diagram fits together

Three highlighted fields, three different lessons. total is schema-valid JSON that's still wrong - tool_use guarantees the shape, not the arithmetic, so semantic checks (does the total match the line items?) still need to happen separately. customer_email is null because the invoice genuinely doesn't have one - a nullable field lets the model say so honestly instead of inventing an address. document_type: "other" plus a detail string is what lets the schema handle a document type nobody anticipated, without needing a schema change first.

Diagram: Sync vs. Batch Decision

How this diagram fits together

The routing question is "is someone waiting right now," not "which is cheaper." A developer blocked on a pre-merge check needs synchronous, full price, because the ~50% batch discount comes with no latency guarantee - it could land in minutes or near the 24-hour window. An overnight report has nobody waiting on it, so the same discount is free money.

Diagram: Self-Review vs. Independent Review

How this diagram fits together

The loop arrow on the left is the failure mode: a model reviewing its own output still has its generation reasoning sitting in context, so it's reviewing "did I follow my own plan" more than "is this actually correct." The dashed "no shared context" line on the right is the fix - a second instance with none of that reasoning has nothing to defend, so it catches issues the generator talked itself past.

Diagram: Multi-Pass Review Flow

How this diagram fits together

Three separate local passes, not one shared pass over three files - that's what keeps depth consistent instead of the first file getting full attention and the third getting skimmed. The integration pass only exists to catch what none of the local passes could see on their own: contradictions between files, like a pattern flagged in file A but approved unchanged in file C.

3Active Recall
Why doesn't "be conservative" or "only report high-confidence findings" actually improve precision?
These are general instructions, not specific categorical criteria. The guide is explicit: general confidence-based language doesn't improve precision the way defining exactly what to report vs. skip does.
How many few-shot examples does the guide suggest per ambiguous scenario, and what should each one show?
2–4 targeted examples, each showing the reasoning for why one action was chosen over plausible alternatives - not just the input/output pair alone.
Does a strict JSON schema via tool_use guarantee the extracted values are correct?
No. It eliminates syntax/formatting errors (missing fields, wrong types, invalid enum values) but not semantic errors - e.g. line items that don't sum to the stated total, or a value placed in the wrong field.
Why use a nullable field instead of a required-with-no-null field for something the customer might not provide?
A required, non-nullable field pressures the model to fabricate a plausible-looking value just to satisfy the schema. Nullable lets it honestly report "not provided" instead.
Your extraction failed validation. When should you retry, and when is retry pointless?
Retry when the mistake is fixable - wrong enum value, wrong field placement, a structural/format error - by appending the specific validation error to a follow-up request. Retry is pointless when the information simply isn't present in the source document; the correct move there is null plus a "missing" flag, not another attempt.
What's the detected_pattern field for?
Recording which code construct or phrase triggered a given finding, so you can later analyze which patterns developers tend to dismiss - i.e. systematic false-positive analysis.
Name the two headline trade-offs of the Message Batches API.
About 50% cost savings, but up to a 24-hour processing window with no guaranteed latency SLA. Good for non-blocking, latency-tolerant work; wrong for anything a user is actively waiting on.
Can a single batch request call a tool mid-request and use the result to continue reasoning?
No - the batch API does not support multi-turn tool calling within one request. Needed context has to be gathered and included up front before submission.
A batch of 500 documents comes back with 12 failures. What's the correct recovery?
Resubmit only the 12 failed documents, identified by their custom_id, with whatever fix is needed (e.g. chunking ones that exceeded context limits) - not the entire batch.
Why is a model reviewing the exact code it just generated, in the same session, a weaker check than an independent review?
It retains the reasoning context from generation, which makes it less likely to question its own prior decisions. An independent instance without that inherited context catches subtler issues.
Why split a 14-file review into per-file passes plus one integration pass, instead of one big pass over everything?
A single pass over many files at once causes attention dilution - inconsistent depth per file, missed bugs, and even self-contradiction (flagging a pattern in one file while approving identical code in another). Per-file local passes stay consistent; a separate integration pass then catches cross-file issues.

4Official Sample Questions (D4)
Q11. (Scenario 5, CI) Real-time Claude calls power (1) a blocking pre-merge check, and (2) an overnight technical-debt report. Manager proposes switching both to the Message Batches API for the 50% savings. How do you evaluate this?
A) Use batch for the technical-debt reports only; keep real-time calls for pre-merge checks.
B) Switch both to batch with status polling.
C) Keep real-time for both, to avoid batch result ordering issues.
D) Switch both to batch with a timeout fallback to real-time.
Show answer
A. Batch has no guaranteed latency SLA (up to 24h), unsuitable for a blocking workflow developers are waiting on, but ideal for an overnight job. B relies on "often faster" completion, not acceptable for a blocking check. C is a misconception - results correlate fine via custom_id. D adds complexity the simple per-workflow match already solves.
Q12. (Scenario 5) A single-pass review of a 14-file PR produces inconsistent depth, misses obvious bugs, and even contradicts itself - flagging a pattern in one file, approving identical code in another. How should you restructure the review?
A) Split into focused passes: analyze each file individually for local issues, then run a separate integration pass for cross-file data flow.
B) Require developers to split large PRs into smaller 3–4-file submissions.
C) Switch to a higher-tier model with a larger context window.
D) Run three independent full-PR passes, only flag issues appearing in at least two of three.
Show answer
A. Directly addresses attention dilution, the actual root cause. B shifts the burden to developers without fixing the review system. C misunderstands that a bigger context window doesn't fix attention quality. D would actually suppress detection of real bugs caught only intermittently by requiring consensus.

5Emergency Recap
Task Statement4.1
Explicit criteria for precision
  • Explicit, categorical criteria beat vague instructions like "be conservative" - write specific rules for what to report vs. skip, not confidence-based filtering.
  • False-positive rates in one category damage trust in accurate categories too - temporarily disable a high-false-positive category while its prompt is improved.
  • Define explicit severity criteria with concrete code examples at each level, for consistent classification.
Task Statement4.2
Few-shot prompting
  • Few-shot examples (2–4, targeted) are the most effective fix for inconsistent output - each showing the reasoning for why one action was chosen over plausible alternatives.
  • They demonstrate ambiguous-case handling, letting the model generalize judgment - e.g. distinguishing acceptable code patterns from genuine issues.
  • Include examples that demonstrate the exact desired output format (location, issue, severity, suggested fix).
  • Also reduces hallucination in extraction - examples across varied document formats fix empty/null extraction of required fields.
Task Statement4.3
Structured output via tool_use
  • tool_use + JSON schema is the most reliable route to guaranteed schema-compliant output, eliminating syntax errors, but not semantic ones (e.g. line items that don't sum to the total).→ See: Diagram, Structured Extraction with tool_use
  • tool_choice: "auto" (may skip), "any" (guarantees a call when the document type is unknown), forced (ensures a specific extraction runs before dependent enrichment steps).
  • Schema design: nullable optional fields so the model isn't pressured to fabricate a value, plus "unclear"/"other" + detail-string enum values for extensibility.→ See: Diagram, A Real Extraction, Annotated
Task Statement4.4
Validation, retry, feedback loops
  • Retry-with-error-feedback: append the specific validation error, plus the original document and failed extraction, to guide correction.→ See: Diagram, Structured Extraction with tool_use
  • Retries are ineffective when information is simply absent from the source - only useful for format/structural errors.
  • detected_pattern fields enable systematic analysis of why developers dismiss certain findings.
  • Design self-correction flows: extract calculated_total alongside stated_total to flag discrepancies; add conflict_detected booleans.
Task Statement4.5
Batch processing strategies
  • Message Batches API: ~50% cost savings, up to 24-hour window, no guaranteed latency SLA - synchronous for blocking pre-merge checks, batch for overnight/weekly, non-blocking work.→ See: Diagram, Sync vs. Batch Decision
  • No multi-turn tool calling inside one batch request.
  • custom_id correlates request/response pairs - use it to resubmit only the failed documents after a run.
  • Calculate batch submission frequency to guarantee an SLA (e.g. 4-hour submission windows to guarantee a 30-hour SLA on top of 24-hour processing).
  • Refine the prompt on a small sample before scaling to a large batch, to reduce resubmission cost.
Task Statement4.6
Multi-instance & multi-pass review
  • Self-review is limited: the model retains its own generation reasoning, making it less likely to question its own decisions.
  • Independent review instances (no prior reasoning context) catch subtler issues - use a second, separate Claude instance.→ See: Diagram, Self-Review vs. Independent Review
  • Multi-pass review splits large reviews into per-file passes (local issues) plus a separate integration pass (cross-file data flow), avoiding attention dilution and contradictions.→ See: Diagram, Multi-Pass Review Flow
  • Run verification passes where the model self-reports confidence alongside each finding, to enable calibrated review routing.
Summary, one line per task statement:
  • 4.1 Specific categorical criteria beat vague conservatism instructions - false positives cost trust across the board.
  • 4.2 2–4 targeted few-shot examples fix both output-format drift and ambiguous-case judgment.
  • 4.3 Forced/any tool_choice + JSON schema kills syntax errors; nullable fields stop fabrication; semantic errors still need checking.
  • 4.4 Retry only fixes fixable mistakes; if the source lacks the info, return null and flag it, don't loop.
  • 4.5 Batch = cheap but no latency guarantee, wrong for anything blocking; custom_id lets you resubmit just the failures.
  • 4.6 A generator reviewing its own output is a weaker check than an independent instance; split big reviews into local + integration passes.
