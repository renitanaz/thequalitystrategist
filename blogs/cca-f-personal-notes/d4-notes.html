Prompt Engineering & Structured Output

Task Statements 4.1–4.6

Source: Claude Certified Architect – Foundations Certification Exam Guide, Domain 4 section, official sample Questions 11 and 12.

Topics Mind Map

1Topic Keywords

4.1 · Explicit Criteria

Explicit criteria
Precise, categorical rules beat vague instructions like "be conservative" - the latter doesn't actually improve precision.
Severity criteria
Explicit per-level criteria with concrete code examples, for consistent classification.
False-positive trust cost
A high false-positive category undermines developer trust even in the categories that are accurate. The fix: temporarily disable it, iterate on its prompt with concrete code examples, then re-enable only once precision improves - not leave it running while you fix it.
Why confidence filtering fails
LLM self-reported confidence is poorly calibrated - the model is often sure about wrong findings and hesitant about right ones. Explicit criteria come first; confidence-based routing is a second-stage refinement on top, not a substitute for criteria (see 4.6).

4.2 · Few-Shot

Few-shot prompting
The most effective technique for consistently formatted, actionable output when instructions alone produce inconsistency - the guide's own number is 2–4 targeted examples per ambiguous scenario, each showing the reasoning for the chosen action.
Ambiguous-case examples
Few-shot examples that demonstrate handling of edge cases, so the model generalizes judgment instead of matching only pre-specified cases.

4.3 · Structured Output

tool_use for structure
The most reliable approach for guaranteed schema-compliant output - eliminates JSON syntax errors (not semantic ones).
tool_choice modes
"auto" may skip the tool, "any" forces some tool, forced selection names one exact tool.
Schema design for production
  • Nullable required fields - must exist in the schema, but the value may be null
  • "other" + detail - a free-text detail field extends an enum when nothing else fits.
  • "unclear" - distinct from "other": use it when the source itself is genuinely ambiguous, so the model isn't forced into a confident-sounding but wrong classification.
Format normalization rules
Formatting conventions (e.g. ISO 8601 dates, decimal currency without symbols) belong in the prompt alongside the schema - the schema enforces structure, the prompt enforces formatting consistency.

4.4 · Validation & Retry

Retry-with-error-feedback
Append the specific validation error to the prompt on retry, along with the original doc and the failed extraction.
What retry can (and can't) fix
  • Can fix - format mismatches, structural/field-placement errors, misplaced values, math the model got wrong.
  • Can't fix - information simply absent from the source. No amount of retrying invents a fact that isn't there.
detected_pattern
Field tracking which code construct triggered a finding, to analyze dismissal/false-positive patterns systematically.
Semantic vs. schema errors
  • Schema syntax errors are eliminated by tool_use.
  • Semantic errors (values don't sum, wrong field) still need validation and retry loops.
Pydantic as validation layer
A Pydantic model does two jobs at once: parsing enforces structure (types, required fields), validators enforce semantics (cross-field rules a JSON schema can't express, like sums matching). Both surface through one ValidationError with per-field messages - exactly the specific error the retry loop needs.

4.5 · Batch Processing

Message Batches API
~50% cost savings, up to a 24-hour processing window, no guaranteed latency SLA.
Blocking vs. non-blocking
Batch fits non-blocking, latency-tolerant work (overnight reports); wrong for blocking workflows (pre-merge checks).
No mid-batch tool calling
The batch API cannot execute a tool mid-request and return results within that same request.
custom_id
Correlates each batch response back to its original request; also used to resubmit only failed documents.

4.6 · Multi-Pass Review

Self-review limitation
A model retains its own generation reasoning, making it less likely to question its own decisions in the same session.
Independent review instance
A separate Claude call without the generator's reasoning context catches subtler issues than self-review.
Multi-pass review
Per-file local analysis passes, plus one separate cross-file integration pass - avoids attention dilution and contradictions.
Context window isn't the fix
A named exam distractor: a bigger context window doesn't fix attention dilution, because the problem is attention quality, not capacity - the model can hold more text but still spreads attention unevenly across files. Only focused per-file passes fix it.
Confidence-Based Routing
Send findings to human review based on the model's self-reported confidence per finding - a second-stage refinement on top of explicit criteria, not a substitute for them (see 4.1). Only works once thresholds are calibrated against known-accuracy data.
Calibrated confidence
Raw self-reported confidence is unreliable for automated routing. Calibrate thresholds by running labelled validation sets (known answers) through the system and checking how reported confidence tracks actual accuracy.
Production Review Architecture
Combines all three concepts into one pipeline: generation → per-file review → integration review → confidence routing → calibration loop. More expensive than single-pass review; worth it wherever missed issues have downstream consequences (CI/CD pipelines, financial extraction, compliance analysis).

Scenario: extraction-as-schema - tool_use is never really "called," the tool just defines the output shape, then Validate decides what happens next.

How this diagram fits together

Two branches out of Validate, and they're not interchangeable:

  • Fixable error (left) - the model produced something wrong that another attempt can plausibly fix. Retry with the specific validation error appended to the prompt.
  • Info absent from source (right) - there's nothing to retry; the document simply doesn't contain that field. The correct move is field: null plus a missing flag, not another API call hoping the answer materializes.

Diagram: Schema-Valid, Semantically Wrong

How this diagram fits together

Three highlighted fields, three different lessons:

  • total - schema-valid JSON that's still wrong. tool_use guarantees the shape, not the arithmetic, so semantic checks (does the total match the line items?) still need to happen separately.
  • customer_email - null because the invoice genuinely doesn't have one. A nullable field lets the model say so honestly instead of inventing an address.
  • document_type: "other" - plus a detail string, lets the schema handle a document type nobody anticipated, without needing a schema change first.

Diagram: Catching and Fixing Semantic Errors

How this diagram fits together

Three ways to catch a semantic error, all producing the same thing at the end: a specific, actionable error message.

  • Calculated vs. stated total - extract both numbers and compare them yourself; a mismatch is an automatic flag, no model judgment required.
  • conflict_detected - for when the source itself contradicts itself; the model reports both values and flags the conflict instead of silently picking one.
  • Pydantic validator - encodes a cross-field rule a JSON schema can't express, and raises one ValidationError with the exact per-field message the retry loop needs.

Whichever mechanism catches it, the fix is the same retry-with-error-feedback pattern: send the original document, the failed extraction, and that specific error back, and ask for a corrected extraction.

The detected_pattern box is a different kind of loop - not per-request, but across many runs over time, spotting which pattern developers keep dismissing so the prompt itself gets refined. And the closing line is the boundary this whole diagram assumes: retry fixes a wrong answer, it can't manufacture one the source never had.

Diagram: Sync vs. Batch Decision

How this diagram fits together

The routing question is "is someone waiting right now," not "which is cheaper."

A developer blocked on a pre-merge check needs synchronous, full price - the ~50% batch discount comes with no latency guarantee, and could land in minutes or near the 24-hour window. An overnight report has nobody waiting on it, so the same discount is free money.

Diagram: Self-Review vs. Independent Review

How this diagram fits together

The loop arrow (left) is the failure mode: a model reviewing its own output still has its generation reasoning sitting in context, so it's reviewing "did I follow my own plan" more than "is this actually correct."

The dashed "no shared context" line (right) is the fix - a second instance with none of that reasoning has nothing to defend, so it catches issues the generator talked itself past.

Diagram: Why Multi-Pass Review Architecture

How this diagram fits together

Top half - why: it's the same bot, same session, reviewing the code it just wrote. It still has all the reasoning it used to justify its own choices sitting in context, so "review this" quietly becomes "did I follow my own plan" instead of "is this actually correct." That's why it can confidently say "looks correct" while the bug is still sitting right there - it isn't lying, it's just not positioned to see its own mistake.

Bottom half - what to do about it: multi-pass review, and specifically the per-file part of it. Three separate local passes, not one shared pass over three files, keeps depth consistent instead of the first file getting full attention and the third getting skimmed.

The integration pass only exists to catch what none of the local passes could see on their own: contradictions between files, like a pattern flagged in file A but approved unchanged in file C. (An independent reviewer - a separate instance entirely - is the other, complementary fix; see the diagram above.)

Diagram: Production Review Architecture

How this diagram fits together

This is the capstone pipeline - it doesn't introduce a new idea, it wires together three you've already seen: multi-pass review (steps 2–3), confidence-based routing (step 4), and calibration (step 5).

  • Steps 2–3 are the per-file plus integration split from the "Why Multi-Pass Review Architecture" diagram above - green throughout, same reasoning.
  • Step 4 is the confidence-routing refinement from the "Vague vs. Explicit Criteria" diagram - amber, and only meaningful once explicit criteria already exist.
  • Step 5 feeds back into step 4 (dashed blue arrow) - calibration isn't a one-time setup, it's a loop that keeps confidence thresholds honest as more labelled data comes in.

The red note at the bottom is the exam-relevant trade-off: this full pipeline costs more than a single pass, so it's a deliberate choice for high-stakes review (CI/CD, financial extraction, compliance), not a default for every review task.

3Active Recall
Why doesn't "be conservative" or "only report high-confidence findings" actually improve precision?
These are general instructions, not specific categorical criteria. The guide is explicit: general confidence-based language doesn't improve precision the way defining exactly what to report vs. skip does.
How many few-shot examples does the guide suggest per ambiguous scenario, and what should each one show?
2–4 targeted examples, each showing the reasoning for why one action was chosen over plausible alternatives - not just the input/output pair alone.
Does a strict JSON schema via tool_use guarantee the extracted values are correct?
No. It eliminates syntax/formatting errors (missing fields, wrong types, invalid enum values) but not semantic errors - e.g. line items that don't sum to the stated total, or a value placed in the wrong field.
Why use a nullable field instead of a required-with-no-null field for something the customer might not provide?
A required, non-nullable field pressures the model to fabricate a plausible-looking value just to satisfy the schema. Nullable lets it honestly report "not provided" instead.
Your extraction failed validation. When should you retry, and when is retry pointless?
Retry when the mistake is fixable - wrong enum value, wrong field placement, a structural/format error - by appending the specific validation error to a follow-up request. Retry is pointless when the information simply isn't present in the source document; the correct move there is null plus a "missing" flag, not another attempt.
What's the detected_pattern field for?
Recording which code construct or phrase triggered a given finding, so you can later analyze which patterns developers tend to dismiss - i.e. systematic false-positive analysis.
Name the two headline trade-offs of the Message Batches API.
About 50% cost savings, but up to a 24-hour processing window with no guaranteed latency SLA. Good for non-blocking, latency-tolerant work; wrong for anything a user is actively waiting on.
Can a single batch request call a tool mid-request and use the result to continue reasoning?
No - the batch API does not support multi-turn tool calling within one request. Needed context has to be gathered and included up front before submission.
A batch of 500 documents comes back with 12 failures. What's the correct recovery?
Resubmit only the 12 failed documents, identified by their custom_id, with whatever fix is needed (e.g. chunking ones that exceeded context limits) - not the entire batch.
Why is a model reviewing the exact code it just generated, in the same session, a weaker check than an independent review?
It retains the reasoning context from generation, which makes it less likely to question its own prior decisions. An independent instance without that inherited context catches subtler issues.
Why split a 14-file review into per-file passes plus one integration pass, instead of one big pass over everything?
A single pass over many files at once causes attention dilution - inconsistent depth per file, missed bugs, and even self-contradiction (flagging a pattern in one file while approving identical code in another). Per-file local passes stay consistent; a separate integration pass then catches cross-file issues.

4Official Sample Questions (D4)
Q11. (Scenario 5, CI) Real-time Claude calls power (1) a blocking pre-merge check, and (2) an overnight technical-debt report. Manager proposes switching both to the Message Batches API for the 50% savings. How do you evaluate this?
A) Use batch for the technical-debt reports only; keep real-time calls for pre-merge checks.
B) Switch both to batch with status polling.
C) Keep real-time for both, to avoid batch result ordering issues.
D) Switch both to batch with a timeout fallback to real-time.
Show answer
A. Batch has no guaranteed latency SLA (up to 24h), unsuitable for a blocking workflow developers are waiting on, but ideal for an overnight job. B relies on "often faster" completion, not acceptable for a blocking check. C is a misconception - results correlate fine via custom_id. D adds complexity the simple per-workflow match already solves.
Q12. (Scenario 5) A single-pass review of a 14-file PR produces inconsistent depth, misses obvious bugs, and even contradicts itself - flagging a pattern in one file, approving identical code in another. How should you restructure the review?
A) Split into focused passes: analyze each file individually for local issues, then run a separate integration pass for cross-file data flow.
B) Require developers to split large PRs into smaller 3–4-file submissions.
C) Switch to a higher-tier model with a larger context window.
D) Run three independent full-PR passes, only flag issues appearing in at least two of three.
Show answer
A. Directly addresses attention dilution, the actual root cause. B shifts the burden to developers without fixing the review system. C misunderstands that a bigger context window doesn't fix attention quality. D would actually suppress detection of real bugs caught only intermittently by requiring consensus.

Task Statement4.1
Explicit criteria for precision
  • Explicit, categorical criteria beat vague instructions like "be conservative" - write specific rules for what to report vs. skip, not confidence-based filtering.→ See: Diagram, Vague vs. Explicit Criteria
  • False-positive rates in one category damage trust in accurate categories too - disable, rework, re-enable: temporarily turn off the high-false-positive category, rework its prompt with concrete examples, and only switch it back on once precision improves.→ See: Diagram, False-Positive Trust Cost
  • Define explicit severity criteria with concrete code examples at each level, for consistent classification.
  • Confidence-based filtering fails because self-reported confidence is poorly calibrated - the model is often sure about wrong findings and hesitant about right ones. Criteria come first; confidence-based routing is a later refinement (see 4.6), never a substitute.
Task Statement4.2
Few-shot prompting
  • Few-shot examples (2–4, targeted) are the most effective fix for inconsistent output - each showing the reasoning for why one action was chosen over plausible alternatives.
  • They demonstrate ambiguous-case handling, letting the model generalize judgment - e.g. distinguishing acceptable code patterns from genuine issues.
  • Include examples that demonstrate the exact desired output format (location, issue, severity, suggested fix).
  • Also reduces hallucination in extraction - examples across varied document formats fix empty/null extraction of required fields.
  • Not every problem is a few-shot problem - malformed JSON wants tool_use, fabricated fields want nullable schema fields, sum mismatches want a validation-retry loop.→ See: Table, Few-Shot vs. Other Techniques
Task Statement4.3
Structured output via tool_use
  • tool_use + JSON schema is the most reliable route to guaranteed schema-compliant output, eliminating syntax errors, but not semantic ones (e.g. line items that don't sum to the total).→ See: Diagram, Structured Extraction with tool_use
  • tool_choice: "auto" (may skip), "any" (guarantees a call when the document type is unknown), forced (ensures a specific extraction runs before dependent enrichment steps). Set by your code in the request, not by Claude.→ See: Diagram, Who Sends tool_choice?
  • Schema design: nullable optional fields so the model isn't pressured to fabricate a value, plus "unclear"/"other" + detail-string enum values for extensibility.→ See: Diagram, Schema-Valid, Semantically Wrong
  • Format normalization rules (ISO 8601 dates, decimal currency without symbols) belong in the prompt alongside the schema - the schema enforces structure, the prompt enforces formatting consistency.
Task Statement4.4
Validation, retry, feedback loops
  • Retry-with-error-feedback: append the specific validation error, plus the original document and failed extraction, to guide correction.→ See: Diagram, Catching and Fixing Semantic Errors
  • Retries are ineffective when information is simply absent from the source - only useful for format/structural errors.
  • detected_pattern fields enable systematic analysis of why developers dismiss certain findings.
  • Design self-correction flows: extract calculated_total alongside stated_total to flag discrepancies; add conflict_detected booleans.→ See: Diagram, Schema-Valid, Semantically Wrong
  • Pydantic - named directly in the exam guide alongside JSON Schema - does both jobs at once: parsing enforces structure, validators enforce semantics (like sums matching). Both surface through one ValidationError with the per-field message the retry loop needs.
Task Statement4.5
Batch processing strategies
  • Message Batches API: ~50% cost savings, up to 24-hour window, no guaranteed latency SLA - synchronous for blocking pre-merge checks, batch for overnight/weekly, non-blocking work.→ See: Diagram, Sync vs. Batch Decision
  • No multi-turn tool calling inside one batch request.
  • custom_id correlates request/response pairs - use it to resubmit only the failed documents after a run.
  • Calculate batch submission frequency to guarantee an SLA (e.g. 4-hour submission windows to guarantee a 30-hour SLA on top of 24-hour processing).
  • Refine the prompt on a small sample before scaling to a large batch, to reduce resubmission cost.
Task Statement4.6
Multi-instance & multi-pass review
  • Self-review is limited: the model retains its own generation reasoning, making it less likely to question its own decisions.
  • Independent review instances (no prior reasoning context) catch subtler issues - use a second, separate Claude instance.→ See: Diagram, Self-Review vs. Independent Review
  • Multi-pass review splits large reviews into per-file passes (local issues) plus a separate integration pass (cross-file data flow), avoiding attention dilution and contradictions.→ See: Diagram, Why Multi-Pass Review Architecture
  • A bigger context window is a distractor here - the problem is attention quality, not capacity. The model can hold more text but still spreads attention unevenly; only focused per-file passes fix it.
  • Run verification passes where the model self-reports confidence alongside each finding, to enable calibrated review routing. Calibrate thresholds against labelled validation sets (known answers) - raw, uncalibrated confidence is unreliable for automated routing.
  • A production review architecture chains all of it together: generation → per-file review → integration review → confidence routing → calibration loop - more expensive than single-pass review, worth it for CI/CD, financial extraction, and compliance work.→ See: Diagram, Production Review Architecture
