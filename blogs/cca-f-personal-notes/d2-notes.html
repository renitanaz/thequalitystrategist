Topics Mind Map

1Topic Keywords

2.1 · Interface Design

Tool description
The primary mechanism an LLM uses for tool selection. Minimal descriptions cause unreliable selection among similar tools.
Misrouting
Caused by ambiguous or overlapping descriptions - e.g. two tools whose descriptions read almost identically.
Keyword-sensitive instructions
Wording in the system prompt that can create unintended tool associations, even overriding a well-written tool description.

2.2 · Structured Errors

isError flag
The MCP pattern for communicating a tool failure back to the agent.
Error categories
Transient (timeout/unavailable), validation (bad input), business (policy violation), permission - each needs a different agent response.
isRetryable
Boolean on structured error metadata telling the agent whether trying again could possibly succeed.
Access failure vs. empty result
An access failure needs a retry decision. A valid empty result means the query succeeded and simply found nothing - not the same thing.

2.3 · Distribution & Choice

Tool-count degradation
The named number: 18 tools instead of 4–5 measurably degrades tool-selection reliability by increasing decision complexity.
Scoped tool access
Give an agent only the tools its role needs, with limited cross-role tools reserved for specific high-frequency needs.
tool_choice
Three modes: "auto" (model may or may not call a tool), "any" (must call some tool, model picks which), forced ({"type":"tool","name":"..."}, must call this exact one).

2.4 · MCP Servers

.mcp.json
Project-level MCP server config, shared team tooling, supports environment-variable expansion (e.g. ${GITHUB_TOKEN}) so secrets aren't committed.
~/.claude.json
User-level MCP server config - personal or experimental servers, not shared with the team.
MCP tools vs. MCP resources
Tools perform actions. Resources expose content catalogs (issue summaries, doc hierarchies, DB schemas) so the agent doesn't need exploratory tool calls just to see what's available.
Simultaneous server discovery
Tools from every configured MCP server are discovered at connection time and are all available to the agent at once.

2.5 · Built-in Tools

Grep
Built-in tool for content search - patterns like function names, error messages, import statements inside file contents.
Glob
Built-in tool for file path pattern matching - finding files by name/extension pattern, not by content.
Edit vs. Read+Write
Edit needs a unique text match to apply a targeted change. When that match isn't unique, the reliable fallback is Read the full file, then Write it back modified.

2Main Pointers
Task Statement2.1
Tool interface design

Knowledge:

  • Descriptions are the primary tool-selection signal: minimal ones cause unreliable selection between similar tools.
  • Good descriptions include input formats, example queries, edge cases, and boundary explanations.
  • Ambiguous/overlapping descriptions cause misrouting.
  • System-prompt wording can create unintended tool associations that override a good description.

Skills:

  • Write descriptions that clearly differentiate purpose, expected inputs/outputs, and when to use this tool versus a similar alternative.
  • Rename a tool and rewrite its description to remove functional overlap with another (e.g. a vague content-analysis tool renamed and re-described for one specific input type).
  • Split an overly generic tool into purpose-specific tools with defined input/output contracts, rather than one tool trying to do three jobs.
  • Review the system prompt itself for keyword-sensitive wording that might be silently overriding otherwise well-written tool descriptions.
Task Statement2.2
Structured error responses

Knowledge:

  • MCP's isError flag communicates tool failure.
  • Four error types matter: transient, validation, business, permission.
  • A generic "Operation failed" message prevents appropriate recovery.
  • Structured metadata (retryable vs. not) prevents wasted retry attempts.

Skills:

  • Return structured error metadata: errorCategory (transient/validation/permission), isRetryable boolean, human-readable description.
  • Include retriable: false plus a customer-friendly explanation for business-rule violations, so the agent can communicate appropriately rather than retry blindly.
  • Implement local error recovery inside a subagent for transient failures; only propagate to the coordinator errors that couldn't be resolved locally, along with partial results and what was attempted.
  • Distinguish an access failure (needs a retry decision) from a valid empty result (a successful query that simply found no matches) - conflating the two is a named failure mode.

Task Statement2.3
Tool distribution & tool_choice

Knowledge:

  • Too many tools on one agent (the guide's own example: 18 instead of 4–5) degrades tool-selection reliability by increasing decision complexity.
  • Agents given tools outside their specialization tend to misuse them (e.g. a synthesis-only agent attempting web searches).
  • Scoped tool access = give each agent only what its role needs, plus limited cross-role tools for high-frequency needs.
  • tool_choice has three modes: "auto", "any", forced selection.

Skills:

  • Restrict each subagent's tool set to what its role actually requires, preventing cross-specialization misuse.
  • Replace an overly generic tool with a constrained alternative (e.g. a raw URL-fetch tool replaced by one that validates the URL is actually a document).
  • Provide a scoped cross-role tool for a high-frequency need (e.g. a narrow fact-check tool for an agent that mostly doesn't need broad access), while complex cases still route through the coordinator.
  • Use forced tool_choice to guarantee a specific tool runs first (e.g. a metadata-extraction step before enrichment steps), processing later steps in follow-up turns.
  • Use tool_choice: "any" to guarantee the model calls some tool instead of returning conversational text.
Task Statement2.4
MCP server integration

Knowledge:

  • MCP server scoping: project-level .mcp.json for shared team tooling vs. user-level ~/.claude.json for personal/experimental servers.
  • Environment-variable expansion (e.g. ${GITHUB_TOKEN}) in .mcp.json keeps credentials out of committed files.
  • Tools from every configured MCP server are discovered at connection time and are all simultaneously available.
  • MCP resources expose content catalogs to cut down on exploratory tool calls.

Skills:

  • Configure shared MCP servers in project-scoped .mcp.json with environment-variable expansion for auth tokens.
  • Configure personal/experimental MCP servers in user-scoped ~/.claude.json.
  • Enhance MCP tool descriptions in detail enough that the agent doesn't default to a weaker built-in tool (like Grep) over a more capable MCP tool that could do the job better.
  • Prefer an existing community MCP server for a standard integration (e.g. a common SaaS tool) over building custom - reserve custom servers for genuinely team-specific workflows.
  • Expose a content catalog as an MCP resource so the agent has visibility into available data without needing exploratory tool calls just to find out what exists.

→ See: Diagram, MCP Scoping

Task Statement2.5
Built-in tools

Knowledge:

  • Grep = content search (function names, error messages, import statements inside files).
  • Glob = file path pattern matching.
  • Read/Write = full-file operations. Edit = targeted modification via unique text matching.
  • When Edit's match isn't unique, Read + Write is the reliable fallback.

Skills:

  • Select Grep to search code content across a codebase - e.g. finding every caller of a function, locating a specific error message.
  • Select Glob to find files by naming pattern - e.g. all files matching a test-file extension pattern.
  • Use Read to load full contents, then Write, when Edit can't find a unique anchor to target.
  • Build codebase understanding incrementally: Grep to find entry points first, then Read to follow imports and trace flows - rather than reading every file upfront.
  • Trace a function's usage across wrapper modules by first identifying all its exported names, then searching for each name across the codebase.

Summary, one line per task statement:
  • 2.1 The description is the routing signal - vague or overlapping descriptions cause misrouting, not model failure.
  • 2.2 Four error categories, each demanding a different agent response; never conflate an access failure with a valid empty result.
  • 2.3 Fewer tools per agent = more reliable selection (18 vs. 4–5 is the number to remember); tool_choice auto/any/forced controls how much freedom the model has.
  • 2.4 .mcp.json is shared/project, ~/.claude.json is personal; resources are for content, tools are for actions.

4Active Recall
What is the single biggest factor driving whether an LLM picks the right tool?
The tool's description - it's the primary mechanism the model uses for tool selection. Minimal descriptions cause unreliable selection among similar tools.
Besides the description text itself, what else can silently affect tool selection?
The system prompt's wording. Keyword-sensitive instructions in the system prompt can create unintended tool associations that override an otherwise well-written tool description.
Name the four MCP error categories and which ones are retryable.
Transient (retryable), validation (not retryable - fix the input), business/policy (not retryable - explain or escalate), permission (not retryable - don't reveal restricted data).
Why is "the query returned zero results" not the same thing as "the query failed"?
A valid empty result means the tool worked and genuinely found nothing - it's a real answer. An access failure means the system couldn't be reached at all and needs a retry decision. Treating an empty result as a failure (or vice versa) is a named reliability mistake.
What specific number does the guide use to illustrate tool-count degradation, and why does it happen?
18 tools instead of 4–5. More tools means more decision complexity for the model at selection time, which measurably worsens reliability.
Explain all three tool_choice modes.
"auto": model may return text instead of calling a tool. "any": model must call a tool but picks which one. Forced ({"type":"tool","name":"..."}): model must call that exact named tool.
Where does a shared team MCP server get configured, versus a personal experimental one?
Shared/team: project-scoped .mcp.json (supports env-var expansion like ${GITHUB_TOKEN} so secrets aren't committed). Personal/experimental: user-scoped ~/.claude.json.
What's the functional difference between an MCP tool and an MCP resource?
A tool performs an action the agent requests. A resource exposes a content catalog (e.g. issue summaries, documentation hierarchies, database schemas) so the agent has visibility into what's available without spending tool calls just to explore.
When you configure multiple MCP servers at once, how does the agent see their tools?
Tools from every configured server are discovered at connection time and are all simultaneously available - not selectively loaded per-request.
Grep vs. Glob - what does each actually search?
Grep searches file content (patterns like function names, error messages, import statements). Glob matches file paths by naming pattern - it doesn't look inside files at all.
Edit just failed because the anchor text wasn't unique. What's the correct fallback?
Read the full file, then Write it back with the modification applied - the reliable fallback when Edit can't find a unique text match to target.
What's the recommended incremental strategy for understanding an unfamiliar codebase with these tools?
Start with Grep to find entry points, then use Read to follow imports and trace flows - rather than reading every file upfront.

5Official Sample Question (D2)
Q2. (Scenario 1, Customer Support) Logs show the agent frequently calls one tool when it should call another (e.g. asking about an order routes to the customer-lookup tool instead of the order-lookup tool). Both tools have minimal descriptions and accept similar identifier formats. Most effective first step?
A) Add 5–8 few-shot examples to the system prompt showing correct routing.
B) Expand each tool's description to include input formats, example queries, edge cases, and boundaries versus the other tool.
C) Add a routing layer that pre-selects the tool from keyword/identifier patterns before the model runs.
D) Consolidate both tools into one that internally determines which backend to query.
Show answer
B. Descriptions are the primary tool-selection mechanism - minimal descriptions are the root cause here, so fixing them is the lowest-effort, highest-leverage first step. A adds token overhead without touching the root cause. C bypasses the model's own language understanding and is over-engineered as a "first step." D is a legitimate architectural option but requires more effort than the situation calls for yet.
