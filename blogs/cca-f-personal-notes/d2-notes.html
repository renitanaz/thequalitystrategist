Topics Mind Map

1Topic Keywords
2.1 · Interface Design
5-element description
Purpose, inputs/outputs, example queries it handles well, edge cases, and boundaries vs. a similar tool - the full checklist for a production-grade description.
When Description Is a Fix
Few-shot examples (token overhead, doesn't touch the root cause), a routing classifier (over-engineered as a first step), and tool consolidation (a legitimate long-term move, but not the first one) are all plausible-looking wrong answers when misrouting comes from minimal descriptions - fixing the descriptions is correct there.
When Descriptions Stop Being the Fix
Once the tool count itself is the problem (past roughly 4–5 on one agent), rewriting descriptions won't help - that's a 2.3 redistribution problem, not a 2.1 wording problem.
Misrouting Problem
  • Issue - ambiguous or overlapping descriptions cause the model to route to the wrong tool, e.g. two tools whose descriptions read almost identically.
  • Fix - rename or re-describe the tools to remove the overlap.
Tool Splitting
  • Issue - one tool doing too many different jobs ends up with a vague description, so the model hesitates or misuses it.
  • Fix - split it into purpose-specific tools, each with a narrow job and a clearly defined input/output contract.
Tool Renaming
  • Issue - a tool's name and description overlap with another's closely enough that the model can't tell which one to call, e.g. a generic analyze_content that's really just extracting web results.
  • Fix - rename and re-describe the tool to reflect exactly what it does, removing the overlapping language.
System Prompt Override
  • Issue - wording in the system prompt can create unintended tool associations, silently overriding an otherwise well-written tool description.
  • Fix - review the system prompt for keyword-sensitive phrasing and reword whatever is biasing tool selection.
2.2 · Structured Errors
isError / isRetryable
  • isError - the MCP pattern for communicating a tool failure back to the agent.
  • isRetryable - a boolean on that error's metadata telling the agent whether trying again could possibly succeed.
Four Error Categories
  • Transient Errors - timeouts, service unavailability, rate limits. isRetryable: true
  • Validation Errors - invalid input, missing req fields, out-of-range values. isRetryable: false
  • Business Errors - policy violations, limits, business rule conflicts. isRetryable: false
  • Permission Errors - access denied, authorisation failures. isRetryable: false
Access failure vs. empty result
An access failure needs a retry decision. A valid empty result means the query succeeded and simply found nothing - not the same thing.
Two named anti-patterns
Silently suppressing an error as if it were a successful empty result, and terminating an entire workflow over one recoverable failure - both are explicit failure modes to avoid.
2.3 · Distribution & Choice
Tool-count degradation
The named number: 18 tools instead of 4–5 measurably degrades tool-selection reliability by increasing decision complexity.
Scoped tool access
Give an agent only the tools its role needs, with limited cross-role tools reserved for specific high-frequency needs.
tool_choice
Three modes: "auto" (model may or may not call a tool), "any" (must call some tool, model picks which), forced ({"type":"tool","name":"..."}, must call this exact one).
Tool consolidation
Merge near-duplicate tools that are variations on one job - e.g. 19 near-identical transform tools collapsed into one transform_data with an enum parameter. Distinct from splitting by role, and pulls in the opposite direction from "constrain."
Distribution decision framework
Sharpen descriptions (few tools, a couple read alike) vs. split by role (different jobs bundled on one agent) vs. consolidate (many variations of one job) vs. constrain (a tool can do more than the agent should be allowed to).
Scoped cross-role tool, by the numbers
A narrow shared tool for a high-frequency need (e.g. verify_fact) handled ~85% of simple lookups directly and cut latency ~40% vs. always routing through the coordinator.
Server boundaries are invisible to the model
Splitting an overloaded toolset across a second MCP server does not fix tool-count degradation - the client flattens every connected server's tools into one list before the model ever sees them.
2.4 · MCP Servers
.mcp.json
Project-level MCP server config, shared team tooling, supports environment-variable expansion (e.g. ${GITHUB_TOKEN}) so secrets aren't committed.
~/.claude.json
User-level MCP server config - personal or experimental servers, not shared with the team.
MCP tools vs. MCP resources
Tools perform actions. Resources expose content catalogs (issue summaries, doc hierarchies, DB schemas) so the agent doesn't need exploratory tool calls just to see what's available.
Simultaneous server discovery
Tools from every configured MCP server are discovered at connection time and are all available to the agent at once.
2.5 · Built-in Tools
Grep
Built-in tool for content search - patterns like function names, error messages, import statements inside file contents.
Glob
Built-in tool for file path pattern matching - finding files by name/extension pattern, not by content.
Edit vs. Read+Write
Edit needs a unique text match to apply a targeted change. When that match isn't unique, widen the anchor with more surrounding context, or use replace_all: true if every occurrence should change the same way - both stay on Edit and cost almost nothing. Escalate to Read + Write only when neither option can disambiguate the target.
The six built-in tools
Read, Write, Edit, Bash, Grep, Glob - each tuned to one distinct job rather than a single general-purpose file tool.

Validation (bad input)NoFix the input - retrying identical input won't help
Business (policy violation)NoExplain to the user / escalate, don't retry
PermissionNoDon't retry, don't reveal restricted data, escalate if needed
Valid empty result (not an error)n/aQuery succeeded, no match - treat as a real answer, not a failure
How this diagram fits together

The "retryable" column is the whole point of categorizing errors at all.

  • Transient - worth retrying; the failure was circumstantial, not caused by the input.
  • Validation, business, permission - not worth retrying; each just burns another call on input that was never going to succeed.
  • Valid empty result (fifth row) - heads off a common bug: this isn't an error at all, so it shouldn't be routed through this table in the first place.

Diagram: A Real Error Response, Before and After

How this diagram fits together

Same failure, two representations.

Before - just an isError flag and a message, which tells the agent something went wrong but nothing about what to do next.

After - adds exactly two fields, errorCategory and isRetryable, and that's enough for the agent to make a retry decision without guessing. Everything else about the response can stay the same.

Diagram: Structured Error Flow

How this diagram fits together

The fork right after isError: true is the one to internalize:

  • Transient - retry locally, inside the subagent, before anyone else finds out it happened.
  • Validation / business / permission - no retry, straight to an explanation instead.

Only what's left unresolved after that - a transient error that kept failing, or a non-retryable one needing escalation - actually reaches the coordinator, and it arrives with partial results and a record of what was attempted, not just a bare failure.

SymptomFixExample
Few tools, a couple read almost alikeSharpen descriptions (2.1)get_customer vs. lookup_order - clarify purpose, inputs, boundaries

How this diagram fits together

Four different-looking symptoms, four different fixes - the exam tests whether you can tell them apart, especially the last two, which pull in opposite directions.

  • Sharpen descriptions - the fix stays in 2.1 as long as the tool count itself isn't the problem.
  • Split by role - the tools are fine individually; the agent just has too many jobs' worth of them at once.
  • Consolidate - the opposite shape: many tools doing trivial variations of the same job, collapsed into one tool with a parameter.
  • Constrain - not a tool-count problem at all; a single tool is simply capable of more than it should be, so it gets replaced with a narrower one.

One trap the guide calls out directly: moving an overloaded toolset onto a second MCP server does not fix any of this. Server boundaries are invisible to the model - the client flattens tools from every connected server into one combined list before the model sees them, so the effective tool count on the agent doesn't change.

How this diagram fits together

Grep vs. Glob split on content vs. path for a reason - reaching for Glob to search inside files (or Grep to find files by name) either returns nothing or returns noise.

Edit's row is the one the exam tests hardest. The moment an anchor isn't unique, the correct next move is still on Edit: widen the anchor with more context, or use replace_all: true when every match should change the same way. Jumping straight to Read + Write the moment Edit reports a non-unique match is a common exam trap - it's the last resort, not the next step.

Deprecation scenario (a recurring worked example): to retire a function safely, Grep for its callers, Glob for their sibling test files, then Grep again inside any wrapper module that re-exports it - incremental exploration beats reading everything upfront.

③ 2.3 · Tool distribution & tool_choice
What specific number illustrates tool-count degradation, and why does it happen?
Explain all three tool_choice modes?
Recap
  • Too many tools on one agent (the guide's own example: 18 instead of 4–5) degrades tool-selection reliability - agents given tools outside their specialization tend to misuse them.
  • Scoped tool access: each agent gets only what its role needs, plus a narrow cross-role tool for high-frequency needs - complex cases still route through the coordinator.
  • tool_choice: "auto" (may skip a tool), "any" (must call something), forced (guarantees a specific tool runs first, e.g. metadata extraction before enrichment).
  • Replace an overly generic tool with a constrained alternative (e.g. a raw URL-fetch tool replaced by one that validates the URL is actually a document).
  • Tool consolidation is a distinct fourth move: many near-duplicate tools doing variations of one job (19 transform tools) collapse into one parameterized tool - different from splitting by role.→ See: Decision Table, Tool Distribution & Consolidation
  • A scoped cross-role tool isn't just theoretical: the guide's verify_fact example handled ~85% of simple lookups directly and cut latency ~40%.
  • Moving an overloaded toolset onto a second MCP server doesn't fix the tool-count problem - the client flattens all connected servers' tools into one list before the model sees them.
④ 2.4 · MCP server integration
Shared team MCP server vs. a personal experimental one - configured where?
Functional difference between an MCP tool and an MCP resource?
Multiple MCP servers configured at once - how does the agent see their tools?
Recap
  • MCP server scoping: project-level .mcp.json for shared team tooling, with environment-variable expansion (e.g. ${GITHUB_TOKEN}) to keep credentials out of committed files, vs. user-level ~/.claude.json for personal/experimental servers.→ See: Diagram, MCP Scoping

  • MCP resources expose content catalogs so the agent has visibility into available data without exploratory tool calls.

  • Prefer an existing community MCP server over building custom - reserve custom servers for genuinely team-specific workflows.
⑤ 2.5 · Built-in tools
Grep vs. Glob - what does each actually search?
Edit just failed because the anchor text wasn't unique - what's the correct fallback?
Recommended incremental strategy for understanding an unfamiliar codebase?
Recap
  • Grep = content search - function names, error messages, import statements, callers.→ See: Decision Table, Built-in Tools
  • Glob = file path pattern matching - e.g. all files matching a test-file extension.
  • Edit needs a unique text match for a targeted change; when that match isn't unique, first widen the anchor with more context or use replace_all: true - both stay on Edit. Read the full file then Write it back is the last resort, only when neither can disambiguate the target.

4Official Sample Question (D2)
Q2. (Scenario 1, Customer Support) Logs show the agent frequently calls one tool when it should call another (e.g. asking about an order routes to the customer-lookup tool instead of the order-lookup tool). Both tools have minimal descriptions and accept similar identifier formats. Most effective first step?
A) Add 5–8 few-shot examples to the system prompt showing correct routing.
B) Expand each tool's description to include input formats, example queries, edge cases, and boundaries versus the other tool.
C) Add a routing layer that pre-selects the tool from keyword/identifier patterns before the model runs.
D) Consolidate both tools into one that internally determines which backend to query.
Show answer
B. Descriptions are the primary tool-selection mechanism - minimal descriptions are the root cause here, so fixing them is the lowest-effort, highest-leverage first step. A adds token overhead without touching the root cause. C bypasses the model's own language understanding and is over-engineered as a "first step." D is a legitimate architectural option but requires more effort than the situation calls for yet.
