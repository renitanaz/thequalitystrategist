1. Claude Ecosystem Map

  • Claude App — hosted product (browser/desktop/mobile). Not a production runtime: you don't own app state, orchestration, tool execution, validation, or deployment. Mostly a reference point, not an architecture layer.
  • Claude API — the model interface inside your own application. Your backend sends messages, system instructions, parameters, tool definitions; Claude returns text, structured data, or a tool-use request. The backend still owns conversation state, auth, permission checks, tool execution, output validation, retries, observability, business-rule enforcement.
  • Claude Code — a developer workflow tool inside a codebase (inspect, edit, test, refactor, document, review). Belongs to development workflow, not application runtime.
  • Agent SDK — structures multi-step orchestration (agents, tools, hooks, handoffs, execution flow) for production workflows that are more than one request/response.
  • MCP (Model Context Protocol) — standard way to expose tools and context to Claude-compatible clients. Not just tool calling — an integration boundary. A good MCP tool needs a clear name, description, typed input schema, structured output, useful error handling, appropriate permissions.
  • The exam-relevant question across all of these isn't "how do I prompt Claude" but which layer should guarantee a given behavior — e.g. a rule like "verify identity before this action" should be a programmatic prerequisite gate in the backend, not just a system-prompt sentence.

2. How Claude Generates a Response not exam scope

  • Text → tokens (word/subword/punctuation fragments) → embeddings (numeric vectors representing meaning) → contextualization (embeddings adjusted based on surrounding tokens, since meaning depends on context) → next-token prediction (repeated one token at a time until the response is complete).
  • The model doesn't have hidden memory of your data, your customers, or prior conversations unless your application sends that context again on every request.
  • Core mental model: Claude is a context-in, next-token-out prediction engine. Prompts, conversation history, documents, tool results, system instructions are all forms of "context."

The official exam guide's Appendix explicitly excludes "Claude's internal architecture, training process, or model weights" and "embedding models... implementation details." This section is background/orientation only, not scored.

3. API Basics: Client, Messages, stop_reason

  • Anthropic provides official SDKs for multiple languages (Python, TypeScript, Java, Go, Ruby, C#, PHP, CLI). Same core concepts across all: create a client, send messages, set parameters, read the response.
  • Store the API key outside source code (environment variable / secrets manager, not hardcoded, not committed to version control).
  • client.messages.create core parameters: model, max_tokens (a ceiling, not a target — Claude stops early if it naturally finishes first), messages (structured list, each with a role).
  • stop_reason values to know: end_turn (finished naturally — safe to show the user), max_tokens (cut off by the token limit — response may be incomplete), tool_use (Claude wants your application to run a tool before continuing).

4. Multi-Turn Conversations

  • Each API request is isolated by default. Claude does not automatically remember previous requests — your application must resend the conversation history explicitly for Claude to have that context.
  • A conversation is just a growing messages list: alternating user and assistant role entries. The application owns and stores this list (in production: a database or session store, not just an in-memory variable).
  • Common mistake: sending only the newest user message on a follow-up turn, omitting the earlier turns — Claude then reasons with no memory of what was already said.
  • Practical limits: very long conversations increase cost, latency, and complexity. Production systems typically don't keep unlimited raw history — they summarize older turns or extract structured facts into separate persistent state (see Context Management, below).

5. System Prompts vs. Message History

  • The messages list answers "what has been said so far." The system prompt answers "how should the assistant behave" — role, tone, durable behavior rules. It has its own place in the request, distinct from the message history.
  • A system prompt is guidance, not a guarantee. If a rule is financially or otherwise critical (e.g. "verify identity before refunding"), the backend should still enforce it programmatically — the prompt is not a substitute for a real guarantee (same principle as D1's hooks/prerequisite-gates content).

6. Model Selection, Temperature, Stop Sequences partly not exam scope

  • Model selection: choose based on task, not by default reaching for the most powerful model. Strong general-purpose model for typical reasoning conversations; smaller/faster model for simple high-volume tasks (classification, routing, short extraction); most capable reasoning model for complex/high-risk tasks (policy exceptions, multi-step analysis, advanced orchestration). Production systems often mix models by role.
  • Temperature: controls how strongly the model follows token probabilities. Near 0 = deterministic/predictable (favor for classification, extraction, policy-driven decisions, consistent support-style replies). Near 1 = more variety (favor for brainstorming/creative tasks). Not "good vs. bad" — match to the task.
  • Stop sequences: a custom string that halts generation when produced. Useful for separating a customer-facing section from internal notes, or stopping at a known boundary. Not a substitute for validation — doesn't guarantee the output before the marker is correct.

The official guide's Appendix lists "Performance benchmarking or model comparison metrics" as out of scope, and doesn't name temperature/stop-sequences as tested skills. Keep as general API literacy, not something to expect a scored question on.

7. Prompt Evaluation Workflow

  • Prompt engineering (writing a better prompt) is different from prompt evaluation (measuring how well it actually performs across realistic inputs, not just the examples you happened to test manually).
  • Basic eval loop: draft a prompt → build a labeled test-case dataset (input + expected output) → run every case through the prompt → grade actual vs. expected → revise the prompt → re-run the same eval to see whether it actually improved.
  • A prompt that "looks good" on a few manual tries is not evidence of reliability — real users send inputs you didn't anticipate.

8. Grading Model Outputs

  • Code-based grading: deterministic checks — is it valid JSON, are required fields present, is a value inside an allowed enum list. Fast, reliable, but only works for answers checkable by strict rules; can't judge quality/tone/policy-following.
  • Model-based grading: a second Claude call evaluates the first Claude call's output against explicit written criteria (not "grade whether it's good" — specific criteria like tone, policy compliance, avoiding unsupported claims). Good for helpfulness, politeness, instruction-following, safety/escalation behavior — but the grader is still a model and can be inconsistent if criteria are vague.
  • Human grading: most accurate, slowest/most expensive — used sparingly, often to spot-check or calibrate the automated graders.
  • Production pattern: combine code-based grading (structure/schema/syntax) with model-based grading (quality/judgment/tone), and always inspect individual failures, not just the average score — an improved average can hide a regression in one category.

9. Clear/Direct Prompting & XML Structure

  • Vague instructions ("help this customer," "be conservative") leave too many decisions open. A strong prompt defines role, task, explicit rules, and a length/format constraint.
  • Anatomy of a production prompt: task, context, rules (always/never), the actual input, output format, and (optionally) success criteria — kept as separate labeled sections rather than one dense paragraph.
  • XML tags are a plain, low-tech way to separate those sections (task / rules / input / output format) so both the model and future developers can tell instruction from data from expected output. Useful as prompts grow to include business rules, examples, and formatting requirements.
  • Prompting improves behavior; it does not replace backend enforcement of a real business rule (repeats the same theme as system prompts and D1 hooks).

10. RAG Overview not exam scope

  • RAG = retrieve relevant context first, then generate an answer using only that retrieved context, instead of stuffing an entire knowledge base into the prompt (expensive, slow, sometimes exceeds context limits, dilutes focus even when it fits).
  • Flow: chunk documents → index them → on a query, retrieve the most relevant chunks → pass just those chunks + the question to the model.
  • Search types: keyword search (exact terms/IDs, fast, strong for precise identifiers), semantic search (embeddings/vector database, matches meaning even with different wording), hybrid (combines both — often the strongest real-world default).
  • RAG quality depends on retrieval quality, not just generation quality — wrong or incomplete retrieved context produces a confident but wrong answer.

The official guide's Appendix explicitly excludes "Embedding models or vector database implementation details." RAG itself is not named in the guide's in-scope topics. Background only.

11. Explicit Criteria & Few-Shot Examples D4

  • Vague judgment words ("be conservative," "only escalate serious cases") force the model to guess your boundary. Replace them with an explicit, enumerated list of triggers/criteria.
  • When one input could match more than one category, state an explicit priority order so classification is deterministic rather than arbitrary.
  • Few-shot examples do two jobs at once: they show the decision boundary (what counts vs. what doesn't, including deliberately showing a near-miss that should not trigger the category), and they lock in the exact output format/field names, preventing "format drift" where the model's answer is reasonable but structurally different from what your code expects.
  • Examples should show both sides of a boundary (what to flag and what not to flag) so the model generalizes the pattern rather than memorizing a fixed list of cases.
  • Prompting handles judgment; backend validation still checks the mechanical constraints (value is one of N allowed categories, output is valid JSON, any critical/irreversible action still runs through code, not model say-so).

12. Tool Schemas, tool_choice, First Tool Use D1D4

  • A tool schema is a contract: tool name, description (when to use it), and an input schema defining required argument shape/types. Claude must satisfy that contract to request the tool.
  • When Claude wants a tool, the response's stop_reason is tool_use and the content includes a tool_use block — a request, not an executed action. The backend executes the real function and controls what actually happens (permissions, business rules).
  • Weak tool schemas are vague about scope; strong ones are narrow, specifically named, and clearly bounded (mirrors D2's 2.1 task statement almost exactly).
  • Required-but-nullable fields matter: if information may be legitimately absent, the model should be able to return null rather than being forced to invent a value.
  • Three tool_choice modes (same as D4 4.3 / D2 2.3 in the official guide): auto (may or may not use a tool), any (must use a tool, model picks which), forced (must use one specific named tool).

13. Structured Output via tool_use D4

  • Asking the model to "just return JSON" as plain text is fragile — extra text, missing commas, wrong-shaped fields are all possible, and the app's parser can break.
  • Defining a tool with a strict input schema and using (often forced) tool_choice is the reliable path: the model's structured output must conform to the schema, largely eliminating syntax-level formatting errors.
  • Schema design patterns: required-but-nullable fields (field must exist in the response, but its value may be null when the source doesn't contain it); enum fields for categorization to avoid free-text label drift; an explicit "unclear" enum value for genuinely ambiguous input; an "other" + free-text detail field for cases outside the fixed category list.
  • A strict schema solves the structural problem (right shape, valid enum, right types) but not the semantic one — the model can still put a correctly-typed but wrong value in a field. Structure and judgment are different problems needing different fixes (schema vs. criteria/examples/evals).
  • Normalization rules belong in the prompt alongside the schema (e.g. "if a field is missing, return null, don't invent one"; "use 'unclear' when ambiguous"; "use 'other' only when nothing else fits").

14. Validation, Retry, Confidence, Human Review D4

  • Schema validation: checks shape — required fields present, correct types, enum values from the allowed list. Semantic validation: checks whether the (structurally valid) values actually make sense given the source input.
  • Retry rule: retry with specific feedback (the failed extraction + the exact validation error) when the mistake is fixable — wrong enum value, wrong field placement, structural mismatch. Do not retry to force information that simply isn't present in the source — the correct behavior there is returning null and flagging the field as missing, not looping until the model fabricates something plausible.
  • Contradiction handling: when a source contains conflicting signals, don't force a single answer — mark the field unclear/ambiguous, set a conflict_detected boolean, and record why.
  • Numeric cross-checks: extract both a stated value and a separately-calculated value (e.g. stated total vs. calculated total from line items); flag disagreement for review rather than silently trusting one.
  • Confidence should typically be field-level, not one global score — some fields in the same extraction can be obvious while others are genuinely uncertain. Confidence must be calibrated against a labeled validation set; a model can be confidently wrong, so raw self-reported confidence isn't trustworthy on its own.
  • Stratified sampling: review examples across high/medium/low confidence bands, not only the low-confidence ones — high confidence doesn't guarantee correctness, and sampling across bands catches systematic errors that would otherwise hide inside "confident" outputs.
  • Accuracy segmentation: measure accuracy by document type and by field, not just one aggregate number — a high overall accuracy can mask a much weaker sub-case.
  • Human review routing triggers: low confidence, detected conflict, missing required information, a request that looks like a policy exception, or anything with outsized financial/business impact.

15. Batch Processing & Multi-Pass Review D4

  • Batch API fits large, latency-tolerant workloads (audits, nightly analysis) — not workloads where a user is actively waiting for an answer. Roughly 50% cost savings, up to a 24-hour processing window, no guaranteed latency SLA.
  • No mid-request tool-calling loop inside a single batch request — if the task needs live multi-step tool use during reasoning, gather the needed context up front before submitting, rather than expecting an interactive loop.
  • Use a stable custom_id per submitted item to correlate each response back to its original input, since batch responses aren't guaranteed to return in submission order.
  • Refine the prompt against a small sample before scaling to a full large batch — avoids paying to run a flawed prompt across thousands of items.
  • On partial failure, resubmit only the failed items (identified by their custom_id) with a fix, not the entire batch.
  • Self-review limitation: a model reviewing its own just-generated output retains the reasoning context that produced it, making it less likely to question its own decisions. Independent review (a separate call/session, different or no prior reasoning context) catches more subtle issues.
  • Multi-pass review pattern: local per-unit analysis pass (e.g. per file) first, focused and consistent in depth, then a separate integration pass looking across those local findings for conflicts, repeated issues, or cross-cutting problems — avoids the attention dilution and internal contradictions that a single massive pass over everything tends to produce.

16. Tool-Use Loop Mechanics D1

  • Claude never executes a tool itself — it decides a tool is needed and returns a structured tool-use request; the application executes it and returns the result.
  • A tool_use block carries three things: the tool name, the input arguments, and a tool_use_id. That ID is what connects the eventual tool_result back to the specific request it answers — necessary because more than one tool call can be in flight.
  • The tool result is appended to conversation history as a message containing a tool_result block carrying that same ID, and the updated history is sent back to Claude for the next step.
  • Loop shape: send conversation → if stop_reason == "tool_use", execute the requested tool(s) → append result(s) → call again → repeat until stop_reason == "end_turn". Matches the official guide's 1.1 loop exactly; a max-iteration cap is a safety backstop only, never the primary stopping logic.
  • A hard-coded fixed call sequence (always call tool A, then B, then C) is brittle for messy, multi-issue real input; a tool-enabled agent chooses the next reasonable step from the current conversation state instead — but the application still enforces which requested tool calls are actually allowed to execute (e.g. rejecting an unverified-customer refund attempt even if the model requested it).

17. Tool Naming, Descriptions, Structured Errors D2

  • A specific tool name that encodes its required input (e.g. a "by email" or "by ID" suffix) helps routing before the model even reads the description.
  • A strong tool description states purpose, expected input, and an explicit boundary against the nearest similar tool — not just a one-line restatement of the function name.
  • Split vs. consolidate: split tools when doing so reduces ambiguity between distinct purposes; consolidate when several tiny tools are always called together on the same input and splitting only adds overhead. No universal rule — it's a judgment call based on which failure mode (misrouting vs. unnecessary complexity) is more likely.
  • A generic error message ("something went wrong") gives the model nothing to act on. Structured error responses should distinguish: validation error (bad input shape/format, not retryable, ask for corrected input), empty result (the tool worked, there's simply no matching record — not an error at all), permission error (not retryable, don't leak restricted data), transient error (retryable, e.g. a timeout).
  • A business-rule failure (e.g. request understood, permitted, but blocked by policy) is its own case: not fixable by retry, needs a customer-appropriate explanation or an escalation path.
  • Local recovery first: handle a transient failure by retrying inside the component that hit it; only propagate upward what genuinely couldn't be resolved locally.

18. Scoped Tool Access, Built-in Tools, MCP D2

  • Giving one agent every available tool (support + inventory + marketing + reporting + risky admin actions) is both a security problem and a reliability problem — more overlapping tools, more chances to pick the wrong one. Give each agent role the smallest useful set for its job; some tools can still be shared across roles when genuinely needed by more than one.
  • tool_choice in practice: auto for normal flexible conversation, any when the workflow structurally requires some tool call before continuing, forced only when the application already knows the exact next required step — overusing forced choice removes the model's ability to pick a better option if one exists.
  • Built-in tools (Claude Code style): Read inspects a file, Write creates/overwrites one, Edit makes a targeted change via a unique text match, Bash runs shell commands, Grep searches file content, Glob matches file paths. If Edit can't find a unique anchor, the safe fallback is Read the file, then Write the modified version back.
  • MCP tools vs. resources: tools perform actions (a lookup, a state change); resources are content the model can read as reference context (policy documents, catalogs). Business action endpoints should be MCP tools; static/reference material fits better as an MCP resource.
  • MCP server config scoping: project-level (shared, version-controlled, e.g. .mcp.json) vs. user-level (personal/local setup, e.g. ~/.claude.json). Secrets belong in environment variables referenced from the config, never hardcoded into it.
  • Prefer an existing community MCP server for a standard integration; reserve building a custom MCP server for something genuinely business/domain-specific, since custom servers carry their own permission, schema, and error-handling design burden.

19. Coordinator–Subagent Architecture D1

  • Hub-and-spoke: the coordinator is the hub, receives the request, decides how to split work, dispatches to specialized subagents, receives their findings, produces one final synthesized answer. Subagents are the spokes and never talk to each other directly.
  • To spawn subagents at all, the coordinator's allowed tools must include the spawning tool (named Task in the exam guide's own wording). Without it, the coordinator can reason about delegation but cannot actually invoke anyone.
  • Each subagent should get a narrow, role-specific tool set (e.g. one subagent can only inspect data relevant to its specialty, not take an action that belongs to another specialty) — this is what actually prevents cross-specialization misuse, more than any prompt instruction could.
  • Subagents have isolated context by default — they do not automatically inherit the coordinator's conversation. A vague delegated task with no supporting facts produces a weak/uninformed subagent response; the coordinator must explicitly pass the exact facts the subagent needs (ID, prior findings, relevant excerpts) rather than relying on any implicit shared memory.
  • For larger handoffs, separate content from metadata in what's passed (source, date, confidence) so downstream synthesis can still track where each fact came from.
  • When two or more delegated tasks are independent (neither depends on the other's result), the coordinator can dispatch them in parallel by emitting multiple spawn-tool calls in one response, rather than waiting on one before starting the next.
  • All subagent output routes back through the coordinator only, which owns final routing, aggregation, and response quality — not any single subagent.
  • Decomposition-granularity warning: don't split work into subagents at too fine a grain (a separate subagent per tiny field or single lookup adds coordination overhead without benefit). Split along meaningful business/functional boundaries instead.

20. Decomposition, Hooks, Handoffs D1

  • Fixed sequential pipeline (prompt chaining): steps and order are known in advance and don't change run to run — appropriate when the process itself is predictable (e.g. a defined verification → check → decision sequence). Keeps each individual call focused rather than asking one prompt to do everything at once.
  • Dynamic decomposition: appropriate for open-ended/investigative work where the right next step depends on what was just discovered — map the situation first, then decide what to investigate, rather than assuming a fixed path up front. Same principle applies to large review tasks: local per-unit passes plus a separate integration pass, instead of one massive undifferentiated pass.
  • Prompts are guidance; when compliance must be guaranteed (not just likely), the rule belongs in a programmatic prerequisite gate in code, not in a system-prompt instruction alone — e.g. blocking a sensitive action until a required prior step has actually completed and been confirmed.
  • Hooks: a post-tool-use hook can normalize/standardize a tool's raw result before the model ever reasons over it (consistent formats mean every downstream prompt doesn't have to defensively handle multiple possible shapes). An interception hook runs before a requested tool call executes and can block it outright if it would violate a rule (e.g. an amount over a defined limit) — the model can still request the action, but the application decides whether it's actually allowed to happen, and can redirect to an escalation path instead.
  • Structured handoff protocol: a handoff (to a human, another agent, or a later workflow step) should carry enough structured facts that the receiver doesn't have to reconstruct context from scratch — the relevant identifiers, root cause, amount/impact, evidence, and a specific reason, not a vague "please review this."

21. Context Management for Long Sessions D5

  • Core rule: the conversation transcript is not your database. As a case grows (verbose tool output, prior notes, old assumptions), important exact facts can move into the middle of a long context and get missed — the "lost in the middle" effect.
  • Maintain a structured persistent facts block (IDs, dates, amounts, decisions, expectations) that survives retries, handoffs, and human review — not just readable prose summaries, which can quietly lose exact details each time they're re-summarized (progressive summarization risk).
  • Trim verbose tool output down to the fields actually needed for the current decision before it enters context, rather than passing through an entire raw record.
  • Place key summaries/findings at the beginning of an aggregated input rather than burying them after pages of supporting detail — mitigates position effects in how the model attends to long inputs.
  • For crash recovery / resumed work: each component/agent can export its state to a known location, and the coordinator loads a manifest of that state on resume rather than replaying the full history.
  • A retryable-vs-not decision (e.g. is it safe to redo an action) should be governed by explicit application state, not by whether the model happens to remember the previous step correctly.
  • Subagent output should be structured findings + metadata, not a long reasoning transcript — easier to verify, store, and pass forward accurately.

22. CLAUDE.md Configuration Hierarchy D3

  • The init-style command scans a project and generates a starting CLAUDE.md (structure, common commands, dependencies, patterns) — a starting point to be manually refined, not a finished configuration.
  • Memory levels: user-level (personal preferences, not shared, not version-controlled) vs. project-level (shared instructions every teammate should get, belongs in version control).
  • Subdirectory-level CLAUDE.md files exist for area-specific rules (e.g. rules that only apply to one API folder) — useful when all the relevant files genuinely live under one directory.
  • When one large CLAUDE.md becomes unwieldy, use import syntax to pull in separate, more focused files rather than one monolithic document.
  • Path-specific rules (a rules directory with YAML frontmatter path/glob matching) are the better choice over subdirectory CLAUDE.md files when the matching files are spread across many different folders rather than confined to one directory (e.g. test files that live next to the code they test, throughout the repo).
  • A quick-add shortcut can save a new discovered convention as memory mid-session without manually editing a file. A memory-inspection command shows exactly which memory files are actually loaded — the right first debugging step when Claude Code keeps ignoring or misapplying a convention.

23. Claude Code Session Management D3

  • A "continue most recent session in this directory" flag picks up right where you left off without needing to specify anything. A "resume" flag with no argument opens a session picker; with a session ID or a human-chosen session name, it resumes that specific one directly. Sessions can be given a readable name at start and renamed later mid-session.
  • Session transcripts are saved locally and continuously, but for anything important, rely on a meaningful session name plus a scratchpad/notes file rather than only the raw chat history.
  • Resume vs. start fresh: resume when the task is unchanged and nothing has moved underneath it — but always re-verify current state (diffs, current file contents, current test results) after resuming rather than trusting stale assumptions. Start a fresh session with a written structured summary (goal, relevant files/functions, failing tests, decisions, next step) when the old session's context became noisy (abandoned explorations, unrelated detours, long pasted logs) or when the underlying code changed — a clean summary beats a messy old transcript.
  • Compaction: reduces context usage in a long session, but summarization risks losing exact details. Before/during compaction, explicitly preserve what must stay exact: file paths, function names, failing test names, exact error text, decisions made, and the next step.
  • Scratchpad files: a persistent project file (not just chat memory) holding stable facts for a long task — supports crash recovery, handoff to someone else, and clean starts in a fresh session, functioning as a lightweight work manifest.
  • Forks: used to explore two different implementation approaches in parallel without polluting the main session — each fork investigates/returns findings (files involved, risks, tests) without editing files, then the results are compared and only the chosen approach gets implemented in the main line.
  • The same "don't paste everything, pass structured findings" principle applies to subagent/exploration output and to raw command/test output — trim to the relevant evidence (e.g. one failing test name + expected vs. actual + the relevant file) rather than an entire raw log.

24. Claude Code Workflows: Commands, Skills, Plan Mode D3

  • Project-scoped slash commands live in the repo (version-controlled, shared team-wide). User-scoped commands live in the personal home config (private, not shared).
  • Skills are for more structured on-demand workflows than a simple command, defined with a skill file and frontmatter: a description (when to invoke it), an argument hint (what input the invoker should supply), an allowed-tools restriction (e.g. read/search only, no edit, for an analysis-only skill), and a fork-context option that runs the skill in an isolated context so its (possibly verbose) exploration doesn't pollute the main conversation — the main session gets back a summary instead.
  • Personal skill variants use a different name than the project's shared skill, so a personal customization doesn't silently override or conflict with the team's version.
  • CLAUDE.md vs. skills: CLAUDE.md = always-loaded standing knowledge (coding standards, test commands, architecture rules). Skills = on-demand structured workflows invoked only when needed (a specific review type, a migration analysis).
  • Plan mode vs. direct execution: plan mode for complex, multi-file, architectural work with more than one valid approach — explore and design before committing to changes, avoiding costly rework from committing early. Direct execution for small, clear-scoped changes. A strong pattern: plan mode to investigate and choose an approach, then direct execution to implement the approved plan.
  • Explore subagent: used for verbose discovery work (tracing dependencies, mapping a codebase) so the main conversation gets a compact structured summary instead of the full raw exploration transcript.
  • Refinement techniques: concrete input/output examples beat vague prose descriptions for clarifying an expected transformation. Test-driven iteration: write the test first, then share the exact failure (expected vs. actual) to guide the next fix. The interview pattern: have Claude ask clarifying questions before implementing, in an unfamiliar or ambiguous domain, to surface assumptions early. Feedback batching: send interacting issues together in one message (since fixing one affects the other); fix genuinely independent issues sequentially.

25. Claude Code in CI/CD D3

  • A CI job can't wait on an interactive back-and-forth — run Claude Code in non-interactive/print mode so the job completes and exits automatically instead of hanging on input it will never receive.
  • For automation, request structured JSON output (optionally constrained by an explicit JSON schema) rather than plain text, so the CI script can reliably parse findings, post PR comments, or fail a build check on specific conditions.
  • Duplicate-comment problem: CI reviews can rerun (new commit, manual rerun) and re-find the same issue. Generate a stable fingerprint per finding (e.g. derived from file path + line + category + normalized message) and skip posting a finding whose fingerprint was already posted.
  • CI-invoked Claude Code still needs project context — CLAUDE.md (conventions, test commands, domain rules) plus existing tests/fixtures in context so review and generated tests are grounded in real project behavior rather than generic guesses.
  • Blocking vs. non-blocking: reserve blocking pre-merge failure for high-confidence, serious findings (security, broken tests, dangerous behavior). Lower-severity findings can post as non-blocking PR comments; broader/deeper review can run as a separate non-blocking overnight report.
  • Independent review: the same session/context that generated an implementation is a weaker reviewer of its own work (it retains the reasoning that produced it, making it less likely to question those choices). A separate, clean review invocation — reading the repo, the diff, project context, tests — without inheriting the implementation session's context, catches more.

26. Escalation, Error Propagation, Provenance D5

  • Escalation triggers should be explicit and behavioral, not sentiment-based: an explicit request for a human (honor immediately, don't force more automated investigation first), a policy that's missing/ambiguous/silent on the specific request, inability to make real progress, or an ambiguous backend match (e.g. more than one candidate record) — clarify or escalate rather than guessing via a heuristic. Being upset alone, with no other trigger, is not automatically an escalation condition.
  • Error propagation in a multi-component system: local recovery first (retry a transient failure inside the component that hit it); only propagate upward what genuinely can't be resolved locally, and propagate it with structure — failure type, what was attempted, any partial results, possible alternatives — not a bare generic status string. Distinguish an access failure (needs a retry/recovery decision) from a valid empty result (the query succeeded, there's just nothing there) — the same distinction as D2's error-category material, now applied at the coordinator level.
  • Provenance / claim-source tracking: preserve where each claim/fact came from through summarization and synthesis steps — source, and ideally a timestamp/publication date. Losing that mapping during compression is a named reliability failure, because downstream steps can no longer verify or reconcile the claim.
  • Conflicting sources: don't silently pick one value when two credible sources disagree — preserve both, annotate the conflict with attribution, and check whether a date difference explains it (a newer source may legitimately supersede an older one rather than truly "contradicting" it) before treating it as an unresolved conflict. Escalate when the decision has real financial/policy weight.
  • Match output rendering to content type in a synthesized report rather than flattening everything into one uniform format — e.g. tabular for numeric/financial comparisons, structured lists for technical findings, prose for narrative content.

27. Domain Mapping & Sample Scenario

  • D1 — agentic loop + tool calls + handoffs + subagents where useful + deterministic enforcement (hooks/gates) for anything critical.
  • D2 — tool interfaces with clear boundaries, structured errors.
  • D3 — CLAUDE.md, slash commands, skills, plan mode, direct execution, session management, CI review.
  • D4 — explicit criteria, few-shot examples, JSON schemas, validation, retry loops, structured findings.
  • D5 — preserved context, safe escalation, error propagation, provenance, uncertainty handling, human-review routing.
  • Weighting reminder: D1 is the largest single domain; D3 and D4 are also heavily represented; D2 is narrower (tools/MCP specifically); D5 has the smallest headline percentage but its reliability concepts recur inside scenario questions from other domains too.

Worked scenario from this lesson (paraphrased, no proprietary example names): a customer's refund request conflicts with policy — the base policy says the return window has passed, but a newer internal memo allows an exception for this specific situation, reviewable only by a human specialist. Correct move: don't deny outright (ignores the newer source), don't approve outright (applies an exception without authority), don't rely on a self-reported confidence score to decide (unreliable proxy for real risk) — explain the conflict, preserve both sources with attribution, summarize the case, and escalate to a human specialist. This is the D5 "preserve provenance + escalate under genuine uncertainty" pattern applied end to end.
