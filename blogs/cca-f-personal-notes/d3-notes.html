1Topic Keywords
3.1 · CLAUDE.md Hierarchy
CLAUDE.md hierarchy
  • User-level (~/.claude/CLAUDE.md) - applies only to that one user, not shared with teammates via version control.
  • Project-level (.claude/CLAUDE.md or root CLAUDE.md) - both paths are valid, the exam may present either.
  • Directory-level (subdirectory files) - applies only inside that one folder.
Concatenation, not precedence
CLAUDE.md files don't override each other - every discovered file loads into the same context, ordered broadest-to-most-specific. On a genuine contradiction, Claude may pick either rule arbitrarily.
settings.json vs. CLAUDE.md
settings.json has strict, client-enforced precedence (managed > local > project > user). CLAUDE.md has none - it's a user message the model usually follows, not a hard enforcement layer.
CLAUDE.local.md
Personal, gitignored-by-convention notes loaded alongside CLAUDE.md at the same level, appended after it. A project-scoped analog of ~/.claude/CLAUDE.md.
@ path imports
Syntax for referencing external files to keep CLAUDE.md modular - just @ followed by a path, no @import keyword. Loads eagerly, so splitting a file doesn't shrink the context Claude actually sees.
.claude/rules/
Directory for topic-specific rule files - an alternative to one monolithic CLAUDE.md.
/memory vs. /context
Current Claude Code splits diagnosis across two commands: /memory lists CLAUDE.md/CLAUDE.local.md/auto-memory locations; /context shows what actually loaded this session. Neither one loads anything.
Surviving /compact
Root CLAUDE.md comes back intact (re-read from disk). Nested subdirectory CLAUDE.md and path-scoped .claude/rules/ files don't - they reload on demand, next time a matching file is touched.
3.2 · Commands & Skills
Unified Skills system
Commands and skills merged into one system: .claude/commands/<name>.md (flat file) and .claude/skills/<name>/SKILL.md (directory) both create the same /name. A flat file dropped directly inside .claude/skills/ does not create a command.
.claude/skills/ is canonical
Adds a supporting-files directory, automatic discovery, and wins over a same-named command. .claude/commands/ still works, for backward compatibility.
Project vs. user commands
.claude/skills/ or .claude/commands/ is shared via version control; ~/.claude/skills/ or ~/.claude/commands/ is personal.
description
Not one of the exam's three named fields, but does the most work: it's what Claude reads to decide whether a skill matches your intent. Omit it and the skill only ever fires when you type /name yourself.
context: fork
Runs a skill in an isolated sub-agent context so its output doesn't pollute the main conversation.
allowed-tools
Pre-approves listed tools so they run without a permission prompt - it does not restrict which tools are available. Every other tool remains callable; use disallowed-tools for actual restriction.
Auto-invocation
Claude can invoke a skill automatically when its description matches user intent, or when a paths frontmatter field matches the file being edited - not just via explicit /name.
Skills vs. CLAUDE.md
Skills = on-demand, task-specific workflows. CLAUDE.md = always-loaded universal standards.
Skill source precedence
When the same skill name exists in more than one source, precedence runs Enterprise > Personal > Project > Plugins - an enterprise-managed skill always wins over a personal, project, or plugin-provided one with the same name.
3.3 · Path-Specific Rules
YAML frontmatter paths
Glob patterns in a .claude/rules/ file that conditionally activate the rule only for matching files.
Path-scoped rules vs. directory CLAUDE.md
Path rules win when matching files are spread across many directories (e.g. test files next to the code they test).
Path rules vs. root CLAUDE.md
Root CLAUDE.md loads for every session regardless of what's being edited. Path-scoped rules load only for matching files - more token-efficient, especially with many convention categories.
Rules vs. skills, both paths-aware
Both can auto-activate on a matching file path, but rules stay in context as always-on background guidance; skills load on-demand as a task-style workflow. "Automatic, always-on convention loading" → rules, not skills.
3.4 · Plan Mode
Plan mode
For complex tasks: large-scale changes, multiple valid approaches, architectural decisions, multi-file modifications.
Direct execution
For simple, well-scoped changes with a clear, single-file fix.
Ambiguity, not difficulty
The deciding axis isn't how hard a task is - it's how well-defined it is. A hard bug fix with a known cause and clear stack trace is still direct execution; a simple-looking feature with several valid designs across modules is still plan mode.
Hybrid: plan then execute
Plan mode to investigate and choose an approach, then direct execution to implement it - a common, testable pattern. Plan then direct, not plan or direct.
Explore subagent
Isolates verbose discovery output, returning a summary to preserve main conversation context.
3.5 · Refinement
Concrete I/O examples
The most effective way to communicate an expected transformation when prose descriptions get interpreted inconsistently.
Test-driven iteration
Write the test suite first (happy path, edge cases, performance), then iterate by sharing test failures - most effective for complex transformations with many edge cases.
Interview pattern
Have Claude ask questions first, to surface considerations the developer hasn't anticipated, before implementing - most effective in an unfamiliar domain.
Interview pattern vs. examples
Different problems, don't conflate them. Interview pattern: you don't know the domain well enough to spot every consideration. Concrete examples: you know the exact transformation, but Claude keeps interpreting your prose inconsistently.
Interacting vs. independent issues
Interacting problems → report together in one message. Independent problems → fix sequentially.
3.6 · CI/CD
-p / --print
Runs Claude Code in non-interactive mode - required in CI so the job doesn't hang waiting for input.
--output-format json
Combined with --json-schema to enforce machine-parseable structured output in CI. Schema-validated data lands in the envelope's structured_output field, not the top level.
Session context isolation
The same session that generated code is less effective reviewing its own changes than an independent review instance.
Batch API vs. real-time
~50% cheaper but no latency SLA, up to 24h. Real-time for blocking pre-merge checks; batch for overnight/weekly, non-blocking runs.
Append vs. replace system prompt
--append-system-prompt keeps Claude Code's default behavior and adds rules on top; --system-prompt replaces the default entirely - use only when the identity/permission model genuinely differs.
--bare
Skips auto-discovery of hooks, skills, plugins, MCP servers, auto memory, and CLAUDE.md - Bash and file read/edit tools only. For fast, predictable scripted runs that don't need project config.
Incremental review context
Include prior findings in the prompt and instruct Claude to report only new or still-unaddressed issues. A context-free re-scan can't tell a deliberately-ignored issue from a new one, so it re-flags everything every push - eroding developer trust in the comments.
--tools vs. --allowedTools
--tools restricts which built-in tools exist in the session at all. --allowedTools / --disallowedTools are permission rules on top of that - they decide whether an existing tool needs approval, not whether it's available.

How this diagram fits together

Read top to bottom for load order, not for who overrides whom in a conflict.

  • User-level (top) - loads first, invisible to teammates.
  • Project-level (middle) - loads next, shared with the whole team through git.

Diagram: CLAUDE.md Load Order & Conflict Handling

How this diagram fits together

Top row - a reading order, not a ranking. By the time all four files have loaded, none of them has "won" anything. They're just concatenated into the same context, broadest first, CLAUDE.local.md appended last at whatever level it sits. That's why the box underneath says "concatenated," not "resolved."

Middle row - what actually happens when two of those loaded instructions disagree: there's no tiebreaker built in. Claude may pick either rule, arbitrarily. That's a real behavior, not a gap in this page's explanation - the docs are explicit about it.

Bottom row - the fix. settings.json has what CLAUDE.md doesn't: a real precedence chain (managed beats local beats project beats user) that the client enforces regardless of what Claude decides. If a rule has to hold on every single run - a blocked tool, a required formatter - it belongs there, or in a hook, not in CLAUDE.md scoping.

How this diagram fits together

The dashed vs. solid boxes are the whole diagram.

  • Dashed - never leaves this machine. User-level CLAUDE.md lives in your home directory, outside the repo entirely, so git pull can't touch it.
  • Solid - a tracked file. Project and subdirectory CLAUDE.md live inside the repo, so git pull hands them to every teammate identically.

Same three levels as the hierarchy diagram earlier - this one just answers "which of these does my coworker actually get."

Diagram: CLAUDE.md, @ Imports, and Rules

How this diagram fits together

The @ import (top) - the arrow only goes one place: from project-level CLAUDE.md down into its own @ path import. The import is explicit and lives inside CLAUDE.md itself (there's no @import keyword - it's just @ followed by a path), so it only ever loads what CLAUDE.md says to load, and it loads eagerly: the imported file's full content lands in context the moment CLAUDE.md is read, same size as if you'd pasted it in directly.

.claude/rules/ (bottom) - nothing points at it, which is the whole point of the red note in the middle. It's discovered independently by Claude Code and activates itself based on which file you're editing - it never needs CLAUDE.md to mention it at all, which is exactly why it's drawn as a separate box below rather than connected to anything above, and why it's the actual tool for shrinking per-session context rather than just organizing a file.

Diagram: Anatomy of the .claude/ Folder

How this diagram fits together

Color is doing the categorizing here.

  • Purple - the CLAUDE.md/config territory (CLAUDE.md, .claude/, settings.json) - committed, shared with the team.
  • Red - anything personal and gitignored-by-convention (CLAUDE.local.md, settings.local.json) - your own overrides, never pushed.
  • Teal - commands/ and skills/ together, because the unified Skills system treats a flat command file and a SKILL.md directory as the same mechanism.
  • Blue - rules/, path-scoped instruction files, distinct from both.

It's here for completeness of the folder, not as something this section tests.

Diagram: A Real SKILL.md, Annotated

How this diagram fits together

The three highlighted lines are the fields the exam's guide names explicitly - name and the skill body are ordinary YAML/prose anyone would guess correctly.

  • context: fork - decides where the output goes: into an isolated subagent, not the main conversation.
  • allowed-tools - only pre-approves the listed tools so they skip the permission prompt; it doesn't restrict anything, every other tool stays callable.
  • argument-hint - only affects the autocomplete UI when you type /reproduce-bug with no arguments; it doesn't validate or enforce anything at runtime.

The one field not highlighted here but worth watching for is description, on line 2 - it's not in the exam's named three, but it's what Claude actually reads to decide whether this skill matches what you just asked for. Leave it out and the skill only ever runs when you type /reproduce-bug yourself.

Diagram: Plan Mode vs. Direct Execution

How this diagram fits together

The top half is the decision itself, and it only has one real question: is the task ambiguous or architectural, not how hard it is.

  • No - goes straight to direct execution, short and done.
  • Yes - doesn't skip direct execution, it defers it: plan mode runs first to explore and choose an approach, and direct execution still does the actual implementing once that approach is locked in.

That's the hybrid pattern the purple pill calls out - it's the same direct execution box either way, just entered after a planning pass instead of immediately.

The worked example below makes the hybrid pattern concrete - a 30-file logging library migration is exactly the kind of task where jumping straight to direct execution risks applying an inconsistent fix across files.

Plan phase does the one-time thinking - which files, what the API diff looks like, what the pattern should be, where the edge cases are - so the execute phase becomes mechanical repetition of an already-decided strategy, not 30 separate design decisions.

Diagram: Refinement Technique Selection

How this diagram fits together
  • 1. Concrete examples - most effective when you already know the right answer, but your prose keeps getting read differently each time. Two or three before/after input-output pairs set the pattern; the model generalizes from those more reliably than from any description.
  • 2. Test-driven iteration - most effective when the transformation itself is too complex for prose or examples to fully capture. Share the failing test output instead of more explanation - "expected X, got Y" leaves no room for interpretation.
  • 3. Interview pattern - most effective in an unfamiliar domain, where you might not know every consideration either. Ask Claude to question the requirements before implementing, instead of prescribing a solution up front.

The red callout exists because examples and the interview pattern get mixed up constantly - both "improve the interaction," but for opposite reasons: one assumes you know the answer, the other assumes you might not.

The bottom pair is a separate decision about delivery, not technique:

  • Batch feedback - use when issues interact, since fixing one changes what "correct" looks like for another; Claude sees every constraint at once.
  • Sequential feedback - use when issues are independent; batching risks Claude misapplying one fix to the wrong part of the code.

Diagram: CI/CD Review Flow

How this diagram fits together

The fingerprint step is the part people forget - without it, every re-run against the same PR posts the same finding again. Fingerprinting each finding (file + line + category, typically) before deciding new-vs-already-posted is what makes a CI review idempotent across repeated pushes, instead of spamming the thread on every commit.

Critical findings take a second path out of that same fingerprint step - straight to failing the build check, on top of the PR comment.

4Official Sample Questions (D3)
Q4. (Scenario 2, Code Generation) You want a custom /review slash command available to every developer when they clone or pull the repo. Where should the command file live?
A) In .claude/commands/ in the project repository.
B) In ~/.claude/commands/ in each developer's home directory.
C) In the CLAUDE.md file at the project root.
D) In a .claude/config.json file with a commands array.
Show answer
A. Project-scoped commands are version-controlled and automatically available to everyone who clones or pulls. B is personal/not shared. C is for project instructions, not command definitions. D describes a mechanism that doesn't exist in Claude Code.
Q5. (Scenario 2) You're restructuring a monolithic application into microservices - dozens of files, decisions about service boundaries and module dependencies. Which approach?
A) Enter plan mode to explore the codebase, understand dependencies, and design an approach before making changes.
B) Start with direct execution and let the implementation reveal the natural boundaries.
C) Use direct execution with comprehensive upfront instructions detailing exactly how each service should be structured.
D) Begin in direct execution and only switch to plan mode if unexpected complexity appears.
Show answer
A. This is exactly what plan mode is for: architectural decisions, multiple valid approaches, large-scale multi-file change. B risks costly rework from dependencies discovered late. C assumes the right structure without exploring the code. D ignores that the complexity is already known up front, not something that might emerge later.
Q6. (Scenario 2) Distinct coding conventions per area (React components, API handlers, DB models), plus test files spread throughout the codebase next to the code they test, all needing the same conventions regardless of location. Most maintainable way to apply conventions automatically?
A) Create rule files in .claude/rules/ with YAML frontmatter specifying glob patterns to conditionally apply conventions by file path.
B) Consolidate all conventions in root CLAUDE.md under headers per area, relying on Claude to infer which section applies.
C) Create skills in .claude/skills/ for each code type, with conventions in their SKILL.md files.
D) Place a separate CLAUDE.md file in each subdirectory with that area's conventions.
Show answer
A. Glob patterns (e.g. **/*.test.tsx) apply automatically based on file path regardless of directory - essential when matching files are spread throughout the codebase. B relies on inference, unreliable. C requires manual invocation or Claude choosing to load it, not deterministic automatic application. D can't cleanly handle files spread across many directories since CLAUDE.md files are directory-bound.
Q10. (Scenario 5, CI) A pipeline script runs claude "Analyze this pull request for security issues" but the job hangs indefinitely, waiting for interactive input. Correct fix?
A) Add the -p flag: claude -p "...".
B) Set environment variable CLAUDE_HEADLESS=true before running.
C) Redirect stdin from /dev/null.
D) Add a --batch flag.
Show answer
A. -p (--print) is the documented way to run non-interactively: processes the prompt, prints the result, exits - exactly what CI needs. B and D reference features that don't exist; C is a Unix workaround that doesn't address Claude Code's actual command syntax.
Q11. (Scenario 5, CI) Real-time Claude calls power (1) a blocking pre-merge check, and (2) an overnight technical-debt report. Manager proposes switching both to the Message Batches API for the 50% savings. How do you evaluate this? (Same official question also referenced under D4 - it's core content for both 3.6 CI/CD and 4.5 batch processing strategies.)
A) Use batch for the technical-debt reports only; keep real-time calls for pre-merge checks.
B) Switch both to batch with status polling.
C) Keep real-time for both, to avoid batch result ordering issues.
D) Switch both to batch with a timeout fallback to real-time.
Show answer
A. Batch has no guaranteed latency SLA (up to 24h), unsuitable for a blocking workflow developers are waiting on, but ideal for an overnight job. B relies on "often faster" completion, not acceptable for a blocking check. C is a misconception - results correlate fine via custom_id. D adds complexity the simple per-workflow match already solves.
