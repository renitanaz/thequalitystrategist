Agentic Architecture & Orchestration

Task Statements 1.1–1.7

Source: Claude Certified Architect – Foundations Certification Exam Guide, Domain 1 section, official sample questions, and Exercise 1/4.

Topics Mind Map

1Topic Keywords

1.1 · The Loop

stop_reason
Field on the API response that drives the loop: "tool_use" = continue, "end_turn" = done.
tool_use_id
ID carried on a tool_use block and echoed back on its matching tool_result block - how the API connects a specific tool request to the right reply when more than one call is in flight.
Agentic loop lifecycle
Send request → inspect stop_reason → execute requested tools → append results to conversation history → repeat.
Model-driven decision-making vs. predefined programmatic decision-making
Claude reasons about which tool to call next from context, as opposed to a pre-configured decision tree or fixed tool sequence.
Loop anti-patterns
Parsing natural-language signals to detect termination; an arbitrary iteration cap as the primary stop mechanism; checking for assistant text content as a "done" signal.

1.2 / 1.3 · Coordination

Hub-and-spoke
Coordinator (hub) manages all inter-subagent communication, error handling, and routing; subagents (spokes) never talk to each other directly.
Isolated context
Subagents do not automatically inherit the coordinator's conversation history - nothing carries over unless explicitly passed in the prompt.
Overly narrow decomposition
Risk named explicitly in the guide: a coordinator that splits a broad topic too narrowly leaves real coverage gaps (see Q7 below).
Task tool
The mechanism for spawning subagents. allowedTools must include "Task" for a coordinator to invoke them.
AgentDefinition
Per-subagent configuration: description, system prompt, and tool restrictions.
Parallel vs. sequential spawning
Parallel: multiple Task calls emitted within a single coordinator response - default choice, use when subagents are independent (e.g. web search + document analysis on unrelated sources). Sequential: one Task call per coordinator turn, waiting for each result - use only when a real dependency exists (subagent B needs subagent A's output before it can start). Sequential otherwise just adds latency for nothing.

1.4 / 1.5 · Enforcement

Workflow enforcement types
Programmatic enforcement (hooks, prerequisite gates) - guaranteed. Contrast with prompt-based guidance, which has a non-zero failure rate even when the rule is stated clearly.
Structured handoff protocol
What a human escalation needs: customer details, a conversation summary, root cause analysis, recommended action - compiled for someone with no access to the conversation transcript.
PostToolUse hook
Intercepts a tool's result to transform/normalize it before the model ever sees it.
PreToolUse
Intercepts an outgoing tool call to enforce a compliance rule (e.g. block a refund over a threshold) before it executes.
SubagentStart
Fires when a subagent spawns via the Task/Agent tool. Observational only - logs the spawn or injects context, but can't block or modify the invocation. To gate spawning itself, use a PreToolUse hook on the Agent tool instead.
SubagentStop
Fires when a subagent finishes and returns results. Can return decision: "block" to send it back to keep working, but can't transform the output - that's a PostToolUse job on the Agent tool call. A subagent's own Stop hooks (in its frontmatter) auto-convert to SubagentStop events at runtime.
Subagent-scoped hooks
A subagent's own AgentDefinition frontmatter can define PreToolUse/PostToolUse hooks that only intercept that subagent's tool calls - not the coordinator's or other subagents'. Enables per-subagent policy (e.g. a billing subagent blocks large refunds; a support subagent doesn't).

1.6 / 1.7 · Decomposition & State

Prompt chaining
A fixed sequence of separate prompts run in order, each step decided in advance: e.g. reviewing a 5-file pull request, one call per file first, then a final call checking whether a change in one file breaks an assumption another file was relying on.
Dynamic decomposition
Adaptive: subtasks are generated based on what's discovered at each step, not fixed up front.
Attention dilution
Too many items in a single pass spreads attention thin - early items get disproportionate depth, later ones get skimmed (e.g. flagging a pattern in file 3 but approving identical code in file 11). Architectural, not a model-capability problem: a bigger model or larger context window doesn't fix it. Fix: per-item passes + a separate cross-item integration pass.
--resume <session-name>
Continues a specific named prior conversation. Only resumes an existing session - name one at start with --name/-n (or /rename mid-session). -c/--continue resumes the most recent session in the directory with no name needed.
fork_session
Branches one session into two independent copies from the same baseline, to explore a divergent approach without touching the original. Not the same thing as a coordinator spawning several subagents at once: that's parallel work on one session, this is a duplicated session. Doesn't fix stale context - a fork inherits the same stale tool results as its baseline.
Stale tool results
Why a fresh session with a structured summary can beat resuming: reasoning from stale results is worse than reasoning from none.

Diagram: stop_reason and Its Two Outputs

How this diagram fits together

The loop only has two exits, and stop_reason is what tells you which one you're at. tool_use means the model wants to act - execute it, append the result, and go around again. end_turn means it's done - stop and hand the response back. Everything else (parsing text for phrases like "I'm finished," using an iteration cap as the primary stop signal) is a workaround for not trusting this field.

Diagram: Decision Tree — Who Picks the Next Tool?

How this diagram fits together

Same two requests, same two tools available (get_customer, process_refund) - the difference is entirely in how the next tool call gets chosen. A pre-configured tree can't see that Request A already has an ID, so it runs the redundant lookup anyway. Model-driven reasoning reads the context first and only calls what's actually missing.

Diagram: Coordinator, Subagents, and the Task Tool

How this diagram fits together

allowedTools: ["Task"] is the gate - without it on both arrows, the coordinator has no way to spawn either subagent. Two arrows leaving in the same response is what makes this a parallel spawn. Each subagent only reports back to the coordinator, never to each other - that's the hub-and-spoke rule in picture form.

Diagram: Parallel vs. Sequential Agent Spawning

How this diagram fits together

The two halves aren't alternative UI for the same thing - they're for genuinely different situations. Parallel only makes sense when A and B don't need each other's output; that's why both Task calls can go out in the same response. Sequential exists specifically because turn 2 needs turn 1's result to even know what to ask for.

How this diagram fits together

Left column: the four steps are already decided before Verify even runs. Right column: Map issue produces two branches, and each one only gets defined by what Map issue actually found - the diagram couldn't have drawn those branches in before running it, the way it could on the left. That's the whole difference between the two patterns.

Diagram: Session Continuation Strategy

How this diagram fits together

Same paused session, three different outcomes depending on one thing: what happened to the underlying work while you were away. Nothing changed → the history is still accurate, resume it. Comparing two approaches → you want both explored, fork. Code moved → the tool results sitting in that history are now wrong, so a fresh session with a summary beats reasoning from stale data.

Flow: The Loop, With a Hook in It

How this diagram fits together

Both hook points sit inside the ordinary loop, not beside it - that's the point. The interception hook gets a look at the call before it runs and can stop it; the PostToolUse hook only sees the result after, and can only reshape it, not undo the call. The dashed line back to the top is just the loop continuing with cleaner data than it started with.

Diagram: PreToolUse vs. PostToolUse

How this diagram fits together

Same two hook names the exam always pairs up, shown doing the two different jobs they're actually capable of. PreToolUse sits before the call, so it can stop process_refund from ever running. PostToolUse sits after get_customer already ran - it can clean up the timestamp it got back, but it could never have blocked that call in the first place.

Diagram: Hook or Prompt? The Decision Framework

How this diagram fits together

The branch point isn't "is this important" - it's "what happens if this fails exactly once." AML and refund approval sit on the hook side because a single miss is a compliance or financial problem. Markdown formatting sits on the prompt side because a single miss is just a slightly uglier response - annoying, not dangerous.

Diagram: Subagent Lifecycle Hooks

How this diagram fits together

The dashed callouts are the trap the exam sets: SubagentStart and SubagentStop sound like they should be able to block and reshape a subagent the way PreToolUse/PostToolUse do - they can't. Start only observes; Stop can only send the subagent back to keep working, never touch its output. Blocking the spawn or rewriting the result is still a PreToolUse/PostToolUse job on the Agent tool call itself.

Diagram: A Real Prerequisite Gate

How this diagram fits together

Step 1 doesn't fail quietly - the hook blocks it and tells the agent exactly what's missing. Step 2 is the agent responding to that error on its own, no human re-prompting it. Step 3 succeeds because the gate's condition is now actually met. That's the deterministic-guarantee point shown as a real transcript instead of stated as a rule.

Diagram: How 1.1, 1.3, and 1.6 Relate

How this diagram fits together

Dependency is the real fork: independent work leads to parallel spawning, dependent work leads to sequential spawning - which then splits into a decomposition strategy, fixed pipeline (order known upfront) or dynamic decomposition (each next step comes from what was just found). This "independent or dependent" question is specifically the coordinator's call - it only applies once you're spawning subagents. Model-driven decision-making (1.1) is not a step in this chain at all; it's the foundation running underneath every step, for every agent, coordinator and subagent alike, the whole time. It's what makes dynamic decomposition possible at the coordinator's planning level, and it's also what a single tool-selection decision looks like at any one loop iteration. And "fixed pipeline vs. dynamic decomposition" (1.6) is broader than the coordinator/subagent picture - it also applies to one agent's own multi-step task planning with no subagents involved at all.

Worked example: model-driven vs. pre-configured tree

Same task, two different implementations - using the refund scenario again. Two incoming requests: Request A, "Refund $50 for cus_8841" (customer ID already known); Request B, "Customer emailed asking for a refund" (no ID given).

Pre-configured decision tree - hardcoded logic: "refund request → always call get_customer → always call check_refund_eligibility → always call process_refund," in that fixed order, no matter what.

  • Request A: runs get_customer anyway (redundant - the ID was already sitting right there in context) → check_refund_eligibility → process_refund
  • Request B: runs get_customer → check_refund_eligibility → process_refund

Both requests get the exact same 3 steps in the exact same order. The tree can't tell the difference between them - it has no way to notice "wait, I already have the ID."

Model-driven decision-making - the model reads what's actually in context at each step:

  • Request A: model sees customer_id already present → skips straight to check_refund_eligibility → process_refund (2 steps)
  • Request B: model sees no ID → calls get_customer first → check_refund_eligibility → process_refund (3 steps)

Different number of steps, different path - decided in the moment from what's actually there, not from a rule written in advance. That's the whole distinction the exam is testing: a decision tree treats every case identically because it can't see the specifics; model-driven reasoning adapts because it does.

3Active Recall
1.What exact API field controls whether the agentic loop continues, and what are its two relevant values?
stop_reason. "tool_use" = continue the loop, "end_turn" = terminate. Not the model's own text output or a turn counter - those are exactly the two loop anti-patterns the guide flags, because neither one actually reads the protocol's own signal.
2.What connects a tool_use request to its tool_result reply, and why does that matter?
The tool_use_id - carried on the tool_use block and echoed back on the tool_result block. It matters because more than one tool call can be in flight at once, so the ID is what lets the correct result get matched to the correct request; call order alone isn't reliable, since results can come back out of sequence.
3.Name all three loop anti-patterns the guide calls out.
(1) Parsing natural-language signals in the model's text to detect termination. (2) An arbitrary iteration cap used as the primary stopping mechanism. (3) Checking for the presence/absence of assistant text content as a completion indicator. All three fail for the same underlying reason: none of them reads stop_reason, the one field the API actually guarantees.
4.In hub-and-spoke orchestration, who handles inter-subagent communication and error routing?
The coordinator only. Subagents never communicate with each other directly - everything routes through the hub. Direct peer-to-peer communication is avoided because it would remove the coordinator's single point of observability and consistent error handling across the whole delegation.
5.Does a subagent automatically inherit the coordinator's conversation history?
No. Context must be explicitly included in the subagent's prompt. There's also no shared memory between separate subagent invocations - automatic inheritance isn't used because it would make each subagent's behavior depend on hidden state, harder to reason about or test in isolation.
6.What configuration is required on the coordinator's side before it can spawn subagents at all?
allowedTools must include "Task" - the Task tool is the actual spawning mechanism. Without it, there's no implicit default that grants subagent access; an attempt to spawn one simply isn't available.
7.How do you actually achieve parallel subagent execution, mechanically?
Emit multiple Task tool calls within a single coordinator response - not across separate turns. Spreading the same calls across separate turns still executes them one at a time; true parallel execution requires all of them in flight together in one response.
8.What's the named risk of a coordinator decomposing a broad topic too aggressively?
Overly narrow task decomposition leads to incomplete coverage of broad research topics - some real subtopics never get assigned to any subagent (this is exactly what official sample Question 7 tests). The fix isn't tighter wording on the same fixed split; it's decomposition that can adapt to what's actually being found.
9.What's the coordinator's iterative-refinement loop, specifically?
It evaluates the synthesis output for gaps, re-delegates to search/analysis subagents with targeted queries, and re-invokes synthesis - repeating until coverage is sufficient. A single synthesis pass without this loop can't catch its own gaps, since nothing ever checks the output against what's missing.
10.Give the textbook example of a programmatic prerequisite gate, and say why a prompt instruction isn't good enough there.
Block process_refund until get_customer has returned a verified customer ID. Prompt instructions alone have a non-zero failure rate, so anything requiring deterministic compliance (identity verification before a financial operation) needs a programmatic gate, not a request.
11.What four things belong in a structured handoff summary to a human agent?
Customer ID, root cause, refund amount (or equivalent transactional detail), and recommended action - because the human has no access to the conversation transcript. A raw transcript dump isn't a substitute: it forces the human to reconstruct the case themselves instead of acting on a ready summary.
12.Distinguish what a PostToolUse hook does from what a tool-call-interception hook does.
PostToolUse: intercepts a tool's result, transforms/normalizes it before the model sees it (e.g. unifying Unix timestamps, ISO 8601, and numeric status codes). Interception hook: intercepts an outgoing tool call before it executes, to block policy-violating actions (e.g. refunds over $500) and redirect elsewhere.
13.Prompt chaining vs. dynamic decomposition - when does each apply?
Prompt chaining (fixed sequential pipeline): a fixed sequence of separate prompts run in order, each step decided up front, for predictable multi-aspect reviews (e.g. reviewing a 5-file pull request, one call per file first, then a final call checking whether a change in one file breaks an assumption another file was relying on). Dynamic decomposition: open-ended investigation where each step's subtasks are generated by what the previous step found. Using a fixed pipeline for genuinely open-ended work fails because the steps aren't knowable in advance; using dynamic decomposition for a fully predictable review just adds unnecessary variability.
14.Why split a large code review into per-file passes plus a separate integration pass?
To avoid attention dilution - a single pass across many files at once produces inconsistent depth and can even contradict itself (flagging a pattern in one file, approving identical code in another). Per-file passes alone aren't enough either: without the separate integration pass, cross-file issues that only show up when files are considered together get missed.
15.A session pauses partway through. You want to explore two different refactoring approaches from the same codebase analysis, without disturbing the original. Which session command do you use, and why not the other one?
fork_session - it branches one session into two independent copies from the same baseline, so both approaches can be explored in parallel without either affecting the source. --resume <session-name> is the wrong tool here: it continues one specific named conversation exactly where it left off, it doesn't create a second branch to compare against.
16.When is starting a brand-new session with a structured summary the better call than resuming?
When the prior session's tool results have gone stale (e.g. the underlying code changed) - reasoning from stale results is worse than reasoning from a clean, accurate summary. Resuming anyway without flagging the change isn't a safe middle ground: the agent would keep reasoning from facts that no longer hold unless it's explicitly told what changed.

4Official Sample Questions (D1)
Q1. (Scenario 1, Customer Support) Production data shows the agent skips get_customer in 12% of cases and calls lookup_order on stated name alone, occasionally causing misidentified accounts and incorrect refunds. Most effective fix?
A) Programmatic prerequisite blocking lookup_order/process_refund until get_customer returns a verified ID.
B) Strengthen the system prompt to say verification is mandatory.
C) Few-shot examples showing the agent always calling get_customer first.
D) A routing classifier enabling only the tool subset appropriate to the request.
Show answer
A. Deterministic guarantee needed - B and C are still probabilistic LLM compliance, D fixes tool availability, not ordering.
Q7. (Scenario 3, Multi-Agent Research) Topic "impact of AI on creative industries" - final reports cover only visual arts, missing music/writing/film. Coordinator logs show it decomposed into "AI in digital art creation," "AI in graphic design," "AI in photography." Root cause?
A) Synthesis agent lacks coverage-gap detection instructions.
B) Coordinator's task decomposition is too narrow, so subagent assignments don't cover all relevant domains.
C) Web search agent's queries aren't comprehensive enough.
D) Document analysis agent is filtering out non-visual sources.
Show answer
B. Every subagent executed its assigned task correctly - the problem is what they were assigned in the first place. This is the "overly narrow decomposition" risk from 1.2's Knowledge list, directly.
Q8. (Scenario 3) A web-search subagent times out. Which error-propagation approach to the coordinator best enables intelligent recovery?
A) Structured error context: failure type, attempted query, partial results, alternative approaches.
B) Retry with backoff internally, return a generic "search unavailable" only after retries exhaust.
C) Catch the timeout, return an empty result set marked successful.
D) Propagate the exception to a top-level handler that kills the whole workflow.
Show answer
A. B hides context, C silently suppresses a real failure as success, D over-reacts by terminating everything. (Cross-references D5's error-propagation task statement too.)
Q9. (Scenario 3) Synthesis agent needs frequent fact-checks; 85% are simple lookups, 15% need deep investigation. Currently every check round-trips through the coordinator to the web-search agent, adding 40% latency. Best fix?
A) Give synthesis a scoped verify_fact tool for the simple case; complex cases still go through the coordinator.
B) Batch all verification needs and send them to web search at the end of the pass.
C) Give synthesis full access to all web-search tools directly.
D) Have the web-search agent proactively cache extra context speculatively.
Show answer
A. Principle of least privilege - scoped tool for the common case, existing coordination pattern kept for the hard 15%. C violates separation of concerns (this is exactly the "tools outside specialization" risk from D2 2.3).

  • Programmatic enforcement (hooks, prerequisite gates) vs. prompt-based guidance for ordering.
  • When deterministic compliance is required (e.g. identity verification before a financial operation), prompt instructions alone have a non-zero failure rate.
  • Structured handoff protocol for mid-process escalation: customer details, a conversation summary, root cause analysis, recommended action.

Task Statement1.5
Hooks: interception & normalization
  • PostToolUse hooks intercept tool results for transformation before the model processes them.
  • Other hook patterns intercept outgoing tool calls to enforce compliance (e.g. block refunds above a threshold).→ See: Diagram, PreToolUse vs. PostToolUse
  • Core distinction: hooks = deterministic guarantee, prompts = probabilistic compliance.→ See: Diagram, Hook or Prompt?
  • Subagent lifecycle hooks complement Pre/PostToolUse: SubagentStart fires on spawn (observational only, can't block); SubagentStop fires on completion and can block by sending the subagent back to work, but can't transform its output.→ See: Diagram, Subagent Lifecycle Hooks

  • PostToolUse hooks normalize heterogeneous formats from different MCP tools - e.g. Unix timestamps, ISO 8601, numeric status codes - into one shape.
  • Tool-call interception hooks block policy-violating actions (e.g. refunds exceeding $500) and redirect to an alternative workflow (human escalation).
  • Choose hooks over prompt-based enforcement whenever a business rule requires guaranteed compliance, not just likely compliance.
  • To gate a subagent spawn, attach PreToolUse to the Agent tool call itself, not SubagentStart; to reshape what the coordinator sees, use PostToolUse on the Agent tool call, not SubagentStop.

Task Statement1.6
Task decomposition strategies
  • Fixed sequential pipelines (prompt chaining) vs. dynamic adaptive decomposition based on intermediate findings.→ See: Diagram, Fixed Pipeline vs. Dynamic Decomposition
  • Prompt chaining is a fixed sequence of separate prompts run in order, each step decided in advance: e.g. reviewing a 5-file pull request, one call per file first, then a final call checking whether a change in one file breaks an assumption another file was relying on.
  • Adaptive investigation plans generate subtasks from what's discovered at each step.
  • Attention dilution is architectural, not a model-capability problem - a more powerful model or a larger context window doesn't fix it. Symptom: inconsistent depth across items, e.g. a pattern flagged in file 3 but approved unchanged in file 11.
  • Match the pattern to the workflow: prompt chaining for predictable multi-aspect reviews, dynamic decomposition for open-ended investigation.
  • Split large code reviews into per-file local analysis + a separate cross-file integration pass, to avoid attention dilution.
  • Decompose open-ended tasks (e.g. "add comprehensive tests to a legacy codebase") by first mapping structure, then identifying high-impact areas, then building a prioritized plan that adapts as dependencies surface.
  • Avoid: a single-pass review with a "better" prompt (still uneven depth, same root cause); batching files into groups without a dedicated cross-batch integration pass (misses issues that only show up across batches); applying a fixed pipeline to genuinely open-ended investigation.

Task Statement1.7
Session state, resumption, forking
  • --resume <session-name> continues a specific named prior conversation.
  • fork_session creates an independent branch from a shared baseline.
  • Resuming after code changes requires explicitly informing the agent what changed.
  • Starting fresh with a structured summary is more reliable than resuming with stale tool results.→ See: Diagram, Session Continuation Strategy
  • Exam vs. current CLI: --resume only resumes an existing session - it never creates one. Name a session at start with --name/-n (or /rename mid-session), then resume it by name later. -c/--continue resumes the most recent session in the directory with no name needed.
  • Use --resume with session names to continue named investigation sessions across work sessions.
  • Use fork_session for parallel exploration branches - e.g. comparing two testing strategies or refactoring approaches from one codebase analysis.
  • Choose resumption when prior context is mostly valid; choose fresh + injected summary when prior tool results are stale.
  • Inform a resumed session about specific file changes for targeted re-analysis, rather than forcing full re-exploration.

  • 1.6 Fixed pipeline for predictable multi-aspect work, dynamic decomposition for open-ended work.
