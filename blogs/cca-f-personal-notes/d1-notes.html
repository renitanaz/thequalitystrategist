2Main Pointers
Task Statement1.1
Agentic loops

Knowledge: the loop is send request → check stop_reason → run tool → append result to history → repeat. Model-driven decisions (Claude picks the next tool from context) is the tested contrast against pre-configured decision trees.

Skills:

  • Loop continues while stop_reason === "tool_use", terminates on "end_turn".
  • Tool results get added to conversation context between iterations so reasoning can incorporate new information.
  • Mechanic: a tool_use block carries the tool name, its input, and a tool_use_id. The application executes the tool, then appends the result as a tool_result block carrying that same ID - that's what lets Claude match a result back to the right request when several calls are in flight.
  • Avoid: parsing natural-language signals for termination; an iteration cap as the primary stop mechanism; checking for assistant text content as a completion indicator.
Task Statement1.2
Coordinator–subagent orchestration

Knowledge: hub-and-spoke - coordinator owns all inter-subagent communication, error handling, and routing. Subagents have isolated context by default. Coordinator owns decomposition, delegation, aggregation, and deciding which subagents to invoke based on query complexity. Named risk: too-narrow decomposition leaves broad topics under-covered.

Skills:

  • Coordinator dynamically selects which subagents to invoke, rather than always routing through the full pipeline.
  • Partition research scope across subagents to minimize duplication (distinct subtopics/source types per agent).
  • Iterative refinement loop: coordinator evaluates synthesis output for gaps, re-delegates to search/analysis subagents with targeted queries, re-invokes synthesis until coverage is sufficient.
  • Route all subagent communication through the coordinator - for observability, consistent error handling, controlled information flow.
Task Statement1.3
Subagent invocation & context passing

Knowledge: the Task tool spawns subagents; coordinator's allowedTools must include "Task". Subagent context must be explicit in the prompt - no automatic inheritance, no shared memory between invocations. AgentDefinition holds each subagent's description, system prompt, tool restrictions. Fork-based session management: fork_session branches one session into two independent copies from the same baseline, letting you explore two approaches without disturbing the original.

Skills:

  • Include complete findings from prior agents directly in the subagent's prompt (e.g. pass web-search + document-analysis output straight to the synthesis subagent).
  • Use structured data formats that separate content from metadata (source URLs, doc names, page numbers) to preserve attribution across handoffs.
  • Parallel spawning = multiple Task calls emitted in one coordinator response, not across separate turns.
  • Coordinator prompts should specify goals + quality criteria, not step-by-step procedure - that's what lets subagents adapt.
Task Statement1.4
Enforcement & handoff patterns

Knowledge: programmatic enforcement (hooks, prerequisite gates) vs. prompt-based guidance for ordering. When deterministic compliance is required (e.g. identity verification before a financial operation), prompt instructions alone have a non-zero failure rate. Structured handoff protocol for mid-process escalation: customer details, root cause analysis, recommended action.

Skills:

  • Programmatic prerequisites block a downstream tool call until a prerequisite step completes - e.g. block process_refund until get_customer returns a verified customer ID.
  • Decompose multi-concern requests into distinct items, investigate each in parallel with shared context, then synthesize one unified resolution.
  • Compile structured handoff summaries (customer ID, root cause, refund amount, recommended action) for a human agent with no transcript access.
Task Statement1.5
Hooks: interception & normalization

Knowledge: PostToolUse hooks intercept tool results for transformation before the model processes them. Other hook patterns intercept outgoing tool calls to enforce compliance (e.g. block refunds above a threshold). Core distinction: hooks = deterministic guarantee, prompts = probabilistic compliance.

Skills:

  • PostToolUse hooks normalize heterogeneous formats from different MCP tools - e.g. Unix timestamps, ISO 8601, numeric status codes - into one shape.
  • Tool-call interception hooks block policy-violating actions (e.g. refunds exceeding $500) and redirect to an alternative workflow (human escalation).
  • Choose hooks over prompt-based enforcement whenever a business rule requires guaranteed compliance, not just likely compliance.
Task Statement1.6
Task decomposition strategies

Knowledge: fixed sequential pipelines (prompt chaining) vs. dynamic adaptive decomposition based on intermediate findings. Prompt chaining is a fixed sequence of separate prompts run in order, each step decided in advance: e.g. reviewing a 5-file pull request, one call per file first, then a final call checking whether a change in one file breaks an assumption another file was relying on. Adaptive investigation plans generate subtasks from what's discovered at each step.

Skills:

  • Match the pattern to the workflow: prompt chaining for predictable multi-aspect reviews, dynamic decomposition for open-ended investigation.
  • Split large code reviews into per-file local analysis + a separate cross-file integration pass, to avoid attention dilution.
  • Decompose open-ended tasks (e.g. "add comprehensive tests to a legacy codebase") by first mapping structure, then identifying high-impact areas, then building a prioritized plan that adapts as dependencies surface.
Task Statement1.7
Session state, resumption, forking

Knowledge: --resume <session-name> continues a specific named prior conversation. fork_session creates an independent branch from a shared baseline. Resuming after code changes requires explicitly informing the agent what changed. Starting fresh with a structured summary is more reliable than resuming with stale tool results.

Skills:

  • Use --resume with session names to continue named investigation sessions across work sessions.
  • Use fork_session for parallel exploration branches - e.g. comparing two testing strategies or refactoring approaches from one codebase analysis.
  • Choose resumption when prior context is mostly valid; choose fresh + injected summary when prior tool results are stale.
  • Inform a resumed session about specific file changes for targeted re-analysis, rather than forcing full re-exploration.
Summary, one line per task statement:
  • 1.1 Trust stop_reason, never text-guessing or a cap as primary logic.
  • 1.2 Hub-and-spoke, coordinator dynamically selects subagents and iteratively refines via re-delegation.
  • 1.3 Context is explicit, never inherited; parallel = same response, multiple Task calls.
  • 1.4 Critical-path ordering is a programmatic gate, not a prompt request.
  • 1.5 PostToolUse normalizes, interception hooks gate - both are guarantees a prompt can't give.
  • 1.6 Fixed pipeline for predictable multi-aspect work, dynamic decomposition for open-ended work.
  • 1.7 Resume when nothing's stale, fork to explore two paths from one baseline, fresh+summary when the ground truth moved.

4Active Recall
What exact API field controls whether the agentic loop continues, and what are its two relevant values?
stop_reason. "tool_use" = continue the loop, "end_turn" = terminate.
What connects a tool_use request to its tool_result reply, and why does that matter?
The tool_use_id - carried on the tool_use block and echoed back on the tool_result block. It matters because more than one tool call can be in flight at once, so the ID is what lets the correct result get matched to the correct request.
Name all three loop anti-patterns the guide calls out.
(1) Parsing natural-language signals in the model's text to detect termination. (2) An arbitrary iteration cap used as the primary stopping mechanism. (3) Checking for the presence/absence of assistant text content as a completion indicator.
In hub-and-spoke orchestration, who handles inter-subagent communication and error routing?
The coordinator only. Subagents never communicate with each other directly - everything routes through the hub.
Does a subagent automatically inherit the coordinator's conversation history?
No. Context must be explicitly included in the subagent's prompt. There's also no shared memory between separate subagent invocations.
What configuration is required on the coordinator's side before it can spawn subagents at all?
allowedTools must include "Task" - the Task tool is the actual spawning mechanism.
How do you actually achieve parallel subagent execution, mechanically?
Emit multiple Task tool calls within a single coordinator response - not across separate turns.
What's the named risk of a coordinator decomposing a broad topic too aggressively?
Overly narrow task decomposition leads to incomplete coverage of broad research topics - some real subtopics never get assigned to any subagent (this is exactly what official sample Question 7 tests).
What's the coordinator's iterative-refinement loop, specifically?
It evaluates the synthesis output for gaps, re-delegates to search/analysis subagents with targeted queries, and re-invokes synthesis - repeating until coverage is sufficient.
Give the textbook example of a programmatic prerequisite gate, and say why a prompt instruction isn't good enough there.
Block process_refund until get_customer has returned a verified customer ID. Prompt instructions alone have a non-zero failure rate, so anything requiring deterministic compliance (identity verification before a financial operation) needs a programmatic gate, not a request.
What four things belong in a structured handoff summary to a human agent?
Customer ID, root cause, refund amount (or equivalent transactional detail), and recommended action - because the human has no access to the conversation transcript.
Distinguish what a PostToolUse hook does from what a tool-call-interception hook does.
PostToolUse: intercepts a tool's result, transforms/normalizes it before the model sees it (e.g. unifying Unix timestamps, ISO 8601, and numeric status codes). Interception hook: intercepts an outgoing tool call before it executes, to block policy-violating actions (e.g. refunds over $500) and redirect elsewhere.
Prompt chaining vs. dynamic decomposition - when does each apply?
Prompt chaining (fixed sequential pipeline): a fixed sequence of separate prompts run in order, each step decided up front, for predictable multi-aspect reviews (e.g. reviewing a 5-file pull request, one call per file first, then a final call checking whether a change in one file breaks an assumption another file was relying on). Dynamic decomposition: open-ended investigation where each step's subtasks are generated by what the previous step found.
Why split a large code review into per-file passes plus a separate integration pass?
To avoid attention dilution - a single pass across many files at once produces inconsistent depth and can even contradict itself (flagging a pattern in one file, approving identical code in another).
What's the difference between --resume and fork_session?
--resume <session-name> continues one specific named conversation exactly where it left off. fork_session creates an independent branch from a shared analysis baseline, for exploring two divergent approaches without disturbing the original.
When is starting a brand-new session with a structured summary the better call than resuming?
When the prior session's tool results have gone stale (e.g. the underlying code changed) - reasoning from stale results is worse than reasoning from a clean, accurate summary. If resuming anyway, the agent must be explicitly told what changed.

5Official Sample Questions (D1)
Q1. (Scenario 1, Customer Support) Production data shows the agent skips get_customer in 12% of cases and calls lookup_order on stated name alone, occasionally causing misidentified accounts and incorrect refunds. Most effective fix?
A) Programmatic prerequisite blocking lookup_order/process_refund until get_customer returns a verified ID.
B) Strengthen the system prompt to say verification is mandatory.
C) Few-shot examples showing the agent always calling get_customer first.
D) A routing classifier enabling only the tool subset appropriate to the request.
Show answer
A. Deterministic guarantee needed - B and C are still probabilistic LLM compliance, D fixes tool availability, not ordering.
Q7. (Scenario 3, Multi-Agent Research) Topic "impact of AI on creative industries" - final reports cover only visual arts, missing music/writing/film. Coordinator logs show it decomposed into "AI in digital art creation," "AI in graphic design," "AI in photography." Root cause?
A) Synthesis agent lacks coverage-gap detection instructions.
B) Coordinator's task decomposition is too narrow, so subagent assignments don't cover all relevant domains.
C) Web search agent's queries aren't comprehensive enough.
D) Document analysis agent is filtering out non-visual sources.
Show answer
B. Every subagent executed its assigned task correctly - the problem is what they were assigned in the first place. This is the "overly narrow decomposition" risk from 1.2's Knowledge list, directly.
Q8. (Scenario 3) A web-search subagent times out. Which error-propagation approach to the coordinator best enables intelligent recovery?
A) Structured error context: failure type, attempted query, partial results, alternative approaches.
B) Retry with backoff internally, return a generic "search unavailable" only after retries exhaust.
C) Catch the timeout, return an empty result set marked successful.
D) Propagate the exception to a top-level handler that kills the whole workflow.
Show answer
A. B hides context, C silently suppresses a real failure as success, D over-reacts by terminating everything. (Cross-references D5's error-propagation task statement too.)
Q9. (Scenario 3) Synthesis agent needs frequent fact-checks; 85% are simple lookups, 15% need deep investigation. Currently every check round-trips through the coordinator to the web-search agent, adding 40% latency. Best fix?
A) Give synthesis a scoped verify_fact tool for the simple case; complex cases still go through the coordinator.
B) Batch all verification needs and send them to web search at the end of the pass.
C) Give synthesis full access to all web-search tools directly.
D) Have the web-search agent proactively cache extra context speculatively.
Show answer
A. Principle of least privilege - scoped tool for the common case, existing coordination pattern kept for the hard 15%. C violates separation of concerns (this is exactly the "tools outside specialization" risk from D2 2.3).
